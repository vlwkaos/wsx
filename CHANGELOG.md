# Changelog

Releases 0.40.4 and older are in [docs/changelog-archive.md](docs/changelog-archive.md).

## [Unreleased]

### Changed

- TUI: from 130 columns the chat has a rail of chats on its left (the manager, the open chats with their counts, For you). `^g` gives it the keys; `Enter` opens a chat. With a task open, `tab` goes chat, task, rail.
- TUI: `⌥Enter` in the chat's message line starts a new line; the line grows to 5 rows.
- TUI: a `#N` in a chat message is a link. `Enter` opens that task beside the chat (from 120 columns; narrower, it fills the pane) with its detail and actions; `tab` moves the keys between the chat and the task, and `Esc` closes it.
- TUI: a mermaid block in the chat or the project overview is drawn as a Unicode diagram when it fits the width (the `mermaid-text` crate). Otherwise it is one link, `▸ diagram not drawn`, and `Enter` shows its source.
- Tasks: a ready task under auto land with checks gets a review job instead of the manager's review. Its host starts one fresh agent of the manager's settings (role `reviewer`, read-only on the working copy) with `wsx task review`'s text and `report.md`; it answers `land`, and the host lands, or `changes` with at most 10 findings, which go to the worker as a turn. After 2 rounds of changes, or with no verdict, the owner lands it. The log has `review{revision, round, verdict, findings, agent, usage}` (its spend counts as the task's `review` part), and the status reads "Ready, under review". A task without checks, or with `land.auto: false`, waits for the owner, also one the manager created. See docs/tasks.md "Review".
- Tasks: a task's events start no manager turn. They reach the chat at once and its agent with its next turn. A plan and a paused task are the owner's: they show under *For you*, push, and remind after 4 h ("Plan ready, waiting for you", "Paused, waiting for you").
- Tasks: a revision's report lists the `assert` lines it removed or changed ("Edited test checks", at most 10), so a change that passes by editing its tests shows at review.
- Deploy: wsx's deploy gate also runs the end-to-end scenarios that the default branch's change since the last good deploy touches (hidden `wsx task touched-scenarios`), so a land that breaks main is caught once, not by each task after it.
- Release: `scripts/release.sh` refuses a version whose CHANGELOG.md section, which becomes the GitHub release body, is over 20000 bytes. 0.43.0's was 122,669. CHANGELOG.md keeps a summary of 0.43.0, and releases 0.40.4 and older moved to `docs/changelog-archive.md` without their commit links, nearly all of which no longer resolve.
- Tasks: wsx no longer makes a chat named after each repo. A repo gets a chat only from `wsx task chat new` or the web New chat; registering it, starting its service or an event makes or opens none. The old home chats stay as plain chats. The repo's main chat is the owner's choice (`wsx task chat main <chat>`; `chat new` sets it for the first chat of a repo): it hears routine results, tasks no open chat owns and a hand-back. With none, those wake nobody and the tasks still show in the ledger. Every chat, the main one too, can be closed.
- Search: `wsx task search` and `wsx memory search` answer with one hit type and rank with one routine. An owner message no longer gets note lines from a second ranker (`notes::matching`); it gets the top 5 records of kinds `rule` and `fact` of the project's memory, found by the same search as `wsx memory search`. `task search` JSON hits also carry `slug`, `scope`, `path`, `status` and `excerpt`; `memory search` transcript hits carry `line`. The first 10 refs of 30 fixed queries are unchanged; no reindex is needed.
- Tasks: `task` and `web` scenarios run on this machine only. A scenario check-run no longer goes to GitHub Actions (`ci:` commands, the orphan-run cancel, the queue limits and main's log lookup are removed); `scripts/scenario.py` starts the parts of a scenario at once, each in its own process, and the scenarios lane's width follows load, RAM and disk (next entry). The checks of one scenario run go at once. GitHub Actions runs the task scenario for pushes to main and release tags. The log kinds `ci_retry`, `ci_queued` and `ci_started` are gone.
- Tasks: one scheduler (`wsx_core::task::schedule`, `docs/design/scheduler.md`) decides when a heavy run starts on this Mac. The scenarios lane runs up to 3 scenario rounds at once while the load per core, free RAM and free disk allow it; waiting runs go by urgency (a land's checks, a task another task waits for, the owner's tasks, the rest). A scenario goes to GitHub Actions only when the Mac cannot run it (free disk under `minFreeGb` after the cleanup, a tool missing) or an urgent run would wait longer than a CI round; the task's status says why (`Running its scenario tests on CI`). `scripts/ci-scenario.py` is back as a dispatcher of a few lines of work (push, wait, read the result). `wsx task slot <command>` replaces `scripts/check-slot.py` for the deploy smoke test and the release handoff. A run also waits while the Mac has fewer free PTYs than a round needs (`waiting for PTYs: <free> free, a round needs ~<n>`). A worker turn starts through the same rule (status `load`: it waits while the load per core is over the start limit, one turn a minute, in order of urgency).
- Tasks: when free disk is under `tasks.minFreeGb` the host first removes the build folder of the project's task copies that nothing built in for 30 minutes (longest idle first) before it makes a task wait, and the repo service does the same each hour below 15 GB free. A cleaned copy builds again in its next check.
- Tasks: stopping an agent also stops the processes descended from it, found by parent pid before the first signal. On macOS 26 the system gives no environment for Apple system binaries (`/bin/zsh`, `/bin/sleep`), so the `WSX_AGENT_TREE` mark missed a tool shell that Claude started in a session of its own.
- CI: the `web` scenario's `chat` part runs on Ubuntu and its `tasks` part stays on macOS, where task agents run (the Seatbelt boundary); the `weblinux` probe scenario is gone, and the Linux jobs restore the Zig packages and the Rust build that a push to main saves.
- Tasks: every chat has the manager's capabilities. What a role runs in another project (`-p <other>`, `say --from-chat`) and whether `new --skills` is offered is one table in `wsx_core::task::policy`; the broker, `wsx task new` and the instructions an agent reads are built from it, so a prompt no longer promises what wsx refuses. A chat's `wsx memory add --source msg:<id>` now reads that chat's own log, not the first chat's.
- Tasks: a task whose checks wait in a queue (the machine's check slot) is in *Waiting*, held by `queue` (`status.waits_on`), and its row says `queued 12 min`; *Moving* means an agent turn or a check that runs now.

### Removed

- Tasks: `wsx task preview` and `tasks.preview` (a tailnet link to try a task, unused in 30 days), with the web's *Try* and the TUI's `T` in a task's detail. A config that still sets `tasks.preview` loads with an "unknown keys ignored" warning. A preview is designed again for the orchestration's workbenches (`docs/design/orchestration.md`).
- Tasks: the hidden `wsx task handback <n>`; run `wsx task hand <n> --back`.
- Tasks: `wsx task widths` and the lane width that check-run records carried (both unreleased); old log lines with `width` still load.
- Tasks: `tasks.manager.reviewMinutes` and the "waits on the manager" stall, which the review job replaces. A config that still sets it loads with an "unknown keys ignored" warning.

## [0.43.0] - 2026-11-16

A summary. The full notes are the [v0.43.0 release](https://github.com/vlwkaos/wsx/releases/tag/v0.43.0).

### Added

- Memory: `wsx memory search|add|update|supersede|reindex|status|list` keeps rules, facts and episodes per project or named scope. A landed task's memo becomes a `fact`, and a worker's first prompt holds the memory's start block.
- Tasks across projects: a manager works in another registered project with `-p <other>`, adds one with `wsx task project add <path> [--clone <git url>]`, and finds earlier messages, decisions and results with `wsx task search`.
- Tasks order: `wsx task after <n> <m>` and `wsx task new --after <m> --because <kind>` park a task until another lands. The owner's go on an action that waits for a land is kept with `--after <n> --owner-said <id>`.
- Agents: a Pi adapter, an `[[agents]]` registry with fallback agents, daily budgets and a stand-in for answers during a limit. An agent that is not Anthropic's own runs under a strict boundary. Every launch sets an explicit effort.
- Tasks: `wsx task push` after the owner's approval, `wsx task post --level warn|bad`, a check slot with `checks` and `scenarios` lanes, keep-warm pings, `tasks.skillsOnly` and `--skills`, and a sweep of old worktrees and sessions (`tasks.prune.*`).
- Panels: `panels:` in `wsx.config.yml`, `format: json` output (gauge, stat, table, list, cards and links), `scope: machine`, and the built-in `this-mac` panel.
- Web: a Media archive, find in a chat, pairing a new device from a paired one, adding and removing projects on Home, Delete on a worktree, `.html` files as pages, pictures and videos in messages, long pastes as files, compact copies of PDF and video uploads, Usage filters and a per-day chart.
- TUI: a routine's last run in its preview and detail, the Media archive (`m`) and one shell per project (`S`).
- Routines: `--findings-exit <codes>` names exit codes that mean the run found something.

### Changed

- Chats: a project has several chats. Each is a manager with a name and a goal, and all share the project's tasks, files, rules and memory.
- Routines recur only; `--at` is gone. wsxd runs the routine scheduler itself, in place of the vendored asched process. A check-in is a timer of the manager host. The daily digest is a routine per project.
- Tasks: one status function (`task::status`) and one chat classification (`chat_rows`) in wsx-core, so the web, the TUI and the CLI say the same. `wsx task why <n>` and `wsx task review <n>` show a task's state and story.
- Manager: it answers each owner message first and asks each question once. wsx refuses the rules it had to remember. On Claude it rotates its conversation at 400000 tokens. A deploy after lands waits for a quiet window (`tasks.deploy.quietMinutes`).
- Web: Approve and Deny are only in the Needs you list. Pills in the composer row replace the head line. Settings > UI and Settings > Usage are reorganized. A new session is a login shell with the agent command typed in.
- wsxd and TUI: no disk I/O under the state lock. Daemon revision 47 drops the `!` shell round (`exchange_shell`); revision 48 adds the `frames` request for previews. The TUI no longer waits for wsxd, and resizes merge.
- wsx-core API (published): the `panel` limits and `panel::plain_text` are private, and `task::ledger::{trigger_text, parse_trigger, local_minute}` moved to `routine::local`.
- Release: `scripts/release.sh` run again for an unpublished version moves its tag to the new commit.

### Fixed

- Tasks: a stopped agent takes its whole process tree, and no process from a task's copy outlives the close. Lands clear a stale `index.lock`, keep checks that passed on the rebased revision and run the newest deployed wsx. A landed task stays landed. A failed or silent manager turn reaches the owner at once, and each turn has a `turn.json` record.
- Terminal: a pane keeps 10,000 scrollback rows. Ghostty read the limit in bytes, so a pane kept 250 to 1,300 rows.
- TUI: keys on Linux are no longer cut off after 1 KiB, a key on macOS echoes in about 7 ms, and a config warning no longer draws over the screen.
- Web: Back restores the list's scroll place, unread follows each chat, idle pages stop ticking, a compact copy past its time limit stops its processes, and a half-saved config no longer drops the queue.
- `wsx daemon restart` gives one true answer. A socket path over the Unix limit fails at once and says so. A project behind a symlink matches wsxd's paths.
- Security: tokio 1.51.6 (RUSTSEC-2026-0386), rustls 0.23.46, rustls-webpki 0.103.16 and webpki-roots 1.0.10.

## [0.41.0] - 2026-10-30

### Added

- Tasks: token use and cost show in the TUI and the web. Each task's cost, input, cache read, cache write, output and turns are in `wsx task show` (and `--json`), the ledger's rows, the TUI task detail and a line on the web task sheet. The project's spend today and in the last 7 days, workers and manager apart, is under the TUI Tasks heading and in the web's `⋯` *Usage* sheet. One reader in wsx-core sums the logs' `usage`, also older lines that held a session's running total, and reads a log again only when it changed ([docs/tasks.md](docs/tasks.md) "Usage").
- Web: the image viewer has a Download control for a To check capture, image or video, so a copy can be kept before the capture is removed 7 days after the item is decided. `GET api/tasks/<project>/checks/<id>/capture?download=1` answers as an attachment named `task-<n>-<id>.<ext>`; the plain URL stays inline. On a phone it offers the file to the share sheet first, and iPhone Safari otherwise saves it to Files ([docs/web-client.md](docs/web-client.md) "Image viewer").
- Tasks: the manager hears of stuck work from wsx itself. A task that stays in one state produced no event, so a wait could sit for hours unseen. The manager host now looks every 10 s and sends one event per stall, with the task, its state, how long it lasted and the evidence: a disk wait while enough space is free (`free 53.0 GB, tasks.minFreeGb is 3`), a limit wait past its reset, a disk, limit or check-slot queue behind a task that does not run, a working or checking task with no log or check output for `tasks.checkTimeoutSeconds` plus 10 minutes, and a working task whose host does not answer. The same stall is not reported again; a new one after progress is ([docs/tasks.md](docs/tasks.md) "Manager").
- Profiles. A `[[profiles]]` entry in `config-v2.toml` (`name`, optional `claude_config_dir`) owns the projects that name it with `profile`. Its agents use that `CLAUDE_CONFIG_DIR`: task workers, the manager, roles, and the sessions and panes started from the TUI, `wsx session create`, `wsx task hand` or a web site, which a restore resumes under the same root. Their skills come from that root, and `wsx agent install claude` also installs the reporting hooks there. A web site grants `projects = { profile = "<name>" }`, which reaches a project that joins the profile at once. The TUI heads the Workspace with the active profile, `P` switches it, and the choice is kept beside the active group. With no `[[profiles]]`, one implicit `default` profile holds every project and wsx rewrites no file. An unknown profile, a duplicate name or a relative folder is named as a config error; a missing folder stops each agent start in that profile ([README](README.md#profiles)).
- Tasks: roles. A role is a second manager with a name, its own brief, notes and chat, for one area such as a long effort through a parent task: `wsx task role new <name> --brief <file>`, `role list`, `role close`, and `--role` on `say` and `chat`. It hears only the events of the tasks it creates and acts only on them; its host leaves when idle, so an idle role costs no agent. wsx itself limits roles: at most `tasks.roles.max` (default 2), the manager's `role new` asks the owner once (a Yes/No card, or `--owner-said`), a name the owner denied waits 7 days, and a role without a turn for `tasks.roles.closeDays` (default 14) is closed with its notes kept. The web lists roles in the project's `⋯` menu and opens their chat at `#/p/<project>/r/<role>`; the TUI's Tasks view lists them under *Roles* ([docs/tasks.md](docs/tasks.md) "Roles").
- Tasks: each worker `result` in the task log names the workflow step it ran in (`step`), what started the turn (`trigger`: a step, a message, a check retry, a check-run answer, a conflict, a result retry, a session limit, a rotation and others) and its main-conversation model calls (`usage.calls`). `scripts/usage-report.py` reads these fields instead of guessing them, and still reads older logs. A worker conversation now also rotates when it was idle for more than `tasks.agent.rotateIdleSeconds` (default 3600) and its context is at least half of `rotateTokens`: the prompt cache is gone after 1 hour, so a resume writes the whole context again. The default `tasks.agent.rotateTokens` drops from 350000 to 200000 ([docs/tasks.md](docs/tasks.md) "Context rotation", "Usage"; [docs/design/usage-audit.md](docs/design/usage-audit.md)).
- TUI: `S` in the Tasks view opens a shell, an ordinary session that worktree mode lists: in the selected task's working copy, or in the project's main checkout from the manager chat. A second `S` enters the same shell. The worker keeps running, unlike `wsx task hand` ([docs/tasks.md](docs/tasks.md) "TUI").
- Tasks: `tasks.preview.local: true` serves a preview on `http://127.0.0.1:<port>/` without `tailscale serve`, for a watch script per branch on this machine. A machine without `tailscale` on `PATH` gets the same local preview instead of a failure ([docs/tasks.md](docs/tasks.md) "Preview").
- TUI: the manager chat. In the Tasks view (`t`), `m` opens the project's manager chat: your messages and the manager's replies with their times, task events and quiet replies as one muted line each, and what the manager does while it works, newest at the bottom (`j`/`k` scroll). `i` writes to the manager the way `wsx task say` does and starts it when it is not running. The open To check items and waiting approvals are listed under the chat: `Tab` selects one, `p`, `s` and `f` pass, skip or fail an item with a note, and `y` or `n` approves or denies a request after a y/n question ([docs/tasks.md](docs/tasks.md) "TUI").
- Tasks: parent tasks. `wsx task new --into <p>` starts a child from task p's branch, and the child lands into p, not main. p is held, so it lands on main once, on the owner's word, with all its children's commits. After each child lands, p runs its checks on the new commits. A child's land waits while p works, checks or waits; p's close and land wait for its open children. The children's To check items join the list when p lands. The ledger shows `parent` and each parent's open `children`, and overlaps leave out a task's own parent and children ([docs/tasks.md](docs/tasks.md) "Parent tasks").
- Tasks: the owner can skip a To check item, `wsx task check skip <id>...` or `--all`, or Skip on the web row. A skipped item is neither passed nor failed: it leaves the open list, no longer holds a release, starts no fix task and stays recorded as skipped. Its capture goes 7 days later, like a decided item's ([docs/tasks.md](docs/tasks.md) "To check").
- Tasks: batch land. `wsx task land <a> <b>...` lands several ready tasks with one run of the checks. A detached copy stacks their revisions on the default branch tip and runs the checks once on the combined tree. Each task then lands without checks of its own when its rebase gives the tree that was checked. A failed batch splits in halves until the failing task lands alone through its own checks ([docs/tasks.md](docs/tasks.md) "Batch land").
- Tasks: each check result has `ms`, how long the check ran, and `queued_ms`, how long its run waited for the machine's check slot, in the task log, `result.json`, `show --json` and the ledger's `checks` rows ([docs/tasks.md](docs/tasks.md) "Checks, revisions and report").
- Tasks: land notice. After a land, each open task that shares files with it gets a message at its next step boundary: the landed commit, the shared files, and to rebase without a `check-run`. A task with no turn to come gets nothing, as its own land rebases it ([docs/tasks.md](docs/tasks.md) "Landing").
- CI: the task scenario (`scripts/test-task.py`) runs on GitHub Actions (macOS) for a push or pull request that changes the task code, and on every release tag ([docs/tasks.md](docs/tasks.md) "Checks, revisions and report").

### Changed

- Tasks: the manager can pass a To check item when the owner's message of its turn says the thing looks good: `wsx task check pass <id>... --owner-said <message>`, checked like the other `--owner-said` actions. The passed item keeps the message id as `owner_said` in `checks.jsonl` and `show --json`. Without `--owner-said`, with `--all`, and for `skip` and `fail`, the manager is still refused. The manager's prompt passes an item only when it is clearly about what the owner called good, and tells the owner in one line which items it passed ([docs/tasks.md](docs/tasks.md) "To check").
- Tasks: a task that resumes from a disk wait holds the disk slot for 60 s, no longer for its whole turn or checks. The tasks behind it resume about a minute apart while there is space, and do not wait an hour behind one long turn. An add during a disk wait now joins the held turn, with its prompt and step, and no longer starts a turn of its own that skips the disk queue ([docs/tasks.md](docs/tasks.md) "Free disk").
- Web: Home orders projects like a messenger. After the projects with needs come those with a message this device has not read, newest first, then the rest by the last owner-facing activity: a message, the owner's message, a task entering its state or an agent session changing state. A worker saving its record or the manager's own commands and events no longer lift a row; the overview's `last_unix_ms` and the row's time follow the same rule. A message arriving in the chat that is open leaves its project read ([docs/web-client-tasks.md](docs/web-client-tasks.md) "Home").
- Web: a manager that writes to the owner on its own, a reply that is not quiet to a turn of only events or a recap, such as after a routine's result, sends a "Manager needs me" push `<manager> wrote to you` that opens the chat. A reply to the owner's message never pushes ([docs/web-client.md](docs/web-client.md) "Notifications").
- Tasks: the handover of a fresh manager conversation also lists the routine results it may not have acted on: at most two lines per routine: its newest run with its failures since its last success folded in, and how often it ran since the previous conversation's last reply, so a rotation no longer loses them ([docs/tasks.md](docs/tasks.md) "Manager").
- Tasks: the checks after a result no longer run a check again when a `check-run` already ran it on the same clean tree; the result is reused and marked `stored`. Before, a worker's `check-run` of the checks was followed by the same checks once more (11 min on wsx). After a rebase or a conflict fix the worker is told to run no `check-run`, and wsx's worker words no longer ask for the `task` scenario on this machine ([docs/tasks.md](docs/tasks.md) "Checks, revisions and report").
- Web task sheet: an open task now opens on how it is doing and how far along it is. The top shows a health word from wsx's facts (working, running checks, waiting for a check slot, waiting for disk or the session limit, stuck, needs you), how long ago the worker last wrote, the workflow steps with the current one marked, and the worker's last sentence, never a raw tool line. A finished task leads with its outcome. Changes, Evidence, Left open, the messages to the worker, Shared files, usage and History are now under one folded *Details*; open To check items and all actions stay at the top ([docs/web-client-tasks.md](docs/web-client-tasks.md) "Task sheet").
- Tasks: an `agent` log line has `said: true` when it is the worker's own words, and the stall finder moved to wsx-core so the web reads the same rule as the manager ([docs/tasks.md](docs/tasks.md) "Manager").

### Fixed

- An open wsx window no longer reports a live wsxd handoff as a failure ("Connection reset by peer"). A window now polls once more before it reports a lost connection, and a request that certainly was not applied is repeated once also when no handoff was seen; a wsxd that really died is still reported ([docs/daemon-live-upgrade.md](docs/daemon-live-upgrade.md) "Transition marker").
- Tasks: the manager chat no longer shows empty rows. A manager's message to another project's manager or a role kept no text in its own log when the agent left out `--json`, so the web showed an empty "To <name>" bubble: such a `say` now always answers in JSON with its text, and an empty `sent` already logged shows nothing. A turn of only replies from other managers or roles is the manager's own work like a turn of events, so its short answer is quiet, and a reply of `-` or nothing shows nothing in the web or the TUI, also in older logs ([docs/tasks.md](docs/tasks.md) "Manager", "Managers talk").
- Tasks: a manager reply that asks the owner something shows "Asks you" on its bubble in the web chat and the TUI chat, and on the project's Home row, until the owner writes after it. wsx decides it from the text: the reply's last line ends with a question mark and is no table row. Such a reply is never quiet, so a question after a turn of only events is a message, not a muted line. The log stores it as `reply.asks`, and the manager's instructions now say to end the reply with its one question ([docs/tasks.md](docs/tasks.md) "TUI", [docs/web-client-tasks.md](docs/web-client-tasks.md) "Home").
- TUI: pane output no longer makes every TUI fetch a snapshot and redraw. Each PTY read in any pane made every TUI open a connection for a snapshot and draw it, about 10 times a second, which slowed the TUI. Only a change in the snapshot redraws now, and a moved cursor is saved on the fast timer, not the 30 s one. wsxd waits for a new connection in `poll(2)` instead of sleeping 20 ms, so a connection no longer waits for its hello ([docs/ui-state-ownership.md](docs/ui-state-ownership.md)).
- TUI: running the wsx unit tests no longer changes what an open TUI shows. Before, `cargo test` in a wsx pane wrote the test windows' cursor, folds and a dismissed `pi` integration prompt into your real `workspace-v3.toml`, which the TUI reads again when it restarts after a daemon upgrade, so the viewed session moved by itself. The tests also synchronized their own project list into your running wsxd, which dropped your worktrees and projects without sessions until the TUI synchronized them again. The TUI now keeps one cache file and one wsxd client for all its reads and writes, and a test gives it private ones. A custom wsxd client never starts or replaces a daemon ([docs/ui-state-ownership.md](docs/ui-state-ownership.md) "Test isolation").
- Web: the open decision list on a phone ends at its last row. With few running tasks and a To check count, an empty block was left between the list and the composer, because Running's half-height cap was a percentage of a body whose height came from its content; the cap now comes from the chat's height ([docs/web-client-tasks.md](docs/web-client-tasks.md) "Project screen").
- Daemon: a wsxd started by a test, fixture or script no longer keeps running after it ends. A main or routine wsxd stops when the directory it serves (the socket's directory, or the asched root) is deleted or replaced, or when the process named by `WSX_EXIT_WITH_PID` ends. The project's tests and scripts set it to their own pid. Before, every TUI or `wsx routine` run under a scratch HOME left a routine daemon behind, and a deleted `.work` folder kept its daemons alive. A user daemon is unchanged ([docs/daemon-discovery.md](docs/daemon-discovery.md) "Lifetime").
- Tasks: a task copy's build folder stays small. `task new` no longer clones main's `target/<profile>/incremental`, the host prunes stale units and old rustc sessions' objects from `target/*/deps` after each run of checks, and wsx builds with line tables (`[profile.dev] debug = "line-tables-only"` in `Cargo.toml`), which keep file:line in panics and backtraces. The main checkout and every task copy build with the same debug level, which is part of cargo's artifact hash, so a copy reuses the dependency build cloned from main and compiles no dependency again. A debugger that needs local variables builds with `CARGO_PROFILE_DEV_DEBUG=full`. A wsx copy measured 19 GB by du before and 1.8 GB after. A deploy or release copy left by a killed run is removed by the next deploy or release ([docs/tasks.md](docs/tasks.md) "Build output").
- Tasks: a worker turn that ends while its background jobs still run (a background subagent such as a review skill's, or a background Bash command) no longer counts as a turn without a result. The host waits for Claude's own turn after the jobs end, which returns the result, at most `tasks.checkTimeoutSeconds` (default 1200 s). Before, the host asked for the result at once and the task failed or waited on the owner with nothing done ([docs/tasks.md](docs/tasks.md) "Claude adapter").
- Tasks: a task whose session limit resets after wsx was replaced continues. Its host handed the turn to the new binary but did not restart until some request came, so the task showed `working` with no turn and kept the machine's limit slot for hours; the next task the slot passed to stopped the same way, and the tasks behind it waited. The turn after the limit now goes to the running agent and the next turn follows the new binary; a turn a timer starts restarts the host at once; and a host holds the limit slot only while its agent runs a turn. A `wsx task` action that reaches a host as it restarts is sent again, not answered with "the task host answer is not valid JSON: EOF".
- Tasks: a manager turn of only events that a usage limit held stays quiet after the reset. Its "-" reply no longer shows as a bubble with an empty list item.
- Web: the chat says when the manager's usage limit pauses it and when it resumes, as muted lines ("Atlas paused: session limit, resumes at 07:45", "Atlas resumed").
- Web: the open decision list of the manager chat no longer cuts rows. With many running tasks *Running* takes at most half of the list and scrolls inside itself under its label, so the rows that need the owner and To check keep their share. The *Running* label is no longer in capitals, so it reads at the rows' small size ([docs/web-client-tasks.md](docs/web-client-tasks.md) "Project screen").
- Web: passing, skipping or failing a To check item in the manager chat no longer moves its bubble to the end as a new message from the manager. The bubble stays at the time the item was added; the decision changes it in place.
- Client: a live handoff of wsxd is no longer reported as a failure by `wsx agent wait` or by opening a terminal. The TUI event monitor and `Client::call` already waited for the successor; these two did not, so a wait open in the old daemon or a stream opened while it handed off ended in an error. Both now wait for the successor once and go on (a repeated wait keeps only the time it had left), and a daemon that died is still reported at once ([docs/daemon-live-upgrade.md](docs/daemon-live-upgrade.md) "Single requests", "Terminal streams").
