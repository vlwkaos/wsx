# 한국어 동료 브리핑체 (ko-reader-brief)

명시적으로 이 스킬을 부를 때는 `/skill:ko-reader-brief`를 사용한다.

문체 이름: **동료 브리핑체** (colleague-briefing voice). 판정 기준은 하나다. **코드를 읽지 않은 동료가 이 글만 보고 무엇이 왜 바뀌었는지 이해하는가.** 친근한 말투가 목적이 아니라, 읽는 사람이 맥락 없이도 판단할 수 있게 만드는 것이 목적이다.

대상: 배포 노트, `CHANGELOG` 항목, GitHub Release 본문, PR 설명, 그리고 배포·변경 맥락의 팀 공지. 이 문체의 표지는 **요약(명사형 목록) + 상세(동작/구현)** 골격이다.
대상 아님:
- 일반 기술 설명 문서, 지식·방법론 노트, 개념 정리, 사용자용 기술 안내 — 변경 이력이 아니라 개념 설명이다. `/skill:ko-explain-voice`로 보낸다.
- 개인 에세이, 문화비판, 사유 기록. `/skill:ko-essay-voice`로 보낸다.

## 프로젝트 하우스 스타일이 우선한다

쓰기 전에 저장소에 고유 스타일 정의가 있는지 확인한다.

1. `AGENTS.md` 또는 `CLAUDE.md`의 스타일 표지(예: `release.changelog.style: <name>`)를 찾는다.
2. 표지가 가리키는 문서(예: `knowledge/coding/*Style*.md`)를 읽는다.
3. 최신 `CHANGELOG.md` 최상단 항목을 실제 예시로 읽는다.

프로젝트 정의가 있으면 그것이 이 스킬보다 우선한다. 충돌하는 지점만 프로젝트 쪽을 따르고, 프로젝트가 말하지 않은 부분은 아래 기본값을 쓴다. 정의가 없으면 아래가 기본값이다. 표지는 있는데 문서가 없으면 추측하지 말고 그 사실을 알린다.

## 어조

- **문장은 합니다체로 쓴다.** 종결어미는 `-습니다`/`-입니다`로 통일한다. 목록의 한 줄 제목(요약 항목, 상세 항목 첫 줄)은 명사형으로 끝내며, 이것은 한다체가 아니다. 기록용 한다체(`-한다`, `-이다`)는 쓰지 않는다. 읽는 대상이 작성자가 아니라 동료이기 때문이다. 같은 저장소나 같은 폴더의 기존 문서가 한다체라는 이유로 낮추지 않는다. 프로젝트 하우스 스타일이 한다체를 **명시적으로** 규정한 경우에만 예외다.
- 담백한 평서체. 과장, 홍보 문구, 감탄사, 이모지를 쓰지 않는다.
- **"배포"**를 쓴다. "릴리스"로 적지 않는다.
- **도메인 우선**: 현실의 규칙이나 이유를 먼저 말하고, 그다음 동작을 말한다. "일방통행 도로에는 중앙선이 없다고 보고…"가 "중앙선 판정 로직을 수정했다"보다 낫다.
- 커밋 로그를 옮겨 적지 않는다. 작성자가 아니라 동료에게 설명한다.
- 경계를 그은 변경이면 **이번 범위 밖**을 명시한다. "…예외 상황은 이번 범위에 넣지 않고 이후 별도로 다룰 예정입니다."
- 확인되지 않은 사용자 영향(성능 향상, 버그 해소 범위)을 추정해 쓰지 않는다.

## 용어

- 산문에서 코드 식별자를 최소화한다. 함수·타입·필드 이름 대신 사용자가 보는 것을 쓴다: "토글", "화살표", "중앙선".
- enum 값과 내부 상태는 도메인 용어로 옮긴다. 프로젝트에 대응표가 있으면 그것을 따른다.
- 예외: 의존성·빌드 항목에서는 라이브러리 이름과 버전을 그대로 적는다. 식별자가 정당한 유일한 자리다.
- 메커니즘 설명은 쓰지 않는다. 내부 구조는 지식 문서의 몫이고 변경 이력의 몫이 아니다.

## 구조

- **요약은 목록으로 쓴다.** 3–6개의 최상위 항목, 항목마다 변경 하나, 영향이 큰 순서. 이야기체 요약 문단은 쓰지 않는다.
  - 요약 항목은 **명사형으로 끝낸다**: "…기능 추가", "…문제 수정", "…적용", "…갱신". 여기서는 `-습니다` 문장을 쓰지 않는다.
  - 이슈 번호는 해당 항목 끝에 붙인다: `… 기능 추가 (#314)`. 커밋 링크는 요약에 두지 않는다.
  - 범위 제한(특정 백엔드 전용, 미룬 예외)은 요약이 아니라 그 항목의 `구현` 줄에 쓴다.
- 그다음 해당하는 분류만 쓴다. 기본값: `### 새로운 기능`, `### 버그 수정`, `### 정리·제거`, `### 내부·빌드`.
  - "리팩토링"보다 "정리·제거"를 쓴다. 의존성·문서·테스트·지식 정리는 "내부·빌드"가 흡수한다.
- **상세 항목은 "무엇"과 "어떻게"를 나눈다.** 항목마다 고정된 모양을 쓴다.

  ```markdown
  - <변경을 이름 붙이는 명사형 한 줄> (커밋·PR 링크)
    - **동작**: 사용자가 보는 것. 무엇이 어떻게 달라지는지, 어떤 버튼·표시가 뜨는지. 1–2문장, 합니다체, 코드 식별자 없음.
    - **구현**: 어떻게 했는지. 메커니즘·임계값·컴포넌트·라이브러리·범위 제한. 1–3문장. 식별자가 허용되는 자리.
  ```

  - 근거 링크(커밋 해시, PR, 이슈)는 첫 줄에만 붙인다. 링크 형식은 저장소의 기존 항목을 따른다.
  - 두 줄을 섞지 않는다. 사용자가 보는 것을 말하는 문장에 메커니즘을 끼우지 않고, 임계값이나 컴포넌트 이름이 나오면 `구현`이다.
  - 할 말이 없는 줄은 뺀다. 내부 항목은 보통 `구현`만 있고, 필요하면 `동작: 사용자에게 보이는 변화는 없습니다.`라고 적는다. 버전 올림·문서 정리처럼 사소한 항목은 첫 줄만 써도 된다.
  - 버그 수정의 `동작`은 사용자가 겪은 전·후를, `구현`은 원인과 조치를 말한다.
- 파일을 나열하지 않는다. 기계적인 변경은 묶는다: "스펙 문서와 단위 테스트를 정리".
- 범위를 빠뜨리지 않는다. 이전 배포부터 현재까지 모든 변경이 최소 한 항목에 대응해야 한다. 지식·세션 정리 커밋도 "내부·빌드" 한 항목으로 접어 넣고, 조용히 버리지 않는다.

## 하지 말아야 할 것

- 한다체로 쓰기. 옆 문서가 한다체라는 것은 근거가 되지 않는다.
- 커밋 제목 그대로 옮기기.
- 요약을 이야기체 문단으로 쓰기. 요약은 명사형 목록이다.
- 상세 항목을 한 덩어리 문단으로 쓰기. `동작`과 `구현`을 나누고, 한 문장에 둘을 섞지 않기.
- 코드 용어로 원리 설명하기.
- 변경된 파일 전부 나열하기.
- 분류를 위해 빈 섹션 만들기.
- 근거 없이 "개선", "최적화"라고만 쓰기. 무엇이 어떻게 달라졌는지 말한다.

## 교정 요청일 때

원문을 다시 쓰기 전에 어떤 기준을 어겼는지 먼저 짚는다. 종결어미, 요약이 문단인지, 상세 항목에서 `동작`·`구현`이 섞였는지, 식별자 노출, 범위 누락, 근거 링크 없음 순으로 확인하고, 고친 부분과 이유를 함께 준다. 원문에 없는 사실을 채워 넣지 않는다. 정보가 모자라면 커밋이나 PR을 확인하거나 작성자에게 묻는다.
