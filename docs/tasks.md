# Tasks (manager mode)

A task is one headless worker on its own branch and working copy. The caller never types into it. Every action is one CLI call; `--json` works on all of them except `digest`, `checkin`, `post` and `check-run`. No wsxd protocol change.

```sh
wsx task new "<prompt>" -p <project> [--from <ref>] [--title <words>] [--model <name>] [--hold <why>] [--files <glob>]... [--plan] [--into <n>] [--after <m> --because needs|files|check] [--size small|full] [--skip <step>]... --json   # or `-` (stdin) or --prompt-file <path>
wsx task list -p <project> [--all] --json
wsx task show <n> -p <project> --json            # record, result.json, report path, host_running, socket
wsx task steer <n> "<text>" --json               # into the running turn
wsx task add <n> "<text>" [--files <glob>]... --json   # after the turn (queued while one runs)
wsx task stop <n> --json                         # interrupt, and nothing else wakes it (see Host, Stop); the next add resumes the conversation
wsx task land <n> [--tried] [--owner-said <id> [--after <m>]] --json   # rebase, check, fast-forward (see Landing)
wsx task hold <n> "<why>" | --off --json         # the owner tries it before it lands; see Hold and trial
wsx task after <n> <m> "<then>" --because needs|files|check | <n> --off --json   # park <n> until <m> lands, then add <then>; see After another task
wsx task trial <n> [--end] --json                # its revision on the live site before it lands
wsx task hand <n> [--back] --json                # owner only: work on the task by hand (see By hand); --back: its commits are checked as the next revision
wsx task preview <n> [--stop] --json             # a link to try the task (tasks.preview); see Preview
wsx task check-run [<n>...]                      # from a worker: run the checks as after its result
wsx task check -p <project> [--json]             # the open "To check" items
wsx task check pass <id>... | --all --json       # owner; the manager: <id>... --owner-said <message>
wsx task check skip <id>... | --all --json       # owner only; closes without a verdict
wsx task check fail <id> [--note <text>] --json    # owner only; closes it as failed, with --note also starts a task that fixes it
wsx task close <n> [--discard] [--owner-said <id> [--after <m>]] --json
```

`-p <project>` and `--json` are global: every `wsx task` command takes them, before or after the subcommand (`digest`, `checkin` and `post` ignore `--json`; `ledger` always prints JSON). `-p` may be left out inside a project folder or when one project is registered. A task number is `3` or `t3`. `new --model <name>` picks the worker's model (one word, at most 256 bytes, not starting with `-`); without it the task uses `tasks.agent.model` (default `opus`). The record keeps it.

## Store

`$XDG_STATE_HOME/wsx/tasks/<project-id>/<n>/`, each folder 0700 and each file 0600, opened without following links.

| File | Content | Limit |
|---|---|---|
| `task.json` | id, project, base, branch `wsx/t<n>`, working copy, pane, adapter, model, tools, checks, agent session, state, revision, `created_by` (`owner`, `manager`, `chat:<name>`, or `manager@<project>` for a task the manager of another project created here: see Managers talk), `small`, `simplified`, `simplify_asked` (the simplify check, see Workflow), `hold` (why the owner tries it first), `after` (`{task, text, since_unix_ms}`: it waits for that task to land), `files` (expected path globs), `plan` (true until a `--plan` task's first result), `waiting` (`{on, reason}` while the state is `waiting`, on `check_slot` while checks wait for the check slot, and on `check_run` while a result waits for its check-run; on `limit` and `check_run` also `until_ms`) | 64 KiB |
| `log.jsonl` | append-only: `created`, `message{prompt\|steer\|add}`, `agent` (short progress; `said: true` on the worker's own words, not a tool call), `blocked{denials}`, `result`, `checks`, `check_retry`, `check_run`, `check_queued{reason}`, `disk_wait{free_mb, min_gb}`, `revision`, `preview{url, port}`, `hand{by, dropped}`, `handback{by, commits}`, `hold{reason, by}`, `after{task, text, by}` (`task` null: the wait was ended by hand), `after_ended{task, landed}`, `limit_wait{until_ms}`, `ping{usage}`, `trial{revision, commit}`, `trial_ended{reason}`, `stopped`, `closed` | 8 MiB for progress, 16 MiB hard |
| `result.json` | latest worker result and check results and `denials` | 256 KiB |
| `report.md` | report of the latest revision | |
| `captures/` | the To check captures and posters kept at the land; kept within `tasks.captureBudgetMb` of the project (see To check) | 2 MiB each image, 25 MiB each video |

- A host's control socket is not in the store: `sun_path` holds 104 bytes on macOS. The task host serves `<TMPDIR>/wsx-<uid>/t-<hash>.sock` and its worker's broker `w-<hash>.sock`, the manager `m-<hash>.sock` and its broker `b-<hash>.sock`, where `<hash>` is 16 hex of sha256 of the store path the socket stands for (`<n>/host.sock`, `<n>/broker.sock`, `manager/manager.sock`, `manager/broker.sock`), and `/tmp` replaces a `TMPDIR` longer than 64 bytes. The folder is 0700 and must belong to the user, the socket is 0600, a host removes its socket when it exits and replaces a stale one when it starts. A host and its callers must share `TMPDIR`; `show --json` and `manager --json` name the socket.
- `<project-id>` is `<name-slug>-<first 8 hex of sha256(project path)>`. Numbers come from a locked `next` counter and are never reused, also after a failed start.
- One writer: the CLI writes before the host starts and after it exits; the host writes everything in between.
- States: `working` (an agent turn runs; also the turn that resolves a landing conflict, which the web reads from the log), `waiting`, `checking`, `ready`, `failed`, `landed`, `closed`. `landed` and `closed` are not open. A `waiting` task names what it waits for in `waiting.on`, with a `reason` in plain words:

  | `on` | Why | Ends when |
  |---|---|---|
  | `owner` | the worker returned `blocked`, was stopped, or its host restarted during a turn | an `add` |
  | `paused` | the worker returned `paused`: its turn ended on a status (an outside run goes on), nothing is asked of the owner | an `add` (the manager continues it) |
  | `disk` | less than `tasks.minFreeGb` is free, or another task resumes from its disk wait | the host finds space (every 30 s) and it is first in the disk queue |
  | `hand` | the owner works in the copy (see By hand) | `handback` |
  | `plan` | a `--plan` task's first result is its plan (see Workflow) | an `add` |
  | `limit` | the agent hit its usage limit (see Claude adapter); `until_ms` names when it resumes | the host continues the session at that time, first in the limit queue |
- A prompt, steer or add is at most 64 KiB.

## Status

One function, `task::status::status` in `crates/wsx-core/src/task/status.rs`, puts a task's state into words: a short **label** for a row or a pill, and a **sentence** that says what it waits for, how long, the facts wsx has and what comes next: `<label>[ for <how long>]: <facts>. <next>`. The web overview (task rows and needs), the task view, the push, the ledger's open rows, `wsx task show` (its `status:` line and `status` in `--json`), the TUI list and detail and the manager's events all show these words, and none makes its own. Rows and pills show the label; the task sheet, the TUI detail and `show` show the sentence. How long counts from the task entering its state (a check slot wait from its `check_queued` entry), in the stall words ("less than a minute", "35 min", "3 h 10 min"). JSON has `status: {kind, label, sentence, since_unix_ms}`, where `kind` names the matching row (`approval`, `stuck`, `stopped`, `interrupted`, `owner`, `paused`, `plan`, `hand`, `disk`, `limit`, `check_slot`, `scenario_slot`, `check_run`, `checking`, `conflict`, `working`, `land_stopped`, `held`, `review`, `ready`, `failed`, `landed`, `closed`): a client picks a tone by it, never by the words; the web sheet reads its task again each minute while `since_unix_ms` is set, and the push uses the label alone, since it is sent once. Decisions never read these words: they test the record (`state`, `waiting.on`, `hold`, approvals). The first row that matches wins:

| Facts | Label | Sentence after the label |
|---|---|---|
| a pending approval of the task | Waiting for your approval | the manager asks: Approve land #3. It goes on when you approve or deny it. |
| `stall::stuck` (a view of one task only: it asks the host) | Stuck | no output for 1 h 0 min. The manager hears of the stall and decides what to do. |
| `owner`, the log's last word a `stopped` "stopped by request" | Stopped | stopped by request. Tell the manager to resume or close it. |
| `owner`, another `stopped` (the host restarted, the new wsx did not start) | Interrupted | the host restarted during a turn. The manager resumes it or tells you why not. |
| `owner`, the worker returned `blocked` | Waiting for your answer | <its question>. Answer the manager; the worker goes on then. |
| `paused` | Paused, the manager continues it | <the worker's status>. The turn ended with a status, not a question: nothing is asked of you. It is no need of the owner (web, push), its pane reads idle, the manager's event wakes the manager, and the event line, the ledger's open count, `list` and `show` say `paused`, not `waiting` (`task::status::state_word`). |
| `owner`, the worker returned `blocked` or idle and the task waits for another (`after`) | Waiting for #m to land | the status of the `after` row below: the worker asks nobody, the manager's event starts no turn, the agent reports idle and the web lists no need (`task::status::owner_waits_after`). A stop or an interrupted host is no such wait. |
| `plan` | Plan ready, waiting for the manager's review | the worker wrote its plan. The manager answers go or what to change, then the build starts. |
| `hand` | Waiting for you to hand it back | you work on it in its session and no agent runs. Commit, then hand it back: its checks run and it lands as usual. |
| `disk` | Waiting for disk space | 1.2 GB free of the 3 GB a task needs (or: #233 goes on first, 2 more tasks ahead). It goes on by itself once there is space. |
| `limit` | Waiting for the usage limit | claude usage limit; resumes at 07:45. It goes on by itself then, one task at a time. |
| `check_slot`, checks lane | Waiting for the check slot | #233 runs its checks now, 2 more tasks ahead. Its checks start when the slot is free. |
| `check_slot`, scenario lane | Waiting for the scenario test slot | #233 runs its scenario tests now, 2 more tasks ahead. Its scenario tests start when the slot is free. |
| `check_run` (state `working`) | Waiting for its check-run | the result waits for check-run web on CI. A failure goes back to the worker; a pass on its committed tree goes on by itself. |
| `checking` | Running checks | 3 checks of r2 run now. When they pass it is ready; a failed check goes back to the worker. |
| `working`, resolving a landing conflict | Resolving a conflict | the worker rebases it onto main. It lands when its checks pass. |
| `working` | Working on build (2 of 3), or Working | the worker runs its turn. Its checks run after its result (or: it is ready after its result; its plan goes to the manager). |
| `ready`, its landing stopped | Landing stopped | <why>. Land it again when that is fixed. |
| `ready`, waiting for another task (`after`) | Waiting for #12 to land | #12 is working. Its checks fail on main until #12 lands (the reason of `--because`). When it lands, wsx sends the task the manager's next instruction. If it is closed instead, the manager is told. |
| `ready`, held | Held | <the hold>. It lands only when you say so, or after a trial you pass. |
| `ready`, the manager reviews it (see Landing) | Ready, waiting for the manager's review | checks 3 of 3 passed. The manager reads the diff, then lands it or asks for changes. |
| `ready`, otherwise | Ready, waiting for you to land it | checks 3 of 3 passed (or: no checks prove it). Land it to put it on main. |
| `failed` | Failed | 1 of 3 checks failed after the worker's retries. Tell the manager, so the worker fixes it. (Or: the worker could not finish. Tell the manager what to do next.) |
| `landed` | Landed | on main (the web adds "; the last deploy does not have it yet"). |
| `closed` | Closed | it ended without landing. |

A slot holder of another project reads `pizzahouse #34`, and a holder that is no task (`scripts/check-slot.py`) by its own label: "<command> (pid 81) runs now". An open task with a hold that is not ready yet adds "Held: <hold>." to its sentence, and one that waits for another task adds "Then it waits for #12 to land." and its reason. The task waited for adds "Waited for by #14, #15." to its sentence (the kinds follow each number when they differ: "#14 (builds on it), #15 (same files)"), `status.waited_by` `[{task, because}]` and, for the task that waits, `status.wait`, the short reason a row shows.
- A task's title is `--title` (at most 60 characters, no control characters, kept in `task.json` as `title`), else the first line of its prompt, at most 120 characters. Either one is shown without a leading `Owner <words>:` (up to 80 characters before the colon; a colon inside brackets or without a space after it, as in `http://`, does not end it): `Owner report: tool permission` reads `tool permission`. A lead-in with nothing after it reads as the words in its brackets (`Owner report (UX failures):` reads `UX failures`), else as the prompt's next non-empty line. `Owner: x` has no words and stays. Only the shown title changes: `task.json` and the prompt keep what was written. Every title shown (ledger, events, the web) comes from this rule, also for tasks from before `--title`. The web shows a task without `--title` by the first sentence of its latest worker summary while it has one (`view::readable_title`).
- Each revision records `base` (the merge base with the default branch, so it follows a rebase) and the paths changed in `base..r<k>`: at most 500 paths and 32 KiB in `paths`, the full count in `paths_total`.
- `new --files <glob>` (repeatable; `add --files` extends) records the paths a task expects to change as `files` in `task.json`: at most 64 globs, each at most 256 bytes, relative to the checkout, without `..`, a valid glob (`*` stays in one folder, `**` crosses folders). A glob without wildcards also covers what is under it.
- `list --json` gives each open task `overlaps: [{id, count, complete, declared}]`, the other open tasks whose paths meet its paths. A task's paths are those its revisions changed plus its `files` globs, so a task with no revision overlaps by its globs alone. Changed paths shared exactly come first; only when none are shared, a meeting through a glob counts and the row has `declared: true`. Two wildcard globs meet when their literal heads and tails agree (`src/*.rs` meets `src/**/*.rs`, not `src/*.md`; this can report a meeting no real path makes). `show --json` adds up to 20 of the task's meeting `paths` per task. `complete` is false when a side kept fewer paths than it changed.

## Working copy

`<parent of main checkout>/<repo>-t<n>`: `git worktree add --no-checkout --detach` at the commit of `--from <ref>` (default: the default branch; the main checkout can be stale, so name a fresher ref when needed; `task.json` records the resolved commit as `base`), an APFS clone (`cp -c -R`, plain copy when that fails) of every top-level entry except `.git` and `target/<profile>/incremental` (see Build output), then `git reset` and `git reset --hard`, `git clean -fd` (ignored build output stays warm; filling the index first means only files that differ from the commit are rewritten, so the others keep their clone's mtime and cargo reuses the cloned build) and `git switch -c wsx/t<n>`. Ignored files of the main checkout, such as `.env` or local credentials, are copied into the working copy too, and the worker can read them. Worktrees nested in the main checkout are removed from the copy, so no `.git` file points at another checkout's admin folder. Projects with `.gitmodules` are refused. A failure removes the folder, worktree, branch and task folder.

## Host

`wsx task new` starts hidden `wsx task host <project-id> <n>` as the argv of a wsxd session named `task-<n>` in the working copy. The host:

1. starts the adapter and sends the prompt;
2. prints one progress line per agent step to its terminal (watch it in wsx like any session);
3. serves its control socket (see Store): one JSON request per connection (`status`, `steer`, `add`, `stop`, `land`, `hold`, `trial`, `hand`, `handback`, `close`), one JSON answer `{ok, state, message}`;
4. reports its pane through `AgentReport` with provider `task`: working and checking as Working, waiting on the owner as Blocked, ready as Done, failed as Error, waiting on disk, hands or a pause as Idle;
5. keeps running through `wsx daemon restart` (live handoff), because it is a pane process.

**Stop.** `wsx task stop <n>` (an open task that is not worked by hand) kills the agent, drops queued adds and logs `stopped`; the task waits on `owner` until an `add` or `steer` from the manager or the owner. Nothing else starts a worker turn for it, on any adapter: a limit or disk wait that ends, a rotation, a ping, a held result, a check retry and a land notice do not. The stop also drops the agent's late output, the disk and limit waits and the checks that run (their results go to the log only). A worker's `check-run` that was started before the stop still ends: its `check_run` entry and kept result are written, and its answer joins the prompt of the turn the next `add` starts. A wake and a stop in the same second end stopped. A second `stop` answers "already stopped". A host restart keeps the wait on `owner`.

A host restarted by a cold daemon start or `wsx session restart task-<n>` (an exited pane) logs `stopped` for a running turn and waits on the owner; the next add resumes. A host restarted while it was checking runs the checks again on the worker's last result, with the project's current checks. A new task's host starts the first turn with the prompt.

A host follows a deploy of wsx. It records the identity (device, inode, size, modification time) of the file it was started as (its argv[0], which `task new` and `say` make absolute). Before each agent turn (an add, a check retry, delivered queued messages) and before a land of a ready task, a task host that finds another file there writes the turn's text to `handoff.txt` (0600; its first line `trigger: "<name>"` keeps what started the turn, none in a file from an older host reads as `restart`), sets `working`, answers its caller and execs that file with the same arguments, also for a turn that a timer starts (after a full disk): the pane and pid stay, and the new host starts the turn with the new launch, resuming the same conversation. While a trial of any project holds a live site (a `trial.json` in the store), no host follows: the new file may be the trial's build, and the hosts follow the build that replaces it when the trial ends. The manager host does the same before its next turn; its messages stay logged and undelivered, so the new host queues them again. A land has no turn to hand over, so the host drops it unanswered, execs the file and the caller's retry reaches the new host, which runs the land with the new code (the caller gets the real outcome). A ready task waits for its land with no other turn, so before this its host kept the old binary for ever. `wsx task` actions (CLI and web) retry for up to 3 s while the socket is gone or when the host closed the request without an answer as it exec'd. Install by replacing the file (`cargo install`, `install`, `mv`, a package manager) with a rename over the path, never by moving the old file away first: a host or a `task new` that starts in that gap finds no file to run (`scripts/deploy-web-live.sh` hard-links the old file as `wsx.previous`, then renames the new one over `wsx`): macOS kills a process that execs an executable overwritten in place, and that host then stays down until `wsx session restart task-<n>`. A host started before this release has no such check: restart it once.

**An older host and a newer request.** A host reads only the requests its wsx knew, and closes one it cannot read without an answer. A deploy that adds a request (`after` was one) leaves every host that started before it unable to take it, and a ready task's host does not exec before such a request. `wsx task` actions (the CLI, the web client, a batch land) go through `call_task_host`: when the host still closes without an answer after the 3 s of retries, and the task is at rest (`ready`, `failed`, or `waiting` on `owner` or `plan`), the caller closes the session `task-<n>` and starts a new one in the working copy with this wsx's `task host`, waits up to 20 s for its socket, and sends the request once more. The new host loads the task as a restart does, so the task, its conversation and its `after` or `hold` stay as they were; its agent starts again on the next turn. A task in a turn or a check, or waiting on `disk`, `limit`, `check_slot`, `check_run` or `hand`, keeps its host (the replacement would stop the turn or drop the wait) and the caller gets an error: the host started before this wsx and cannot read the request while the task is `<state>`; repeat it when the task is ready or waits for the owner. The repeat then replaces the host. `wsx session restart` cannot do this: wsxd restarts only an exited pane. Part 38 of `scripts/test-task.py` runs it with a stand-in host that closes every request but `status`.

**A host that is gone.** A host that never started (its pane died on start, or a deploy replaced the wsx file while it started: task #303 stayed `working` with a log of only `created` and the prompt) or died leaves no socket, and nothing else restarts it. The same `call_task_host` handles it for any open task (not `landed` or `closed`), whatever its state: a host that is gone holds no turn, check or wait, so a restart loses nothing. When the socket is still gone after the 3 s of retries, the caller looks at the session `task-<n>` of the working copy. A session that is missing or whose pane exited gets a new host at once (a missing one is created); a live pane that has no socket may be a host that follows a replaced wsx and waits for the first run of the new file, so it gets up to 20 s to bind it first. The caller then sends the request once more, and the task, its conversation and its `after` or `hold` stay as they were; a `working` task starts its turn again as a restart does. `wsx task new` does the same when its host has not answered in 10 s, so a host that fails to start is replaced once and the task is not left without one. A task with a live host keeps its behavior. Part 39 of `scripts/test-task.py` kills a host of a task marked `working`, then an `add` restarts it and the turn runs, and a `hold` creates the lost session again.

## Agents

A task host and a manager host drive one headless agent through an adapter (`crates/wsx/src/task/agent.rs`): `claude` (Claude adapter) or `pi` (Pi adapter). `tasks.agent.adapter` and `tasks.manager.adapter` pick it. `tasks.agent.effort` and `tasks.manager.effort` (`low`, `medium`, `high`, `xhigh`, `max`; default `high` on every model, also `sonnet` and `--size small`; set `medium` only for an `opus` worker) go on every launch as Claude's `--effort` or Pi's `--thinking`, also a fallback agent's; a task keeps its own as `effort` on the record (`high` with `task new --size small`, whatever `tasks.agent.effort` says), and the views show it after the model. The hosts never read an adapter's stream: each maps it to the same turn results, usage and usage limit.

- Registry: the global `config-v2.toml` names the agents the owner uses, each `[[agents]]` with `name`, `command` (a session's command line), and for tasks `adapter`, `model`, `budget_usd_per_day`, `may` (the capabilities it passed, see Permissions, which also pick the jobs it fills) and `extension` (Pi adapter). `tasks.agent.fallback` and `tasks.manager.fallback` list up to 4 of those names, best first; a project that names none uses the owner's `~/.config/wsx/wsx.config.yml` lists. Workers need none: without one they wait and resume by themselves.
- `may` picks the jobs a fallback choice gives an agent (`Role::filled_by`, the one rule; `AgentEntry::allows` and `agent::fallback` read it). With no `may` an agent is a full fallback: the manager's turns and a task's steps, never the stand-in. With one, it fills each job whose own capability it lists: `create_task` the manager, `answer` the stand-in (the `organizer`), `result` a worker; `may = ["note", "handoff"]` fills none. `roles` and `minimal` are gone: a config with `roles` fails to load and names `may`, one with `minimal` fails as an unknown field.
- A limit belongs to an account: `claude`, or `<adapter>-<provider>` for a model written `provider/id` (`pi-anthropic`). Every limit an agent reports is kept for the machine in `tasks/agents/<account>.json` (`since_ms`, `until_ms`), so all hosts see it: a manager or a worker on a fallback makes no call to learn it again. A limit with no reset time (a backoff) that comes within 15 minutes of the last one's end keeps its `since_ms`: the backoffs in a row are one limit, as long as from `since_ms` to `until_ms`.
- Budget: an account other than Claude may spend the smallest `budget_usd_per_day` its agents set (1..=10000, default 10) in a local day, kept in `tasks/agents/<account>.spend.json` (one file, the current day only; two hosts writing at once can lose one turn's cost). Past it the account counts as limited until midnight. A local model reports no cost.
- One conversation is best, so going down waits: a limit whose length (above) is within `tasks.agent.maxWaitMinutes` (default 300, 0..=11520; Claude's 5-hour limit) is waited out as Claude adapter "Usage limit" says. A longer one moves the task or the manager to the first fallback that fills the job and has no limit on record; with none, it waits.
- Going up is at once (for a failed sign-in, see above). Before every turn the manager host looks again: when its own agent's limit is over, the next turn starts a fresh conversation on it, logged as `rotated{reason: "back on <adapter>"}`, opening with the handover and any held messages in full. A worker on a fallback goes home the same way when its fallback refuses it or its wait ticks with its own agent free; otherwise it stays until the task closes, since a second switch costs another cold start.
- A failed sign-in (`agent::auth_failed`) does not wait: the manager or worker moves at once to the first fallback that fills the role, has no limit on record and is not on an account with a failed sign-in on record. A Claude failure marks account `claude`, so every Claude agent is skipped; a Pi agent on `anthropic/...` is account `pi-anthropic` with its own login and is allowed. It is the long limit's path: the manager rotates with the handover and its held messages (the one chat line is the `rotated` reason `<adapter> moved to <fallback>: sign-in expired`; `state.json` `agent.sign_in` is true), a worker logs `agent_switch{reason: "sign-in expired"}` then `rotated` (its record has `fallback` and `sign_in`). The failure is kept in `tasks/agents/<account>.auth.json` (`since_ms`, `until_ms` = the retry time ahead): every host skips the account with no call, a new task starts on the fallback, and a worker whose own account is on record moves before its turn. Going home is at the first turn after the record ends (a manager only with a turn waiting, so an idle one does not move each 5 minutes): the own agent is tried again in a new conversation, the first success removes the record, and a try that fails moves the task or manager back. One rule decides when a failed sign-in is tried again: `store::sign_in_retry_ms` (5 minutes, `WSX_TEST_SIGN_IN_RETRY_SECS` for `scripts/test-task.py`), used by the record's end, by the manager's sign-in hold and by a worker's wait. With no usable fallback the manager keeps the sign-in hold of "Manager". A worker does not end `failed`: it waits like a usage limit (`limit_wait` in its log, state `waiting` on `limit`, the machine's limit queue) until the record ends, with the waiting reason `sign-in expired; tries again at HH:MM`, stops its agent process, and tries the turn again in a new process that resumes the conversation; the try that goes through removes the record and the task goes on by itself, and one that fails again waits again. A task whose turn starts while its account's record holds waits the same way with no call. A worker that fails sign-in on its fallback moves to the next one.
- A worker's switch ends its conversation as a rotation does (Context rotation): `agent_switch{from, to, reason}`, then `rotated{reason}`, and a new conversation that opens with the task's prompt, any handoff notes, the step, and the turn the limited agent did not finish, with the note that it wrote no notes.
- The manager's switch rotates at once; its first turn opens with the handover and the held messages in full. `state.json` `agent{name, adapter, model}` keeps the fallback across host restarts. A fallback runs its own model; `eventModel` applies only to the manager's own agent.
- Stand-in: during a hold, an owner message with no answer yet goes to the first agent that fills the `organizer` role with no limit on record (`may = ["answer"]`, `adapter: pi`, typically a local model behind Pi's `models.json`). It is one call with no tools and no stored conversation, given the notes, the last exchanges, the ledger summary and the message, and it has at most 3 minutes. Its reply is logged as `reply{provisional: <name>}` and the chats mark it with a warning icon named "Stand-in, not checked". The message stays due: the own agent answers it after the hold, and its first turn lists the stand-in's replies, says they may be wrong, and asks it to correct them. A stand-in that fails or cannot be reached counts as limited for 5 minutes, and the status line stays. Events never go to a stand-in.
- A new task starts on the first available fallback when its agent's limit or failed sign-in is on record. Its record has `fallback` (and `sign_in` for a sign-in) like a switched task's, so it goes home the same way.
- Shown agent: `agent{adapter, model, fallback}` is the agent in use now, not the configured one. A task's is its record's `adapter` and `model` (a switch rewrites them), `fallback` true once a usage limit switched it (the record's `fallback`, set with the `agent_switch` event); the manager's is `state.json` `agent` (`fallback` true), else `tasks.manager.adapter` and `model` (never `eventModel`), or for a role its own `role.json` agent. The ledger's open rows carry it (`crates/wsx-core/src/task/view.rs` `task_agent`, `manager_agent`); the TUI shows it in a task's detail ("Agent") and in the manager chat's heading. There is no effort: Claude Code takes `--effort <level>` and Pi `--thinking <level>`, but wsx passes neither and neither stream reports one, so none is shown.
- Process tree (`agent.rs` `AgentProcess`): each agent leads its own process group and gets `WSX_AGENT_TREE=<host pid>-<n>`, unique to that process, which its tool processes inherit. A stop (close, `stop`, rotation, switch, discard, re-exec, and the end of its output stream, also a read error) closes stdin, sends SIGTERM to the group and to every process of the owner's user whose environment holds that value (Claude's Bash tool starts each shell in a session of its own, out of the group), gives the agent 5 s, sends SIGKILL to the same set, then reaps the agent: no tool process, dev server or test run outlives it and no zombie stays. The host signals only these: never itself, never a process whose argv has `__wsx_resume_supervisor`, never by name. A process that cleared its environment and left the group is not found by this stop; `close` and the sweep find it by its executable (see Close, Stale worktrees). A read error on the agent's output logs `agent` "cannot read the agent's output: <error>; the host stops it" before the stop. A thread writes the agent's stdin, so a hung agent never blocks the host: at most 64 lines wait, then a send fails with "<adapter> does not read its input".
- An adapter without structured output returns a worker's result with `wsx task result -` (the result JSON on stdin) through the task host's broker, during the turn; the host checks it against the result schema and uses the last one when the turn ends.

## Claude adapter

`claude -p --input-format stream-json --output-format stream-json --verbose --setting-sources project,local --permission-mode bypassPermissions --model <model> --append-system-prompt <rules> --settings <no AI attribution> --json-schema <result schema> [--plugin-dir <owner skills>]` (see Permissions and Workflow), with `--session-id <uuid>` first and `--resume <uuid>` after a stop. The environment keeps only `HOME USER LOGNAME PATH SHELL LANG LC_ALL LC_CTYPE TMPDIR CLAUDE_CONFIG_DIR ANTHROPIC_API_KEY`, the proxy variables (`HTTPS_PROXY HTTP_PROXY NO_PROXY` and lowercase; a strict agent gets its own egress proxy's instead, see Permissions), `NODE_EXTRA_CA_CERTS SSL_CERT_FILE CARGO_HOME RUSTUP_HOME`, then `tasks.env` (see Config); of `WSX_*` only what the host sets (`WSX_TASK_BROKER`, `WSX_AGENT_TREE`, a manager's `WSX_TASK_ACTOR`). When the project's profile sets `claude_config_dir` (docs/configuration.md "Profiles"), `CLAUDE_CONFIG_DIR` is that folder for the worker, the manager and every role, and a missing folder stops the start with that reason. `GIT_EDITOR=true`, since no terminal can edit a commit or rebase message. A stdout line over 4 MiB is dropped in buffer-sized steps.

- Steer: a stream-json user message during a turn. Claude does not save it in its history, so the host logs it. A steer with no running turn is sent as an add.
- Reply text: a turn's text is every text block of the turn's main-conversation `assistant` lines (a subagent's and an API error's excluded), in order, joined with a blank line, since the `result` event's `result` holds only the last block: a manager that answers, calls tools and then closes would show the owner only the close. A block of `-` or nothing is dropped, so a turn whose only block is `-` has no words and reads as quiet (`says_nothing`). With no text block seen, `result` is the text, and an error result's `result` is its reason. The Pi adapter joins its `message_end` text blocks the same way. A worker's result is its structured output and does not change. Thinking is never shown, but both adapters count its characters (`TurnResult.thought`, Claude's `thinking` blocks and Pi's `thinking` content, main conversation only): a manager turn with at least 100 of them and at least twice the reply's characters (a `-` or empty reply counts 0) gets one follow-up turn, sent as a recap request (hidden in the chat), "Your answer to the owner was only in your thinking. Write it now as reply text, or reply - if it held nothing for the owner." The reply `-` stays quiet. No second follow-up until the owner writes again, so a follow-up that thinks as much starts no third turn.
- Usage (`usage` on `result` and the manager's `reply`): the token counts are the result's, summed over the turn's model calls; `context_tokens` and `model` are the last main-conversation call's (`assistant` lines without `parent_tool_use_id`); `session_cost_micro_usd` is Claude's `total_cost_usd`, the session's running total (a resumed process restores the earlier spend), and `cost_micro_usd` is this turn's part of it, the difference from the session's previous turn (the whole total when it is lower, as after a crash; after `handback` the first turn also counts what the owner's own `claude --resume` of the session spent while worked by hand). `calls` counts the turn's main-conversation model calls (distinct `assistant` message ids: Claude writes one line per content block). `adapter` names the adapter that ran the turn (`claude`, `pi`; the Pi adapter writes it too). A worker `result` also has `step` (the workflow step's name) and `trigger`, what started the turn: `step` (the first turn or a step's start), `message` (an add, or messages queued until a turn or checks ended), `check_retry`, `verify` (Human Verify items sent back), `check_run` (a check-run's answer after the result), `conflict`, `result_retry`, `limit` (after a session limit), `rotation` (a fresh conversation's first turn), `disk`, or `restart` (only in lines from before the re-exec logged its cause). A turn that a deploy re-exec carried (see below) keeps the trigger it had and adds `reexec: true` to its `result`; `scripts/usage-report.py` counts it under that trigger and prints how many came through a re-exec. A ping turn (Context rotation) logs `ping{usage}` instead of a result; `scripts/usage-report.py` counts it with trigger `ping`. Ref: [cost tracking](https://code.claude.com/docs/en/agent-sdk/cost-tracking). `scripts/usage-report.py` turns these fields into tables per day, task, step and manager turn, the manager's also by trigger: the owner, a peer, or the kind of the event that woke the turn, with how many ran no `wsx task` command that acts and how many replied `-` or one line; several state folders add up (`docs/design/usage-audit.md`).
- Usage totals (`crates/wsx-core/src/task/usage.rs`): a task's `usage` sums its log's `result` lines and the project's sums them over the tasks and the manager's replies, each `{cost_micro_usd, input_tokens, cache_read_tokens, cache_creation_tokens, output_tokens, turns}`. A line from before `session_cost_micro_usd` (commit 94f0b26) has it 0 and its `cost_micro_usd` was the session's running total, so its turn's part is the difference from the previous such line, as `scripts/usage-report.py` counts it. `show --json` and the ledger's `open` and `recent` rows carry the task's; the ledger's `usage` (also behind the web's usage routes, Usage filters below) is the project's `{today, week, days}`: `today` (since local midnight) and `week` (since the local midnight 6 days ago), each `{workers, manager}`, and `days`, those 7 days newest first, each `{day_ms, parts, usage}` with the cost in micro USD per part (`build`, `plan`, `context`, `review`, `memo`, `other` for any other worker turn, `manager`; a part with no cost is left out) and the day's whole `usage` (the sums above, for the token chart). A task not updated in those days is not read for them, and each log is read again only when its size or time changed. Chats' turns and the manager log's part before its newest roll are not counted. The manager's ledger summary does not carry them.
- Usage filters (`usage::Filter`, `usage::all`): the web's `api/tasks/<project>/usage` and `api/tasks/usage` and the TUI count only the turns of `period` (`today` since this machine's midnight, `week` the 7 days, `five_hour` or `seven_day` since the start of Claude's current window of that kind, none while it has reset; at most 8 days back; the days then start at its local midnight), `who` (`workers` or `manager`) and `agent`: an adapter (`claude`) or `adapter/model` (`claude/claude-opus-5-5`). A turn's agent is its usage's `adapter` and `model`. A worker line from before `adapter` takes its task's `adapter` from task.json (a switch rewrote it, so an earlier fallback's turns count under the current agent); a manager line from before it is `unknown`, since no record names the manager's agent then; a line with no model is `<adapter>/unknown`. The answer adds `total` (the slice's sum), `agents` (each adapter and `adapter/model` of the 7 days, unfiltered), `projects` and `limits`. The ledger's `usage` is unfiltered.
- Claude's limit state: Claude Code (2.1.316) sends a `rate_limit_event` with each turn, also while allowed: `rate_limit_info {status, resetsAt, rateLimitType, overageStatus, isUsingOverage, unifiedWindows: {five_hour, seven_day: {utilization (0 to 1), resetsAt, status}}}`. The Claude adapter keeps the newest as it came in `tasks/agents/claude.rate.json` (`{unix_ms, info}`, one file for the `claude` account, rewritten; `store::note_rate_limit`); a record older than 8 days is removed when read. `usage::limits` gives `[{agent, as_of_ms, status, windows: [{kind, status, utilization, resets_ms, start_ms}]}]` with only the windows not reset yet; `start_ms` is `resets_ms` less 5 hours or 7 days, the start of the window the limit counts (the web's window periods). An older line without `unifiedWindows` gives its one `rateLimitType` window, with no share. Pi's RPC (1.4.0) reports no limit, so it has none.
- A structured result that comes while background jobs still run (the count below) is taken at once; the host logs `agent` "the result came while <n> background job(s) run", since each job's notice later starts Claude's own turn.
- A turn that ends without a valid structured result: when its `usage` counts no token, it is Claude's own turn for a background-task notification (a `run_in_background` job that ended or was killed, also on `--resume`), which answers no message; the task host logs `agent` "claude ended its own turn with no result: ignored" and keeps waiting, and the manager host logs no reply for it. A model turn without a result that ends while background jobs still run (a background subagent or Bash command: the non-`ambient` entries of the last `system` `background_tasks_changed` line, a live set that starts empty with each process) is no missing result: the task host logs `agent` "the turn ended while <n> background job(s) run: waiting for their notice", keeps the turn running and takes the result from Claude's own turn after a job's `task_notification`. The wait lasts at most `tasks.checkTimeoutSeconds` (default 1200 s, the longest a single check may run) from the first such turn and is not extended by later ones; then the host logs "no notice from <n> background job(s) in <s> s: the turn ended without a result" and goes on as below. Any other model turn without a result gets one fixed turn that asks for the result as the turn's last call; a second turn without one fails the task ("the agent ended with success and no result"). An error result fails at once.
- Usage limit: a `result` with `api_error: "usage_limit_reached"` (Claude's "You've hit your session limit · resets 12:10am (Asia/Seoul)") is no result. It runs no checks and spends no check retry. The reset comes from `rate_limit_info.resetsAt` (unix seconds, on the rejected `rate_limit_event` and on the API error's `assistant` line), else from the text when its zone is this machine's; the host resumes 5 s after it. With neither, or a reset in the past or more than 8 days ahead, it backs off: 5 minutes, doubled for each limit in a row, at most an hour. The task waits on `limit` with the reason "session limit; resumes at <HH:MM local>" and logs `limit_wait{until_ms}`; the manager gets the waiting event, not a `failed` one, and the web sends no notification for it. At that time the host sends the same session "The session limit has reset. Continue the task where it stopped." with any message that came meanwhile (an `add` or `steer` during the wait joins that turn; `stop` and `hand` end the wait). Tasks resume one at a time, oldest wait first: each joins the machine's limit queue (`tasks/limit-slot/`, an `flock` like the disk queue) and holds the limit slot until its agent answers again, so a limit that has not lifted stops only one (a host with no running agent turn holds no slot: a stop, a hand or a failed start lets it go; the turn after the limit stays with the running host even when wsx was replaced, and the next turn follows the new file); one behind waits with "session limit has reset; queued for limit behind <project> t<n>". A host restarted during the wait resumes at the same `until_ms`. The manager host holds the turn the limit ended the same way (`state.json` `limit{until_ms, attempt, ids, events}`, logged as a `limit` entry with the resume time, and a `limit` entry without one when the held turn continues; the chat shows both as status lines, docs/web-client-tasks.md): it delivers no other turn until then, and its first turn after it answers the held messages and those that came meanwhile. A held turn whose every message is an event is a turn of only events: its short reply is quiet, and `-` shows nothing. A limit past `tasks.agent.maxWaitMinutes` moves the task or the manager to a fallback agent instead (see Agents).
- Only the worker's own word makes the task wait without checks: `status: blocked` (a question or a need: on `owner`) or `status: paused` (the turn ends while something outside goes on and nobody is asked: on `paused`), each with the summary's first line as the reason. A worker that must wait for an outside run ends its turn `paused`; the manager continues it with an `add`, after a `wsx task checkin --after` when the run is long. Tool calls Claude denied (`permission_denials`) are evidence: they are logged on the `result` event, listed in `result.json` (`denials`, also in `show --json`) and under Evidence in the report, and checks still run.
- Result schema: `{status: done|blocked|paused|failed, summary, decisions[{choice, reason}], evidence[{check, proof}], human_verify[{check, where, capture, poster, pass_if}], left_open[], notes, memo}` (`memo`: see Memo; a result without it reads as empty).

## Pi adapter

`pi --mode rpc --session-id <id> --session-dir <owner's Pi folder>/sessions/wsx --model <model> [-e <extension>] --no-extensions --no-mcp --no-prompt-templates --no-themes --no-context-files --no-skills --no-approve --append-system-prompt <rules> [--append-system-prompt <project AGENTS.md or CLAUDE.md>] [--skill <owner skills>]` (`crates/wsx/src/task/pi.rs`, Pi docs `rpc.md`). The owner's interactive Pi setup (extensions, global `AGENTS.md`, discovered skills) is left out; the project's own context file and the lent skills come in, as Claude's project settings do. `--session-id` opens the conversation or creates it, so the host's ID is the conversation.

- Extension: an `[[agents]]` entry with `adapter = "pi"` may set `extension = "<absolute path>"` (a file; validated with the registry). A launch whose model is that entry's (the first entry with `adapter = "pi"` and that `model`) adds `-e <path>`, so a lean runner loads although `--no-extensions` stays. A path that is not a file fails the launch ("extension ... is not a file"): the plain runner never starts in its place. A tier 3 agent will also get `--no-tools` here once the registry has `tier` (`pi.rs` marks the place; docs/design/local-model-fallback.md 8, W1).
- Runner policy: a launch with an extension also writes `policy.json` (mode `600`) into its Pi folder and sets `PYGMALION_POLICY` (its path) and `PYGMALION_POLICY_SHA256` (lowercase hex SHA-256 of its bytes). The file is `{tools, read, write, secrets}` and comes from the same paths as the Seatbelt profile (`Boundary::runner_file`): `tools` is the four of Pi (`read`, `bash`, `edit`, `write`), none for a stand-in; `read` is `/`; `write` is the agent's own folders (a worker: its copy and task folder; a manager: its folder and the overview) and `TMPDIR`, not the git folder, since git runs through bash; `secrets` is every folder the profile denies reading (`p` and `p/**`) and the credential file. The runner is a second layer: it cannot deny a subpath of an allowed folder, and it does not match bash command text, so the profile stays the gate for bash and for the git folder. The agent can rewrite `policy.json` (it is in `TMPDIR`), but the hash then no longer matches and the runner denies every call. Pi's stderr is piped: a runner line `{"pygmalion":"deny",...}` or `{"pygmalion":"policy",...}` becomes a progress line of the task or the manager (`runner denied write <path>: <reason>`, clipped), never the agent's words; any other stderr line goes to the host's stderr as before. `scripts/fake-pi-rpc.py` checks the variables, the hash and the shape; `scripts/test-task.py` part 23r shows a write outside the copy refused by the runner (the deny line in the log) and by the profile.
- Pi folder: each launch sets its own `PI_CODING_AGENT_DIR`, a `0700` folder in `TMPDIR` named `wsx-pi-<host pid>-<n>` that holds a copy of the owner's `models.json` (and the runner policy) (from their `PI_CODING_AGENT_DIR`, else `~/.pi/agent`), and removes it when the agent stops (a crashed host leaves it to `TMPDIR`). The owner's `settings.json`, packages, extensions and `auth.json` are not read: a provider key comes from the environment (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`) or `models.json`. Conversations live in the owner's `sessions/wsx` (`--session-dir`), so a restarted host opens the same ID. `scripts/fake-pi-rpc.py` records `argv`, the folder, its file names and `models.json` in the trace; `scripts/test-task.py` part 36 asserts them.

- A message is an RPC `prompt` with `streamingBehavior: steer`; one run, `agent_start` to `agent_settled`, is one turn. Its text is every assistant message's text, joined as in the Claude adapter's Reply text. Usage sums the run's assistant messages (`input`, `output`, `cacheRead`, `cacheWrite`, `cost.total`); the context is the last message's input and cache tokens.
- The worker's result comes through `wsx task result -` (Agents); the instructions carry the schema.
- A run that ends in an error whose words name missing credit or billing, a refused login or an unknown model counts as a limit of 6 hours, after Pi's own retries: nothing tells when the owner fixes it. One that names a 429, a rate limit, a usage limit, a quota or an unreachable server is a limit with no reset time: the host backs off (Claude adapter "Usage limit") or switches (Agents). Another error ends the turn as an error result.
- A stand-in's call (Agents) adds `--no-session --no-tools --thinking off` and `--system-prompt` with its own words, in place of `--session-id`, Pi's coding prompt, the project's context file and the lent skills.
- `set_model` takes `provider/id`. Stop queues `abort` without waiting for Pi to read it, then stops the process tree as Agents says.

## Permissions

wsx owns the boundary (`crates/wsx/src/task/boundary.rs`). The task host and the manager host start the agent as `/usr/bin/sandbox-exec -p <profile> <adapter argv>`, so one macOS Seatbelt profile per role covers the whole agent process tree: Bash, file tools, MCP servers and hooks. Inside it the adapter runs in its own no-prompt mode (Claude: `--permission-mode bypassPermissions`, no sandbox settings, no permission rules, no classifier), so nothing waits on a permission. The adapter only supplies its argv; another adapter adds argv and stream parsing. On a platform without Seatbelt (Linux) an agent start fails with a clear error; bubblewrap comes later. Before each agent start the host applies the profile once to `/usr/bin/true`; when sandbox-exec refuses it (a profile it cannot parse, or a host that runs inside another sandbox, where Seatbelt answers `sandbox_apply: Operation not permitted`), the start fails with sandbox-exec's words as the task's `stopped` reason and its failed result, which the ledger and the report show. Claude Code and Codex confine commands the same way (https://code.claude.com/docs/en/sandboxing, https://developers.openai.com/codex/security).

The profile is a deny-list on `(allow default)`; the last matching rule wins:

| Rule | Worker | Manager |
|---|---|---|
| no read or write | `~/.ssh`, `~/.aws`, `~/.gnupg` | same |
| no write | `~/Library/Keychains` (reads stay: the agent's own sign-in reads the login keychain), the wsx config folders (the platform one and `$XDG_CONFIG_HOME/wsx`), the wsx state folder, the routine store (`routines` beside wsxd's socket: wsxd runs the routines written there outside the boundary, see Routines), other task copies `<repo>-t<n>` (also those made after the launch), the default branch's ref and reflog in the main repository's git folder (and their `.lock`): lands stay with wsx; that git folder's `hooks` and `config`, which run or apply in the owner's own git | the same as a worker, but the default branch's ref and reflog stay writable: when a land refuses on the owner's uncommitted changes in the main checkout, the manager commits them on main after the owner's yes (see Manager); its instructions allow no other git write: a push or a rewrite of the default branch is `wsx task push` (see Push) |
| no signal | a signal (`kill`, `pkill`, `killall`) to any process outside its own sandbox: `(deny signal)` then `(allow signal (target same-sandbox))`. Each `sandbox-exec` is its own sandbox, so an agent signals only its own tree (its jobs, test daemons, browsers, check processes, also when daemonised), never another worker, the manager, wsxd or the owner's processes; the refusal is EPERM | the same |
| written again | its working copy and its task folder | its `manager/` folder and the project overview (and files beside it with the overview's name as prefix) |

Everything else is open, the main checkout's working tree (the project folder) included, which the deny-list does not name: a worker can write it, and a land refuses only for its changed files that the land changes too (see Landing). Also open: writes in home (`~/.cargo`, `~/.config/ir`, `~/Library`), any host, loopback listen, PTYs, Chrome. Paths are matched as real paths (`/var` is `/private/var`). Nothing is granted: there is no `wsx task allow`, no permission wait and no `grants.json`. A record that waited on `permission` reads as waiting on `owner`; old `granted` log lines and grant approval requests are skipped when read. Tool calls an agent reports as denied are still evidence (`permission_denials`, see Claude adapter); a worker that cannot go on returns `blocked` and the task waits on `owner`. The worker's instructions say to stop a job only by the pid or process group it started, never `pkill -f` or `killall`: a `pkill -f` on a script's name once matched the `claude` argv of three other workers, whose workflow text names that script, and ended them (2026-11-05). Seatbelt does not start inside another sandbox, so tests that start task hosts run as checks (the host runs them outside the boundary). `scripts/test-task.py` part 23 runs one probe as a fake worker that is not Claude and part 32h runs the same probe through the real Claude when one is on `PATH`: refused are `~/.ssh` (read and write), the state folder outside the task folder, another copy (one that exists and one made after the launch), main's ref, `.lock` and reflog, and the git folder's `hooks` and `config`; a signal to a process outside the sandbox is refused and one to its own child is allowed; allowed are the own copy and task folder, `$TMPDIR`, `~/.cargo/registry`, `~/Library`, loopback and a PTY; `scripts/test-manager-boundary.py` checks the manager with the real Claude, which also kills its own child and fails with EPERM on a `sleep` outside and on a second `sandbox-exec` with the manager's profile (`wsx task boundary-profile`, hidden).

**One rule: role, agent, trust.** What an agent may do is decided outside the model, in one place: `wsx_core::task::policy`. `Policy::of(trust, role, agent)` is the role's group of capabilities cut down to what the agent's `[[agents]]` entry passed, and the brokers refuse the rest (exit 2), whatever the prompt says.

*Capability* (one enum, `Capability`): `read` (`list`, `show`, `ledger`, `deployed`, `chat`, `search`, `check`, `manager`, `routine list|show|logs`), `notify` (`post`, `digest`, `say`), `answer` (reply text to the owner), `backlog` (`after`, `hold`), `note` (write the manager's notes), `handoff` (write a rotation's handoff notes), `create_task` (`new`), `direct` (`add`, `steer`, `stop`, `preview`), `close` (`close`), `discard` (`close --discard`), `land_child` and `land` (`land` into a parent task, onto the default branch), `deploy` (`deploy`, `release`, `push`, `trial`, `project add`), `routine` (`routine add|edit|delete|enable|disable|run|cancel|fire`, `checkin`), `approve` (`approve`, `deny`, `hand` with or without `--back`, `chat new|list|close`, the old `handback`, `dismiss` and the hidden host commands, which the CLI judges itself for a manager) `result` (a worker's `result` and `check-run`), `recall` (`wsx memory search|recall|status|list`), `remember` (`wsx memory add|update|supersede|reindex`) and `decide` (a `rule` record). `recall` is every role's, whatever `may` lists; an untrusted agent has neither `remember` nor `decide`. `MemoryCmd::needs` names the one each memory subcommand needs. `TaskCmd::needs` names the capability each subcommand needs, in a match that does not compile for a new subcommand; `answer`, `note` and `handoff` are checked by the jobs that use them.

*Role* (a built-in table in `policy.rs`, no group in config; an entry's `may` picks which of them it fills, see Agents):

| Role | Capabilities | Runs as |
|---|---|---|
| manager | all | the manager host |
| area | all but `discard`, `land`, `deploy`, `routine`, `approve`, `result` (it has `recall`, `remember` and `decide`); it acts only on tasks it created and lands only a child into its parent | each named chat's host (`WSX_TASK_ACTOR=chat:<name>`) |
| organizer | `read`, `answer`, `backlog`, `note`, `recall` | an entry whose `may` lists `answer`: the stand-in during a hold; the backlog's upkeep is not started yet |
| worker | `result`, `recall`, `remember` | the task host |

*Agent*: an `[[agents]]` entry may list `may = ["read", "answer"]`, the capabilities it passed. A missing list is all of the role's capabilities; a stand-in lists `may = ["answer"]`. Several entries with one adapter and model give what all of them pass. The owner writes the list by hand after a tier test.

*Trust* decides the profile and the approval rules, not the capabilities. An agent is `trusted` only when it is the Claude adapter with no `ANTHROPIC_BASE_URL` in its environment (`tasks.env` or the profile). Every other agent is `untrusted`: the Pi adapter with any model, and Claude pointed at another endpoint (the model name is not read: Anthropic's endpoint serves only Claude models). The host derives it at each agent start; no config key sets it.

| | trusted (Claude) | untrusted |
|---|---|---|
| Profile | the text above, unchanged | the same denials, and also: no write except `/dev/null`, terminals and PTYs, `$TMPDIR`, the role's own folders (a worker: its copy, its task folder and the main repository's git folder, which its commits use; a manager or role: its `manager/` folder and the overview; the default branch's ref, `hooks` and `config` stay denied), and the adapter's own state folder (`$CLAUDE_CONFIG_DIR` or `~/.claude`, `$PI_CODING_AGENT_DIR` or `~/.pi/agent`) with its credential file (`.credentials.json`, `auth.json`) unreadable |
| Reads | all but the secrets above | also not `~/.config/gh`, `~/.netrc`, `~/.npmrc`, `~/.claude` (unless it is the adapter's folder), the Keychains and wsx's config folders |
| Network | open | loopback (a local model server, the agent's own tests), the host's broker socket, and no Unix socket else: wsxd's is denied by name too. A remote provider only through the egress proxy (below); a direct connection to any other address is refused |
| Programs | any | `sudo`, `su`, `osascript`, `launchctl` and `open` do not start |
| Environment | the adapter's kept variables | the same, and of `ANTHROPIC_API_KEY` and `OPENAI_API_KEY` only the one its provider needs |
| Outward commands | `tasks.*.approve` | always a request to the owner; `--owner-said` is ignored (also for `check pass` and routine changes, which run outside the boundary) |

A strict agent on a remote provider reaches it through the host's egress proxy and nothing else. The provider is the `baseUrl` of `providers.<provider>` in the `models.json` of Pi's folder, else the built-in provider's own (`anthropic` is `api.anthropic.com`, `openai` is `api.openai.com`; port 443); Claude on another endpoint has its `ANTHROPIC_BASE_URL`. A built-in `anthropic` also names `platform.claude.com:443`, where Pi's sign-in refreshes its token. A provider wsx cannot name, or one on this machine's loopback, gets no proxy and reaches nothing remote. `sandbox-exec` accepts only `*` or `localhost` as the host of a network address, so the profile cannot name a remote host: it allows the loopback and refuses every other address, the resolver included. The proxy (`crates/wsx/src/task/egress.rs`) is an HTTP CONNECT tunnel the task host or manager host starts on `127.0.0.1` with an ephemeral port for each strict agent process, and stops with it (the listener, every tunnel and every thread; the port refuses afterwards). Its allowlist is the provider's host and port. It tunnels bytes (no TLS interception) and answers 403 to any other CONNECT target and to any plain HTTP request, so a provider on a plain `http` base URL works for Pi (it tunnels every origin) and not for Claude, which sends a plain request. It resolves the name itself and refuses a name that resolves to a loopback, private, link-local or shared (Tailscale) address unless the provider itself is on such an address (an IP literal or `localhost` is known at once; any other name is decided by its first lookup, in the proxy's own thread, and kept for the launch, so a slow resolver only slows that agent's first request, never the host; a provider on the LAN by its IP or name works). At most 32 tunnels at once (the next gets 503); a request head over 8 KiB or slower than 10 s ends; a tunnel with no byte for 10 minutes ends. The agent's environment holds `HTTPS_PROXY`, `HTTP_PROXY` (and lowercase) as `http://127.0.0.1:<port>` and `NO_PROXY=127.0.0.1,localhost,::1`; the host's own proxy variables are not passed to a strict agent. Pi reads them itself (its HTTP client is undici's `EnvHttpProxyAgent` with tunnels); a client that ignores them is refused by the profile, never let through (any address that is not this machine's: Seatbelt counts the machine's own addresses as `localhost`). The loopback stays open to every port, so a strict agent could also use another agent's proxy, which names that agent's provider, not a wider one. A trusted agent has no proxy and keeps today's open network. A built-in provider also keeps its key variable and its sign-in file (`auth.json`) readable; any other provider's key is `apiKey` in `models.json`. Not built yet: a per-launch Pi folder with only the provider's own sign-in (docs/design/local-model-fallback.md W2): until then `auth.json` of a built-in provider is readable whole by that agent.

The manager host checks every `task` command its agent sends against the policy (the argv is parsed as the CLI parses it); the task host checks a worker's the same way, and its role grants only `result`, `check-run` and `wsx memory` (below). A refusal exits 2 and names the cause: the role's group lacks the command (`chat new is not for a chat; ask the manager`), or the agent did not pass it (`... is beyond what this agent may do (`may` of its [[agents]] entry); it passed: ...`). An argv that parses to no command runs nothing in the CLI either and is passed on. The CLI keeps the finer rules (the owner's word, a task's creator, a child into its parent) and the same group table for a command that reaches it by another way. A command without the broker (`WSX_TASK_BROKER` unset) runs as the owner's CLI, but writes the state, which the profile denies. `WSX_TASK_TRUST` is the host's mark, like the actor: missing means trusted, any other value than `trusted` means untrusted. `scripts/test-task.py` section 23s runs a scripted weak model (`scripts/fake-weak-model.py`) as a Pi worker, which tries each forbidden file, network, program, signal, git and `wsx task` action as the write tool, as bash and as `python -c`, an untrusted manager with and without a `may` list, and a named chat on an agent that passed only `answer` and `note`. Not built yet (docs/design/local-model-fallback.md W2): Pi's `--no-tools` and its per-launch agent folder.

- The broker: a host serves `<TMPDIR>/wsx-<uid>/b-<hash>.sock` (the manager host, for `manager/broker.sock`) or `w-<hash>.sock` (a task host, for `wsx task check-run`) and gives the agent `WSX_TASK_BROKER=<that socket>`. Under it the `wsx` CLI runs nothing itself: a `task` command sends its argv, the folder and, when an argument is `-`, its standard input (UTF-8, at most 1 MiB) to the socket, prints the answer's stdout and stderr and exits with its code; any other command is refused (exit 2). The manager host refuses argv that is not `task <subcommand>` and the hidden `task host` and `task manager-host`, runs its own wsx binary with `WSX_TASK_ACTOR=manager` in that folder (the main checkout when it is not a folder), keeps at most 1 MiB of stdout and of stderr and stops a command after 15 minutes (exit 124); a deploy or release answers when it started (see Deploy and release). So a heredoc, `;`, `&&` or a pipe works, and the approval rules still see the manager actor. The host also gives each command `WSX_TASK_TRUST=trusted|untrusted`, the trust of the agent that runs now, and runs only a command its agent's policy grants (below).

## Workflow

The stages are fixed: the manager talks the request through with the owner and sizes it, workers build (a larger task plans first), the host checks, the manager reviews and lands. The words each stage gets are the project's:

```yaml
tasks:
  skills: owner          # or none (default): lend workers the owner's skills, as the manager has them
  skillsOnly: [develop, seek]   # optional: a worker gets only these (task new --skills replaces it); empty or unset = all
  workflow:
    build: "..."         # added to every worker's instructions
    review: "..."        # added to the manager's review of a ready task
    idle: "..."          # the idle task's prompt; empty (default) is off
    steps:               # the worker's turns in order; none (default) is one build turn
      - name: context
        prompt: Use owner:recall to load the context of this task.
      - name: plan
        prompt: Use owner:develop to explore and plan. Do not edit yet.
      - name: build
        prompt: Implement the plan.
```

**Steps.** With `steps` the host sends each step as its own turn of the same worker conversation: the first turn is the prompt and "Step 1 of N, <name>: <prompt>", and a result with status `done` starts the next step, with any message queued during the turn. Each step's text ends by asking the worker to wait for or stop each background job it started before its result, since a job that ends after the result starts Claude's own turn that answers nothing new; the last step's text also asks for the result's memo (see Memo), so no step of its own is needed for it. The checks run after the last step, as after any result; check retries, conflicts and adds after that are ordinary turns. A step that needs the owner's decision returns `blocked` and the task waits on `owner`; the answer continues the same step. The task record keeps `steps` as they were at `task new` and `step`, the index of the current one; the web shows it under *Running* as `plan (2/3)`. A project's `tasks.workflow.steps` wins; a project without them takes the owner's from `~/.config/wsx/wsx.config.yml` (or under `$XDG_CONFIG_HOME`), of which only `tasks.workflow.steps` is read. At most 12 steps; a name is 1 to 32 letters, digits, `-` or `_`, unique; a prompt is 1 to 16 KiB of text. A bad step refuses `task new`. `task new --skip <step>` (repeatable) leaves that step out of this task's `steps`, for a prompt that already carries the context and the plan; a name that is not a step, or skipping every step, refuses `task new`.

**Lean flow** (`crates/wsx/src/task/cmd/new.rs` `folded_steps`, `host.rs` `task_context`). Whatever `steps` a config lists, wsx runs no turn only to load context or to write the memo:

- The first turn opens, after the prompt, with the host's task context: the task's `--files`, the open tasks that share them (as in Store "overlaps") and the memory's start block ([memory.md](memory.md) "Start set": the area briefs of `memory.areas` and the brief and rules of the role that created the task; no fact records), the block at most 4 KiB with what did not fit named. With none of these it is left out.
- At `task new` a step named `context` is not a turn: its prompt joins the next other step as "If the task context above is not enough: <prompt>", so the worker loads more only when the block does not cover the task. A step named `memo` is not a turn either: its prompt joins the step before it as "For the memo: <prompt>", and the last step's result carries the memo as always. The record keeps the folded steps; with no other step it keeps none and the task is one turn. The saving is about one first turn's recall work, not the turn's whole cost: the first-turn cache write moves to the first real step (docs/design/usage-audit.md "Audit 2026-11-04").
- `task new --size small` is for a change the manager can state (what changes, where, how it proves itself): only the `build` step (with the folded words; no step when there is none) on `tasks.agent.smallModel` with effort `high`. `--model` still wins; `--skip` does not go with it. The default `--size full` runs every step on `tasks.agent.model`.
- **Simplify check** (`host.rs` `settle_result`, `claude.rs` `runs_simplify`, `TaskRecord::simplify_missing`). A full task's worker must load the simplify skill, and wsx reads that from the agent's own record, not the worker's words. Claude's stream carries each `Skill` tool call: a `tool_use` named `Skill` whose `input.skill` is `simplify` or `owner:simplify` sets `simplified` on the record (kept across rotations, resumes and host restarts, so every session of the task counts). When the last step ends `done` and the task is not `small` (`--size small` sets `small`), has steps, runs on the `claude` adapter, was lent the skill (`<n>/skills-plugin/skills/simplify` exists: `tasks.skills: owner`, and `skillsOnly` if set names it) and never loaded it, the host sends the worker back once (`simplify_asked`, log `result` trigger `simplify`: "Run owner:simplify on your changes ... then finish as before") and then goes on to the checks whatever it does. A task that still has not loaded it (`simplify_asked` and not `simplified`) is ready with "simplify did not run": in its status sentence (`checks 1 of 1 passed; simplify did not run`) and as `; simplify did not run` at the end of the manager's `ready` event. A plan-only result and a step before the last are never checked; a project that lends no simplify skill is not checked. **Pi** keeps no record of a loaded skill (it reads a skill's file with its read tool, which looks like any read), so its tasks are skipped rather than guessed.

- Defaults name no skill. `build`: keep the change lean, reuse what exists, remove what the change makes dead, and simplify the diff before finishing. `review`: nothing beyond the fixed review (the owner's words, no copy of an existing helper, no dead code, nothing unasked).
- With `skills: owner` the task host writes the skills plugin into the task folder (`<n>/skills-plugin/`, as the manager's) and passes `--plugin-dir`; the worker gets `Skill` and is told to look at the skills and follow any whose description fits the work. With no skills folder there is no plugin. `skillsOnly`, or a task's own `wsx task new --skills a,b` in its place (the record's `skills`; `owner:<name>` is `<name>`; refused when the project lends none), makes `skills-plugin/skills/` a folder of links to just the named skills (the manager keeps all, and its instructions name `--skills`); a name the owner lacks is skipped with a warning on the host's stderr. A skill list costs tokens in every worker prefix (docs/design/token-usage.md).
- The idle task: when `idle` is set, the manager host itself (not the agent, so it is deterministic) looks once per quiet period (see Recap) and starts one ordinary task, titled "Consolidate project knowledge", with `idle` as its prompt, `created_by: manager` and no workflow steps (hidden `task new --no-steps`: one turn), so it waits for the manager's review and lands through the normal checks. It starts only when a file in the main checkout's `knowledge/sessions/<project>/` changed after the last idle task started, and that task is no longer open; `state.json` keeps both (`idle_task`, `idle_ms`). Otherwise it starts nothing and says nothing. With `recapMinutes: 0` there is no idle task. A failed start is tried again the next period.
- Plan first: `task new --plan` ends the first prompt with a request to write a short plan (goal, files, approach, how it proves it) as the result and to edit nothing. That result runs no checks: the host clears `plan` and the task waits on `plan` ("the worker wrote its plan"), which the manager hears as an event and the web shows as working. The manager reads it (`show --json`) and continues with `wsx task add <n>` (go, or what to change); the task then goes on as any other. A Claude worker's instructions send a search across many files to the Explore subagent in the foreground (`run_in_background: false`; `model: sonnet`, or `model: haiku` for a plan's code reading), bringing back findings with file:line: a background one came after the plan's result (docs/design/manager-reliability.md "F"). Pi has no subagents. Its instructions: use it, or `--hold`, for large work or work costly to undo, not small fixes.

**Context rotation.** A worker conversation that grows past `tasks.agent.rotateTokens` (default 200000, 1000..=2000000; the main checkout's config at that turn) continues in a fresh one, since every model call reads the whole context again (`crates/wsx/src/task/host.rs` `rotation_due`). The size is the last model call's context of the latest result. A conversation of at least half that size also rotates when the agent last answered (a result or a session limit) more than `tasks.agent.rotateIdleSeconds` ago (default 3600, 0..=86400, 0 = never): Claude's prompt cache lives 1 hour, so a resume after that writes the whole context again; then `rotated` has `reason` "idle <n> min" and the handoff request says so. Before the next turn (a step, a message, a check-run answer, a retry), the host asks the worker, in the old conversation, to write handoff notes to `rotate-notes.md` in its task folder (what it does now, what is done and remains, decisions, files, checks, lessons; at most 12 KB) and to return a result that is not checked: it logs `agent` "handoff notes: …", not a `result`. Then it ends that conversation, clears `agent_session`, logs `rotated{tokens, reason}` and starts the waiting turn in a new conversation that opens with: the task continues from a closed conversation, see git for the working copy, load the project knowledge again (recall or seek), the task's prompt, the notes inline (a path when they are larger than 16 KiB), the current step when the waiting turn is not that step's start, then the waiting turn and any queued message. Never for the turn that asks again for a missing result, nor while a `check-run` waits. A host started after a re-exec knows the size from the next result on.

**Keep-warm pings.** A wait the host knows is pinged, not rotated (`host.rs` `ping_due`). The worker waits on its checks (state `checking`, also on the check slot) or on a queued `check-run`'s answer. When its agent last answered `tasks.agent.keepWarmSeconds` ago (default 3300, 0..=3599, 0 = never), the host sends one no-op turn ("wsx keep-alive: ... answer with the one word ok"). The agent's answer reads the cached context and writes it again for another hour. The host logs `ping{usage}`: no result, no step, no checks, no `agent` line. The ping counts as an answer, so the idle rotation above counts from it. Rules:

- At most 3 pings in a row (`KEEP_WARM_PINGS`): a real turn resets the count. Three pings keep a wait warm for about 3 h 40 min. Each costs about $0.03 at 120k context, against about $1 for the rewrite after a gap of over 1 h. A longer wait rotates as before.
- No ping in a usage limit (the task's own wait or the account's limit record), a disk wait, by hand, on a fallback that is not Claude, when the last answer is over 1 h old (the cache is gone), or when the context has reached `rotateTokens` (that turn rotates anyway).
- No ping for a task that is ready or waits on the owner: such a wait often ends with no next turn.
- A turn that comes during a ping (a check-run answer, a check retry, a message) starts when the ping ends. A ping that meets a usage limit is no answer (Claude's refusal costs nothing); the next real turn meets the limit and waits as usual.

## Checks, revisions and report

After each result that is not blocked or paused the host runs `tasks.checks` with `/bin/sh -c` in the working copy (the checks and `tasks.checkTimeoutSeconds` as the main checkout's config has them at that moment, so a task started before they changed lands through the current gate; the record's `checks` follow) (`tasks.checkTimeoutSeconds`, default 1200, and the whole output, stdout and stderr in the order written, kept in `check-<n>.log` in the task folder (`check-run-<n>.log` for a worker's `check-run`, overwritten by the next run of that check) while the check runs to its end; the result keeps the log's last 8 KiB, and a cut result starts with `[the first <N> bytes are cut; the whole output is in <log>]`; no `WSX_*`, plus `tasks.env`; a timed-out check's process group is killed; a process the check left behind holds only the log, so the check ends with its shell), then sets `refs/wsx/task/<n>/r<k>` to the worker's HEAD. The host commits nothing; the worker commits. `ready` needs worker status `done` and every check at exit 0; otherwise `failed`. When the worker said `done` but a check failed, the host first sends the failure back: it logs `check_retry{revision, attempt, commands}` and starts a worker turn with each failed command, how it ended and the last 3 KiB of its output; the checks run again on the result as a new revision. After 2 such turns the task is `failed` as before; a message from the owner or the manager (an add) allows 2 more. A landing's checks are never retried. **Check slot.** Two lanes, one run at a time in each, on the machine, for every project and task host of the wsx state folder; tasks still work in parallel. The `checks` lane takes `tasks.checks` runs (after a result, a landing's rebase, a trial's rebase, a batch) and a worker's `check-run` of plain checks. The `scenarios` lane takes a worker's `check-run` that names a local `tasks.scenarios` entry (a run that mixes both too; a `ci:` scenario takes no slot, see Scenarios) and `scripts/check-slot.py` users (`deploy-web-live.sh`'s smoke test and live handoff, `release.sh`'s live handoff). So a plain run may run beside a scenario: that load is accepted; more than one run per lane overloaded the machine and failed timed scenarios. A lane's slot is an `flock` on `tasks/check-slot/slot.lock` (checks; the path is kept so older hosts still serialize with checks) or `tasks/scenario-slot/slot.lock` (`crates/wsx/src/task/slot.rs`), which the kernel frees with its process, so a killed or crashed host never blocks the queue. A waiter keeps its own ticket file locked; a ticket whose lock is free is a dead waiter's and is removed. The runs of a lane take its slot: first come, first served, except that a landing's checks go before every other waiting run (they are closest to the default branch). A worker's `check-run` whose checks only format or compile (one plain `cargo fmt`, `cargo build` or `cargo check` command each, without `&`, `|`, `;`, `$`, redirections or a second line) skips the queue. While a run waits, the record's `waiting` is `{on: check_slot, reason: "queued for the check slot behind <project> t<n>[ and <k> more]" ("the scenario test slot" in its lane)}` with the state still `checking` (or `working` for a worker's run), the log gets `check_queued{reason}`, the pane says it, and `waiting` clears once the slot is taken. Each check's timeout counts from that moment, not while it waits. **Time.** Each check result (in `checks` and `check_run` log events, `result.json`, `show --json` and the ledger's `checks` rows) has `ms`, how long the check ran, and `queued_ms`, how long its run waited for the check slot before it (0 for a run that takes no slot); a result reused from an earlier run on the same tree has `stored: true` and that run's `ms`. **Check-run.** In the build the worker runs only the checks its change touches (`wsx task check-run 2 3`, by number as its instructions list them), never the full set: the host runs that once after the result. A check that fails in code the worker did not touch is not the task's to fix: the worker does not run it again and names it in its summary. Under `WSX_TASK_BROKER` the CLI sends the argv to the task host's broker, which runs those checks in the check slot exactly as after a result, answers each command and how it ended (the output of a failed one) with exit 0 when all passed, and logs `check_run{results}`; no revision is recorded. When the working copy is clean (no tracked change and no untracked file) the host keeps each result with HEAD's tree id, if the tree is the same when the run ends and the check did not time out or fill the disk. A later `check-run` on that tree answers a kept check whose command is unchanged from its result, marked `(stored: it ran on this tree before)`, and runs only the others; with none left it runs nothing and logs nothing. A check that exits 75 (EX_TEMPFAIL, a failure outside the tree such as a CI runner's network) is never kept, here or for the checks after a result: its answer says `(a temporary failure, not kept: the next check-run runs it again)`, and the next `check-run` on the same tree runs it again. The kept results live in the host's memory, for one tree at a time. The CLI waits for the answer without a read timeout while the checks run. A run that must wait for the check slot (the host gets its `check_queued`) answers every waiting call at once with exit 0 and `queued for the machine's check slot: its answer comes after your result` (a run with a `ci:` scenario answers `queued on CI: ...` as soon as it starts), which tells the worker to finish its step and return its result without polling: the queue (20-90 min) outlasts an agent's background job, and a waiting turn costs model calls (`docs/design/usage-audit.md`, Audit 2026-11-04). The host does not exec a replaced wsx binary while a `check-run` waits or owes its answer, since that would drop the run. A run never starts beside the task's own running or queued one: a repeat `check-run` of the same checks on the same HEAD commit (a client that gave up and asks again) joins it and gets its answer (`queued` again for a queued run, also after it ended: its answer goes to the turn after the result). One on another commit never joins: it answers `queued behind your check-run on commit <12 chars>` at once and starts when the pending run ends (a later one replaces it, and a stop drops it). The pending run's answer then joins the next turn, a held result waits for the new run, and the new run's answer comes as a queued run's. A run that still waits for its slot is not cancelled: it runs, and only its answer is late. One of other checks on the same commit is refused until it ends, and one that comes while the checks after a result run is refused. The checks after a result reuse the kept results too: a check that a `check-run` ran on the same clean tree, with an unchanged command, is not run again (`stored: true`), and with none left the checks take no slot. After a rebase or a conflict fix the worker runs no `check-run` (its instructions and the conflict turn say so): the checks after its result prove the rebased tree. When the worker returns its result (`done` or `blocked`) while its `check-run` has no answer, the result waits for the run to end (the task stays `working`, the step does not advance). While it runs, the record's `waiting` is `{on: check_run, reason: "the result waits for check-run <names>[ on CI]", until_ms}`, where `until_ms` is the run's start (or the moment it took its slot) plus its time limit: each local check's `tasks.checkTimeoutSeconds`, and 125 min for a `ci:` one (60 min of queue for a CI runner plus 60 min of run, plus 5 min to start and fetch the files). A `ci:` run writes little output, so the stall check reports that wait only after `until_ms`, never as silent (see Stalls). When the run ends, the worker gets one `check_run` turn with the answer: `Your check-run ended. Its answer, on commit <12 chars>:`, then the text the CLI would print, and its next result takes the normal path (the next step, or the checks). A queued run that ended before the result starts that turn right after the result; any other run that ended before the result starts no turn. **A pass needs no turn:** when such a run passed (exit 0 for every check, on a clean tree that was unchanged when it ended, so its results are kept) and the held result is `done`, the host starts no turn. On the last step it adds one `evidence` entry (`wsx task check-run (recorded by the host)`, the answer as proof) to the held result, shows in the report, and the result goes on to the checks at once; the evidence is named `wsx task check-run <names> passed (recorded by the host)`, and the manager's `ready` event for that revision lists it as `check-run <names> passed (recorded by the host)` before `worker says:`, since the worker's words were written while the run was pending. On an earlier step the answer joins the next step's prompt. A failure, a changed or dirty tree, or a result that is not `done` still starts the `check_run` turn. The checks of a result also never run beside their own earlier run: a result that comes while they wait or run (Claude's own turn for a background task's notice can answer again) is answered by that run, which records one revision; on a new commit they run once more when it ends, and after a `blocked` result they record nothing and the task keeps its wait. **Scenarios.** `tasks.scenarios` maps a name to a slower end-to-end command. A worker runs one only by naming it, `wsx task check-run web`, or by its number after the checks (the names in order); its instructions list them. It runs like a named check (the slot, the timeout, `tasks.env`, kept results), never in a bare `check-run`, after a result or in a land. A scenario whose command starts with `ci:` runs the rest on the host, which waits on CI: it takes no check slot, so any number run at once beside the lanes, and its run answers `queued on CI` at once; the answer comes as the turn after the result, like a queued run's. In a run that mixes it with local checks it starts at once and the others wait for their lane. It times out after 125 min, not `tasks.checkTimeoutSeconds`: the script's queue limit (60 min with no job started) plus its run limit (60 min from the first job's start) plus 5 min to start and fetch the files. **Parts.** `wsx task check-run web --part tasks` reruns one part of one scenario (exactly one scenario is named; the part is letters, digits, `-` and `_`): the host puts `export WSX_SCENARIO_PART='<part>';` before the command (after `ci:`), and the project's command decides what a part is. A part's pass is not a full pass: its result is kept nowhere and no evidence is recorded, its answer says so and the worker gets an answer turn, and the full run still gates the task, so the worker runs the scenario whole once before its result. wsx's own scenarios have parts, one CI job each: `web` has `chat` and `tasks` (`scripts/test-web-client.py --part`), `task` has `core` (sections 0 to 21c of `scripts/test-task.py`: new, steer, close, landing, checks, deploy and release, the manager's start and notes; about 9 min), `worker` (22 to 32u: approvals, the boundary probe, the worker's checks, limit waits; about 8 min) and `host` (32d to 39: the disk queue, stalls, roles, other projects (33r: a manager works in another one), the fallback agent, older and lost hosts; about 9 min), the whole being about 25 min. `scripts/test-task.py --part <part>` runs one; with no `--part` it runs all three in order, as one script. A part run alone starts from the fixture and makes the project state the sections before it left (`fresh_project`, `store_up` and, for the manager, `manager_up`, which `core` runs in section 20), so a section that needs state from an earlier part builds its own. A part run and a full run of the same scenario never join each other. The command is the project's: it sends the working copy's HEAD to CI, waits for the run and exits with its result. wsx's `task`, `web` and `weblinux` (the web scenario on Ubuntu, a probe of whether `web` can leave macOS) scenarios are `ci: python3 -B scripts/ci-scenario.py <name>`: the script refuses a dirty tree, pushes HEAD's tree with origin/main's `.github/workflows` (the `gh` token has no `workflow` scope) over https to `wsx-scenario/<name>/<unix time>-<commit>` (`--<part>` after the commit for `--part` or `WSX_SCENARIO_PART`); a job `if` cannot read the matrix, so every part's job starts, a gate step in each ends the other parts' jobs green at once, and the script leaves a job named for another part out of its waits, its start time and its failed list, waits for `ci.yml` (jobs `task-scenario` and `web-scenario` on macOS, `web-scenario-linux` on Ubuntu, at most 5 at once for the account; the `test` jobs skip such a branch), says how long the run waited in GitHub's queue when its first job starts (`queued <n> min before its jobs started`), cancels a run whose jobs have not started in 60 min (`QUEUE_SECONDS`; a runner problem, not the tree, so it exits 75 and the host keeps no result) or have not ended 60 min after the first one started (`RUN_SECONDS`; the queue wait does not count against it; it fails), prints the last 150 log lines of each failed job and the names of the failed jobs (the part is in the name, and with `fail-fast: false` one run reports every failed part), polls the run with one request (`gh api repos/<repo>/actions/runs/<id>`) every 30 s, every 60 s after 10 min, and reads the jobs only when the run's status changes, every 5 min (`JOBS_SECONDS`: with a part the run is `in_progress` while its own job still queues) and at the end (it was `gh run view --json status,conclusion,jobs` every 10 s, which spent the account's 5000 requests an hour when several tasks ran scenarios: 10:04 on 2026-11-10 every `web` check-run ended `HTTP 0: API rate limit exceeded`), treats a rate limit answer (a 429, a 403 that names the limit, or any failed call while `gh api rate_limit`, which does not count, shows the core limit at 0) as no failure: it waits until the reset time, or `Retry-After` / 60 s for a secondary limit, and runs the call again, and exits 75 when the reset is after the script's deadline (125 min, the host's `ci:` limit) or when the token is invalid (`HTTP 401`, one line), says its `gh` call count at the end (the cleanup calls never wait), exits 75 instead of 1 when the failed log shows a network or runner failure (`TEMPORARY_FAILURES` in the script: `UnknownHostName`, `Could not resolve host`, `unable to connect to server`, `Connection reset`, `Connection timed out`, `TLS handshake`, `The operation was canceled`, HTTP 5xx, a lost runner) and no `FAIL`, `AssertionError` or `Traceback` line (see Check-run), unpacks the run's `scenario-files-<part>` artifacts (each a `files.tar`, kept 1 day, every part's even when another failed) into the same paths under `.work/` (the web scenario's captures in `.work/web-captures`, for `human_verify`) and deletes the branch; a branch a killed script left is deleted by the next run once it is 3 hours old (no CI job may write: release.yml calls ci.yml with `contents: read`). **Orphan runs.** The account runs 5 macOS jobs at once, so a run whose script is gone (killed, or its cancel hit the rate limit) holds a slot, and every new run queues behind it (2026-11-10: 10 such runs, and `web` check-runs ended `no job started in 60 min of queue`). At its start the script cancels every `wsx-scenario/*` run that is queued or in progress and older than its whole time (125 min; two list requests, one cancel for each), and its own cancel at the end waits out a rate limit (at most 15 min, `CANCEL_WAIT_SECONDS`). **Build cache.** `task-scenario` and `web-scenario` share one rust-cache `shared-key` (`scenario-build`) and only restore it (`save-if: false`, Zig set up with `use-cache: false`); the `scenario-cache` job, on a push to main, builds `cargo build --locked -p wsx -p wsx-daemon` and is the only job that saves it (a branch reads the default branch's caches, never another branch's). The rule: a job that runs only on scenario branches (`wsx-scenario/*`) never saves a cache, since no other run can read it and each save counts against the repo's 10 GB cache limit. A scenario job reaches CI only with main on origin, which only `scripts/release.sh` pushes: until a release carries it, `ci-scenario.py` stops with "origin/main's ci.yml has no job for wsx-scenario/<name>/", and a `--part` that main's matrix does not list stops it the same way. By hand, for debugging, run the job's command locally: `cargo build -p wsx -p wsx-daemon && python3 -B scripts/test-web-client.py --browser`. The `task-scenario` job also runs on a push or pull request that changes `crates/wsx/src/task`, `crates/wsx-core/src/task` or `scripts/test-task.py`, and always on a release tag. Like the checks, the scenarios are the main checkout's config, never the working copy's. Any other argv is refused, and so is a run while the owner works by hand.

**Shared failure.** A check that fails the same way in two tasks fails on main, not in the tasks. When a host records a check result (a worker's `check-run` or the checks after a result), `wsx-core` `task::failure` takes a key for each failing command: the command and the last line of its output that has `FAIL`, `FAILED` (each as a whole word, so GitHub's env echo `CACHE_ON_FAILURE: false` is none) or `AssertionError` (else the last `error` line that is not cargo's `could not compile`, `previous error` or `test run failed`), digits normalised to `0` for the compare and the key only (a `scripts/ci-scenario.py` log line loses its job, step and time prefix and GitHub's `##[error]` mark first, and GitHub's `Process completed with exit code` line is generic, so two runs that fail on different asserts share no key). A timeout, a result without such a line and a full disk give no key. The host compares the keys with the newest result of each command in the other tasks of the project, read from the last 128 KiB of the logs (`check_run` and `checks` events up to 24 h old, the 40 newest tasks, a command that passed later does not count). With two or more tasks on one key it posts one event line to the manager, started if needed, that wakes a turn: `checks fail the same way in #a, #b, likely on main: `<command>` ends with `<line>`; one fix task, not one per task`, where `<line>` is the line as the newest task printed it (clipped), digits intact. The key is posted once per day (`post-keys.json` in the project's folder, as `wsx task post --key`), so a host restart or a second host posting at once posts it at most once a day (the file is read and written without a lock: two hosts that finish in the same instant can both post). The worker whose `check-run` failed also gets the sentence ``<command>`: the same failure is in #a; it is likely on main, not your change.`` at the end of the answer, every time, so it does not spend turns on it.

**Free disk.** Before an agent turn and before checks the host needs `tasks.minFreeGb` (default 5; wsx sets 3, see Config "Build output") free on the working copy's volume. Below it the task waits on `disk` with the reason "<n> GB free of the <m> GB a task needs" and logs `disk_wait`; it looks again every 30 s and runs the turn or the checks once there is space, without spending a check retry. Messages that arrive meanwhile, also while the task is queued behind another, join the waiting turn and never start one of their own; during held checks they follow the checks. Tasks resume from a disk wait one at a time, so they do not fill the freed space at once: each waiting task joins the machine's disk queue (`tasks/disk-slot/`, an `flock` like the check slot), the oldest wait first. Once there is space the first one resumes and holds the disk slot for 60 s, or less when its turn or checks end sooner; the next one resumes at its next look after that, only if there is still space. A long turn never holds the queue. A task behind another keeps waiting on `disk` with the reason "queued for disk behind <project> t<id>". A check whose output says `No space left on device` waits the same way and runs again, and so does a worker that returns `blocked` while the disk is low: it is told there is space again and continues.

The worker proves what it can: its result has `evidence` (`{check, proof}`, the command or capture path) for each check a command, a test or a capture shows, and `human_verify` only for how it looks or feels: a state a fixture can stage is the worker's to prove. `report.md` has Summary (with one "Decided:" line when the worker made decisions), Changes (`base..r<k>` commits and diffstat, plus uncommitted files), Evidence ("4 checks passed", each check, then the worker's evidence), To check (the `human_verify` items) and Left open, built from the log, git and `result.json` only.

## To check

There is no verdict per task: a task the checks prove lands, and what needs a person waits in one list per project, `tasks/<project-id>/checks.jsonl`. When a task lands, its host adds the `human_verify` items of the landed revision as `{id: c<n>, task, revision, commit, check, where, capture, poster, pass_if, state: open, note, fix_task, unix_ms}` (`poster` only with a video; a row without it reads as none; `unix_ms` is when the row was written, and a read item also has `added_unix_ms`, the `unix_ms` of its first row), once per task and revision, before it sets `landed` (items of a revision whose landing conflicted are kept when the resolving turn leaves them out). The file only grows, under a lock: a later line with the same id is the item's current row.

- A worker's item is `{check, where, capture, poster, pass_if}`: what a person looks at or feels in plain words, where (a URL, a page path or the screen), the path of an image or a short video of it in the working copy (or empty), a video's thumbnail image (or empty; ignored for an image) and when it passes. At the land the host copies each capture inside the working copy, a PNG, JPEG or WebP image of at most 2 MiB or an MP4 video (an ISO BMFF file, its first box `ftyp`) of at most 25 MiB, to `captures/r<revision>-<n>.<ext>` in the task folder, and a video's poster, an image, to `captures/r<revision>-<n>.poster.<ext>`, before the copy goes; another file is dropped with a line in the pane. A worker that sends a video for an iPhone writes it with `-movflags +faststart`, so it plays before it is all read.
- A capture stays while its item is open, and after it is passed, failed or skipped, until the project's captures (images, videos and posters, in every task folder) take more than `tasks.captureBudgetMb` (default 1024, i.e. 1 GiB; 1..=1048576). The manager host checks this when it starts and then hourly, under the list's lock; over the budget it removes the files of the oldest decided items until the rest fit: the skipped and failed items first, oldest first, then the passed ones, oldest first. An open item's files are never removed, so open captures alone may exceed the budget. Measured 2026-11-11: all projects' captures were 61 MB in 84 files (iam-studio 58 MB, the largest file 4.6 MB), so the default is about 17 times the largest project. The row stays without its files; the web shows "Capture removed" and the Media list "Removed". The age of a decision removes nothing.
- An item is the worker's to prove when its check or `pass_if` holds a code span (a command) or when it has no capture and its `where` does not name a real device or real data: an item about a screen comes with a capture of that state. A `done` result with such items goes back to the worker once, in one message, before the checks and within the check retries: it stages the state in a fixture, proves it in evidence and keeps only what a person checks.

- `wsx task check` lists the open items; `show --json` has the task's items as `to_check`; the ledger counts them.
- `check pass <id>...` or `--all` marks open items `passed`; an unknown or settled id refuses the whole call.
- `check skip <id>...` or `--all` closes open items as `skipped` the same way: not passed and not failed, for an item long overdue or no longer worth a look. It starts no task, leaves the open list (so it does not hold a release) and stays `skipped` in `checks.jsonl`, `show --json` and the web.
- `check fail <id>` closes an open item as `failed`: no task starts, the manager starts the fix from the owner's note (below). `check fail <id> --note <text>` also starts a task titled "Fix: <check>" whose prompt holds the check, `pass_if`, the note and the original `report.md` path; the new record has `fixes: c<n>`, and the item gets the note and `fix_task`.
- `check skip` and `check fail` refuse with `WSX_TASK_ACTOR=manager`: they are the owner's. `check pass` refuses it too, except `check pass <id>... --owner-said <message>`: the manager passes the named items when the owner's message of its running turn says the thing looks good and the item is clearly about it (the same proof as in "Approvals"; an id outside the turn refuses, and `--all` stays refused). The passed row keeps `owner_said: <message id>` in `checks.jsonl` and `show --json`, so the owner's word can be traced; the owner's own pass by a button has none (its note's message is `note_said`, below). The reply `x` that skips an item sets `owner_said` to that reply's id too.
- The web's *Pass* and *Fail* close the item at once (`check pass <id>`, `check fail <id>`), then open the manager's composer as a reply to it. A reply to an item is `wsx task say` with the owner's text `> check <id>` and an empty line before the words (the web's Reply on an item, in the chat bubble or the To check list, writes it). The manager host reads it in `checks::item_reply`:

  | Item | Words | What happens |
  |---|---|---|
  | open | only `x` (also `X`, or `ㅌ`, the same key on a Korean keyboard, with spaces around it) | skipped as `check skip` does; the owner's message is logged as delivered and answered with a quiet post, "Skipped: <check>"; no manager turn |
  | open | other words | go to the manager with the item's check as their quote line (`> <check>`); the item stays open |
  | passed or failed, no note yet | other words (at most `MAX_NOTE_BYTES`) | kept as the item's `note` (the web shows "Passed: <note>", "Failed: <note>"), and go to the manager quoted with the check; for a failed item they start with `To check <id> failed: `, so the manager starts or adds the fix |
  | passed or failed, with a note | other words | go to the manager as above; the note stays |
  | closed | only `x` | the quiet post "Already <state>: <check>"; no turn |

  The logged message keeps the item it answers as `check: "c<n>"` next to `quote` (an `x` that skips and every other reply to an item; none for an id no item has). The chat row has it as `quoted_check`: a tap on the message's quote goes to the item's bubble in the chat, or opens the To check list at it when the bubble is not among the rows (the TUI selects the item in its list), and `wsx task search c<n>` finds the message, since its digest holds the id. The item keeps `owner_said` (the reply `x` that skipped it) and `note_said` (the message whose words are its `note`). An id no item has loses the quote line. An `x` that quotes a message (`> message <id>`) is the manager's, as before. Sending nothing after *Pass* or *Fail* leaves the verdict without a note.
- A log line that does not parse (a last line cut by a crash) is skipped when a log is read.

## Media

The project's media archive lists what was captured or posted, so the owner can see it again (`wsx_core::task::media`, which the web's Media sheet and the TUI's list only render). Newest first, in pages of 24 (`before` is the previous page's `next`, `<unix_ms>:<id>`), filtered by `kind` (`image`: jpg, jpeg, png, webp, gif; `video`: mp4, webm) and `task`. It is not a glob over the project's files (the Files view browses them). Three sources:

| Source | What | Date | Gone when |
|---|---|---|---|
| `capture` | a To check item's capture, with its task, check text, verdict and poster | when the item was collected | the budget removed the file |
| `file` | a picture or video `files/<path>` that a message of the manager, a chat or a peer links (`![alt](files/<path>)`, `[name](files/<path>)`; a path off the checkout is left out) | the message's | the file is no longer in the main checkout |
| `upload` | a file an owner message attached (the web's media store, `[attached files]` lines) | the message's | the store no longer has it (the web decides; the TUI lists no uploads) |

A gone item stays in the list, marked "Removed" (capture, file) or "Expired" (upload), with its date, so the owner sees it existed. A message has no task, so a task filter lists captures only. Reading is bounded: the logs are read from their end, only lines that name a file are parsed, and reading stops once the page and one item more are found.

## By hand

The owner can take a build over and work on it directly, with the worker's context.

1. `wsx task hand <n>` (the web's *Take over*) refuses with `WSX_TASK_ACTOR=manager`, and while the task is `checking`, `landed`, `closed` or already worked by hand. The host stops a running turn, drops queued messages, logs `hand{by: owner, dropped}` and waits on `hand`.
2. No second worktree or branch: the owner works in the task's own working copy on `wsx/t<n>`, with its warm build. `hand` opens a wsxd session `task-<n>-hand` there (one only; a second `hand` names the open one) running `claude --resume <agent_session> --fork-session --system-prompt-snapshot off`, or the login shell when the task has no conversation yet.
   - `--fork-session` copies the conversation under a new id, so the worker's own transcript stays as it was; the next `add` resumes it, and it sees the owner's commits in git.
   - Claude records a conversation's system prompt on its first request and reuses it after `--resume` until the conversation is compacted (https://code.claude.com/docs/en/cli-reference, "System prompt flags in resumed conversations"). `--system-prompt-snapshot off` rebuilds it, so the owner gets Claude's own prompt with their user settings and CLAUDE.md, not the headless worker rules. The worker's boundary, `--settings` and `--permission-mode` are launch flags and do not carry over.
   - Nothing is written into the working copy. `hand --json` gives `session` and `context`: the working copy, branch, HEAD, a short `git status` and the paths of `report.md` and `result.json` (its `memo`); `show --json` gives the same under `hand` while the task waits on `hand`.
3. While it waits on `hand` nothing else writes the copy or its conversation: `add`, `steer` and `land` are refused with a message that names `hand <n> --back`; every path that starts a turn (a check retry, queued messages, a disk-wait resume) starts none; no checks run, a worker's `check-run` is refused, and nothing lands by itself. The manager reads it from the ledger and leaves the task alone. `close` keeps its rules.
4. `wsx task hand <n> --back` (the web's *Hand back*; `wsx task handback <n>` is its hidden old name) refuses while tracked changes are uncommitted, and the session stays. Otherwise the host logs `handback{by: owner, commits}` (the commits after the last revision), writes a `done` result that keeps the worker's Human Verify items and memo, and runs `tasks.checks` on the next revision: the task becomes `ready` or `failed` as after a worker result, and the manager's review and the close after a land apply. A failed check is not sent back to the worker; the owner adds a message or hands again. The CLI then closes `task-<n>-hand`; the forked transcript stays in Claude's store.

## Landing

`wsx task land <n>` asks the host to:

1. refuse unless the task is `ready` (a task worked by hand names `hand <n> --back`);
2. refuse when the worker left uncommitted tracked changes;
3. when the branch contains the default branch tip and HEAD has the ready revision's tree, keep its check results and go to 4; when HEAD moved past it (a child landed, see Parent tasks), run the checks as a new revision and come back to 3; otherwise rebase it there in the working copy:
   - a conflict aborts the rebase, logs `conflict{onto, paths}`, and starts a worker turn that rebases and resolves (the task is `working`); the normal checks then make it `ready`, and it lands again by itself under auto land, without a second review;
   - a clean rebase whose tree is the tree of the current revision (the default branch's changes were already in the branch), with the project's checks still the ones that passed on it, keeps that revision's check results and fast-forwards at once;
   - any other clean rebase reruns the checks as a new revision. When they pass, the land goes back to the start of 3: a default branch that moved while they ran (another task landed) is rebased onto again and checked again, without a second `land`. A failure logs `land_stopped`;
4. fast-forward the default branch: `git merge --ff-only` in the checkout that has it checked out, refused only when that checkout has changed files (tracked or new) that the land changes too, naming those files and the checkout; its other uncommitted files stay as they are (`git merge --ff-only` keeps them). wsx never stashes or commits the owner's files; `git update-ref` with the old tip as guard when no checkout has it;
   - when git refuses the merge with `index.lock: File exists`, the host looks at that checkout's own `index.lock` (a linked worktree's git dir for its own). Stale means older than 5 minutes by mtime and no process has it open (`lsof -t`; a missing or failing `lsof` is not stale): the host removes that file, logs `lock_cleared{path, age_s}` and runs the merge once more (a batch land's own git steps do the same and print a `lock_cleared:` line in the follow-up log). Removing the file is itself a file event, so a watcher's `git status` may take a new lock at that moment (seen on 2026-11-05 in pizzahouse, where `lsof -t index.lock` found no file and a moment later pid 85218: some process there retakes the lock briefly, likely an editor or a git GUI): a refused run waits for a lock that is gone or young, looking every 0.2 s for up to 3 s, before it refuses; a merge that fails after a removal says which lock wsx had removed. An old lock that a process holds, or whose holder cannot be checked, refuses at once. Otherwise the land refuses and the message names the lock, its age and the holder's pid when known, for the owner to settle. wsx removes no other lock file and no lock younger than 5 minutes;
5. add the To check items, log `landed{commit}` and set `landed`. An `add` or `steer` that waited for the worker while the checks ran is not delivered: the host drops it, and the manager gets one event `#<n> landed at <commit> while <k> add(s) to it waited for the worker; they were not delivered because the task landed:` with each first line. A landed or closed task refuses `add` and `steer` and starts no turn, so the `close` that follows leaves it `landed`. After a rebase the task goes from `checking` straight to `landed`, back to `checking` or `working` when the default branch moved meanwhile, or to `ready` with `land_stopped`.

**Auto land** (`tasks.land.auto`, default `true`): the project lands without the owner's hands. A ready task the owner created, with at least one check declared and not held (see Hold and trial), no longer lands by itself on passing checks: it waits for the manager's review like a manager task, and the manager lands it without approval. Only a landing's own revision lands at once: after a conflict's resolving turn whose checks pass, the host lands from `checking` without a stop at `ready`. A landing that stops (a dirty main checkout, uncommitted work) logs `land_stopped` and leaves the task `ready`. With no checks nothing proves the work, so an owner task waits `ready` for a land by hand; so does every owner task with `auto: false`.

**Manager review.** A task the manager created (`created_by: manager`) never lands by itself. It waits `ready`, with or without checks, and so does an owner task under auto land (`TaskRecord::manager_reviews`); its event asks the manager to review: the manager reads `git -C <working copy> diff <base>..HEAD` against the owner's words and for lean code (and `tasks.workflow.review`), then runs `wsx task land <n>` or `wsx task add <n> "<what is missing>"`. The manager never sends a task back to rebase: the land rebases and checks again. The web shows such a task under Running ("Ready, waiting for the manager's review", see Status), not as a need of the owner.

**Land notice.** After a land on the default branch the host sends each open task that shares files with it (the ledger's `overlaps`, also through declared `--files`) a message: the landed commit, the shared files, and to run `git rebase <commit>` at its next step boundary without a `check-run`. It is logged as an `add` message and joins a turn that starts anyway (a step, an add, a check answer, a check retry, a conflict): it never starts one. A notice that finds the worker's turn ending (the result, then the checks) is dropped when the checks end without a turn of the worker's, since the land rebases it. A task without a running turn or a wait (ready, checking, failed) gets nothing, as its own land rebases it.

**After a land** the host starts two detached `wsx task` commands, each in a session of its own with its output in `tasks/<project-id>/follow-up.log` (emptied past 4 MiB): `deploy --if-new` when `tasks.deploy.auto` is on (see Deploy and release), then `close <n>`, which removes the working copy, its build and the branch. The task stays `landed` (its log ends with `closed`), and the task folder and `refs/wsx/task/<n>/r<k>` stay.

## Batch land

`wsx task land <a> <b>...` lands several ready tasks, in that order, with one run of the checks. It refuses `--tried`, a chat, a task named twice, one that is not ready, has a parent or is held, and a manager under `tasks.land.approve`; then the first task's host starts `wsx task land-batch` (hidden) as its own process, outside the caller's boundary, its lines in the follow-up log (`crates/wsx/src/task/batch.rs`):

1. A detached copy `<repo>-batch-<pid>` beside the main checkout (cloned like a task copy, warm build) gets each task's ready revision on the default branch tip by `git cherry-pick`, in order, and keeps the tree after each. A task that does not apply, or has nothing new, leaves the batch and lands alone after it.
2. The project's checks run once on the stacked tree, in the check slot as a land's (first in the queue), with `tasks.env` and the timeout; each prints its exit, `ms` and `queued_ms`, its output in `batch-check-<n>.log` in the project's task folder.
3. They pass: each task gets `land` with its tree (`HostRequest::Land { batch_tree }`). Its host rebases as in Landing; when the rebase gives that tree, the tasks before it are on the default branch and it fast-forwards without checks of its own. Any other tree, such as after a land between them, takes the normal path and its own checks.
4. They fail: the batch splits in halves, the first half lands first, and each half is checked the same way. A single task lands alone through `land` and its own checks, so the failing one ends with `land_stopped`.
5. The copy is cleaned and removed; the last line gives the whole time and the number of batch check runs. A copy whose process is gone is removed by the next batch.

## Hold and trial

Some work the owner wants to try before it lands: a larger piece handed over, a long branch, a change that is costly to undo. The manager tells this apart from pipeline work by judgment and holds such a task (`new --hold`, `hold <n> "<why>"`); the owner holds or releases one in the web.

- **Hold.** `hold` (one line, at most 240 characters) is on the record and in the ledger. A held task never lands by itself, also when the owner created it, and the manager lands it only on the owner's word. A held task the manager created is the owner's need, not the manager's review. `hold <n> --off` releases it; a ready task then waits for a land by hand.
- **Trial.** `trial <n>` puts a ready revision on the live site (`tasks.deploy.command`) before it lands. It refuses without a deploy command, with `tasks.deploy.public: true`, and for a manager when `tasks.deploy.approve` is on. The project has one slot, `tasks/<project-id>/trial.json` `{task, revision, commit, by, unix_ms}`, taken under `trial.lock`; a second task's trial is refused until the first ends.
  1. The host rebases the branch onto the default branch tip when it lacks it, and the checks run on the new revision (a conflict starts the worker turn that resolves it and ends the trial). The trial goes live with the revision the owner would land: the host names its commit in the slot, logs `trial{revision, commit}` and starts `wsx task deploy --trial <n>`, which records `trial: <n>` in `deploys.jsonl`.
  2. While the slot is taken, the default branch does not deploy: the `deploy --if-new` after a land answers that it waits, and `deploy` and `release` by hand refuse. Lands go on. Hosts do not follow a replaced wsx binary (see Host), because it may be the trial's build.
  3. It ends when the owner passes it (`land <n> --tried`, owner only, the web's *Pass and land*): the task lands without adding its Human Verify items to To check. It also ends on `trial <n> --end`, on an `add` (the web's *Fail: tell the manager* mentions the task to the manager, which sends it), on `hand`, on `close`, on failed checks after the rebase and when its deploy fails. The task logs `trial_ended{reason}` and `deploy --if-new` deploys the default branch tip again.
- `deployed` and the ledger's `deploys` carry `trial`: `null`, or the slot with `stage` `preparing` (rebase and checks), `deploying` or `live` (its deploy succeeded).
- A live site cannot always roll back: a stored format, a migration or a newer daemon may stay. Such a change goes to a preview instead (see Preview). For wsx itself, `scripts/deploy-web-live.sh` replaces the binaries and restarts the web server only, so a trial runs its web and CLI against the running daemon. A `wsx daemon restart` during a trial would start its daemon, and the default branch's build cannot take that daemon back: wsxd refuses a handoff to an older build ("handoff target is not newer", checked from the dev build to 0.31.0). The terminals stay, and the newer daemon runs until a cold restart.

## After another task

The manager parks a task until another lands with `wsx task after <n> <m> "<what to do then>" --because <kind>` (`--off` ends it). The kind is required and says why the task waits; a missing or unknown one is refused with the list:

| `--because` | Status sentence |
|---|---|
| `needs` | It builds on #m's change. |
| `files` | It changes the same files as #m, so it lands after it. |
| `check` | Its checks fail on main until #m lands. |

The kind is `after.because` in `task.json` and in the `after` log event; a wait set before it existed has none and shows no reason. `show --json`, the ledger and the web overview carry it in `after` and in `status`. Hold means only that the owner tries the task first; a wait for a landing is not that, and reads differently ("Waiting for #m to land", status kind `after`).

- `wsx task new --after <m> --because <kind>` makes the task with the wait set: its host starts no turn (it waits on `owner`, shown as the wait), so it does not build on a base without #m. When #m lands, or the manager runs `after <n> --off`, or #m is closed (the manager gets `wait over ... #n started without it`), the host moves the copy onto the default branch tip and starts the first turn. `wsx task after` on a task that already runs only parks it: its turn goes on and the wait holds its review and land.
- `after` is a field of `task.json`, not a state: it works on a ready task and on a working one (the turn finishes first). It is refused for a task that is not open, for `m` equal to `n`, and for an `m` that is not an open task of the project. A role acts only on the tasks it created.
- While it is set a ready task is not "ready, not reviewed": the manager gets no review event or stall for it, and it does not land by itself. The owner's hold is separate and shows first.
- The manager host looks every 10 s (with the stalls). When `m` has landed, the task host clears the wait, logs `after_ended{landed: true}` and adds the text as a manager add (the turn starts as for any add; a working task queues it). When `m` was closed without landing, or has no record, it logs `after_ended{landed: false}` and the manager gets one event `#<n> wait over: #<m> was closed without landing; nothing was added to #<n>`. A task that lands, closes, or gets `--off` ends its wait too. A task that becomes ready while it waits has `; waits for #<m> to land` in its ready event, so the manager does not land it early. A host that does not answer keeps the wait for the next look.
- A wait still open after 24 h is a stall, reported once (see Manager, Stalls). Two tasks that wait for each other never end by themselves, so they reach this stall.

## Parent tasks

Long work in several steps lands on main once. Any open task becomes a parent when a child names it: `wsx task new --into <p>` (not with `--from`). A parent is one level: a child takes no children.

- **Create.** `--into` holds p ("parent of #n") when it is not held, so p lands only on the owner's word. The child starts from p's tip, its `default_branch` is `wsx/t<p>` and its `task.json` has `parent: p`. Its boundary denies the refs of p's branch and of the default branch.
- **Child land.** It lands only on a parent at rest, `ready` or `failed`; otherwise it refuses with "parent #p is busy (<state>)", stays `ready`, and p's next event names it ("children ready to land: #c") so the manager lands it again. A parent that waits on the owner, a plan, disk or the usage limit is busy too: a new revision would drop its wait. Otherwise the land rebases onto p's tip and fast-forwards in p's working copy (Landing 3 and 4), then asks p's host to check the commits: p logs `child_landed{child, commits}` and runs its checks on the next revision with a `done` result that keeps its Human Verify items and memo, as after a handback. Its close follows; no `deploy --if-new`, since main did not move.
- **Unchecked HEAD.** Any land whose branch already has the default branch tip fast-forwards only when HEAD has the ready revision's tree; otherwise the checks run first, so a parent whose host missed a child's land never lands it unchecked.
- **To check.** A child's land copies its captures into its task folder and keeps its items in its `result.json`, not in the list. p's land into main adds them under the child's number, after p's own.
- **Close or land of p** refuse while it has open children, naming them, also with `--discard`. Conflicts with main come only at p's land, as for any task.
- `parent` is in `list --json`, the ledger's open rows and the web's task summary; a parent's ledger row has `children`, the count of its open children. `overlaps` leaves out a task's own parent and children.

## Project overview

`tasks/<project-id>/overview.md` (`page.md` before; a project that has only `page.md` gets it renamed once, when the overview is read or the manager starts) is the owner's one-screen picture of the project: the goal, the open tasks as a mermaid graph, live plans in short and the open questions. Finished work and old decisions go out; decisions are in `decisions.md`. The cap is 60 lines and 4,000 characters (`MAX_OVERVIEW_LINES`, `MAX_OVERVIEW_CHARS` in `store.rs`). The manager host creates the file with those sections when it is missing (0600; an existing one stays). The manager edits it with its own tools: its instructions say to update a section in place, never create another overview, and to call it "the project overview" in a reply. After each manager turn the host reads the file; over the cap, it sends the manager one follow-up turn at once (a message from wsx that names the sizes and the cap). It asks once until the owner writes again or a turn leaves the file within the cap, so a manager that fails does not loop. The web shows only the first 60 lines and 4,000 characters, with a note. Workers do not write it: their boundary denies the state folder outside their own task folder. The web client shows it ([web-client-tasks.md](web-client-tasks.md) "Project overview").

## Ledger

`wsx task ledger -p <project>` prints JSON of at most 16 KiB, the manager's source of truth:

- `auto_land`, `preview` (`tasks.preview` is set: a task can be tried) and `to_check` (the count of open items);
- `open`: each open task with number, title (80 chars), state, revision, `parent` and `children` (see Parent tasks), overlaps, the Human Verify item count of its latest result, the last result summary (240 chars), `checks` (each check of the latest result as `{command, outcome: passed|failed|timed out}`, the command at most 120 chars), `waiting` (`{on, reason}`), `land_blocked_by` of a ready task (the main checkout's changed files its land would overwrite, so its Land refuses until they are committed or stashed; `[]` when none), `usage` (see Usage), in attention order (waiting, failed, ready, working and checking);
- `recent`: the last 10 landed or closed tasks, each with its `usage` and its worker's `memo` (600 chars) when it left one (the manager already got it in the task's event, see Memo). An older or a closed task's story is not here: `history` names the read, `wsx task search --task <n>` (see Search);
- `usage`: the project's spend today and in the last 7 days, workers and manager apart (see Usage);
- `deploys`: the `deployed` status, with `configured` per kind (whether its command is set);
- `routines`: the project's routines (see Routines), at most 20, each `{name, enabled, trigger, next_run_unix_ms, running, last}` with `last` the newest run's `{status, exit, unix_ms, duration_ms}` or `null` (no message id: the web's routine rows carry it, the ledger does not, so it costs no tokens); `{error}` when the scheduler does not answer and the project has routines, `[]` when it has none;
- `main`: the main checkout's path, branch and number of changed files (tracked or new);
- `stray_worktrees`: the project's worktrees from `git worktree list` and wsxd's state that are neither the main checkout nor an open task's working copy, each `{path, branch, dirty, unmerged, missing, sessions}` (`dirty`: uncommitted files; `unmerged`: commits neither merged into the default branch nor pushed, both from the sweep's rule `stale::loss`, null when git did not answer in time; `missing`: the folder is gone; `sessions`: wsxd sessions there, 0 when wsxd does not answer), sorted by path, at most 20, the rest counted in `stray_worktrees_omitted`. They are cleanup candidates the manager names to the owner; the ledger deletes nothing (the host's sweep removes the clean, merged or pushed, idle ones: "Stale worktrees").

- `notes`: only when git did not answer. Every git call of the ledger waits at most 10 s (`task::copy::READ_TIMEOUT`); a folder whose git timed out is not asked again in that build, its facts are left out (`main.branch` or `changed_files` null, no `land_blocked_by` entries, a stray worktree's flags false) and a line names it ("git did not answer in 10 s in <path>; its facts are left out"). The TUI shows each note under the spend lines in the warning colour.

When it would pass 16 KiB, the memos are left out first, then the least urgent open tasks, counted in `open_omitted`.

A quote at the head of a message (`> <line>`, the owner's or a manager's) is one muted line, `▎ <line>`, and is link 0 of that message: `[` reaches it. Enter on a quote with an id (`quoted_id`, see "A quote" under "Manager") scrolls to that message, marks its heading (reversed) and centers it; when the rows do not hold it, the chat reads the part of the log around it (`Window::Around`, any age the log keeps), the footer says `Esc: newest`, and Esc (or `G`, or sending a message) reads the newest part again. A quote with no id scrolls to the newest message above with that first line, or says that it is no longer in the conversation shown. A post of wsx, not an agent turn (a reply marked `post`: a routine's run, the digest, `wsx task post`, the session news), has its bar `│` in the secondary colour, as the web gives it a secondary border; a reply that asks keeps the accent bar.
- `i` or `Enter` writes on the last line; `Enter` sends it as `wsx task say` does (the manager starts when it is not running), `Esc` leaves the line with its draft. A message that was not sent comes back to the line, and a failure stays above the chat until the next action. `Esc` goes back to the list.
- `/` finds text in the chat, case-insensitive, on the last line with its count (`2/5`, from the oldest match). The chat is read again for each change of the words, from the oldest entry that shows them (`Window::Find`, "Log window"), so a find reaches every message; `Esc` clears the find and the chat returns to the newest 200 entries, read from the log's end ("Log window"). Each match is reversed, the current one also in yellow and scrolled to the middle. A find starts at the newest match; `Enter` keeps it and gives the keys back to the chat, where `n` goes to the older match and `N` to the newer one (before an approval's `n`), and `Esc` clears it. The next `Esc` leaves the chat.
- The chat reads the log, the items and the approvals again when a store file changed, and asks the manager host for its status every second, off the UI thread like the list; messages and decisions run off it too, one at a time.
- In the Workspace tree a project's name is bold text, in the accent while its manager has an open question (`wsx_core::task::chat::asking`, the rule of the web's Home row; `crates/wsx/src/ui/workspace_tree.rs`). After the name (and the `[N]` of a folded project) come the need marks, each with its count and none for zero: `!N` for what waits for the owner (waiting, failed and ready tasks, and pending approvals), `✓N` for open To check items, `…N` for tasks at work. The counts are `wsx_core::task::needs::Needs`, the rule of the web's Home row (`needs`, `to_check`, `working` of the overview; `needs::stage` decides which tasks wait for the owner). The TUI reads the questions (each project's manager log back to the questions' 7 days) and the counts every 2 s off the UI thread; the counts are read again only when the project's `store::stamp` (size and time of the store's files, no parse) or `land.auto` changed. A project without a store or a manager log has no marks and never asks. A narrow tree (the one-cell rail) shows the accent only. `n`/`N` in the Workspace stop at the sessions that need attention and at the Project rows that ask or show `!` or `✓` (not `…`), in tree order; a blocked session still comes first under `blocked_first`. The tree keeps the owner's own order: it is not sorted by need. The Terminal prefix `n`/`N` visits sessions only.

## Log window

Every reader of a manager log reads it from its end (`ManagerDir::read_back` in `wsx-core` `task/store.rs`): the last 256 KiB, then four times as much until the reader has what it needs, or the newest two files whole (at most 16 MiB). A task's `log.jsonl` uses the same reader (`TaskDir::last_entry`). What a chat needs is `wsx_core::task::chat::read_chat` with its `Window`, the one rule for the web's chat route, the TUI's chat and `wsx task chat`:

| Window | Shows | Reads back to |
|---|---|---|
| `Tail` | the newest 200 entries | 200 shown entries |
| `After(id)` | the newest 200 after message `id` | an entry at or before `id` (ids grow) |
| `Find(words)` | from the oldest entry whose row shows the words (name, tag, quote, text; case-insensitive) to the end; `Tail` when none does | the start |
| `Around(id)` | 200 entries from the 40 before message `id` (a tap on a quote; web `?around=<id>`, `wsx task chat --around <id>`); `Tail` when `id` is not in the log | the message and 40 entries before it, over every rolled file (`ManagerDir::read_around`; the other windows read the newest two) |

Each also reads back 7 days, for the open questions ("Questions"), and to a reply or a step, for what the manager does now. A quote by id (`resolve_quote`) reads back to its id, over every rolled file. Finding an old message across projects is `wsx task search` ("Search"), not `Find`. Each step reads only the bytes before the last one. On the wsx manager log (2.8 MB, 9,264 entries, 2026-11-06; release build, the fastest of 41 runs in process): the whole read 5.4 ms, `Tail` and `After` 0.5 ms, `Find` 5.7 to 8.8 ms, `asking` 2.1 ms (it parses only owner messages, questions and `answered`; 7 days are 1.08 MB of that log).

## Search

`wsx task search <words> [-p <project> | --all] [--task n] [--limit n] [--reindex] [--json]` finds an earlier message, decision or step of a task's story and ranks it, so a manager after a new conversation (and the owner) finds the old decision and quotes it by id. `-p` (or the project of the current folder) searches one project, `--all` every registered one. The one owner is `wsx_core::memory::index`, the built-in index of the `memory` contract ([memory.md](memory.md)); `wsx_core::task::search` is another name for it. `wsx task search` ranks the transcripts below and nothing else, with raw BM25 scores; `wsx memory search` ranks them together with the project's memory records, scores them in 0..1 and can add an external backend ("Search backend" in memory.md). The same digest serves both. The web and the TUI have no search box.

| Searched | Record | Where it comes from |
|---|---|---|
| Messages of the owner, other managers and chats | `message` | the manager log and each chat's log (`ManagerDir::read_back_where`) |
| Replies that say something | `reply` | the same logs; wsx's events, recaps, quiet replies and `-` are no conversation and are left out |
| A task's title and prompt | `task` | `task.json`, the first prompt in the task's `log.jsonl` |
| A task's latest result: summary, memo, decisions, left open | `result` | `result.json` |
| A task's story, open or closed: its start (branch), each add and steer, every turn's result summary (not only the latest), each revision, the checks (the failed commands), stops, the landing, the close (discarded or kept) | `history` | the task's `log.jsonl`, one line each (`task::history::line`, also the wording of the history read) |
| Decisions and memo lines | `decision`, `memo` | `notes/decisions.md`, `notes/decisions-archive.md`, `notes/context.md`, `notes/context-archive.md`, read as they are now |

Tool steps and agent commands are not indexed. A record keeps at most 4 KiB of text (a `history` line 1 KiB); the log keeps the rest. A turn's summary is in the digest twice when it is the latest: as the `result` and as a `history` line. A quote line at the head of a message is not indexed (it is another message's text).

Each hit has `project`, `kind`, `id` (the message id in that chat), `task`, `unix_ms`, `by` (owner, manager, `manager:<project>`, `chat:<name>`, task, notes), `line` (the first line, at most 160 characters), `score` and `reference`: `<project>:<id>`, `<project>:<chat>:<id>`, `<project>#<task>` or `<project>:notes/<file>`. A message or reply of the manager chat of the project the search ran in also has `quote`, the line `> message <id>` that a reply opens with to quote it ("A quote" under "Manager"); another project's message cannot be quoted by id (its id belongs to its own log), so quote its words or name its `reference`. A hit that names a task also has `outcome`, where that task is now, read when the search runs and never kept in the digest: `landed 11-07 cd67238e1f90`, `closed: discarded`, `closed`, or an open task's state with its revision (`ready r2`); so the manager needs no `show` per hit. Text output is one line per hit, `[<outcome>]` after the reference. A manager reads other projects' hits with `--all` (`-p` of another project is refused to a manager, as for the chat).

Ranking is BM25 (k1 1.2, b 0.75) over lower-case words of letters and digits; the words of all searched projects count together, a hit holds at least one of the words, more of them and rarer ones score higher, equal scores go to the newer. A run of Han, Kana or Hangul has no spaces, so each pair of neighbouring characters is a word (a lone character is itself), in the records and in the query alike.

Each project keeps a digest, `tasks/<project-id>/search.jsonl`: one line per record, written by the search that finds it new. Freshness is on read, under `search.lock` of the project: a search reads the manager and each role log back from its end only until the newest message id it already holds (ids grow, the `Mark` record keeps the newest id scanned, also when it was no conversation), a task's title once, its result again when `result.json` is newer, and each task's `log.jsonl` from the end of the newest `history` line it holds (`end`, the byte offset after that line): a log that is not longer costs one stat, a closed task never reads again, and progress lines are skipped by their first bytes before any parse; a line still being written (no `\n` yet) waits for the next search. An older digest catches up with the logs on its next search, with no `--reindex`. Nothing is written on the append path of a host. The digest is append-only, grows with the words said, and survives a manager's new conversation (it never depends on the session) and, for the part it already holds, a log roll; the logs are the source, so `--reindex` deletes the digest and builds it again from the logs and tasks that exist (it reads the newest rolled file and the current one; older rolled files stay for `Around`). A digest line that does not parse is skipped, and a cut last line gets a line of its own. A project that is not registered any more is not searched by `--all`; its digest stays with its tasks folder and goes when that goes.

`wsx task search --task <n> [-p <project>] [--limit n] [--json]`, with no words, reads one task's story from its log (not the digest), open or closed, so the manager needs no `log.jsonl`: dated lines, newest last, `<date> <hh:mm> <label> <first line>` (UTC; label `start`, `prompt`, `add`, `steer`, `result`, `revision`, `checks`, `stopped`, `landed`, `closed`; a run of agent progress is one `steps` line). The last `--limit` lines (40) are shown and `N earlier lines left out` says what is not. JSON: `{task, title, state, outcome, skipped, entries: [{unix_ms, label, text}]}`. With words, `--task` keeps only that task's hits. The rows come from `task::history::timeline`, the same builder as the web sheet's History (`timeline` in the task detail); `history::line` is the one wording of an event for both. The ledger keeps no history: it has one `history` field naming this read, and the manager's instructions name it too.

Measured on a fixture, not on a real store (2026-11-07, release build, 300 landed tasks, 22.7 MB of task logs of 120 progress lines, 3 results, 3 adds each, nothing else in the project; the fastest of 15 warm runs): the digest grew from 60 KB (300 task records, 20 ms to build) to 534 KB (2,700 records, 40 ms to build), and a search with nothing new from 1.6 to 7 ms. The same on the real store is for the manager to measure.

Measured on this machine's store (2026-11-07, release build, copy of the store: 18 projects, 4,023 records, 3.5 MB of digests from 4.9 MB of manager logs and 29 MB of task logs): a search of all of it takes 29 ms in process when warm (the fastest of 15 runs 26 ms, 39 ms median with the process start), 211 ms for the first build of every digest. Of that, reading and parsing the digests takes most; the scan itself is linear in the digests, so 5 times the text is about 150 ms: past that, add an inverted index file per project (not built; no new dependency needed).

## Manager

```sh
wsx task manager -p <project> --json             # start the manager, or report the running one
wsx task say -p <project> "<text>" --json        # or `-` or --prompt-file; returns {id} at once
wsx task chat -p <project> [--after <id> | --around <id>] --json # messages, replies, rotations; asks
wsx task search -p <project> [--all] <words> --json # ranked earlier messages, decisions, task history ("Search")
wsx task search -p <project> --task <n> --json   # one task's dated history, open or closed ("Search")
wsx task dismiss -p <project> <reply id> --json  # the owner's: an open question asks no more
```

One manager per project runs as hidden `wsx task manager-host <project-id>` in a wsxd session `task-manager` in the main checkout (no working copy); `say` starts it when it is not running. Its agent uses `tasks.manager` (`model`, default `opus`; `eventModel`, default `off`; `rotateTokens`, default 400000 on Claude and 150000 on any other adapter, the adapter that runs now, a fallback's too; a set value wins), project and local settings only (so the MCP tools those settings allow), every tool with no prompt inside the manager boundary (see Permissions), and git reads that take no lock (`GIT_OPTIONAL_LOCKS=0`, so `git status` does not write the index). The owner's skills reach it as a plugin: before each launch the host writes `manager/skills-plugin/` (`.claude-plugin/plugin.json` named `owner`, `skills` a link to `<the profile's claude_config_dir>/skills`, else `$CLAUDE_CONFIG_DIR/skills` or `~/.claude/skills`) and passes `--plugin-dir`; the skills are `owner:<name>`. With no such folder there is no plugin and the instructions leave the skills out. User settings stay unloaded: they could add hooks, folders and allow rules. Its instructions (`manager.workflow.batch`; it handles each `waiting.on`; its one git write is the owner's uncommitted files on main after the owner's yes; it keeps notes and decisions, keeps the project overview, and talks to other projects' managers. A running manager keeps the instructions its conversation started with until it rotates; a wsx with changed instructions starts each manager's next turn as a fresh conversation (below), which opens with its notes and decisions. Its environment is the worker allowlist plus `WSX_TASK_BROKER`, `WSX_TASK_ACTOR=manager` and `GIT_OPTIONAL_LOCKS=0`; the host puts its own `wsx` first on `PATH` and runs the commands with its own environment (see Permissions).

- `manager/log.jsonl` (rolls to `log.<n>.jsonl` past 8 MiB, `log.1.jsonl` the oldest; every roll is kept, uncompressed, since the backward read needs byte offsets; whole-log readers and the usage totals read the newest roll and the current file) has `message{id, from: owner|events, text, short, quote}` (`short`: an events message's events as the chat shows them, one `{text, task}` each, written where each event is made: `#3 done`, `#3 stalled`, `Approved land #5`, `Denied land #5`, `Dropped discard #42: <why>`, a deploy or a routine line's first clause; an entry without it shows each line's first clause), `delivered{ids}`, `reply{id, to, text, usage, quiet, asks, post, quote}` (`post` on a reply wsx posted with no agent turn, `post()` in the manager host: `wsx task post`, the digest, the session news) (`asks` when the reply asks the owner: its last line ends with a question mark and is no table row, and a closing code fence does not count (`asks_owner`); the manager's instructions say to end with a plain question only when a new decision is needed now. `quiet` when the turn held only events, or only replies of other managers or of roles (`manager-reply:<p>`, `role-reply:<name>`; their questions are not), and the reply is one line of at most 200 characters and does not ask; the web shows it as a muted line, and a longer reply, also one stored as quiet before this rule, is a message; a reply of `-` or nothing reads as quiet whatever its turn, so no chat shows it. Web and TUI set a reply that asks off in the accent color (the web: a thin border on the bubble and the project's name on Home; the TUI: a bar at the left of its lines) until it is answered, see "Questions"), `answered{id}` (the owner dismissed that question), `agent` (its commands), `rotated{tokens}`, `ping{usage}` (a keep-warm turn: no reply, not in the chat, and `chat_window` leaves it out, so pings use none of its 200 entries) and `stopped`. `manager/state.json` keeps the conversation, the digest of its instructions, the next id and what was already reported.
- Talk or work: no switch, no command. The instructions have the manager judge from the owner's words in each message whether the owner wants to talk it over (a question, "what do you think", "let's discuss", "one by one") or wants work done ("fix", "do", "go", "agreed, do it"). To talk it over, it stays in chat: reads the code and the copies itself (read-only), answers the points in turn, one per reply when asked one by one, gives its own view and ends with the question that moves it on. It starts no task and sends no `add` or `steer` for those points, keeps the edits the owner agrees to, and when the owner says to do them runs one `wsx task new` (or one `wsx task add`) with all of them. The Claude and the Pi manager get the same text. `scripts/bench-manager.py --cases discussion` runs it against the real CLI.
- Questions: each reply that asks is one question, open until it is answered (`wsx_core::task::chat::open_asks`, the one rule of the web and the TUI). An owner message that quotes it (the web's *Reply*, the TUI's `r`) answers it; an owner message with no quote answers the newest open question before it; one that quotes anything else answers none. The owner's dismiss (`wsx task dismiss <id>`, the web's reservoir, the TUI's `d`) writes `answered{id}`, which wakes no turn; the manager's and a role's agent are refused it (`WSX_TASK_ACTOR`), as `check skip` is. A question older than 7 days asks no more. Several questions wait at once: each keeps its accent, the web's reservoir and the TUI's items list them, and only an answered one clears. The rule reads only the log, so a Claude and a Pi manager are alike. Each turn of a manager or role ends its input (before the ledger summary) with `Open questions`: one line per open question, `- <reply id>: <first line, 120 characters>` (`chat::asking`, the same rule), and no section when none is open; the instructions say to ask it once and never restate it, since Needs you holds it.
- One turn at a time. Waiting owner messages go together in one turn, each headed with its id, before waiting events.
- A quote: a reply that opens with the line `> message <id>` quotes that message instead of saying its words again (the instructions ask for it when a reply would restate a plan, a promise or a wait). A reply that opens with no quote of its own and says something quotes the one message it relates to when it will not sit directly under it. `chat::quoted_message` is the one place that chooses the message and decides, two cases: (1) a turn with owner messages: the newest owner message among the messages of its turn (`to`) is the answered one, quoted when (a) the turn held more than one owner message, or (b) any chat item (an owner message, a reply, an event row, a role or task notice; `in_chat`) was logged after it and before the reply; (2) a turn of only events: the reply follows up the manager's own earlier reply, the newest one that names (`#<n>`) a task the events report (a promise such as "I'll land #360 once CI passes"), quoted only when that reply is among the last 50 chat entries and other chat items lie between it and the turn's own messages. A reply directly under what it answers, and one that is neither case, has no quote; a quiet line of an events turn (the manager's own work) is never quoted. The quote has the same format and `quote` id as an explicit one (a quote of that message's own quote is left out, as always). The host adds it in `Manager::quoted`, for the manager, a role and the stand-in during a hold alike. A reply that says nothing stays as it is; a quote the manager wrote, also one that quotes an earlier reply, wins, and a bad id still drops the line without the owner's quote taking its place. The quote closes no question and answers none: `open_asks` reads an owner message's quote, never a reply's, and a question's line is its words after the quote. `scripts/usage-report.py` and `scripts/retrospect.py` count only a quote whose id is not one of the reply's `to`, so the quote counts stay the manager's own. The id is the one in an `Owner (message <id>)` heading, in a handover line (`Owner (message 2085): …`, `You (reply 2090): …`), in `wsx task chat --json`, or in the turn's last line `Your last reply: <id>.` (state `last_reply`, left out of a turn of only events). When the host logs the reply (`resolve_quote`) it replaces that line with the owner's quote format, `> <first line of that message, its own quote left out, at most 120 characters>` and an empty line, so the stored text, the web and the TUI read one format (the web chat's *Reply*, [web-client-chat.md](web-client-chat.md)), and the entry keeps the quoted message's id as `quote` (`quoted_id` in a chat row), so a tap opens the chat at that message at any age the log keeps, after a rotation too. The owner's *Reply* (web) and `r` (TUI) send the same `> message <id>` line, which the host resolves when it logs the message; a quote an older host or a hand wrote has no id and keeps the text match. An owner message whose quote has an id answers the question with that id. Only a message the chat shows as a bubble can be quoted: the owner's, another manager's or a role's, or a reply that says something. A bad, unknown or unquotable id drops the line, the reply stands and the host's progress line says so. A reply that quotes is a message, never a quiet line. The Home row and the role list preview skip the quote line. The instructions' text grew by 14 bytes for this (8,643 to 8,657, measured on the template of `instructions`), and by 94 characters when they were tightened to ask for a quote whenever a reply refers to an earlier message or reply (9,973 to 10,067, `instructions()` of `scripts/bench-manager.py`). `scripts/usage-report.py` counts the quotes per manager and role (table "Quotes": replies that say something, those that open with a quote), and `scripts/retrospect.py` posts "Quotes: m of n replies".
- Only events that need the manager's judgment start a turn (`state_wakes`, and `wakes` of the line's short). A landing, a close, a wait on `limit` or `disk`, a held parent that is ready again after a child landed on it and its checks passed (`ready` from its own worker or with failed checks still wakes), an idle worker whose task waits for another to land, a task stopped by request (`wsx task stop`, by the owner or the manager: its wait on `owner` says `stopped by request`), and a successful deploy under `tasks.deploy.auto` are logged and shown at once, and reach the agent with its next turn, headed `Events`. When that turn holds owner messages, theirs come first and the line "Answer message <id> first." goes before the events. A restarted host reads `wakes` from the logged short; a message logged before it counts as waking.
- An agent's error is no reply: the log has `stopped{reason}` and a `limit` entry with the retry time, and the turn tries again with the usage limit's backoff. After 3 in a row the next try starts a fresh conversation, since the conversation may be the cause. A failed sign-in (`agent::auth_failed`: Claude's `Failed to authenticate`, `authentication_failed`, `Please run /login`) is the exception: with a usable fallback the manager moves to it at once ("Agents"); with none the hold is marked `auth`, the turn retries every `store::sign_in_retry_ms` (5 minutes, "Agents") in a new agent process that resumes the same conversation (a running process keeps its old credentials), it never starts a fresh conversation, the log gets `stopped` (saying to sign in again) once, not on each try, and no `limit` entry (a `limit` without a time reads as the end of a hold, so neither the stop nor a retry would show as held; the next reply ends it), and an owner message during the hold tries at once. While a turn of the hold runs, a message that came after it is the chat's waiting line (`wsx task chat --json` lists `waiting`; the text marks it `(waiting)`).
- Events: the host checks the task records every second. A change of (state, revision) into `ready`, `failed`, `landed`, `closed` or `waiting` (not on `hand`) becomes a line written by wsx, `#<n> <state> r<k>: <title, 80 chars>; [waits on <on>: <status sentence>; ]checks <passed> of <total> passed; [check-run <names> passed (recorded by the host); ]worker says: <summary, 160 chars>` (without the checks part when there are none); a `ready` task whose worker did not load the simplify skill after the one send-back adds "; simplify did not run" (Workflow); `landed` and `closed` add "; memo: <memo, one line, 600 chars>" when the worker left one, and `landed` adds "; <n> to check" when the landing added items. Closing a landed task keeps `landed`, so it sends no second event. A new failed deploy or release becomes `<kind> of <commit, 12> failed (exit <n>); its output ends:` and its last 10 lines, indented; a new successful deploy or release becomes `<kind> of <commit, 12> succeeded after <s> s`, so a manager that waits for one goes on (`state.json` `deploys_seen_ms` keeps the newest record seen). A routine run that ended becomes `routine <name> succeeded after <s> s` (no line when it wrote nothing to stdout, see Routines), or `routine <name> failed|could not start|was cancelled|was interrupted (exit <n>); its output ends:` and the last 10 lines of its final output, indented (`routines_seen` keeps the newest end seen, in seconds; a run is reported once its second has passed). Lines are logged as one `events` message when 3 s have passed since the last one and no turn runs, so events during a turn or close together arrive merged.
- Stalls: a task that stays in one state produces no change, so every 10 s the host also looks at each open task for a stall (`crates/wsx-core/src/task/stall.rs`) and reports a new one as an event line `#<n> stalled r<k>: <title>; <state> for <how long>; <evidence>`, for example `#7 stalled r2: Fix the parser; waiting on disk for 3 h 10 min; free 53.0 GB, tasks.minFreeGb is 3`. How long counts from the task's last state change. A stall seen only in the present must still be there after 60 s (two disk polls of the task host, longer than a host's exec handoff or a land's rebase holds its socket) (`WSX_TEST_STALL_GRACE_SECS` replaces the 60 s; it is for `scripts/test-task.py` only, in wsxd's environment):

  | Stall | When |
  |---|---|
  | its cause is gone | waits on `disk` with at least `tasks.minFreeGb` free, on `limit` after `until_ms`, or on `check_run` after `until_ms` (its run's time limit, when the host has stopped it and answered), and is not queued |
  | its queue does not move | waits on `disk`, `limit` or `check_slot` "queued for ... behind `<project> t<n>`", and that task (of any project) is not working or checking, its host does not answer, or it is silent as below. A dead holder frees its `flock` at once, so this is what stops a queue. `scripts/check-slot.py` writes its own label, so a stale task label does not count |
  | silent | working or checking without a wait, with no write to `log.jsonl` or a `check-*.log` for `tasks.checkTimeoutSeconds` plus 10 minutes: the longest a check or a background job's wait runs, plus one Bash call (Claude's maximum). The evidence names the last log entry |
  | its host is down | working, checking, or waiting on `disk` or `limit`, and its host does not answer `status` |
  | waits for another task | `after` still open 24 h after `wsx task after` (it ends by itself when that task lands or closes); reported once |
  | waits on the manager | ready and reviewed by the manager (`land_reason` "the manager reviews it": it created the task, or `tasks.land.auto` with checks), or waiting on `plan`, with no state change (`add`, steer, land, close), `hold` or `check-run` for `tasks.manager.reviewMinutes` (default 30, `0` is off, a fraction allowed) since it entered the state. The line reads `ready for 35 min; the manager has not reviewed it`. Its marker is the state's start, so it is reported once per entry. Owner waits (`owner`, `hand`, approvals), a held task and a task the manager parked with `wsx task after` (that is its review; the 24 h row reports a long wait) are none |

  Each stall has a marker (its kind with the wait's start, the holder, or the time of the last progress), and `state.json` `stalls` keeps the one reported per open task, so a stall is reported once, also across a restart; progress or a new wait makes a new stall that is reported again. A first start reports the stalls it finds. Nothing is reported while things are fine. The manager's instructions: act on it with `wsx task` (a silent worker: `stop`, then `add`), start a task that fixes wsx when the evidence shows its bug, else tell the owner in one line. The chats show it as other events (`#7 stalled`).
- Restart: `state.json` records the reported state of each task only when its message is logged, and `delivered` marks what reached the agent. A restarted host queues logged messages that were never delivered, and those delivered to a turn that got no reply (the host or the agent died after `delivered`: every one after the last agent `reply` that no `reply.to` names, except the ids a limit hold keeps, which its turn delivers), so each reaches the next turn once and one with a reply is not delivered again; it reports changes it has not reported, so no event is lost. When the agent fails to start a turn, its messages go back to the front of the queue (`stopped` is logged once per run of failures) and the next try is 30 s later. Its first start takes the existing tasks as they are, without events.
- Messages from another project's manager are headed `Manager <project>` (or `Manager <project> replies`) and go after owner messages and before events.
- Every turn's message ends with a ledger summary the host writes: `Ledger summary from wsx (...)`, the open tasks by state, the To check and waiting approval counts, the tasks whose (state, revision) changed since the last turn (every open task in a fresh conversation), at most 12 lines of `#<n> <state> r<k>: <title, 60 chars>`, and the last deploy when one is configured. `state.json` keeps what the last summary showed (`turn_seen`). The manager runs `wsx task ledger` only when it needs more, so a turn does not start with a 16 KiB tool result that every later call of the turn reads again.
- Model per turn: a turn of only events (or only replies, as for `quiet` above) runs on `eventModel` while no ready task the manager created waits for its review; any other turn runs on `model`. The host switches the running process with the stream-json control request `set_model` (the SDK's `setModel`), so the conversation stays. Claude's prompt cache is per model, so a switch writes the conversation into the other model's cache: on scripts/bench-manager.py a Sonnet event turn cost a median 0.063 USD against 0.023 USD on Opus, hence `off`.
- After a reply whose context passes `rotateTokens` (unset: 400000 on Claude, 150000 on Pi; `manager_rotate_limit` in `crates/wsx-core/src/model/workspace.rs` is the one rule), the next turn starts a fresh conversation and the log has `rotated`; the ledger carries the state. The context is the last model call's (`usage.context_tokens`), not the result's sum over the turn's calls: a turn of 5 tool calls at 30k counts 30k, not 150k. Rotating on the sum made nearly every turn a fresh conversation (19 of 21 turns on the owner's log), at a median 0.32 USD a turn against 0.02 USD in a kept conversation.
- Claude keeps the system prompt a conversation began with, also on `--resume`; settings, tools and model apply at every start. `state.json` keeps a digest of the instructions the conversation began with (`instructions`). A host whose instructions differ, or a state without the digest (from an older host), starts a fresh conversation and logs `rotated{tokens: 0, reason}`, except when the conversation is warm: its agent answered less than 60 min ago and its context is under 100k tokens (`state.json` `last_reply_ms`, `context_tokens`). Then the same conversation goes on and the turn opens with the new instructions as a message ("Your instructions changed"), with no rotation, since a rotation there costs a cold start.
- Idle rotation: before a turn, a conversation whose agent answered over 60 min ago (Claude's prompt cache lives 1 hour) and whose context is over 60k tokens starts a fresh one with the handover instead of a cold resume; `rotated{tokens, reason: "idle over 60 min with <n>k context"}`. The size limit stays `rotateTokens`. A wait the manager host knows is pinged instead: while a task of the project works or checks, its event wakes the manager later. When the manager's own Claude agent last answered `tasks.agent.keepWarmSeconds` ago, the host sends the same ping as to a worker (Context rotation), at most 3 between real turns, never in a usage limit or with a stand-in. The host logs `ping{usage}`, not a `reply`, so the chat does not show it. The ping does not count as activity for the recap, and it moves the idle clock (`last_reply_ms`).
- The first turn of every fresh conversation opens with the manager's notes: `notes/decisions.md` newest line first, then `notes/context.md`, at most 10 KiB together ("Notes budget"). Whatever it leaves out is named in the message, never cut silently. After a rotation a handover follows: the last 4 owner messages and replies, each at most 600 characters (a post of `wsx task post` or the digest shows as `Posted: <text>`, not as the manager's `You:`), then, from the scheduler's run records, the routine results it may not have acted on, at most two lines per routine in the order of their newest run: the newest run, with the failures since the routine's last success folded into it (`routine nightly failed (exit 3); 3 failures since its last success at 2026-10-27 03:00`, or `..., never succeeded`), and, when more than that one run ended after the previous conversation's last reply, `routine <name> ran <n> times since your last reply, <k> of them without success`.

The web client shows the manager chat, the tasks, their reports and their fixed actions, and notifies about them: [web-client-tasks.md](web-client-tasks.md).

## Managers talk

A manager may reach the manager of another registered project, and nothing else of it:

- `wsx task ledger -p <other>` reads its state.
- `wsx task say -p <other> --from-manager "<text>"` sends it a message. The manager host's broker sets `WSX_TASK_FROM` to its own project, and the message is logged in the other manager's log as `message{from: "manager:<project>"}`. The sender's log gets `sent{to, text}`: a message from a manager or a role always answers in JSON with its `text`, `--json` or not, and the host logs `sent` from it. A `sent` with no text (older hosts logged one without `--json`) shows nothing in the web or the TUI. The web shows both as bubbles, each manager by its name ("Config"): "<project>" in the receiving chat, "To <other>" in the sending one; a project with `tasks.manager.name` shows that name instead ("Atlas", "To Atlas"), read only from projects the site grants.
- `--reply` answers such a message (`from: "manager-reply:<project>"`). Each delivered message from a manager allows one reply to it, and a reply allows none, so no two managers answer each other in a loop.
- `wsx task new|show|list|add|steer|stop|hold|land|close -p <other>` (not `close --discard`) works in the other project: the task is in its store, as the owner's `-p` makes it, with its numbers, branch, working copy, checks, land target and boundary, and the other project's manager host (which `new` starts) watches it. Deploys, releases, pushes, approvals, `close --discard`, routines, roles and `project add` stay the other project's, and every other command with `-p <other>`, and `--from-manager` to its own project, is refused by the broker.
- The task's `created_by` is `manager@<project>`, the manager that created it. Like a manager's own task it never lands by itself: it waits `ready` for that manager's review. The other project's manager host sends every event of the task to the manager of `<project>` through `say` (from `events`, which starts its host), and its own manager does not hear them. The lines read `<other> #<n> landed r1: ...`, and the chat row has no task chip (a chip links into the chat's own project): the web and the TUI both show the words `<other> #<n> done`. A host that does not take them hands them back to the other manager. The task's To check items stay in the other project's list.
- Its memo: when the task leaves, the other project keeps it in its scope as before, and the host also stores it in the scope of `<project>`: a `fact` verified by `task:<other>#<n>` with the landed commit and the paths, which `stale` checks in the other project's folder (docs/memory.md "Capture"). The `landed` event line in the chat carries it as well (`memo: ...`).

## Chats

A chat is a manager with a name and a goal. A project has several: the first is the manager that always exists; the others are for one area each, such as a long branch effort driven through a parent task, `qa` or `release`. Each chat has its own log, notes, goal and name; the project (files, tasks, the owner's rules, the memory store) is shared. A chat starts with only its own context and reaches another chat's by `wsx task search` or by `say` to that chat, never by loading it. A chat stays in its own project: only the first chat's manager reaches another project, so the broker refuses a chat every `-p <other>` command but `ledger`. Research is a task with research skills (`task new --skills`), not a chat.

```sh
wsx task chat new <name> [--goal <file>] [--agent <entry>] -p <project> --json   # the owner's; --goal - reads stdin
wsx task chat list -p <project> --json          # open and closed chats, each with its `agent` entry, `adapter`, `model` and `running`
wsx task chat close <name> -p <project> --json  # its notes and log stay
wsx task say --to <name> "<text>" -p <project> --json
wsx task chat [--chat <name>] -p <project> --json
```

- Store: `tasks/<project-id>/chats/<name>/` holds what `manager/` holds (`log.jsonl`, `state.json`, `notes/`, `skills-plugin/`), an optional `goal.md` (at most 8 KiB) and `chat.json` (`{agent?}`); `closed` marks a closed chat. A name is a lowercase letter, then lowercase letters, digits or `-`, at most 24; `manager` is refused. `chat new` of a closed name opens it again with its notes; of an open one it refuses.
- Agent: `--agent` names an `[[agents]]` entry with an adapter and a model (checked when the chat opens, as `task new --model` is checked). Its turns run on that adapter and model in place of `tasks.manager.adapter` and `model`; `tasks.manager.eventModel` does not apply to it. With none, the chat runs the manager's agent. A fallback in the chat's `state.json` shows and runs as the manager's does (see Agents). A name the config no longer holds runs the manager's agent. The ledger's `chats`, `chat list` and the chat's heading show the chat's own agent.
- Host: `wsx task manager-host <project-id> --chat <name>` in the session `task-<name>` (`--role` is an alias: the argv wsxd stored for a session before chats starts the same host). `say` starts it; it leaves 20 s after its last message or turn with an empty queue, so an idle chat has no agent and no pane. Its instructions are the manager's after a preamble with the goal; a new goal changes the digest, so the next turn starts a fresh conversation. Rotation, handover and notes work as for the manager. Its agent runs as `WSX_TASK_ACTOR=chat:<name>`.
- Events: only the manager host watches the store. An event of a task that an open chat created (`created_by: "chat:<name>"`) goes to that chat through `say` (from `events`), which starts its host; every other event, and one whose chat is closed or whose host did not take it, goes to the manager. The recap, the idle task, approvals, deploys, routines and the project overview stay with the manager.
- What a chat may do: the `area` row of the table in Permissions, which is the one rule. It creates tasks, and adds, steers, stops, holds, closes (not `--discard`) and lands only the tasks it created, a land only of a child into its parent. `chat new|list|close`, `approve`, `deny`, `trial`, `deploy`, `release`, `push`, `close --discard` and routine add, edit, delete, enable and disable and `checkin` are refused to it. `chat new|list|close` are refused to the manager as well: the owner opens and closes chats, no approval card asks for one. The manager and the owner act on every task.
- Talk: `wsx task say [--to <name>] --from-chat "<text>"` from the manager or a chat reaches another chat, or the first chat without `--to`; the message is `from: "chat:<sender>"` (the first chat is `manager`) and the sender's log gets `sent{to: "chat:<name>"}`. `--reply` answers once, as between managers (see Managers talk).
- Show: `wsx task chat` prints the rows the other chats show (`chat::read_for`, one read for the CLI, the TUI and the web): the first chat's approvals and To check items only. The ledger lists `chats`, the open ones. The TUI's Tasks view lists them under *Chats*, the chat's model before its goal; `Enter` opens a chat, the manager's chat view without its To check items and approvals. A chat holds its own log only: a new chat shows no earlier event of the project. Its title is `<project> · <chat>` in the web and the TUI, its own replies are under the chat's name, and a message of the first chat is under `<manager's shown name> manager` (`chat::manager_name_in`), never the bare project name.
- Before chats: a project had role rooms in `roles/<name>/` (`brief.md`, `role.json`), `tasks.roles.max` and `closeDays`, the manager's `role new` approval and a denied-name wait. The first open of a project's store in each process moves it (`chats::migrate`, idempotent): `roles/<n>` to `chats/<n>`, `brief.md` to `goal.md`, `role.json`'s adapter and model to the `[[agents]]` entry that has both (none: dropped with a warning), the values `role:<n>` and `role-reply:<n>` in task records and logs to `chat:<n>` and `chat-reply:<n>`, and the approval lines of the removed `role` action dropped. `tasks.roles` in a project config is an unknown field.

## Recap

After `tasks.manager.recapMinutes` (default `0`, off, at most 1440, a fraction allowed: `0.5` is 30 seconds) with no message and no turn, the manager host looks once; the next look waits another quiet period. It may start the idle task (see Workflow), and it logs a message from `recap` that asks the manager for a recap only when something changed since the last recap (`state.json` `recap_ms`): an event about a land, a close, a new wait, a stall or an approval decision, a new approval request, or a To check item. An owner message alone is no change. The request is fixed text written by wsx: a recap of at most 8 lines (what landed and is live, what runs, what waits for the owner and why), read from the ledger, with no task started. It ends with the token cost since the last recap, from the logs' `cost_micro_usd`: the manager's replies and the workers' results with their turn counts, and the three costliest tasks. The manager answers in an ordinary turn. The web does not show the request and tags the answer "Recap" ("Asks you" instead while a recap that asks is unanswered). A quiet project gets one recap, not one per period.

## Memo

Proposed redesign of the memo, the notes and the search as one memory system: [design/memory-system.md](design/memory-system.md).

Durable project knowledge moves from workers to the manager, kept small:

1. The worker's instructions: before a build finishes, put in the result's `memo` a short, lean memo of durable project knowledge a later task needs (a convention, a gotcha, a decision and its reason), a few lines at most; empty when there is none. It is kept in `result.json`.
2. When a task lands or closes, the manager host stores its memo as a memory record (a `fact` verified by the landed task, else an `episode`; the same memo is one record) and writes `manager/notes/context.md` from the records as `- #<n>: <memo>`, and no turn runs for it. The line is at most 240 characters (the full memo stays in the task's `result.json`). There is no line cap; past 32 KiB the oldest such lines show in `notes/context-archive.md` only. See "Notes budget" and [memory.md](memory.md) "Notes". The file opens every fresh conversation. The manager fixes a line only when it sees one is wrong, with `wsx memory update`. A role's memo is still a line of its own `context.md`.
3. The event of a task that lands or closes also carries its memo (see Manager), and the ledger shows it on each `recent` task (see Ledger).

A project whose skills keep knowledge in files opts in through its own words: `tasks.workflow.build` can tell workers to save it with a skill, and `tasks.workflow.idle` to consolidate it (see Workflow). wsx names no skill.

## Notes budget

A fresh conversation knows only what its first message holds, so the notes never lose a fact without the manager knowing it. All of this is message text, not instructions: the cached instructions do not grow.

| Part | Rule |
|---|---|
| First message | `decisions.md` newest first, first claim: up to 6 KiB, and `context.md` the rest, at least 4 KiB (its first lines, the project section, up to half, then its newest memo lines); a short file leaves the rest to the other; 10 KiB together |
| Left out | Each file's block ends `NOT SHOWN: context.md lines 14-54 of 60 ... Read <absolute path> for them`; `notes/context-archive.md` and `notes/decisions-archive.md` are named when they exist |
| Records | For the manager the four files are views of its project's memory records ([memory.md](memory.md) "Notes"), written after each record is stored: `decisions.md` holds the active rules, each as `- <date> <the owner's words>`, `decisions-archive.md` the replaced ones, `context.md` the section lines and the memos, `context-archive.md` the memos past the ceiling. The manager records a decision with `wsx memory add --kind rule ... --words`, never by editing the file. Nothing asks the manager to compact a file: a rule leaves `decisions.md` only when a newer one replaces it (`--supersedes`, `wsx memory supersede`), and the start budget names what it leaves out. A hand edit of a view is reported (a line in the host's progress, `wsx memory status` `drift`) and kept as `<file>.drift` when the next write renders the file again. A role's notes stay files of its own |
| Archive | Past 32 KiB of `context.md`, the oldest `- #<n>:` lines show in `notes/context-archive.md` only (written first; read as its last 256 KiB). The replaced rules are in `decisions-archive.md` |
| Search | An owner message gets the lines of the notes that the first message did not show (the left-out lines of both files, their two archives, and the exchanges before the last rotation except the handover's 4) and that share a rare word with it, under `Notes that match this message and are not in your context`: at most 5 lines, 240 characters each, 1 KiB. A word is rare when at most a quarter of those lines hold it; words are cut to 6 characters (`restart` meets `restarted`) and ASCII words need 4. With no match nothing is added; events, recaps and replies get none |

Measured on a 60-line, 14.2 KB `context.md` with one decision (bytes of the notes in the first message, about 4 per token): before 8,140 (the oldest 17 memo lines gone, unnamed), after 10,461 with the left-out lines named; once the manager has compacted the file (1.4 KB) both start at about 1.5 KB, and a file at the 4 KiB target starts at about 4.2 KB, half of the old 8 KiB. A search hit adds about 260 bytes. The numbers are constants in `crates/wsx/src/task/notes.rs`. The earlier conversation's exchanges come from the last MiB of `log.jsonl`.

## Preview

For a project with `tasks.preview`, a person can try a task on a link. wsx configures none: a wsx change lands and deploys to the live app.

1. `wsx task preview <n>` (the manager on "try #n", the web's *Try* on a To check row and in the task sheet) answers the running preview, or starts a detached `wsx task preview-host`.
2. The preview host takes the first port of `tasks.preview.ports` that nothing listens on and runs `tasks.preview.command` with `$PORT` in its own process group: in the task's working copy, or for a landed task in a temporary copy `<repo>-preview-<n>` of its landed commit. Output goes to `preview.log` in the task folder.
3. Once `GET <ready>` answers 200 (within 180 s), it runs `tailscale serve --bg --https=<port> http://127.0.0.1:<port>` (tailnet only, port-scoped, never `reset`), writes `preview.json` `{url, port, pid, until_unix_ms}` with `url` `https://<this machine's tailnet name>:<port>/`, and logs `preview{url, port}`. With `tasks.preview.local: true`, or when no `tailscale` is on `PATH`, it runs no `tailscale` and the url is `http://127.0.0.1:<port>/`: a watch script per branch on this machine only.
4. It stops after 60 minutes, on `preview <n> --stop` (`preview.stop`), when the command exits and when the task closes. Then it turns the Serve mapping off when it made one, ends the process group (TERM, then KILL after 5 s) and removes the temporary copy after `cargo clean`. A start that fails leaves `preview.error`, which `preview` answers.

## Approvals

Approvals are only for what goes public or is lost. `tasks.land.approve` and `tasks.deploy.approve` (default `false`) and `tasks.release.approve` (default `true`) decide whether the manager may land, deploy or release alone. A `wsx task` command run with `WSX_TASK_ACTOR=manager` (the manager host sets it for its agent) that needs approval does not act: it appends `request{id: a<n>, action, task, revision, commit}` to `tasks/<project-id>/approvals.jsonl` and answers that the owner was asked. `close --discard`, `push` and `project add` by the manager always ask. The ledger lists pending requests under `approvals`. An id is `a<n>` after the highest id of any line, also one this wsx cannot read, and a decision settles only the requests of its id before it: an older wsx counted only the lines it could read, gave a new request the id of a decided one (`a9`, a discard of #42 on 2026-10-25) and so hid it with no outcome.

- **The owner's words.** In a manager turn that began with an owner message, `land`, `close --discard`, `deploy`, `release` and `push` take `--owner-said <id>`, the id in that message's `Owner (message <id>)` heading, when the owner asked for that action ("close #42"). The CLI checks that the last delivered turn of `manager/log.jsonl` has no reply yet and holds that message from the owner, appends the `request` and `decision{approved: true, owner_said: <id>, outcome: "approved by owner message <id>"}`, and runs the action; a message outside the turn refuses with nothing run. Such a decision becomes no event.
- **After a landing.** The owner may say go before the action can run: a release that needs a task's changelog, a push of a fix still in a worker's hands. The manager passes `--after <n>` with `--owner-said <id>` to `land`, `close --discard`, `deploy`, `release` or `push`. The message is checked now, in the owner's turn, as above (an id outside the turn, a closed, missing or own task as `<n>` refuses with nothing recorded); then the CLI appends `request{after: <n>, said: <id>}` and no decision, and answers that it runs when #n lands. No Yes/No card: the ledger's `approvals` lists it as "release after #382, approved by the owner", the web shows it under Running and the TUI chat as a `waits` line, and `approve` of its id refuses. When #n is `landed`, the manager host runs the action as `approve` would, outside the turn, and records `decision{approved: true, owner_said: <id>}`; the result reaches the manager as the usual `approval <id> (...)` event. A release keeps the open To check items, as `--owner-said` does now; a push, deploy or release with no `--commit` uses the default branch tip at that time. When #n is closed without landing, or a newer request covers it (One request per item), it is dropped: `dropped; #382 is closed, so release waits for nothing`. A land or discard of a task that moved on is dropped as any request is. A host restart while it runs may start it again; the second run refuses (the deploy lock, a task already landed, a commit already on origin).
- **Project add.** `wsx task project add <path> [--clone <url>]` adds a project the manager's work needs. Run by the manager it appends `request{action: "project", path, url}`; the Needs you card reads "Approve project add <path>" with the URL under it. The owner's approval, or the owner's own run, checks and then runs it in the host, outside the boundary: it refuses a path outside the owner's home (or `..`, or home itself), an existing folder that is not a git repository, a missing folder with no `--clone`, a URL that is not `ssh://`, `https://` or `user@host:path` (`file://` only when `WSX_TEST_ALLOW_FILE_CLONE` is set, for the scenarios), and a project already registered by that path (the answer names it) or that name. The manager's request is refused the same way before the owner is asked. A missing folder is cloned with `git clone` and the login session's ssh agent (as push has it; a failed clone leaves no folder); then `ops::register_project`, the registration of the web's Add project and the TUI's `p`, saves the config and tells wsxd. The decision is `done: project <name> added at <path>`, the manager's event, and `wsx task say -p <name>` then reaches the new project. A new request for the same path replaces the waiting one.
- **One request per item.** The owner never sees related requests as a list. A new request of the same project replaces each waiting one it covers: a `push`, `deploy` or `release` whose commit contains (or is) the waiting request's commit (no commit means the default branch tip; a push with `--force` covers one without, not the reverse), and a `close --discard` of the same task. The older is settled `decision{approved: false, outcome: "dropped; replaced by a170"}`, the manager hears it as `approval a169 (push) dropped; replaced by a170`, and `approve` of the older id refuses ("approval a169 was decided: dropped; replaced by a170; nothing ran"). Requests that do not cover each other (another line of history, another task) stay separate; one request should do what it can for every open item. A `land` and a role request are never replaced.
- **Dropped.** The manager host drops a pending request whose task is no longer open or moved past the requested revision: `decision{approved: false, outcome: "dropped; #42 is closed"}`. The event `approval a9 (discard #42) dropped; #42 is closed` tells the manager, and the chat shows the owner "Dropped discard #42: #42 is closed".
- **In the chat.** The web shows a pending request's Deny and Approve inside the manager reply that ended the turn which asked for it, besides its reservoir row ([web-client-tasks.md](web-client-tasks.md)).

```sh
wsx task approve a3 -p <project> --json            # run the action as the owner would
wsx task deny a3 [--note <text>] -p <project> --json
```

Both refuse when `WSX_TASK_ACTOR=manager`, and so do `hand` and `hand --back` (and its old name `handback`): the manager may tell the owner to run them. In the web a second Approve while the action runs, or after it was decided, answers what happened instead of an error. `approve` refuses a land or discard for a task that moved past the requested revision (recorded as not run; ask again). Otherwise it runs the action as its own `wsx task ... --json` command without the actor mark and records `decision{id, approved, note, outcome}`. Decisions reach the manager as events (`approval a3 (land #5) approved; done: ...`). Writers lock the file; requests are numbered under that lock.

This is a guard against the manager's mistakes, not a security boundary: the manager's tools allow every `wsx task` command, and anything running as the owner can leave out `WSX_TASK_ACTOR`. 

## Routines

A routine is `wsx routine` (docs/cli.md "Routines"): a cron or event trigger and an argv that the scheduler in wsxd runs in the main checkout, outside any task and boundary. `wsx task routine <list|show|add|edit|delete|enable|disable|run|cancel|logs|fire> -p <project> --json` is the same command for the manager, whose broker runs only `wsx task`. Run as the manager (`WSX_TASK_ACTOR=manager`), `add`, `edit` and `delete` need `--owner-said <id>`, an owner message of the running turn (see Approvals), and otherwise refuse with nothing run; the other actions need none. wsxd runs routines without `WSX_TASK_ACTOR`, also when a manager's command started it. The ledger lists them (see Ledger) without starting wsxd. The manager host reads the scheduler's run records every second: a run that ended becomes an event, and a handover after a rotation lists the runs the manager may not have acted on (see Manager).

A run that succeeds with empty stdout gives nothing, for every routine: no event, no turn, no message. Any other run's end becomes an event, and the manager answers it:

| Routine | The event | The owner reads |
|---|---|---|
| `post = true` (the default) | one line `routine <name> succeeded after 4 s` (or `failed (exit 3)`, or `found something (exit 1)`) `; for the owner; output ends: <the last 1,500 characters of its final output, newlines as ⏎>; files: [board.html](files/<path>) …`, a link to each of up to 3 files of the main checkout the output names (a word with `/` or `.`, relative to the checkout or absolute inside it, never under `.git`) | the manager's reply to it, a normal message in plain words: what the run found, the links and what it needs from the owner. The instructions say a routine line marked 'for the owner' is answered with a short message, never `-`, and that reply is never quiet, though the turn runs on `eventModel` as any events turn does. The chat shows the event as its first clause only, `routine board succeeded after 4 s`. The web opens a `files/` link in its files page ([web-client.md](web-client.md) "Files") |
| `post = false` (`--no-post`) | `routine <name> succeeded after 4 s; its output ends:` and the last 10 lines of its output, | nothing required: the event is the manager's own work, answered with a quiet line or `-` |

A failure of a `post = false` routine is also that event. `routine add|edit --no-post` stores `post = false`; the ledger's routine rows have `post`. The host reads the runs only between turns, since an event inside a turn would read as its end. A restart does not make an event of a run again: the mark of the newest run seen is saved with the event. So a routine that has nothing to say prints nothing, and one that reports to the owner itself pipes into `wsx task post` (below) and prints nothing.

`routine add|edit --findings-exit <codes>` (a comma list of 1 to 255, never 0; `edit` replaces all fields, so repeat it) stores `findings_exit` in the routine, absent when empty. A run whose command exits with one of them is `findings`, not `failed`: it ran to its end and found something (a scan that exits 1 for "review" and 2 for "strong evidence" and 3 for a real failure lists `1,2`). It counts as a completed run where "last success" and "never succeeded" are told (the handover). It is attention, not failure: the run is never skipped as an empty success: it gives the event with `found something (exit 1)` in place of `succeeded after 4 s` or `failed (exit 3)` (also with empty output), and the manager tells the owner what it found. The ledger row has `last.status: "findings"` and `findings_exit`; the web's Routines pill and list show it in the attention color, the TUI tree in the warning color. A code not listed stays `failed`. The scheduler reads a routine's codes when the run ends, so an edit during a run counts. Daemon revision 42; a store without the field reads as before.

A run's end in the chat: the events message above is the run's message (`ManagerEvent::Message` from `events` whose `short` has `RunRecord::result_line()`, the first clause of the line, at or after the run's end; `chat::run_messages`). The web's routine rows carry its id as `last.message` and the TUI's routine detail finds it on opening; a tap or Enter opens the chat at it (`Window::Around`). A run that made no event (a success with empty output) has none and shows no message line. The ledger does not carry the id.

Triggers (`wsx task routine add|edit` take exactly one; the ledger's `trigger` shows it the same way). A routine always recurs: there is no one-shot trigger, and a command that runs once goes through its approved action (for example `wsx task project add`), not a routine. A stored routine with an old `at` trigger is removed with its runs when wsxd takes the store (daemon revision 50), logged once per project:

| Flag | Trigger text | Runs |
|---|---|---|
| `--cron "0 6 * * *"` | `0 6 * * *` | at each matching local minute |
| `--event <kind>` | `event:<kind>` | when wsx fires that kind; a routine still running drops it |

`routine edit --new-name <name>` renames the routine. `add|edit|delete|enable|disable --revision <n>` names the store revision the change expects (default: the current one); a stale one is refused (`stale routine revision: expected <n>, actual <m>`). `routine fire --kind <kind> --event-id <id> [--payload <json>]` fires an event by hand: the scheduler runs each (kind, id) once and prints `no matching routines` when none matches and `deduplicated` when it saw the id; the payload defaults to `null`.

The manager host fires these kinds, each with `WSX_EVENT_PAYLOAD` (compact JSON) and an id the scheduler runs once (it keeps the newest 4,096 ids per project). A project with no enabled routine of that kind sends no request:

| Kind | When | Payload |
|---|---|---|
| `task.<state>` (`ready`, `failed`, `landed`, `closed`, `waiting`) | with the task's event line | `{task, title, revision, state}` |
| `deploy.succeeded`, `deploy.failed`, `release.succeeded`, `release.failed` | a new deploy record | `{commit, exit}` |
| `project.idle` | each quiet period's look (see Recap; none with `recapMinutes: 0`) | `{unix_ms}` |

"After 5 lands" or "only on main" is the routine command's own check, from the logs: the scheduler has no filters and no counts.

**Scheduler.** It runs in wsxd (`crates/wsx-daemon/src/routine.rs`; the `routine` request, daemon revision 41), one per wsxd. Before, it was the separate asched process (`wsxd __wsx_routine_daemon`, its own socket).

| Part | How |
|---|---|
| Store | `routines/` beside wsxd's socket: `projects/<key>.json` per project (routines, revision, claimed minutes, runs, event ids), `logs/<key>/<run id>/{stdout,stderr}.log`. Only wsxd writes it; the manager host and the ledger read it. A flock on `routines.lock` makes one wsxd its owner |
| Minutes | Each minute once (`claims`), also after a restart. A cron minute missed while wsxd was down does not run. Cron reads the local clock: at a spring-forward change the skipped local times do not come, so a routine due then skips that day; at a fall-back change the repeated hour comes twice, so a routine due in it runs twice. A cron whose day of month names no date (`0 0 30 2 *`) is refused |
| A run | `wsxd __wsx_routine_run`, in its own process group, starts the argv, which writes `pid` and then takes its own group (a cancel stops the supervisor's group, then the group `pid` names, so no moment leaves the command running), keeps each output file at most 8 MiB (the start and the last 128 KiB) and writes `result.json` at the end. The run's record takes the result within a second. A run whose supervisor is gone without a result is `interrupted` |
| Kept | The newest 20 runs per routine; an older run's folder goes with it. A deleted routine's runs and folders go at once |
| Live handoff | A running run goes on: the successor takes the store's lock when the source exits, and finishes the record from `result.json`. A stop (`wsx daemon stop`, SIGTERM, the lifetime rules) cancels the running runs |
| Import | At its first start the owner's wsxd (default socket, or any wsxd with `ASCHED_ROOT`) copies asched's store (`~/Library/Application Support/asched`, `~/.config/asched` on Linux) with each run's output, after asking a running asched daemon to stop (one that does not stop in 30 s gets a warning and may run its routines twice until it ends). A project or run history that cannot be read (bad TOML, a file over 64 MiB) is left out with a warning, and the rest imports; only regular output files are copied, and a routine with an `at` trigger is left out. A store that cannot be set up stops the scheduler until `wsx daemon restart`, and each routine request names the error. A run asched had running is `interrupted`, its output ends `interrupted by the upgrade from asched to wsxd's scheduler`. asched's files stay. Test: `crates/wsx/tests/routine_wsxd_lifecycle.rs` with a store asched wrote (`crates/wsx/tests/fixtures/asched-store`) |

### Check-in

`wsx task checkin -p <project> (--in 40m|2h|1d | --at <time>) --why "<what to look at>"` sets the manager's one pending check-in (1 minute to 7 days ahead): `checkin{at_ms, why}` in `manager/state.json`, set through the manager host's socket, also during a turn. It is no routine and runs no command, so it needs no `--owner-said` and the Routines list never shows it; the host fires it. At the time, between turns, the host sends the event `check-in: <why>` and clears it. The state is saved, so a host restart keeps it and fires it late when it is past due. A new check-in replaces the last. A role is refused (capability `routine`); the command needs a running manager host.

`wsx task post -p <project> [--title <line>] [--level info|warn|bad] [--key <k>]` posts stdin (at most 16 KiB) to the chat as the digest does: a `message{from: events, text: <title>}` and a reply with no usage marked `post`, so no manager turn. Empty stdin posts nothing. A routine that reports to the owner pipes into it, or calls it, and prints nothing. The `--title` defaults to `routine`. `--level` is `info` by default, which is all of the above; `warn` or `bad` (any other value refuses, exit 2) marks the reply: the chat shows the word in the heading and the bar in the warning or error colour (TUI), or a `Warn` or `Bad` tag and a border in the attention or danger colour (web), and every device of every site that grants the project and has "Manager needs me" on gets one push of its own, `<project>: <title>` over the post's first line ([web-client.md](web-client.md) "Notifications"). `--key` (1-64 characters of `A-Za-z0-9._-`, else exit 2) drops a post whose project and key had a kept post in the last 10 minutes: exit 0, `deduped: <key>`, nothing posted, no push. The time of each kept key is in `post-keys.json` of the project's task folder, and keys older than a day leave it; an empty post and a failed post keep none. It runs from a script, a routine or a LaunchAgent with no `WSX_*` variable: it needs `-p`, the config and state folders (`HOME`, or `XDG_CONFIG_HOME` and `XDG_STATE_HOME` when they are set for the manager), the same `TMPDIR` as the manager host (its socket is `$TMPDIR/wsx-<uid>/`), and the manager host running (else exit 1). While a manager turn runs the post waits, up to 30 minutes, then fails: a level does not jump the turn. The post and the dedupe file are written by `wsx task post`, not by the host, so two posts of one key within the same instant may both pass.

wsx's own `retrospect` routine (docs/design/dynamic-routines-retrospect.md): `scripts/retrospect.py <state dir> -p <project>` posts the spend since its last post, what the owner asked 3 or more times, phrases the manager repeated in 5 or more replies, and, from one `claude -p --model sonnet --effort high` call (`scripts/retrospect-prompt.md`), which replies the owner turned down and up to 3 product changes. It writes the whole report to `<state dir>/retrospect/<unix ms>.md` (the newest 14 stay).

A project gets a daily digest by having a routine that runs `wsx task digest`; no device has a digest switch:

```sh
wsx task routine add digest -p <project> --cron "0 9 * * *" --arg wsx --arg task --arg digest --arg=-p --arg <project>
```

`wsx task digest -p <project> [--since <unix seconds>]` posts each task that became ready, failed (with the first check that did not pass) or landed, in its latest state, and the last `deployed <commit>` and `released <commit>`. It prints nothing, so it costs no manager turn. It starts at the newest digest in the project's chat log, else 24 h back; a run with nothing to say posts nothing, so the next run covers its time.

| Case | What happens |
|---|---|
| Lines, host free | The command sends `Post` over `manager.sock`. The host, the log's one writer, logs `message{from: events, text: "daily digest"}`, `delivered` and a `reply` with no usage, marked `post` |
| Push | A `post` reply is wsx's: "Manager needs me" shows its lines in place of `<manager> wrote to you` (docs/web-client.md "Notifications") |
| A turn runs | The host refuses, because a reply inside a turn would read as its end. The command tries again for up to 30 minutes, then fails. Run by the manager itself it fails at once: it runs inside that turn |
| Lines, no host | Exit non-zero, nothing posted: the failed run reaches the manager when its host starts, and the next run covers the time |
| No lines | Exit 0, with or without a host |

## Session news

The project chat also tells when one of the project's own agent sessions needs the owner: the sessions Home counts ([web-client-tasks.md](web-client-tasks.md) "Home"), not a task worker, a hand session or the manager (provider `task` or `manager`, or the label `task-<n>`, `task-<n>-hand`, `task-manager`; `wsx_core::task::session_news::is_task_session`). The project's manager host (not a role's) looks at wsxd's snapshot every 2 s while it runs, with the manager idle or not. A session whose agent pane has exited, or whose attached agent is `error` or `blocked`, is posted as `wsx task post` posts, with no manager turn: `message{from: events, text: "session <provider> in <branch>"}` and the reply `[<provider> in <branch>](session/<id>) exited|needs input|ended in an error`. The web turns `session/<id>` into the session's chat (its terminal for a site without chat); the TUI shows the text as written.

| Case | What happens |
|---|---|
| Once | One post per entry into the state. A session that leaves it and enters again (its state began again) gets a new one. `state.json` `sessions_seen` keeps each posted session's `<state>:<since>` across a restart |
| First start | What is in need then is the baseline, not news. Later, a state that still holds when the host starts is posted |
| A turn runs | The host looks again after the turn: a post inside it would read as its end |
| wsxd does not answer | Nothing changes: no session reads as gone |
| No host | No post. The host starts with the manager |

No push is added, and the post is unread as any post is.

## Stale worktrees

Old worktrees and their sessions pile up: the owner opens them by hand when the manager does not work, then goes back to the manager. One rule decides what is stale: `wsx_core::stale`. The manager host's sweep, the web's worktree delete and the TUI's `d` read it and nothing else.

| Case | What happens |
|---|---|
| Never judged | The main checkout (its shell session stays), an open task's working copy, a worktree with a task's session, a session with a live agent turn (working or blocked) or a program in the foreground, a session whose clock wsxd does not give (an older daemon), a worktree whose git did not answer in 10 s |
| Idle | A session is idle when none of its panes printed or got input for `tasks.prune.idleDays` (default 14, a fraction allowed, 0 is off). The clock is `last_io_unix_ms` in wsxd's `pane_activity` (daemon revision 49): a shell or agent that still prints is not idle. A worktree with no session is idle since git last moved its HEAD. A daemon restart starts every clock again |
| Close | Each idle session of a worktree other than the main checkout is closed. Nothing else is touched |
| Remove | A worktree idle for `tasks.prune.removeDays` (default 30, 0 is off; at least `idleDays`) that is clean (no tracked or untracked change) and whose branch is merged into the default branch or on a remote (`git rev-list <branch> --not <default> --remotes` is empty) is removed with `ops::delete_worktree`: its sessions close, `git worktree remove` and `git branch -d` run with no force |
| Flag | An idle worktree with uncommitted files or commits neither merged nor pushed stays. The chat names what it holds, once (again only when the text changes) |
| Leaked processes | The processes of the owner's user whose executable lies in the working copy of a closed or landed task, or of an open task whose folder is gone, are stopped as `close` stops them (see Close). An open task's existing copy, a folder that holds the main checkout, and a path the system cannot read are never touched. This runs at each sweep, also when both `tasks.prune` values are 0 |

The sweep runs in the manager host, off its loop, at start and every hour (`WSX_TEST_PRUNE_SWEEP_SECS` shortens it for the task scenario), for the host's project. It posts what it did as event lines (`pruned: removed worktree <b> (clean, merged or pushed, idle N days)`, `pruned: closed 2 idle sessions in <b>`, `pruned: stopped 3 processes that outlived task #400 (closed, <copy>): pid 1155 <path>, ...`, `pruned: worktree <b> is idle and kept: it has 3 uncommitted files (...)`) that start no manager turn (`Short::quiet`, as a landing does): the chat shows them and the manager's next turn lists them. No wsxd, no change.

The owner deletes by hand in the web Sessions tab (`Delete` on a worktree other than the main checkout, with `session_start` and `files_write`; `GET api/worktrees/<id>` names the loss, `DELETE api/worktrees/<id>[?confirm=true]` deletes) and in the TUI (`d` on a worktree). A clean merged or pushed worktree goes after one confirm. Uncommitted files or commits neither merged nor pushed refuse with `needs_confirm` until the confirm names them (`3 uncommitted files (a, b, c) and 2 commits that are not merged or pushed`); the confirmed delete forces the removal and deletes the branch (`git worktree remove --force`, `git branch -D`). The server reads the loss again at the delete. The main checkout, a task's working copy and a worktree with a task's session are refused (409 `main_checkout`, `task_session`). `wsx worktree delete` keeps its rule: it refuses uncommitted work and keeps an unmerged branch. The ledger's `stray_worktrees` lists the same worktrees with their flags.

## Deploy and release

```sh
wsx task deploy -p <project> [--commit <ref> | --if-new] [--owner-said <id> [--after <n>]] --json    # tasks.deploy.command
wsx task release -p <project> [--commit <ref>] [--owner-said <id> [--after <n>]] --json   # tasks.release.command
wsx task deployed -p <project> --json
```

Deploys and releases of a project run one at a time under `tasks/<project-id>/deploy.lock`. A `deploy` or `release` by hand (the owner's, the manager's, an approved request's) checks what is below, takes the lock without waiting and refuses while another deploy or release runs ("a deploy or release of <project> runs"). It then starts a detached `wsx task` that holds the lock and runs the command, and answers at once: "<kind> of <commit, 12> started", with `started: true` and the commit in `--json`. So the manager's broker limit (15 minutes) does not cut a release; the result arrives in `deployed`, the ledger's `deploys` and, for the manager, as an event (see Manager). `--if-new` waits for that lock and then does nothing when the last successful deploy is already the default branch tip, so the deploys that quick lands start run once for the newest commit. With `tasks.deploy.auto: true` every land starts one (see Landing); `tasks.release` has no `auto`.

The command runs with `SSH_AUTH_SOCK` from wsx-core `git::ssh_agent`, as a push does (see Push, "The agent"): wsxd's own socket when it answers, else the login session's agent. A failure whose output has `Permission denied (publickey)` gets the same agent words in its record. A routine run gets the same `SSH_AUTH_SOCK`.

`release` refuses while To check items are open, and so does `deploy` with `tasks.deploy.public: true`, before anything runs or is asked; a deploy that is not public runs and its answer ends "<n> to check on the deployed site". Some items can be checked only on the released build, so a release the owner's own message asked for (`release --owner-said <id>`, an owner message of the manager's running turn) runs with open items, and its answer ends "still to check on the release: c34, c35". `deploy` and `release` make a temporary detached working copy of one commit (default: the default branch tip) beside the main checkout, run the command there with `/bin/sh -c` and `WSX_DEPLOY_COMMIT` (killed with its process group after 2 hours), record `{kind, commit, exit, unix_ms, duration_ms}` in `tasks/<project-id>/deploys.jsonl` (past 4 MiB it rolls over to `deploys.1.jsonl`; readers see the last MiB across both), then `cargo clean` and remove the copy. They never run in a task's working copy. A run killed before its end (a caller's timeout) leaves its `<repo>-<kind>-<pid>` copy; the next deploy or release removes, after `cargo clean`, each such detached copy whose process is gone (a worktree on a branch stays). The output is read to its end, keeping the last 8 KiB of each stream, and printed when the command ends (a run by hand prints into `tasks/<project-id>/follow-up.log`), to stderr with `--json`; a failed attempt also records it as `output` (stdout, then stderr). `deployed` gives, per kind, whether its command is set (`configured`), the last successful commit, how many default-branch commits it lacks (`behind`), how many attempts failed since (`failed_since`) and, when one did, `failed`: the newest failed attempt's `{commit, exit, unix_ms, output}` with the last 40 lines of its output (at most 4 KiB). The web's project overview folds that output under the deploy line and opens it at its last lines. `scripts/deploy-web-live.sh` also writes its whole output to `.work/web-live/deploy.log` (the run before is `deploy.log.1`) and ends a failure with the step that failed. Its gate is the debug build, `scripts/runtime-smoke.py` and `scripts/terminal-context-check.sh` (the live handoff scenario, from the newest older Homebrew release when one is installed, else without that leg and saying why; it needs `tmux` on PATH), each in the check slot (see Checks), then the release build and the install: a few minutes. wsx's own release is `scripts/release.sh`: it refuses a version that origin already has as a tag or that CHANGELOG.md has no section for, runs the same live handoff (`scripts/terminal-context-check.sh`, in the check slot), pushes the commit to main, pushes the annotated tag `v<version>` and watches `release.yml`, which runs `ci.yml`'s tests before it builds or publishes anything, then reports the GitHub release, crates.io and the Homebrew tap. A failure ends with the step that failed. A test failure ends with "NOT PUBLISHED: tests failed": the tag is on origin but nothing is published, so fix main, delete the tag (`git push origin :refs/tags/v<version>` and `git tag -d v<version>`) and release again; `WSX_RELEASE_DRY_RUN=1` runs the checks and prints the builds, pushes and waits. The task and web end-to-end scripts are wsx's `tasks.scenarios`; its `workflow.build` tells a worker to run the scenario of each area it changed.

## Push

```sh
wsx task push -p <project> [--commit <ref>] [--force] [--owner-said <id> [--after <n>]] --json
```

`push` puts the default branch tip, or `--commit`, on `origin`'s default branch and then moves the local default branch there. Nobody inside a boundary can do that: the default branch's ref is the host's, and `~/.ssh` is denied, so an ssh push fails (`known_hosts: Operation not permitted`). The manager's broker runs `push` in the manager host, outside the boundary, with the owner's git config and ssh keys; an approved request runs it from the owner's `wsx task approve` or the web. A worker's broker refuses it like every command but `check-run`, and a role is refused.

- **Always asked.** Run by the manager, `push` first checks what it can (the commit, origin's tip with `git ls-remote`, the local move) and then asks: `request{action: push, commit: <sha>, lease}`, shown as "Approve push #319 #320 (9 commits)", or "Approve push <sha, 12> (1 commit)" with no landed task ("Approve force push" with `--force`). `--owner-said <id>` runs it when the owner's message of the turn asked for it (see Approvals). There is no `approve` setting.
- **What it carries.** The request records `tasks` (the landed tasks whose landed commit lies in origin's tip..the commit; commits carry no task ids, so the match is each landed task's `landed` log entry) and `commits` (their count). The label reads "Approve push #319 #320 #321 (9 commits)" in the web, the TUI chat and `ledger --json` (`approvals[].label`); a push with no landed task names the commit. A request for the same or a later commit replaces the waiting one (see Approvals).
- **One at a time.** A push that is not a request takes `push.lock` of the project, waits for it, and reads origin's tip under it. Two approved pushes ran together once and the older won the ref (`cannot lock ref 'refs/heads/main'`). An approved fast-forward whose commit contains origin's tip goes on although origin moved while it waited; one that origin already has refuses ("is already on origin main").
- **Fast-forward only.** Without `--force` the commit must contain origin's tip and the local default branch (or the local branch already has it: lands since the ask stay), else it refuses with "a rewrite needs --force" and asks nothing.
- **A rewrite** (a squash the owner asked for: a task makes the commit on its branch, for example with `git commit-tree`). `--force` records origin's tip as `lease` and pushes with `--force-with-lease=refs/heads/<branch>:<lease>`; when origin moved since the request, it refuses ("moved from ... since the push was asked; ask again"). The local branch moves with `git reset --keep` where it is checked out, so the owner's uncommitted changes stay; a change to a file the move rewrites refuses the push before anything is pushed. The answer names the old tips and the open tasks based on the old branch ("open tasks on the old main: #5"): their branches still hold the old commits, so the owner decides whether to close or redo them.
- **Bounds.** `git ls-remote` and `git push` run with no stdin, `GIT_TERMINAL_PROMPT=0` and `GIT_SSH_COMMAND="ssh -o BatchMode=yes -o ConnectTimeout=5"` (wsx's `git_cmd`): ssh never asks, so a key needs an ssh agent or no passphrase, and the owner's own `core.sshCommand` does not apply; `~/.ssh/config` and `known_hosts` do. **The agent.** wsxd, its hosts and the web server keep the environment of the shell that first started wsxd, through every handoff, such as an ssh login with no agent; the login session's agent socket also moves at each login. So a call to a remote (`push`, `ls-remote`, the TUI's fetch: wsx-core `git::remote_cmd`) gives ssh `SSH_AUTH_SOCK` when that socket answers, else the login session's agent: on macOS the `SSH_AUTH_SOCK` of `launchctl print gui/<uid>/com.openssh.ssh-agent`. When the server takes no key (`Permission denied (publickey)`), the answer says which agent ssh asked ("ssh offered the keys of the login session's ssh agent at <path> and the server took none: add the key to that agent ..."), or that it found none and why ("ssh had no agent: SSH_AUTH_SOCK is not set and the login session has no agent ...": no one is logged in to the Mac's desktop). The boundary still denies `~/.ssh` and drops `SSH_AUTH_SOCK` for agents. Both stop after 120 s, for a server that stalls after it connects. Nothing is pushed on a refusal: every check comes before the push. The decision's outcome is the record: `approval a7 (push) approved; done: pushed main to origin: 1a2b3c4d5e6f (forced over 9f8e7d6c5b4a); local main was ...`. The remote is always `origin`, the branch always the default branch.

`crates/wsx/tests/task_deploy.rs` pushes to a local bare repository as the owner: a fast-forward moves it; a rewrite without `--force`, a stale lease and an overlapping uncommitted change refuse it and move nothing; a lease that matches rewrites origin and the local branch. `scripts/test-task.py` part 22a runs the manager's way: a denied push leaves origin, an approved one moves it, and a forced one names an open task. `task_deploy.rs` also makes the manager's requests (with two fabricated landed tasks): the newer drops the older and lists #7 #8 and 2 commits, a request on another line and a deploy on it stay, a newer deploy drops the older, and two waiting requests approved at once (an origin hook that takes a second makes them overlap) end at the newer commit with no `cannot lock ref`. On CI it also pushes to an ssh origin, a `/usr/sbin/sshd` on 127.0.0.1, from a wsxd with no `SSH_AUTH_SOCK`: with no key the login agent holds, the push asks nothing and names that agent; with the key loaded with `ssh-add`, the approved push moves the ssh origin.

## Close

`close` refuses while `wsx/t<n>` has commits that are not on the default branch, unless `--discard` or the task is `landed`; a task worked by hand closes by the same rules, its hand session with the other sessions. A landed task closes itself (see Landing) and keeps the state `landed` unless `--discard`. It stops the task's preview, asks the host to close, waits for it to exit, removes the sessions of the working copy, stops the processes left in the copy (below), runs `cargo clean` when the copy has `Cargo.toml`, and removes the worktree, folder and branch. `--discard` also deletes `refs/wsx/task/<n>/*`. The task folder stays as history (`list --all`).

**Processes left in the copy.** A daemon a worker starts (a `wsxd` from the copy's `target/`) leaves the agent's process group and may clear `WSX_AGENT_TREE`; wsx does not drop the mark itself (wsxd's start and handoff keep the caller's environment), so the agent stop cannot find it. Before the copy goes, `close` (also a landed task's own) stops every process of the owner's user whose executable lies under the working copy (`wsx_core::process::stop_under`, by pid): SIGTERM, 5 s, SIGKILL, then it waits for each to go. It never stops itself, and it leaves alone a process whose path the system cannot read or that the user may not signal. The path is `proc_pidpath` on macOS (when the file was removed, the absolute path the process was started with from `KERN_PROCARGS2`; a relative one cannot be placed) and `/proc/<pid>/exe` on Linux. A root that is not absolute or has fewer than three parts matches nothing. The log gets an `agent` line (`close stopped 2 process(es) left in the working copy: pid 1155 <path>, ...`), and `--json` lists `processes_stopped: [{pid, path}]`.

## Config

```yaml
tasks:
  agent: { adapter: claude, model: opus, smallModel: sonnet, effort: high, rotateTokens: 200000, rotateIdleSeconds: 3600, keepWarmSeconds: 3300, fallback: [], maxWaitMinutes: 300 }
  skills: none                                                   # owner: lend workers the owner's skills (see Workflow)
  workflow: { build: "...", review: "...", idle: "" }   # see Workflow
  checks: ["cargo fmt --check"]
  env: { CARGO_INCREMENTAL: "0" }                                # for the worker's commands and the checks
  checkTimeoutSeconds: 1200
  minFreeGb: 5
  captureBudgetMb: 1024                                          # most the project's To check captures keep (see To check)
  land: { approve: false, auto: true }
  deploy: { command: "sh deploy.sh", approve: false, public: false, auto: true }
  release: { command: "sh release.sh", approve: true }
  preview: { command: "npm run serve -- --port $PORT", ready: /health, ports: 9100-9199 }
  manager: { name: Atlas, adapter: claude, model: opus, effort: high, eventModel: off, recapMinutes: 0, reviewMinutes: 30, fallback: [] }   # eventModel: a model or off; rotateTokens: unset is 400000 on Claude (its 1M window), 150000 on Pi
  prune: { idleDays: 14, removeDays: 30 }                        # see Stale worktrees; 0 is off
memory:
  areas: { "web/**": "docs/web-brief.md" }                       # the brief joins the first prompt of a task whose --files meet the glob (memory.md "Start set")
```

`tasks.manager.name` is the name the owner reads for the manager: the web chat's author and typing bubble ("Atlas is typing"), another project's chat, the TUI row (`task-manager (Atlas)`) and `wsx task manager --json` (`name`). It is trimmed, one line without control characters, at most 64 bytes; empty is no name, and without one the manager reads as its project's name (`task-manager (wsx)`, "wsx is typing"). Inside, the manager stays `manager`: the session label `task-manager`, the provider, `WSX_TASK_ACTOR` and `from: manager:<project>`; the name is not in its instructions. The name is the manager's address for a later talk between managers by name.

Defaults: adapter `claude`, worker and manager model `opus` (`task new --model` overrides the worker's), `smallModel` for `task new --size small` `sonnet` with the `claude` adapter and else the worker's model, no extra tools, no owner skills, the default workflow words, no checks, `minFreeGb: 5` (0..=100000), `captureBudgetMb: 1024` (1..=1048576), `deploy.auto: false`, no preview (`ready` defaults to `/`, `ports` to `9100-9199`, above 1023, `local` to `false`). An old `tasks.sandbox`, `tasks.agent.tools` or `tasks.manager.tools` is an unknown key. Up to 64 checks and 64 scenarios (a name starts with a letter, then letters, digits, `-` and `_`); `checkTimeoutSeconds` is 1..86400; a model is at most 256 bytes and a check 16 KiB. `task new` refuses a config that does not parse or has a known key of the wrong type or value. An unknown key, at any level, is ignored: a wsx older than the file still lands, deploys and starts tasks. One warning names the file and up to 8 key paths (`tasks.env`, `futureTop`); a CLI command prints it on stderr, a task host, a manager host or the web server prints it once in its log, and the TUI shows it as the project notice. There is no typo matching. `tasks.env` holds up to 64 variables: a name is letters, digits and `_` (not first a digit), never `PATH`, `GIT_EDITOR` or `WSX_*`, which wsx sets; a value is one line of at most 16 KiB.

**Build output.** `tasks.env` is set, as the task had it at `task new`, for the worker (on top of the kept environment, see Claude adapter) and for every check, by the host and by `check-run`, so the checks reuse the worker's build. It is not set for a `hand` session, a preview, a deploy or `close`'s `cargo clean`. A Rust project keeps one build folder per working copy, cloned from the main checkout (see Working copy). wsx sets `CARGO_INCREMENTAL: "0"`, and its `Cargo.toml` sets `[profile.dev] debug = "line-tables-only"` for the main checkout and every copy alike: an incremental build names its objects by rustc session and never removes the old ones, and line tables keep the file:line of a panic and of a test's backtrace (`RUST_BACKTRACE=1`) in a smaller build. A clone shares main's blocks until main's next build or `cargo clean` replaces them; then they are the copy's own. So `task new` does not clone `target/<profile>/incremental`, which a copy never reads, and after each run of checks, the host's and a `check-run`'s, the host prunes `target/*/deps` (`crates/wsx-core/src/task/build.rs`): a unit (`<name>-<hash>`) older than the copy whose name the copy has built since, such as main's units of other settings (main builds incrementally, so its workspace crates have other hashes), and in each unit the objects of all but its newest rustc session. On macOS the dev profile keeps a binary's `.rcgu.o` files beside it for its debug info, so they pile up there. A wrong guess costs a rebuild: cargo rebuilds a unit whose output is gone. Measured on wsx (2026-10-29, 3 rounds of `cargo build -p wsx -p wsx-daemon` and `cargo nextest run --workspace --no-run` after a `wsx-core` edit; unique is the free space `cargo clean` gives back):

| copy | du | unique | first round | later rounds |
|---|---|---|---|---|
| before: all of main's target cloned, no prune | 19 GB | 0.76 GB; the other 18 GB become the copy's own as main's builds replace them | 42 s | 32 to 33 s |
| full debug info, pruned | 2.5 GB | 0.78 GB | 39 s | 31 to 33 s |
| line tables, pruned (wsx's setting) | 1.8 GB | 0.92 GB | 49 s | 28 to 32 s |
| cold build without a clone, line tables (other tasks were building) | 1.1 GB | 1.1 GB | 103 s | |

The debug level is part of cargo's artifact hash: set as `CARGO_PROFILE_DEV_DEBUG` in `tasks.env` it gave a copy's dependencies other hashes than main's, so every copy compiled them again. In `Cargo.toml` main builds the same units, and a copy reuses the clone of them; `CARGO_INCREMENTAL` does not change a dependency's hash, since cargo never builds a dependency incrementally. A debugger that needs local variables builds with `CARGO_PROFILE_DEV_DEBUG=full`. For wsx, `minFreeGb: 3` is one task's whole build with margin. Do not share one `CARGO_TARGET_DIR` or `build.build-dir` between copies: cargo (1.93) gives a workspace crate the same file name in every checkout and keeps source paths relative, so a copy whose files are older than another copy's build reuses that build and runs the other copy's code (measured with wsx: a 3 s "fresh" build without the copy's own change), and parallel builds wait on the folder's lock.
