# Tasks (manager mode)

A task is one headless worker on its own branch and working copy. The caller never types into it. Every action is one CLI call; `--json` works on all of them. No wsxd protocol change.

```sh
wsx task new "<prompt>" -p <project> [--from <ref>] [--title <words>] [--model <name>] [--hold <why>] [--files <glob>]... [--plan] --json   # or `-` (stdin) or --prompt-file <path>
wsx task list -p <project> [--all] --json
wsx task show <n> -p <project> --json            # record, result.json, report path, host_running, socket
wsx task steer <n> "<text>" --json               # into the running turn
wsx task add <n> "<text>" [--files <glob>]... --json   # after the turn (queued while one runs)
wsx task stop <n> --json                         # interrupt; the next add resumes the conversation
wsx task land <n> [--tried] [--owner-said <id>] --json   # rebase, check, fast-forward (see Landing)
wsx task hold <n> "<why>" | --off --json         # the owner tries it before it lands; see Hold and trial
wsx task trial <n> [--end] --json                # its revision on the live site before it lands
wsx task hand <n> --json                         # owner only: work on the task by hand; see By hand
wsx task handback <n> --json                     # owner only: its commits are checked as the next revision
wsx task preview <n> [--stop] --json             # a link to try the task (tasks.preview); see Preview
wsx task check-run [<n>...]                      # from a worker: run the checks as after its result
wsx task check -p <project> [--json]             # the open "To check" items
wsx task check pass <id>... | --all --json       # owner only
wsx task check skip <id>... | --all --json       # owner only; closes without a verdict
wsx task check fail <id> --note <text> --json    # owner only; starts a task that fixes it
wsx task close <n> [--discard] [--owner-said <id>] --json
```

`-p` may be left out inside a project folder or when one project is registered. A task number is `3` or `t3`. `new --model <name>` picks the worker's model (one word, at most 256 bytes, not starting with `-`); without it the task uses `tasks.agent.model` (default `opus`). The record keeps it.

## Store

`$XDG_STATE_HOME/wsx/tasks/<project-id>/<n>/`, each folder 0700 and each file 0600, opened without following links.

| File | Content | Limit |
|---|---|---|
| `task.json` | id, project, base, branch `wsx/t<n>`, working copy, pane, adapter, model, tools, checks, agent session, state, revision, `created_by` (`owner` or `manager`), `hold` (why the owner tries it first), `files` (expected path globs), `plan` (true until a `--plan` task's first result), `waiting` (`{on, reason}` while the state is `waiting`, and on `check_slot` while checks wait for the check slot; on `limit` also `until_ms`) | 64 KiB |
| `log.jsonl` | append-only: `created`, `message{prompt\|steer\|add}`, `agent` (short progress), `blocked{denials}`, `result`, `checks`, `check_retry`, `check_run`, `check_queued{reason}`, `disk_wait{free_mb, min_gb}`, `revision`, `preview{url, port}`, `hand{by, dropped}`, `handback{by, commits}`, `hold{reason, by}`, `limit_wait{until_ms}`, `trial{revision, commit}`, `trial_ended{reason}`, `stopped`, `closed` | 8 MiB for progress, 16 MiB hard |
| `result.json` | latest worker result and check results and `denials` | 256 KiB |
| `report.md` | report of the latest revision | |
| `captures/` | the To check captures and posters kept at the land; removed 7 days after their item is passed or failed (see To check) | 2 MiB each image, 25 MiB each video |

- A host's control socket is not in the store: `sun_path` holds 104 bytes on macOS. The task host serves `<TMPDIR>/wsx-<uid>/t-<hash>.sock` and its worker's broker `w-<hash>.sock`, the manager `m-<hash>.sock` and its broker `b-<hash>.sock`, where `<hash>` is 16 hex of sha256 of the store path the socket stands for (`<n>/host.sock`, `<n>/broker.sock`, `manager/manager.sock`, `manager/broker.sock`), and `/tmp` replaces a `TMPDIR` longer than 64 bytes. The folder is 0700 and must belong to the user, the socket is 0600, a host removes its socket when it exits and replaces a stale one when it starts. A host and its callers must share `TMPDIR`; `show --json` and `manager --json` name the socket.
- `<project-id>` is `<name-slug>-<first 8 hex of sha256(project path)>`. Numbers come from a locked `next` counter and are never reused, also after a failed start.
- One writer: the CLI writes before the host starts and after it exits; the host writes everything in between.
- States: `working` (an agent turn runs; also the turn that resolves a landing conflict, which the web reads from the log), `waiting`, `checking`, `ready`, `failed`, `landed`, `closed`. `landed` and `closed` are not open. A `waiting` task names what it waits for in `waiting.on`, with a `reason` in plain words:

  | `on` | Why | Ends when |
  |---|---|---|
  | `owner` | the worker returned `blocked`, was stopped, or its host restarted during a turn | an `add` |
  | `disk` | less than `tasks.minFreeGb` is free, or another task resumes from its disk wait | the host finds space (every 30 s) and it is first in the disk queue |
  | `hand` | the owner works in the copy (see By hand) | `handback` |
  | `plan` | a `--plan` task's first result is its plan (see Workflow) | an `add` |
  | `limit` | the agent hit its usage limit (see Claude adapter); `until_ms` names when it resumes | the host continues the session at that time, first in the limit queue |
- A prompt, steer or add is at most 64 KiB.
- A task's title is `--title` (at most 60 characters, no control characters, kept in `task.json` as `title`), else the first line of its prompt, at most 120 characters. Either one is shown without a leading `Owner <words>:` (up to 80 characters before the colon; a colon inside brackets or without a space after it, as in `http://`, does not end it): `Owner report: tool permission` reads `tool permission`. A lead-in with nothing after it reads as the words in its brackets (`Owner report (UX failures):` reads `UX failures`), else as the prompt's next non-empty line. `Owner: x` has no words and stays. Only the shown title changes: `task.json` and the prompt keep what was written. Every title shown (ledger, events, the web) comes from this rule, also for tasks from before `--title`. The web shows a task without `--title` by the first sentence of its latest worker summary while it has one (`view::readable_title`).
- Each revision records `base` (the merge base with the default branch, so it follows a rebase) and the paths changed in `base..r<k>`: at most 500 paths and 32 KiB in `paths`, the full count in `paths_total`.
- `new --files <glob>` (repeatable; `add --files` extends) records the paths a task expects to change as `files` in `task.json`: at most 64 globs, each at most 256 bytes, relative to the checkout, without `..`, a valid glob (`*` stays in one folder, `**` crosses folders). A glob without wildcards also covers what is under it.
- `list --json` gives each open task `overlaps: [{id, count, complete, declared}]`, the other open tasks whose paths meet its paths. A task's paths are those its revisions changed plus its `files` globs, so a task with no revision overlaps by its globs alone. Changed paths shared exactly come first; only when none are shared, a meeting through a glob counts and the row has `declared: true`. Two wildcard globs meet when their literal heads and tails agree (`src/*.rs` meets `src/**/*.rs`, not `src/*.md`; this can report a meeting no real path makes). `show --json` adds up to 20 of the task's meeting `paths` per task. `complete` is false when a side kept fewer paths than it changed.

## Working copy

`<parent of main checkout>/<repo>-t<n>`: `git worktree add --no-checkout --detach` at the commit of `--from <ref>` (default: the default branch; the main checkout can be stale, so name a fresher ref when needed; `task.json` records the resolved commit as `base`), an APFS clone (`cp -c -R`, plain copy when that fails) of every top-level entry except `.git` and `target/<profile>/incremental` (see Build output), then `git reset` and `git reset --hard`, `git clean -fd` (ignored build output stays warm; filling the index first means only files that differ from the commit are rewritten, so the others keep their clone's mtime and cargo reuses the cloned build) and `git switch -c wsx/t<n>`. Ignored files of the main checkout, such as `.env` or local credentials, are copied into the working copy too, and the worker can read them. Worktrees nested in the main checkout are removed from the copy, so no `.git` file points at another checkout's admin folder. Projects with `.gitmodules` are refused. A failure removes the folder, worktree, branch and task folder.

## Host

`wsx task new` starts hidden `wsx task host <project-id> <n>` as the argv of a wsxd session named `task-<n>` in the working copy. The host:

1. starts the adapter and sends the prompt;
2. prints one progress line per agent step to its terminal (watch it in wsx like any session);
3. serves its control socket (see Store): one JSON request per connection (`status`, `steer`, `add`, `stop`, `land`, `hold`, `trial`, `hand`, `handback`, `close`), one JSON answer `{ok, state, message}`;
4. reports its pane through `AgentReport` with provider `task`: working and checking as Working, waiting on the owner as Blocked, ready as Done, failed as Error, waiting on disk or hands as Idle;
5. keeps running through `wsx daemon restart` (live handoff), because it is a pane process.

A host restarted by a cold daemon start or `wsx session restart task-<n>` logs `stopped` for a running turn and waits on the owner; the next add resumes. A host restarted while it was checking runs the checks again on the worker's last result, with the project's current checks. A new task's host starts the first turn with the prompt.

A host follows a deploy of wsx. It records the identity (device, inode, size, modification time) of the file it was started as (its argv[0], which `task new` and `say` make absolute). Before each agent turn (an add, a check retry, delivered queued messages) a task host that finds another file there writes the turn's text to `handoff.txt` (0600), sets `working`, answers its caller and execs that file with the same arguments, also for a turn that a timer starts (after a full disk): the pane and pid stay, and the new host starts the turn with the new launch, resuming the same conversation. While a trial of any project holds a live site (a `trial.json` in the store), no host follows: the new file may be the trial's build, and the hosts follow the build that replaces it when the trial ends. The manager host does the same before its next turn; its messages stay logged and undelivered, so the new host queues them again. `wsx task` actions (CLI and web) retry for up to 3 s while the socket is gone or when the host closed the request without an answer as it exec'd. Install by replacing the file (`cargo install`, `install`, `mv`, a package manager): macOS kills a process that execs an executable overwritten in place, and that host then stays down until `wsx session restart task-<n>`. A host started before this release has no such check: restart it once.

## Claude adapter

`claude -p --input-format stream-json --output-format stream-json --verbose --setting-sources project,local --permission-mode bypassPermissions --model <model> --append-system-prompt <rules> --settings <no AI attribution> --json-schema <result schema> [--plugin-dir <owner skills>]` (see Permissions and Workflow), with `--session-id <uuid>` first and `--resume <uuid>` after a stop. The environment keeps only `HOME USER LOGNAME PATH SHELL LANG LC_ALL LC_CTYPE TMPDIR CLAUDE_CONFIG_DIR ANTHROPIC_API_KEY`, the proxy variables (`HTTPS_PROXY HTTP_PROXY NO_PROXY` and lowercase), `NODE_EXTRA_CA_CERTS SSL_CERT_FILE CARGO_HOME RUSTUP_HOME`, then `tasks.env` (see Config); no `WSX_*`. When the project's profile sets `claude_config_dir` (README "Profiles"), `CLAUDE_CONFIG_DIR` is that folder for the worker, the manager and every role, and a missing folder stops the start with that reason. `GIT_EDITOR=true`, since no terminal can edit a commit or rebase message. A stdout line over 4 MiB is dropped in buffer-sized steps.

- Steer: a stream-json user message during a turn. Claude does not save it in its history, so the host logs it. A steer with no running turn is sent as an add.
- Usage (`usage` on `result` and the manager's `reply`): the token counts are the result's, summed over the turn's model calls; `context_tokens` and `model` are the last main-conversation call's (`assistant` lines without `parent_tool_use_id`); `session_cost_micro_usd` is Claude's `total_cost_usd`, the session's running total (a resumed process restores the earlier spend), and `cost_micro_usd` is this turn's part of it, the difference from the session's previous turn (the whole total when it is lower, as after a crash; after `handback` the first turn also counts what the owner's own `claude --resume` of the session spent while worked by hand). `calls` counts the turn's main-conversation model calls (distinct `assistant` message ids: Claude writes one line per content block). A worker `result` also has `step` (the workflow step's name) and `trigger`, what started the turn: `step` (the first turn or a step's start), `message` (an add, or messages queued until a turn or checks ended), `check_retry`, `verify` (Human Verify items sent back), `check_run` (a check-run's answer after the result), `conflict`, `result_retry`, `limit` (after a session limit), `rotation` (a fresh conversation's first turn), `disk` or `restart` (a re-exec handoff). Ref: [cost tracking](https://code.claude.com/docs/en/agent-sdk/cost-tracking). `scripts/usage-report.py` turns these fields into tables per day, task, step and manager turn (`docs/design/usage-audit.md`).
- A turn that ends without a valid structured result: when its `usage` counts no token, it is Claude's own turn for a background-task notification (a `run_in_background` job that ended or was killed, also on `--resume`), which answers no message; the task host logs `agent` "claude ended its own turn with no result: ignored" and keeps waiting, and the manager host logs no reply for it. A model turn without a result that ends while background jobs still run (a background subagent or Bash command: the non-`ambient` entries of the last `system` `background_tasks_changed` line, a live set that starts empty with each process) is no missing result: the task host logs `agent` "the turn ended while <n> background job(s) run: waiting for their notice", keeps the turn running and takes the result from Claude's own turn after a job's `task_notification`. The wait lasts at most `tasks.checkTimeoutSeconds` (default 1200 s, the longest a single check may run) from the first such turn and is not extended by later ones; then the host logs "no notice from <n> background job(s) in <s> s: the turn ended without a result" and goes on as below. Any other model turn without a result gets one fixed turn that asks for the result as the turn's last call; a second turn without one fails the task ("the agent ended with success and no result"). An error result fails at once.
- Usage limit: a `result` with `api_error: "usage_limit_reached"` (Claude's "You've hit your session limit · resets 12:10am (Asia/Seoul)") is no result. It runs no checks and spends no check retry. The reset comes from `rate_limit_info.resetsAt` (unix seconds, on the rejected `rate_limit_event` and on the API error's `assistant` line), else from the text when its zone is this machine's; the host resumes 5 s after it. With neither, or a reset in the past or more than 8 days ahead, it backs off: 5 minutes, doubled for each limit in a row, at most an hour. The task waits on `limit` with the reason "session limit; resumes at <HH:MM local>" and logs `limit_wait{until_ms}`; the manager gets the waiting event, not a `failed` one, and the web sends no notification for it. At that time the host sends the same session "The session limit has reset. Continue the task where it stopped." with any message that came meanwhile (an `add` or `steer` during the wait joins that turn; `stop` and `hand` end the wait). Tasks resume one at a time, oldest wait first: each joins the machine's limit queue (`tasks/limit-slot/`, an `flock` like the disk queue) and holds the limit slot until its agent answers again, so a limit that has not lifted stops only one (a host with no running agent turn holds no slot: a stop, a hand or a failed start lets it go; the turn after the limit stays with the running host even when wsx was replaced, and the next turn follows the new file); one behind waits with "session limit has reset; queued for limit behind <project> t<n>". A host restarted during the wait resumes at the same `until_ms`. The manager host holds the turn the limit ended the same way (`state.json` `limit{until_ms, attempt, ids, events}`, logged as a `limit` entry with the resume time, and a `limit` entry without one when the held turn continues; the chat shows both as status lines, docs/web-client-tasks.md): it delivers no other turn until then, and its first turn after it answers the held messages and those that came meanwhile. A held turn whose every message is an event is a turn of only events: its short reply is quiet, and `-` shows nothing. Only the `claude` adapter has this signal; an adapter without it fails such a turn as an error result.
- Only the worker's own `status: blocked` makes the task wait (no checks run): on `owner` with the summary's first line as the reason. Tool calls Claude denied (`permission_denials`) are evidence: they are logged on the `result` event, listed in `result.json` (`denials`, also in `show --json`) and under Evidence in the report, and checks still run.
- Result schema: `{status: done|blocked|failed, summary, decisions[{choice, reason}], evidence[{check, proof}], human_verify[{check, where, capture, poster, pass_if}], left_open[], notes, memo}` (`memo`: see Memo; a result without it reads as empty).

## Permissions

wsx owns the boundary (`crates/wsx/src/task/boundary.rs`). The task host and the manager host start the agent as `/usr/bin/sandbox-exec -p <profile> <adapter argv>`, so one macOS Seatbelt profile per role covers the whole agent process tree: Bash, file tools, MCP servers and hooks. Inside it the adapter runs in its own no-prompt mode (Claude: `--permission-mode bypassPermissions`, no sandbox settings, no permission rules, no classifier), so nothing waits on a permission. The adapter only supplies its argv; another adapter adds argv and stream parsing. On a platform without Seatbelt (Linux) an agent start fails with a clear error; bubblewrap comes later. Before each agent start the host applies the profile once to `/usr/bin/true`; when sandbox-exec refuses it (a profile it cannot parse, or a host that runs inside another sandbox, where Seatbelt answers `sandbox_apply: Operation not permitted`), the start fails with sandbox-exec's words as the task's `stopped` reason and its failed result, which the ledger and the report show. Claude Code and Codex confine commands the same way (https://code.claude.com/docs/en/sandboxing, https://developers.openai.com/codex/security).

The profile is a deny-list on `(allow default)`; the last matching rule wins:

| Rule | Worker | Manager |
|---|---|---|
| no read or write | `~/.ssh`, `~/.aws`, `~/.gnupg` | same |
| no write | `~/Library/Keychains` (reads stay: the agent's own sign-in reads the login keychain), the wsx config folders (the platform one and `$XDG_CONFIG_HOME/wsx`), the wsx state folder, the routine scheduler's folder (`~/Library/Application Support/asched`, or `$ASCHED_ROOT`: wsxd runs the routines written there outside the boundary, see Routines), other task copies `<repo>-t<n>` (also those made after the launch), the default branch's ref and reflog in the main repository's git folder (and their `.lock`): lands stay with wsx; that git folder's `hooks` and `config`, which run or apply in the owner's own git | the same as a worker, but the default branch's ref and reflog stay writable: when a land refuses on the owner's uncommitted changes in the main checkout, the manager commits them on main after the owner's yes (see Manager); its instructions allow no other git write |
| written again | its working copy and its task folder | its `manager/` folder and the project page (and files beside it with the page's name as prefix) |

Everything else is open, the main checkout's working tree (the project folder) included, which the deny-list does not name: a worker can write it, and a land refuses only for its changed files that the land changes too (see Landing). Also open: writes in home (`~/.cargo`, `~/.config/ir`, `~/Library`), any host, loopback listen, PTYs, Chrome. Paths are matched as real paths (`/var` is `/private/var`). Nothing is granted: there is no `wsx task allow`, no permission wait and no `grants.json`. A record that waited on `permission` reads as waiting on `owner`; old `granted` log lines and grant approval requests are skipped when read. Tool calls an agent reports as denied are still evidence (`permission_denials`, see Claude adapter); a worker that cannot go on returns `blocked` and the task waits on `owner`. Seatbelt does not start inside another sandbox, so tests that start task hosts run as checks (the host runs them outside the boundary). `scripts/test-task.py` part 23 runs one probe as a fake worker that is not Claude and part 32h runs the same probe through the real Claude when one is on `PATH`: refused are `~/.ssh` (read and write), the state folder outside the task folder, another copy (one that exists and one made after the launch), main's ref, `.lock` and reflog, and the git folder's `hooks` and `config`; allowed are the own copy and task folder, `$TMPDIR`, `~/.cargo/registry`, `~/Library`, loopback and a PTY; `scripts/test-manager-boundary.py` checks the manager with the real Claude.

- The broker: a host serves `<TMPDIR>/wsx-<uid>/b-<hash>.sock` (the manager host, for `manager/broker.sock`) or `w-<hash>.sock` (a task host, for `wsx task check-run`) and gives the agent `WSX_TASK_BROKER=<that socket>`. Under it the `wsx` CLI runs nothing itself: a `task` command sends its argv, the folder and, when an argument is `-`, its standard input (UTF-8, at most 1 MiB) to the socket, prints the answer's stdout and stderr and exits with its code; any other command is refused (exit 2). The manager host refuses argv that is not `task <subcommand>` and the hidden `task host` and `task manager-host`, runs its own wsx binary with `WSX_TASK_ACTOR=manager` in that folder (the main checkout when it is not a folder), keeps at most 1 MiB of stdout and of stderr and stops a command after 15 minutes (exit 124); a deploy or release answers when it started (see Deploy and release). So a heredoc, `;`, `&&` or a pipe works, and the approval rules still see the manager actor.

## Workflow

The stages are fixed: the manager talks the request through with the owner and sizes it, workers build (a larger task plans first), the host checks, the manager reviews and lands, and after a request's tasks land one housekeeping task consolidates their code. The words each stage gets are the project's:

```yaml
tasks:
  skills: owner          # or none (default): lend workers the owner's skills, as the manager has them
  workflow:
    build: "..."         # added to every worker's instructions
    review: "..."        # added to the manager's review of a ready task
    batch: "..."         # the housekeeping task's prompt
    idle: "..."          # the idle task's prompt; empty (default) is off
    steps:               # the worker's turns in order; none (default) is one build turn
      - name: context
        prompt: Use owner:recall to load the context of this task.
      - name: plan
        prompt: Use owner:develop to explore and plan. Do not edit yet.
      - name: build
        prompt: Implement the plan.
```

**Steps.** With `steps` the host sends each step as its own turn of the same worker conversation: the first turn is the prompt and "Step 1 of N, <name>: <prompt>", and a result with status `done` starts the next step, with any message queued during the turn. The checks run after the last step, as after any result; check retries, conflicts and adds after that are ordinary turns. A step that needs the owner's decision returns `blocked` and the task waits on `owner`; the answer continues the same step. The task record keeps `steps` as they were at `task new` and `step`, the index of the current one; the web shows it under *Running* as `plan (2/3)`. A project's `tasks.workflow.steps` wins; a project without them takes the owner's from `~/.config/wsx/wsx.config.yml` (or under `$XDG_CONFIG_HOME`), of which only `tasks.workflow.steps` is read. At most 12 steps; a name is 1 to 32 letters, digits, `-` or `_`, unique; a prompt is 1 to 16 KiB of text. A bad step refuses `task new`. `task new --skip <step>` (repeatable) leaves that step out of this task's `steps`, for a prompt that already carries the context and the plan; a name that is not a step, or skipping every step, refuses `task new`.

- Defaults name no skill. `build`: keep the change lean, reuse what exists, remove what the change makes dead, and simplify the diff before finishing. `review`: nothing beyond the fixed review (the owner's words, no copy of an existing helper, no dead code, nothing unasked). `batch`: consolidate the code the tasks changed, merge duplicates, remove dead code and empty layers, keep behavior and public interfaces, lower the net line count; the checks prove the behavior is unchanged.
- Each text is at most 16 KiB, newlines allowed, no other control characters; it is trimmed.
- With `skills: owner` the task host writes the skills plugin into the task folder (`<n>/skills-plugin/`, as the manager's) and passes `--plugin-dir`; the worker gets `Skill` and is told to look at the skills and follow any whose description fits the work. With no skills folder there is no plugin.
- The housekeeping task is an ordinary task the manager starts after the last task of a request lands, when no open task changes the same files. It lands like any other.
- The idle task: when `idle` is set, the manager host itself (not the agent, so it is deterministic) looks once per quiet period (see Recap) and starts one ordinary task, titled "Consolidate project knowledge", with `idle` as its prompt, `created_by: manager` and no workflow steps (hidden `task new --no-steps`: one turn), so it waits for the manager's review and lands through the normal checks. It starts only when a file in the main checkout's `knowledge/sessions/<project>/` changed after the last idle task started, and that task is no longer open; `state.json` keeps both (`idle_task`, `idle_ms`). Otherwise it starts nothing and says nothing. With `recapMinutes: 0` there is no idle task. A failed start is tried again the next period.
- Plan first: `task new --plan` ends the first prompt with a request to write a short plan (goal, files, approach, how it proves it) as the result and to edit nothing. That result runs no checks: the host clears `plan` and the task waits on `plan` ("its plan waits for the manager"), which the manager hears as an event and the web shows as working. The manager reads it (`show --json`) and continues with `wsx task add <n>` (go, or what to change); the task then goes on as any other. Its instructions: use it, or `--hold`, for large work or work costly to undo, not small fixes.

**Context rotation.** A worker conversation that grows past `tasks.agent.rotateTokens` (default 200000, 1000..=2000000; the main checkout's config at that turn) continues in a fresh one, since every model call reads the whole context again (`crates/wsx/src/task/host.rs` `rotation_due`). The size is the last model call's context of the latest result. A conversation of at least half that size also rotates when the agent last answered (a result or a session limit) more than `tasks.agent.rotateIdleSeconds` ago (default 3600, 0..=86400, 0 = never): Claude's prompt cache lives 1 hour, so a resume after that writes the whole context again; then `rotated` has `reason` "idle <n> min" and the handoff request says so. Before the next turn (a step, a message, a check-run answer, a retry), the host asks the worker, in the old conversation, to write handoff notes to `rotate-notes.md` in its task folder (what it does now, what is done and remains, decisions, files, checks, lessons; at most 12 KB) and to return a result that is not checked: it logs `agent` "handoff notes: …", not a `result`. Then it ends that conversation, clears `agent_session`, logs `rotated{tokens, reason}` and starts the waiting turn in a new conversation that opens with: the task continues from a closed conversation, see git for the working copy, load the project knowledge again (recall or seek), the task's prompt, the notes inline (a path when they are larger than 16 KiB), the current step when the waiting turn is not that step's start, then the waiting turn and any queued message. Never for the turn that asks again for a missing result, nor while a `check-run` waits. A host started after a re-exec knows the size from the next result on.

## Checks, revisions and report

After each result that is not blocked the host runs `tasks.checks` with `/bin/sh -c` in the working copy (the checks and `tasks.checkTimeoutSeconds` as the main checkout's config has them at that moment, so a task started before they changed lands through the current gate; the record's `checks` follow) (`tasks.checkTimeoutSeconds`, default 1200, and the whole output, stdout and stderr in the order written, kept in `check-<n>.log` in the task folder (`check-run-<n>.log` for a worker's `check-run`, overwritten by the next run of that check) while the check runs to its end; the result keeps the log's last 8 KiB, and a cut result starts with `[the first <N> bytes are cut; the whole output is in <log>]`; no `WSX_*`, plus `tasks.env`; a timed-out check's process group is killed; a process the check left behind holds only the log, so the check ends with its shell), then sets `refs/wsx/task/<n>/r<k>` to the worker's HEAD. The host commits nothing; the worker commits. `ready` needs worker status `done` and every check at exit 0; otherwise `failed`. When the worker said `done` but a check failed, the host first sends the failure back: it logs `check_retry{revision, attempt, commands}` and starts a worker turn with each failed command, how it ended and the last 3 KiB of its output; the checks run again on the result as a new revision. After 2 such turns the task is `failed` as before; a message from the owner or the manager (an add) allows 2 more. A landing's checks are never retried. **Check slot.** One check run at a time on the machine, for every project and task host of the wsx state folder; tasks still work in parallel. The slot is an `flock` on `tasks/check-slot/slot.lock` (`crates/wsx/src/task/slot.rs`), which the kernel frees with its process, so a killed or crashed host never blocks the queue. A waiter keeps its own ticket file locked; a ticket whose lock is free is a dead waiter's and is removed. The checks after a result, after a landing's rebase and after a trial's rebase, and a worker's `check-run` of all checks, take the slot: first come, first served, except that a landing's checks go before every other waiting run (they are closest to the default branch). A worker's `check-run` whose checks only format or compile (one plain `cargo fmt`, `cargo build` or `cargo check` command each, without `&`, `|`, `;`, `$`, redirections or a second line) skips the queue. While a run waits, the record's `waiting` is `{on: check_slot, reason: "queued for the check slot behind <project> t<n>[ and <k> more]"}` with the state still `checking` (or `working` for a worker's run), the log gets `check_queued{reason}`, the pane says it, and `waiting` clears once the slot is taken. Each check's timeout counts from that moment, not while it waits. **Time.** Each check result (in `checks` and `check_run` log events, `result.json`, `show --json` and the ledger's `checks` rows) has `ms`, how long the check ran, and `queued_ms`, how long its run waited for the check slot before it (0 for a run that takes no slot); a result reused from an earlier run on the same tree has `stored: true` and that run's `ms`. **Check-run.** In the build the worker runs only the checks its change touches (`wsx task check-run 2 3`, by number as its instructions list them), never the full set: the host runs that once after the result. A check that fails in code the worker did not touch is not the task's to fix: the worker does not run it again and names it in its summary. Under `WSX_TASK_BROKER` the CLI sends the argv to the task host's broker, which runs those checks in the check slot exactly as after a result, answers each command and how it ended (the output of a failed one) with exit 0 when all passed, and logs `check_run{results}`; no revision is recorded. When the working copy is clean (no tracked change and no untracked file) the host keeps each result with HEAD's tree id, if the tree is the same when the run ends and the check did not time out or fill the disk. A later `check-run` on that tree answers a kept check whose command is unchanged from its result, marked `(stored: it ran on this tree before)`, and runs only the others; with none left it runs nothing and logs nothing. The kept results live in the host's memory, for one tree at a time. The CLI waits for the answer without a read timeout, as long as the queue and the checks take; the host does not exec a replaced wsx binary while a `check-run` waits, since that would close its socket unanswered. A run never starts beside the task's own running or queued one: a repeat `check-run` of the same checks (a client that gave up and asks again) joins it and gets its answer, one of other checks is refused until it ends, and one that comes while the checks after a result run is refused. The checks after a result reuse the kept results too: a check that a `check-run` ran on the same clean tree, with an unchanged command, is not run again (`stored: true`), and with none left the checks take no slot. After a rebase or a conflict fix the worker runs no `check-run` (its instructions and the conflict turn say so): the checks after its result prove the rebased tree. The worker never returns its result while its `check-run` has no answer. When it does (`done` or `blocked`), the result waits for the run to end (the task stays `working`); then the worker gets one turn with the answer, the text the CLI would print, and its next result takes the normal path. A run that ended before the result starts no turn. The checks of a result also never run beside their own earlier run: a result that comes while they wait or run (Claude's own turn for a background task's notice can answer again) is answered by that run, which records one revision; on a new commit they run once more when it ends, and after a `blocked` result they record nothing and the task keeps its wait. **Scenarios.** `tasks.scenarios` maps a name to a slower end-to-end command. A worker runs one only by naming it, `wsx task check-run web`, or by its number after the checks (the names in order); its instructions list them. It runs like a named check (the slot, the timeout, `tasks.env`, kept results), never in a bare `check-run`, after a result or in a land. wsx's own `task` scenario (`scripts/test-task.py`, 20+ min) runs on GitHub Actions instead (`.github/workflows/ci.yml` job `task-scenario`, macOS): on a push or pull request that changes `crates/wsx/src/task`, `crates/wsx-core/src/task` or `scripts/test-task.py`, and always on a release tag; the worker's build words no longer ask for it. Like the checks, the scenarios are the main checkout's config, never the working copy's. Any other argv is refused, and so is a run while the owner works by hand.

**Free disk.** Before an agent turn and before checks the host needs `tasks.minFreeGb` (default 5; wsx sets 3, see Config "Build output") free on the working copy's volume. Below it the task waits on `disk` with the reason "Disk full: <n> GB free of the <m> GB a task needs" and logs `disk_wait`; it looks again every 30 s and runs the turn or the checks once there is space, without spending a check retry. Messages that arrive meanwhile, also while the task is queued behind another, join the waiting turn and never start one of their own; during held checks they follow the checks. Tasks resume from a disk wait one at a time, so they do not fill the freed space at once: each waiting task joins the machine's disk queue (`tasks/disk-slot/`, an `flock` like the check slot), the oldest wait first. Once there is space the first one resumes and holds the disk slot for 60 s, or less when its turn or checks end sooner; the next one resumes at its next look after that, only if there is still space. A long turn never holds the queue. A task behind another keeps waiting on `disk` with the reason "queued for disk behind <project> t<id>". A check whose output says `No space left on device` waits the same way and runs again, and so does a worker that returns `blocked` while the disk is low: it is told there is space again and continues.

The worker proves what it can: its result has `evidence` (`{check, proof}`, the command or capture path) for each check a command, a test or a capture shows, and `human_verify` only for how it looks or feels: a state a fixture can stage is the worker's to prove. `report.md` has Summary (with one "Decided:" line when the worker made decisions), Changes (`base..r<k>` commits and diffstat, plus uncommitted files), Evidence ("4 checks passed", each check, then the worker's evidence), To check (the `human_verify` items) and Left open, built from the log, git and `result.json` only.

## To check

There is no verdict per task: a task the checks prove lands, and what needs a person waits in one list per project, `tasks/<project-id>/checks.jsonl`. When a task lands, its host adds the `human_verify` items of the landed revision as `{id: c<n>, task, revision, commit, check, where, capture, poster, pass_if, state: open, note, fix_task, unix_ms}` (`poster` only with a video; a row without it reads as none; `unix_ms` is when the row was written, and a read item also has `added_unix_ms`, the `unix_ms` of its first row), once per task and revision, before it sets `landed` (items of a revision whose landing conflicted are kept when the resolving turn leaves them out). The file only grows, under a lock: a later line with the same id is the item's current row.

- A worker's item is `{check, where, capture, poster, pass_if}`: what a person looks at or feels in plain words, where (a URL, a page path or the screen), the path of an image or a short video of it in the working copy (or empty), a video's thumbnail image (or empty; ignored for an image) and when it passes. At the land the host copies each capture inside the working copy, a PNG, JPEG or WebP image of at most 2 MiB or an MP4 video (an ISO BMFF file, its first box `ftyp`) of at most 25 MiB, to `captures/r<revision>-<n>.<ext>` in the task folder, and a video's poster, an image, to `captures/r<revision>-<n>.poster.<ext>`, before the copy goes; another file is dropped with a line in the pane. A worker that sends a video for an iPhone writes it with `-movflags +faststart`, so it plays before it is all read.
- A capture stays while its item is open. The manager host removes the files (image, video, poster) of an item passed, failed or skipped more than 7 days ago, the web media lifetime ([web-client.md](web-client.md) "Media"), when it starts and then hourly, under the list's lock. The row stays without its files; the web shows "Capture removed".
- An item is the worker's to prove when its check or `pass_if` holds a code span (a command) or when it has no capture and its `where` does not name a real device or real data: an item about a screen comes with a capture of that state. A `done` result with such items goes back to the worker once, in one message, before the checks and within the check retries: it stages the state in a fixture, proves it in evidence and keeps only what a person checks.

- `wsx task check` lists the open items; `show --json` has the task's items as `to_check`; the ledger counts them.
- `check pass <id>...` or `--all` marks open items `passed`; an unknown or settled id refuses the whole call.
- `check skip <id>...` or `--all` closes open items as `skipped` the same way: not passed and not failed, for an item long overdue or no longer worth a look. It starts no task, leaves the open list (so it does not hold a release) and stays `skipped` in `checks.jsonl`, `show --json` and the web.
- `check fail <id> --note <text>` starts a task titled "Fix: <check>" whose prompt holds the check, `pass_if`, the note and the original `report.md` path; the new record has `fixes: c<n>`, and the item gets `state: failed`, the note and `fix_task`.
- All three refuse with `WSX_TASK_ACTOR=manager`: checking is the owner's.
- A log line that does not parse (a last line cut by a crash) is skipped when a log is read.

## By hand

The owner can take a build over and work on it directly, with the worker's context.

1. `wsx task hand <n>` (the web's *Take over*) refuses with `WSX_TASK_ACTOR=manager`, and while the task is `checking`, `landed`, `closed` or already worked by hand. The host stops a running turn, drops queued messages, logs `hand{by: owner, dropped}` and waits on `hand`.
2. No second worktree or branch: the owner works in the task's own working copy on `wsx/t<n>`, with its warm build. `hand` opens a wsxd session `task-<n>-hand` there (one only; a second `hand` names the open one) running `claude --resume <agent_session> --fork-session --system-prompt-snapshot off`, or the login shell when the task has no conversation yet.
   - `--fork-session` copies the conversation under a new id, so the worker's own transcript stays as it was; the next `add` resumes it, and it sees the owner's commits in git.
   - Claude records a conversation's system prompt on its first request and reuses it after `--resume` until the conversation is compacted (https://code.claude.com/docs/en/cli-reference, "System prompt flags in resumed conversations"). `--system-prompt-snapshot off` rebuilds it, so the owner gets Claude's own prompt with their user settings and CLAUDE.md, not the headless worker rules. The worker's boundary, `--settings` and `--permission-mode` are launch flags and do not carry over.
   - Nothing is written into the working copy. `hand --json` gives `session` and `context`: the working copy, branch, HEAD, a short `git status` and the paths of `report.md` and `result.json` (its `memo`); `show --json` gives the same under `hand` while the task waits on `hand`.
3. While it waits on `hand` nothing else writes the copy or its conversation: `add`, `steer` and `land` are refused with a message that names `handback`; every path that starts a turn (a check retry, queued messages, a disk-wait resume) starts none; no checks run, a worker's `check-run` is refused, and nothing lands by itself. The manager reads it from the ledger and leaves the task alone. `close` keeps its rules.
4. `wsx task handback <n>` (the web's *Hand back*) refuses while tracked changes are uncommitted, and the session stays. Otherwise the host logs `handback{by: owner, commits}` (the commits after the last revision), writes a `done` result that keeps the worker's Human Verify items and memo, and runs `tasks.checks` on the next revision: the task becomes `ready` or `failed` as after a worker result, and the manager's review and the close after a land apply. A failed check is not sent back to the worker; the owner adds a message or hands again. The CLI then closes `task-<n>-hand`; the forked transcript stays in Claude's store.

## Landing

`wsx task land <n>` asks the host to:

1. refuse unless the task is `ready` (a task worked by hand names `handback`);
2. refuse when the worker left uncommitted tracked changes;
3. when the branch contains the default branch tip and HEAD has the ready revision's tree, keep its check results and go to 4; when HEAD moved past it (a child landed, see Parent tasks), run the checks as a new revision and come back to 3; otherwise rebase it there in the working copy:
   - a conflict aborts the rebase, logs `conflict{onto, paths}`, and starts a worker turn that rebases and resolves (the task is `working`); the normal checks then make it `ready`, and it lands again by itself under auto land, without a second review;
   - a clean rebase whose tree is the tree of the current revision (the default branch's changes were already in the branch), with the project's checks still the ones that passed on it, keeps that revision's check results and fast-forwards at once;
   - any other clean rebase reruns the checks as a new revision. When they pass, the land goes back to the start of 3: a default branch that moved while they ran (another task landed) is rebased onto again and checked again, without a second `land`. A failure logs `land_stopped`;
4. fast-forward the default branch: `git merge --ff-only` in the checkout that has it checked out, refused only when that checkout has changed files (tracked or new) that the land changes too, naming those files and the checkout; its other uncommitted files stay as they are (`git merge --ff-only` keeps them). wsx never stashes or commits the owner's files; `git update-ref` with the old tip as guard when no checkout has it;
5. add the To check items, log `landed{commit}` and set `landed`. After a rebase the task goes from `checking` straight to `landed`, back to `checking` or `working` when the default branch moved meanwhile, or to `ready` with `land_stopped`.

**Auto land** (`tasks.land.auto`, default `true`): the project lands without the owner's hands. A ready task the owner created, with at least one check declared and not held (see Hold and trial), no longer lands by itself on passing checks: it waits for the manager's review like a manager task, and the manager lands it without approval. Only a landing's own revision lands at once: after a conflict's resolving turn whose checks pass, the host lands from `checking` without a stop at `ready`. A landing that stops (a dirty main checkout, uncommitted work) logs `land_stopped` and leaves the task `ready`. With no checks nothing proves the work, so an owner task waits `ready` for a land by hand; so does every owner task with `auto: false`.

**Manager review.** A task the manager created (`created_by: manager`) never lands by itself. It waits `ready`, with or without checks, and so does an owner task under auto land (`TaskRecord::manager_reviews`); its event asks the manager to review: the manager reads `git -C <working copy> diff <base>..HEAD` against the owner's words and for lean code (and `tasks.workflow.review`), then runs `wsx task land <n>` or `wsx task add <n> "<what is missing>"`. The manager never sends a task back to rebase: the land rebases and checks again. The web shows such a task as working ("the manager reviews it"), not as a need of the owner.

**Land notice.** After a land on the default branch the host sends each open task that shares files with it (the ledger's `overlaps`, also through declared `--files`) a message: the landed commit, the shared files, and to run `git rebase <commit>` at its next step boundary without a `check-run`. It joins the worker's next turn, logged as an `add` message, and starts no turn: a task without a running turn or a wait (ready, checking, failed) gets nothing, as its own land rebases it.

**After a land** the host starts two detached `wsx task` commands, each in a session of its own with its output in `tasks/<project-id>/follow-up.log` (emptied past 4 MiB): `deploy --if-new` when `tasks.deploy.auto` is on (see Deploy and release), then `close <n>`, which removes the working copy, its build and the branch. The task stays `landed` (its log ends with `closed`), and the task folder and `refs/wsx/task/<n>/r<k>` stay.

## Batch land

`wsx task land <a> <b>...` lands several ready tasks, in that order, with one run of the checks. It refuses `--tried`, a role, a task named twice, one that is not ready, has a parent or is held, and a manager under `tasks.land.approve`; then the first task's host starts `wsx task land-batch` (hidden) as its own process, outside the caller's boundary, its lines in the follow-up log (`crates/wsx/src/task/batch.rs`):

1. A detached copy `<repo>-batch-<pid>` beside the main checkout (cloned like a task copy, warm build) gets each task's ready revision on the default branch tip by `git cherry-pick`, in order, and keeps the tree after each. A task that does not apply, or has nothing new, leaves the batch and lands alone after it.
2. The project's checks run once on the stacked tree, in the check slot as a land's (first in the queue), with `tasks.env` and the timeout; each prints its exit, `ms` and `queued_ms`, its output in `batch-check-<n>.log` in the project's task folder.
3. They pass: each task gets `land` with its tree (`HostRequest::Land { batch_tree }`). Its host rebases as in Landing; when the rebase gives that tree, the tasks before it are on the default branch and it fast-forwards without checks of its own. Any other tree, such as after a land between them, takes the normal path and its own checks.
4. They fail: the batch splits in halves, the first half lands first, and each half is checked the same way. A single task lands alone through `land` and its own checks, so the failing one ends with `land_stopped`.
5. The copy is cleaned and removed; the last line gives the whole time and the number of batch check runs. A copy whose process is gone is removed by the next batch.

## Hold and trial

Some work the owner wants to try before it lands: a larger piece handed over, a long branch, a change that is costly to undo. The manager tells this apart from pipeline work by judgment and holds such a task (`new --hold`, `hold <n> "<why>"`); the owner holds or releases one in the web.

- **Hold.** `hold` (one line, at most 240 characters) is on the record and in the ledger. A held task never lands by itself, also when the owner created it, and the manager lands it only on the owner's word. A held task the manager created is the owner's need, not the manager's review. `hold <n> --off` releases it; a ready task then waits for a land by hand.
- **Trial.** `trial <n>` puts a ready revision on the live site (`tasks.deploy.command`) before it lands. It refuses without a deploy command, with `tasks.deploy.public: true`, and for a manager when `tasks.deploy.approve` is on. The project has one slot, `tasks/<project-id>/trial.json` `{task, revision, commit, by, unix_ms}`, taken under `trial.lock`; a second task's trial is refused until the first ends.
  1. The host rebases the branch onto the default branch tip when it lacks it, and the checks run on the new revision (a conflict starts the worker turn that resolves it and ends the trial). The trial goes live with the revision the owner would land: the host names its commit in the slot, logs `trial{revision, commit}` and starts `wsx task deploy --trial <n>`, which records `trial: <n>` in `deploys.jsonl`.
  2. While the slot is taken, the default branch does not deploy: the `deploy --if-new` after a land answers that it waits, and `deploy` and `release` by hand refuse. Lands go on. Hosts do not follow a replaced wsx binary (see Host), because it may be the trial's build.
  3. It ends when the owner passes it (`land <n> --tried`, owner only, the web's *Pass and land*): the task lands without adding its Human Verify items to To check. It also ends on `trial <n> --end`, on an `add` (the web's *Fail* sends the owner's note this way), on `hand`, on `close`, on failed checks after the rebase and when its deploy fails. The task logs `trial_ended{reason}` and `deploy --if-new` deploys the default branch tip again.
- `deployed` and the ledger's `deploys` carry `trial`: `null`, or the slot with `stage` `preparing` (rebase and checks), `deploying` or `live` (its deploy succeeded).
- A live site cannot always roll back: a stored format, a migration or a newer daemon may stay. Such a change goes to a preview instead (see Preview). For wsx itself, `scripts/deploy-web-live.sh` replaces the binaries and restarts the web server only, so a trial runs its web and CLI against the running daemon. A `wsx daemon restart` during a trial would start its daemon, and the default branch's build cannot take that daemon back: wsxd refuses a handoff to an older build ("handoff target is not newer", checked from the dev build to 0.31.0). The terminals stay, and the newer daemon runs until a cold restart.

## Parent tasks

Long work in several steps lands on main once. Any open task becomes a parent when a child names it: `wsx task new --into <p>` (not with `--from`). A parent is one level: a child takes no children.

- **Create.** `--into` holds p ("parent of #n") when it is not held, so p lands only on the owner's word. The child starts from p's tip, its `default_branch` is `wsx/t<p>` and its `task.json` has `parent: p`. Its boundary denies the refs of p's branch and of the default branch.
- **Child land.** It lands only on a parent at rest, `ready` or `failed`; otherwise it refuses with "parent #p is busy (<state>)", stays `ready`, and p's next event names it ("children ready to land: #c") so the manager lands it again. A parent that waits on the owner, a plan, disk or the usage limit is busy too: a new revision would drop its wait. Otherwise the land rebases onto p's tip and fast-forwards in p's working copy (Landing 3 and 4), then asks p's host to check the commits: p logs `child_landed{child, commits}` and runs its checks on the next revision with a `done` result that keeps its Human Verify items and memo, as after a handback. Its close follows; no `deploy --if-new`, since main did not move.
- **Unchecked HEAD.** Any land whose branch already has the default branch tip fast-forwards only when HEAD has the ready revision's tree; otherwise the checks run first, so a parent whose host missed a child's land never lands it unchecked.
- **To check.** A child's land copies its captures into its task folder and keeps its items in its `result.json`, not in the list. p's land into main adds them under the child's number, after p's own.
- **Close or land of p** refuse while it has open children, naming them, also with `--discard`. Conflicts with main come only at p's land, as for any task.
- `parent` is in `list --json`, the ledger's open rows and the web's task summary; a parent's ledger row has `children`, the count of its open children. `overlaps` leaves out a task's own parent and children.

## Project page

`tasks/<project-id>/page.md` is the owner's one-page picture of the project: the goal, the tasks and how they relate as a mermaid graph, the plans, the decisions and the open questions. A plan longer than a few lines goes here as its own section with a mermaid diagram, and the chat reply links it. The manager host creates it with those sections when it is missing (0600; an existing page stays). The manager edits it: its instructions say to update a section in place when it changes, never to rewrite the whole file or create another page, and to call it "the project page" in a reply. Workers do not write it: their boundary denies the state folder outside their own task folder. The web client shows it ([web-client-tasks.md](web-client-tasks.md) "Project page").

## Ledger

`wsx task ledger -p <project>` prints JSON of at most 16 KiB, the manager's source of truth:

- `auto_land` and `to_check` (the count of open items);
- `open`: each open task with number, title (80 chars), state, revision, `parent` and `children` (see Parent tasks), overlaps, the Human Verify item count of its latest result, the last result summary (240 chars), `checks` (each check of the latest result as `{command, outcome: passed|failed|timed out}`, the command at most 120 chars), `waiting` (`{on, reason}`), `land_blocked_by` of a ready task (the main checkout's changed files its land would overwrite, so its Land refuses until they are committed or stashed; `[]` when none), in attention order (waiting, failed, ready, working and checking);
- `recent`: the last 10 landed or closed tasks, each with its worker's `memo` (600 chars) when it left one (the manager already got it in the task's event, see Memo);
- `deploys`: the `deployed` status, with `configured` per kind (whether its command is set);
- `routines`: the project's routines (see Routines), at most 20, each `{name, enabled, trigger, next_run_unix_ms, running, last}` with `last` the newest run's `{status, exit, unix_ms, duration_ms}` or `null`; `{error}` when the scheduler does not answer and the project has routines, `[]` when it has none;
- `main`: the main checkout's path, branch and number of changed files (tracked or new);
- `stray_worktrees`: the project's worktrees from `git worktree list` and wsxd's state that are neither the main checkout nor an open task's working copy, each `{path, branch, merged_into_main, dirty, missing, sessions}` (`missing`: the folder is gone; `sessions`: wsxd sessions there, 0 when wsxd does not answer), sorted by path, at most 20, the rest counted in `stray_worktrees_omitted`. They are cleanup candidates the manager names to the owner; nothing deletes them.

When it would pass 16 KiB, the memos are left out first, then the least urgent open tasks, counted in `open_omitted`.

## TUI

`t` in the TUI's Workspace opens the selected project's Tasks view from the same ledger (`crates/wsx/src/task_list.rs`, `crates/wsx/src/ui/tasks.rs`):

- The heading names the project with the To check count and the waiting approvals.
- `Open` lists the open tasks waiting, failed, ready, checking, then working; `Recent` the ledger's landed and closed ones. Each row is the title, the number in muted text, the state word and what it waits for (`<on>: <reason>`, or `try first: <hold>`). Below 40 columns a row drops the number, below 64 what it waits for; the title and state stay.
- `j`/`k` move, `Enter` shows the task: state, what it waits for, each check as passed or failed, its To check items, then the summary (or a closed task's memo). `j`/`k` scroll it, `Esc` goes back; `Esc` or `t` closes the list.
- While it is open the view compares the size and time of the store's files (`store::watched_files`, as the web client's watch) every second off the UI thread, and reads the ledger again only when one changed. A failed read keeps the last list and says why above it.
- An open or asked role is a row under *Roles*, after *Open*: its name, its state (`open` or `asked`) and the first line of its brief. `Enter` on an open role opens its chat as `m` opens the manager's, titled with the role's name, without To check items and approvals (see Roles).
- `S` opens a shell, an ordinary wsxd session: in the working copy of the task on the selected row or in its detail, and in the project's main checkout from the chat or an empty list. It enters a session already open there that runs no agent and no foreground job and is not the worker's own pane, else it creates one as `s` in the Workspace does (`action_task_shell` in `crates/wsx/src/app/actions.rs`). Worktree mode lists the same session. Unlike `hand`, the worker keeps running; a task without a working copy opens nothing.
- `m` in the list opens the project's manager chat (`crates/wsx/src/task_chat.rs`, `crates/wsx/src/ui/task_chat.rs`). The heading names the project with the counts; the line under it says what the last action answered, what runs ("Sending…"), what the manager does while it works (its last step, as the web's typing line) or that it is not running. The conversation is `chat_window` of `manager/log.jsonl`, newest at the bottom: owner messages ("You"), the manager's replies and other managers' messages each as the author, the time and the wrapped words; each event line written by wsx as its first clause (`#3 ready r2: <title>`), and quiet replies, new conversations and stops as one muted line; wsx's recap request is left out. `j`/`k` scroll and `G` goes back to the newest.
- Under the chat are the open To check items (id, task, check, then `pass if`, and `where` from 100 columns) and the pending approvals ("Approve land #7"), at most a third of the height. `Tab` selects one; `p` passes and `s` skips the selected item, `f` asks for a note and fails it (which starts the fix task, as `check fail`), and `y` or `n` asks "Approve land #7? y/n" or "Deny land #7? y/n" and then runs `approve` or `deny`. The footer names only the keys the selected item takes.
- `i` or `Enter` writes on the last line; `Enter` sends it as `wsx task say` does (the manager starts when it is not running), `Esc` leaves the line with its draft. A message that was not sent comes back to the line, and a failure stays above the chat until the next action. `Esc` goes back to the list.
- The chat reads the log, the items and the approvals again when a store file changed, and asks the manager host for its status every second, off the UI thread like the list; messages and decisions run off it too, one at a time.

## Manager

```sh
wsx task manager -p <project> --json             # start the manager, or report the running one
wsx task say -p <project> "<text>" --json        # or `-` or --prompt-file; returns {id} at once
wsx task chat -p <project> [--after <id>] --json # messages, replies, rotations
```

One manager per project runs as hidden `wsx task manager-host <project-id>` in a wsxd session `task-manager` in the main checkout (no working copy); `say` starts it when it is not running. Its agent uses `tasks.manager` (`model`, default `opus`; `eventModel`, default `off`; `rotateTokens`, default 150000), project and local settings only (so the MCP tools those settings allow), every tool with no prompt inside the manager boundary (see Permissions), and git reads that take no lock (`GIT_OPTIONAL_LOCKS=0`, so `git status` does not write the index). The owner's skills reach it as a plugin: before each launch the host writes `manager/skills-plugin/` (`.claude-plugin/plugin.json` named `owner`, `skills` a link to `<the profile's claude_config_dir>/skills`, else `$CLAUDE_CONFIG_DIR/skills` or `~/.claude/skills`) and passes `--plugin-dir`; the skills are `owner:<name>`. With no such folder there is no plugin and the instructions leave the skills out. User settings stay unloaded: they could add hooks, folders and allow rules. Its instructions (`manager.rs` `instructions`): the owner talks to it in a chat as to a colleague, and it answers in a few short lines, not a report; a turn of only events is its own work: it acts and replies with one line, or `-` when nothing changed for the owner, and writes more only for a decision the owner must make now; it never hands the owner chores (commands, deletes, settings, verifying a task) and does such work through a task or drops it; it starts a request for work at once and says the plan in a few lines in the same reply, and asks first only for a choice that changes what the owner gets and the owner has not made, or for large work or work costly to undo (then `--plan` or `--hold`); a longer plan goes on the project page with a mermaid diagram; `task new` gets `--title`, one `--files` per expected path or glob and a prompt that stands alone; it picks the worker by the work: a change it has read and can state exactly, with a prompt that carries the files, what they do now, the change and its proof, runs with `--model sonnet` and `--skip` for the steps the prompt already did (context, plan), while deep exploration, an unknown cause or a change to a module's design keeps the default model and every step, and a broad hunt is one read-only audit task per area that writes its findings to a file, then one task per fix; before `task new` it compares the request with the open tasks' titles and files: similar work or the same area goes to that task with `add`, and a new task is only for separate work; it never asks the owner to wait; it reviews every ready task that waits for it for the owner's words and lean code, never sends a task back to rebase, and reports checks from the ledger; it holds work the owner wants to be sure of and puts long multi-step work into one parent task (`--into`, see Parent tasks); it names the owner's message with `--owner-said <id>` when that message asks for the action (see Approvals); after a request's last task lands it starts one housekeeping task with `tasks.workflow.batch`; it handles each `waiting.on`; its one git write is the owner's uncommitted files on main after the owner's yes; it keeps notes and decisions, folds each memo, keeps the project page, and talks to other projects' managers. A running manager keeps the instructions its conversation started with until it rotates; a wsx with changed instructions starts each manager's next turn as a fresh conversation (below), which opens with its notes and decisions. Its environment is the worker allowlist plus `WSX_TASK_BROKER`, `WSX_TASK_ACTOR=manager` and `GIT_OPTIONAL_LOCKS=0`; the host puts its own `wsx` first on `PATH` and runs the commands with its own environment (see Permissions).

- `manager/log.jsonl` (rolls to `log.1.jsonl` past 8 MiB) has `message{id, from: owner|events, text}`, `delivered{ids}`, `reply{id, to, text, usage, quiet}` (`quiet` when the turn held only events and the reply is one line of at most 200 characters; the web shows it as a muted line, and a longer reply, also one stored as quiet before this rule, is a message), `agent` (its commands), `rotated{tokens}` and `stopped`. `manager/state.json` keeps the conversation, the digest of its instructions, the next id and what was already reported.
- One turn at a time. Waiting owner messages go together in one turn, each headed with its id, before waiting events.
- Events: the host checks the task records every second. A change of (state, revision) into `ready`, `failed`, `landed`, `closed` or `waiting` (not on `hand`) becomes a line written by wsx, `#<n> <state> r<k>: <title, 80 chars>; [waits on <on>: <reason>; ]checks <passed> of <total> passed; worker says: <summary, 160 chars>` (without the checks part when there are none); `landed` and `closed` add "; memo: <memo, one line, 600 chars>" when the worker left one, and `landed` adds "; <n> to check" when the landing added items. Closing a landed task keeps `landed`, so it sends no second event. A new failed deploy or release becomes `<kind> of <commit, 12> failed (exit <n>); its output ends:` and its last 10 lines, indented; a new successful deploy or release becomes `<kind> of <commit, 12> succeeded after <s> s`, so a manager that waits for one goes on (`state.json` `deploys_seen_ms` keeps the newest record seen). A routine run that ended becomes `routine <name> succeeded after <s> s`, or `routine <name> failed|could not start|was cancelled|was interrupted (exit <n>); its output ends:` and the last 10 lines of its final output, indented (`routines_seen` keeps the newest end seen, in seconds; a run is reported once its second has passed). Lines are logged as one `events` message when 3 s have passed since the last one and no turn runs, so events during a turn or close together arrive merged.
- Stalls: a task that stays in one state produces no change, so every 10 s the host also looks at each open task for a stall (`crates/wsx/src/task/stall.rs`) and reports a new one as an event line `#<n> stalled r<k>: <title>; <state> for <how long>; <evidence>`, for example `#7 stalled r2: Fix the parser; waiting on disk for 3 h 10 min; free 53.0 GB, tasks.minFreeGb is 3`. How long counts from the task's last state change. A stall seen only in the present must still be there after 60 s (two disk polls of the task host, longer than a host's exec handoff or a land's rebase holds its socket):

  | Stall | When |
  |---|---|
  | its cause is gone | waits on `disk` with at least `tasks.minFreeGb` free, or on `limit` after `until_ms`, and is not queued |
  | its queue does not move | waits on `disk`, `limit` or `check_slot` "queued for ... behind `<project> t<n>`", and that task (of any project) is not working or checking, its host does not answer, or it is silent as below. A dead holder frees its `flock` at once, so this is what stops a queue. `scripts/check-slot.py` writes its own label, so a stale task label does not count |
  | silent | working or checking without a wait, with no write to `log.jsonl` or a `check-*.log` for `tasks.checkTimeoutSeconds` plus 10 minutes: the longest a check or a background job's wait runs, plus one Bash call (Claude's maximum). The evidence names the last log entry |
  | its host is down | working, checking, or waiting on `disk` or `limit`, and its host does not answer `status` |

  Each stall has a marker (its kind with the wait's start, the holder, or the time of the last progress), and `state.json` `stalls` keeps the one reported per open task, so a stall is reported once, also across a restart; progress or a new wait makes a new stall that is reported again. A first start reports the stalls it finds. Nothing is reported while things are fine. The manager's instructions: act on it with `wsx task` (a silent worker: `stop`, then `add`), start a task that fixes wsx when the evidence shows its bug, else tell the owner in one line. The chats show it as other events (`#7 stalled`).
- Restart: `state.json` records the reported state of each task only when its message is logged, and `delivered` marks what reached the agent. A restarted host queues logged messages that were never delivered and reports changes it has not reported, so no event is lost. Its first start takes the existing tasks as they are, without events.
- Messages from another project's manager are headed `Manager <project>` (or `Manager <project> replies`) and go after owner messages and before events.
- Every turn's message ends with a ledger summary the host writes: `Ledger summary from wsx (...)`, the open tasks by state, the To check and waiting approval counts, the tasks whose (state, revision) changed since the last turn (every open task in a fresh conversation), at most 12 lines of `#<n> <state> r<k>: <title, 60 chars>`, and the last deploy when one is configured. `state.json` keeps what the last summary showed (`turn_seen`). The manager runs `wsx task ledger` only when it needs more, so a turn does not start with a 16 KiB tool result that every later call of the turn reads again.
- Model per turn: a turn of only events runs on `eventModel` while no ready task the manager created waits for its review; any other turn runs on `model`. The host switches the running process with the stream-json control request `set_model` (the SDK's `setModel`), so the conversation stays. Claude's prompt cache is per model, so a switch writes the conversation into the other model's cache: on scripts/bench-manager.py a Sonnet event turn cost a median 0.063 USD against 0.023 USD on Opus, hence `off`.
- After a reply whose context passes `rotateTokens`, the next turn starts a fresh conversation and the log has `rotated`; the ledger carries the state. The context is the last model call's (`usage.context_tokens`), not the result's sum over the turn's calls: a turn of 5 tool calls at 30k counts 30k, not 150k. Rotating on the sum made nearly every turn a fresh conversation (19 of 21 turns on the owner's log), at a median 0.32 USD a turn against 0.02 USD in a kept conversation.
- Claude keeps the system prompt a conversation began with, also on `--resume`; settings, tools and model apply at every start. `state.json` keeps a digest of the instructions the conversation began with (`instructions`). A host whose instructions differ, or a state without the digest (from an older host), starts a fresh conversation and logs `rotated{tokens: 0, reason}`.
- The first turn of every fresh conversation opens with the manager's notes: `notes/decisions.md` newest line first, then `notes/context.md`, at most 8 KiB together. After a rotation a handover follows: the last 4 owner messages and replies, each at most 600 characters, then, from the scheduler's run records, the routine results it may not have acted on, at most two lines per routine in the order of their newest run: the newest run, with the failures since the routine's last success folded into it (`routine nightly failed (exit 3); 3 failures since its last success at 2026-10-27 03:00`, or `..., never succeeded`), and, when more than that one run ended after the previous conversation's last reply, `routine <name> ran <n> times since your last reply, <k> of them without success`.

The web client shows the manager chat, the tasks, their reports and their fixed actions, and notifies about them: [web-client-tasks.md](web-client-tasks.md).

## Managers talk

A manager may reach the manager of another registered project, and nothing else of it:

- `wsx task ledger -p <other>` reads its state.
- `wsx task say -p <other> --from-manager "<text>"` sends it a message. The manager host's broker sets `WSX_TASK_FROM` to its own project, and the message is logged in the other manager's log as `message{from: "manager:<project>"}`. The sender's log gets `sent{to, text}`. The web shows both as bubbles, each manager by its name ("Config"): "<project>" in the receiving chat, "To <other>" in the sending one; a project with `tasks.manager.name` shows that name instead ("Atlas", "To Atlas"), read only from projects the site grants.
- `--reply` answers such a message (`from: "manager-reply:<project>"`). Each delivered message from a manager allows one reply to it, and a reply allows none, so no two managers answer each other in a loop.
- Every other command with `-p <other>`, and `--from-manager` to its own project, is refused by the broker. A manager creates and changes tasks only in its own project.

## Roles

A role is the manager host with a name: a persistent chat with its own brief and notes for one area, such as a long branch effort driven through a parent task, `qa` or `release`. The manager is the role that always exists. Design: [design/profiles-and-parent-tasks.md](design/profiles-and-parent-tasks.md) "C".

```sh
wsx task role new <name> --brief <file> [--owner-said <id>] -p <project> --json   # or --brief - (stdin)
wsx task role list -p <project> --json          # open, asked and closed roles, each with `running`
wsx task role close <name> -p <project> --json  # its notes and log stay
wsx task say --role <name> "<text>" -p <project> --json
wsx task chat --role <name> -p <project> --json
```

- Store: `tasks/<project-id>/roles/<name>/` holds what `manager/` holds (`log.jsonl`, `state.json`, `notes/`, `skills-plugin/`) and `brief.md`; `closed` marks a closed role. A name is a lowercase letter, then lowercase letters, digits or `-`, at most 24; `manager` is refused.
- Host: `wsx task manager-host <project-id> --role <name>` in the session `task-<name>`. `say` starts it; it leaves 20 s after its last message or turn with an empty queue, so an idle role has no agent and no pane. Its instructions are the manager's after a preamble with the brief; a new brief changes the digest, so the next turn starts a fresh conversation. Rotation, handover and notes work as for the manager. Its agent runs as `WSX_TASK_ACTOR=role:<name>`.
- Events: only the manager host watches the store. An event of a task that an open role created (`created_by: "role:<name>"`) goes to that role through `say` (from `events`), which starts its host; every other event, and one whose role is closed or whose host did not take it, goes to the manager. The recap, the idle task, approvals, deploys, routines and the project page stay with the manager.
- What a role may do: create tasks, and add, steer, stop, hold, close (not `--discard`) and land only the tasks it created, a land only of a child into its parent. `role new`, `role close`, `approve`, `deny`, `trial`, `deploy`, `release`, `close --discard` and routine add, edit, delete, enable and disable are refused to it. The manager and the owner act on every task.
- Talk: `wsx task say [--role <name>] --from-role "<text>"` from the manager or a role reaches another role, or the manager without `--role`; the message is `from: "role:<sender>"` (the manager is `manager`) and the sender's log gets `sent{to: "role:<name>"}`. `--reply` answers once, as between managers (see Managers talk).

The guard is wsx's, not the prompt's:

1. `tasks.roles.max` (default 2, at most 8) open roles besides the manager; pending requests count. `role new` past it refuses and names them.
2. The manager's `role new` is an approval request `{action: "role", role, brief}` (see Approvals): a Yes/No card in the chat, or `--owner-said <id>` when the owner's message of the running turn asked for it. The owner's `role new` opens the role at once.
3. After the owner denies a role, `role new` of that name refuses for 7 days, also for the owner.
4. A role with no log entry for `tasks.roles.closeDays` (default 14, a fraction allowed) is closed by the manager host, checked every 10 s, and by `role new` and `role list`; the manager hears `role <name> closed by wsx: ...`. 14 days, because a role exists for work over weeks and its parent task may wait on the owner for more than a week.

The ledger lists `roles`, the open and asked ones. The TUI's Tasks view lists them under *Roles*; `Enter` opens a role's chat, the manager's chat view without its To check items and approvals.

## Recap

After `tasks.manager.recapMinutes` (default `0`, off, at most 1440, a fraction allowed: `0.5` is 30 seconds) with no message and no turn, the manager host looks once; the next look waits another quiet period. It may start the idle task (see Workflow), and it logs a message from `recap` that asks the manager for a recap only when something changed since the last recap (`state.json` `recap_ms`): an event about a land, a close, a new wait, a stall or an approval decision, a new approval request, or a To check item. An owner message alone is no change. The request is fixed text written by wsx: a recap of at most 8 lines (what landed and is live, what runs, what waits for the owner and why), read from the ledger, with no task started. It ends with the token cost since the last recap, from the logs' `cost_micro_usd`: the manager's replies and the workers' results with their turn counts, and the three costliest tasks. The manager answers in an ordinary turn. The web does not show the request and tags the answer "Recap". A quiet project gets one recap, not one per period.

## Memo

Durable project knowledge moves from workers to the manager, kept small:

1. The worker's instructions: before a build finishes, put in the result's `memo` a short, lean memo of durable project knowledge a later task needs (a convention, a gotcha, a decision and its reason), a few lines at most; empty when there is none. It is kept in `result.json`.
2. The event of a task that lands or closes carries its memo (see Manager), so every memo reaches the manager when its task leaves, however many tasks leave before a rotation. The manager's instructions: in that turn, fold each memo into `manager/notes/context.md` with Bash (lean, duplicates merged, stale lines dropped, at most 60 lines); read that file when a conversation starts.
3. The ledger shows the memo on each `recent` task (see Ledger). After a rotation the fresh conversation's first message always opens with `Handover`, which asks the manager to fold the ledger's memos first, as a catch-up for one a turn missed.

A project whose skills keep knowledge in files opts in through its own words: `tasks.workflow.build` can tell workers to save it with a skill, and `tasks.workflow.idle` to consolidate it (see Workflow). wsx names no skill.

## Preview

For a project with `tasks.preview`, a person can try a task on a link. wsx configures none: a wsx change lands and deploys to the live app.

1. `wsx task preview <n>` (the manager on "try #n", the web's *Try* on a To check row and in the task sheet) answers the running preview, or starts a detached `wsx task preview-host`.
2. The preview host takes the first port of `tasks.preview.ports` that nothing listens on and runs `tasks.preview.command` with `$PORT` in its own process group: in the task's working copy, or for a landed task in a temporary copy `<repo>-preview-<n>` of its landed commit. Output goes to `preview.log` in the task folder.
3. Once `GET <ready>` answers 200 (within 180 s), it runs `tailscale serve --bg --https=<port> http://127.0.0.1:<port>` (tailnet only, port-scoped, never `reset`), writes `preview.json` `{url, port, pid, until_unix_ms}` with `url` `https://<this machine's tailnet name>:<port>/`, and logs `preview{url, port}`. With `tasks.preview.local: true`, or when no `tailscale` is on `PATH`, it runs no `tailscale` and the url is `http://127.0.0.1:<port>/`: a watch script per branch on this machine only.
4. It stops after 60 minutes, on `preview <n> --stop` (`preview.stop`), when the command exits and when the task closes. Then it turns the Serve mapping off when it made one, ends the process group (TERM, then KILL after 5 s) and removes the temporary copy after `cargo clean`. A start that fails leaves `preview.error`, which `preview` answers.

## Approvals

Approvals are only for what goes public or is lost. `tasks.land.approve` and `tasks.deploy.approve` (default `false`) and `tasks.release.approve` (default `true`) decide whether the manager may land, deploy or release alone. A `wsx task` command run with `WSX_TASK_ACTOR=manager` (the manager host sets it for its agent) that needs approval does not act: it appends `request{id: a<n>, action, task, revision, commit}` to `tasks/<project-id>/approvals.jsonl` and answers that the owner was asked. `close --discard` by the manager always asks. The ledger lists pending requests under `approvals`. An id is `a<n>` after the highest id of any line, also one this wsx cannot read, and a decision settles only the requests of its id before it: an older wsx counted only the lines it could read, gave a new request the id of a decided one (`a9`, a discard of #42 on 2026-10-25) and so hid it with no outcome.

- **The owner's words.** In a manager turn that began with an owner message, `land`, `close --discard`, `deploy` and `release` take `--owner-said <id>`, the id in that message's `Owner (message <id>)` heading, when the owner asked for that action ("close #42"). The CLI checks that the last delivered turn of `manager/log.jsonl` has no reply yet and holds that message from the owner, appends the `request` and `decision{approved: true, owner_said: <id>, outcome: "approved by owner message <id>"}`, and runs the action; a message outside the turn refuses with nothing run. Such a decision becomes no event.
- **Dropped.** The manager host drops a pending request whose task is no longer open or moved past the requested revision: `decision{approved: false, outcome: "dropped; #42 is closed"}`. The event `approval a9 (discard #42) dropped; #42 is closed` tells the manager, and the chat shows the owner "Dropped discard #42: #42 is closed".
- **In the chat.** The web shows a pending request's Deny and Approve inside the manager reply that ended the turn which asked for it, besides its reservoir row ([web-client-tasks.md](web-client-tasks.md)).

```sh
wsx task approve a3 -p <project> --json            # run the action as the owner would
wsx task deny a3 [--note <text>] -p <project> --json
```

Both refuse when `WSX_TASK_ACTOR=manager`, and so do `hand` and `handback`: the manager may tell the owner to run them. In the web a second Approve while the action runs, or after it was decided, answers what happened instead of an error. `approve` refuses a land or discard for a task that moved past the requested revision (recorded as not run; ask again). Otherwise it runs the action as its own `wsx task ... --json` command without the actor mark and records `decision{id, approved, note, outcome}`. Decisions reach the manager as events (`approval a3 (land #5) approved; done: ...`). Writers lock the file; requests are numbered under that lock.

This is a guard against the manager's mistakes, not a security boundary: the manager's tools allow every `wsx task` command, and anything running as the owner can leave out `WSX_TASK_ACTOR`. 

## Routines

A routine is `wsx routine` (README "Agent integrations and routines"): a cron or event trigger and an argv that the scheduler in wsxd runs in the main checkout, outside any task and boundary. `wsx task routine <list|show|add|edit|delete|enable|disable|run|cancel|logs|fire> -p <project> --json` is the same command for the manager, whose broker runs only `wsx task`. Run as the manager (`WSX_TASK_ACTOR=manager`), `add`, `edit` and `delete` need `--owner-said <id>`, an owner message of the running turn (see Approvals), and otherwise refuse with nothing run; the other actions need none. The scheduler that a manager's command starts runs its routines without `WSX_TASK_ACTOR`. The ledger lists them (see Ledger) without starting the scheduler. The manager host reads the scheduler's run records every second: a run that ended becomes an event, and a handover after a rotation lists the runs the manager may not have acted on (see Manager).

## Deploy and release

```sh
wsx task deploy -p <project> [--commit <ref> | --if-new] --json    # tasks.deploy.command
wsx task release -p <project> [--commit <ref>] [--owner-said <id>] --json   # tasks.release.command
wsx task deployed -p <project> --json
```

Deploys and releases of a project run one at a time under `tasks/<project-id>/deploy.lock`. A `deploy` or `release` by hand (the owner's, the manager's, an approved request's) checks what is below, takes the lock without waiting and refuses while another deploy or release runs ("a deploy or release of <project> runs"). It then starts a detached `wsx task` that holds the lock and runs the command, and answers at once: "<kind> of <commit, 12> started", with `started: true` and the commit in `--json`. So the manager's broker limit (15 minutes) does not cut a release; the result arrives in `deployed`, the ledger's `deploys` and, for the manager, as an event (see Manager). `--if-new` waits for that lock and then does nothing when the last successful deploy is already the default branch tip, so the deploys that quick lands start run once for the newest commit. With `tasks.deploy.auto: true` every land starts one (see Landing); `tasks.release` has no `auto`.

`release` refuses while To check items are open, and so does `deploy` with `tasks.deploy.public: true`, before anything runs or is asked; a deploy that is not public runs and its answer ends "<n> to check on the deployed site". Some items can be checked only on the released build, so a release the owner's own message asked for (`release --owner-said <id>`, an owner message of the manager's running turn) runs with open items, and its answer ends "still to check on the release: c34, c35". `deploy` and `release` make a temporary detached working copy of one commit (default: the default branch tip) beside the main checkout, run the command there with `/bin/sh -c` and `WSX_DEPLOY_COMMIT` (killed with its process group after 2 hours), record `{kind, commit, exit, unix_ms, duration_ms}` in `tasks/<project-id>/deploys.jsonl` (past 4 MiB it rolls over to `deploys.1.jsonl`; readers see the last MiB across both), then `cargo clean` and remove the copy. They never run in a task's working copy. A run killed before its end (a caller's timeout) leaves its `<repo>-<kind>-<pid>` copy; the next deploy or release removes, after `cargo clean`, each such detached copy whose process is gone (a worktree on a branch stays). The output is read to its end, keeping the last 8 KiB of each stream, and printed when the command ends (a run by hand prints into `tasks/<project-id>/follow-up.log`), to stderr with `--json`; a failed attempt also records it as `output` (stdout, then stderr). `deployed` gives, per kind, whether its command is set (`configured`), the last successful commit, how many default-branch commits it lacks (`behind`), how many attempts failed since (`failed_since`) and, when one did, `failed`: the newest failed attempt's `{commit, exit, unix_ms, output}` with the last 40 lines of its output (at most 4 KiB). The web's project page folds that output under the deploy line and opens it at its last lines. `scripts/deploy-web-live.sh` also writes its whole output to `.work/web-live/deploy.log` (the run before is `deploy.log.1`) and ends a failure with the step that failed. Its gate is the debug build and `scripts/runtime-smoke.py`, which holds the check slot (see Checks), then the release build and the install: a few minutes. wsx's own release is `scripts/release.sh`: it refuses a version that origin already has as a tag or that CHANGELOG.md has no section for, runs the live handoff from the newest older Homebrew release (`test-terminal-context.py --released-wsx`, in the check slot), pushes the commit to main, pushes the annotated tag `v<version>` and watches `release.yml`, which runs `ci.yml`'s tests before it builds or publishes anything, then reports the GitHub release, crates.io and the Homebrew tap. A failure ends with the step that failed. A test failure ends with "NOT PUBLISHED: tests failed": the tag is on origin but nothing is published, so fix main, delete the tag (`git push origin :refs/tags/v<version>` and `git tag -d v<version>`) and release again; `WSX_RELEASE_DRY_RUN=1` runs the checks and prints the builds, pushes and waits. The task and web end-to-end scripts are wsx's `tasks.scenarios`; its `workflow.build` tells a worker to run the scenario of each area it changed.

## Close

`close` refuses while `wsx/t<n>` has commits that are not on the default branch, unless `--discard` or the task is `landed`; a task worked by hand closes by the same rules, its hand session with the other sessions. A landed task closes itself (see Landing) and keeps the state `landed` unless `--discard`. It stops the task's preview, asks the host to close, waits for it to exit, removes the sessions of the working copy, runs `cargo clean` when the copy has `Cargo.toml`, and removes the worktree, folder and branch. `--discard` also deletes `refs/wsx/task/<n>/*`. The task folder stays as history (`list --all`).

## Config

```yaml
tasks:
  agent: { adapter: claude, model: opus, rotateTokens: 200000, rotateIdleSeconds: 3600 }
  skills: none                                                   # owner: lend workers the owner's skills (see Workflow)
  workflow: { build: "...", review: "...", batch: "...", idle: "" }   # see Workflow
  checks: ["cargo fmt --check"]
  env: { CARGO_INCREMENTAL: "0" }                                # for the worker's commands and the checks
  checkTimeoutSeconds: 1200
  minFreeGb: 5
  land: { approve: false, auto: true }
  deploy: { command: "sh deploy.sh", approve: false, public: false, auto: true }
  release: { command: "sh release.sh", approve: true }
  preview: { command: "npm run serve -- --port $PORT", ready: /health, ports: 9100-9199 }
  manager: { name: Atlas, adapter: claude, model: opus, eventModel: off, rotateTokens: 150000, recapMinutes: 0 }   # eventModel: a model or off
  roles: { max: 2, closeDays: 14 }                               # see Roles
```

`tasks.manager.name` is the name the owner reads for the manager: the web chat's author and typing bubble ("Atlas is typing"), another project's chat, the TUI row (`task-manager (Atlas)`) and `wsx task manager --json` (`name`). It is trimmed, one line without control characters, at most 64 bytes; empty is no name, and without one the manager reads as its project's name (`task-manager (wsx)`, "wsx is typing"). Inside, the manager stays `manager`: the session label `task-manager`, the provider, `WSX_TASK_ACTOR` and `from: manager:<project>`; the name is not in its instructions. The name is the manager's address for a later talk between managers by name.

Defaults: adapter `claude`, worker and manager model `opus` (`task new --model` overrides the worker's), no extra tools, no owner skills, the default workflow words, no checks, `minFreeGb: 5` (0..=100000), `deploy.auto: false`, no preview (`ready` defaults to `/`, `ports` to `9100-9199`, above 1023, `local` to `false`). An old `tasks.sandbox`, `tasks.agent.tools` or `tasks.manager.tools` is an unknown key. Up to 64 checks and 64 scenarios (a name starts with a letter, then letters, digits, `-` and `_`); `checkTimeoutSeconds` is 1..86400; a model is at most 256 bytes and a check 16 KiB. `task new` refuses a config that does not parse or has a known key of the wrong type or value. An unknown key, at any level, is ignored: a wsx older than the file still lands, deploys and starts tasks. One warning names the file and up to 8 key paths (`tasks.env`, `futureTop`); a CLI command prints it on stderr, a task host, a manager host or the web server prints it once in its log, and the TUI shows it as the project notice. There is no typo matching. `tasks.env` holds up to 64 variables: a name is letters, digits and `_` (not first a digit), never `PATH`, `GIT_EDITOR` or `WSX_*`, which wsx sets; a value is one line of at most 16 KiB.

**Build output.** `tasks.env` is set, as the task had it at `task new`, for the worker (on top of the kept environment, see Claude adapter) and for every check, by the host and by `check-run`, so the checks reuse the worker's build. It is not set for a `hand` session, a preview, a deploy or `close`'s `cargo clean`. A Rust project keeps one build folder per working copy, cloned from the main checkout (see Working copy). wsx sets `CARGO_INCREMENTAL: "0"`, and its `Cargo.toml` sets `[profile.dev] debug = "line-tables-only"` for the main checkout and every copy alike: an incremental build names its objects by rustc session and never removes the old ones, and line tables keep the file:line of a panic and of a test's backtrace (`RUST_BACKTRACE=1`) in a smaller build. A clone shares main's blocks until main's next build or `cargo clean` replaces them; then they are the copy's own. So `task new` does not clone `target/<profile>/incremental`, which a copy never reads, and after each run of checks, the host's and a `check-run`'s, the host prunes `target/*/deps` (`crates/wsx-core/src/task/build.rs`): a unit (`<name>-<hash>`) older than the copy whose name the copy has built since, such as main's units of other settings (main builds incrementally, so its workspace crates have other hashes), and in each unit the objects of all but its newest rustc session. On macOS the dev profile keeps a binary's `.rcgu.o` files beside it for its debug info, so they pile up there. A wrong guess costs a rebuild: cargo rebuilds a unit whose output is gone. Measured on wsx (2026-10-29, 3 rounds of `cargo build -p wsx -p wsx-daemon` and `cargo nextest run --workspace --no-run` after a `wsx-core` edit; unique is the free space `cargo clean` gives back):

| copy | du | unique | first round | later rounds |
|---|---|---|---|---|
| before: all of main's target cloned, no prune | 19 GB | 0.76 GB; the other 18 GB become the copy's own as main's builds replace them | 42 s | 32 to 33 s |
| full debug info, pruned | 2.5 GB | 0.78 GB | 39 s | 31 to 33 s |
| line tables, pruned (wsx's setting) | 1.8 GB | 0.92 GB | 49 s | 28 to 32 s |
| cold build without a clone, line tables (other tasks were building) | 1.1 GB | 1.1 GB | 103 s | |

The debug level is part of cargo's artifact hash: as `CARGO_PROFILE_DEV_DEBUG` in `tasks.env` (up to 0.41.0) it gave a copy's dependencies other hashes than main's, so every copy compiled them again. In `Cargo.toml` main builds the same units, and a copy reuses the clone of them; `CARGO_INCREMENTAL` does not change a dependency's hash, since cargo never builds a dependency incrementally. A debugger that needs local variables builds with `CARGO_PROFILE_DEV_DEBUG=full`. For wsx, `minFreeGb: 3` is one task's whole build with margin. Do not share one `CARGO_TARGET_DIR` or `build.build-dir` between copies: cargo (1.93) gives a workspace crate the same file name in every checkout and keeps source paths relative, so a copy whose files are older than another copy's build reuses that build and runs the other copy's code (measured with wsx: a 3 s "fresh" build without the copy's own change), and parallel builds wait on the folder's lock.
