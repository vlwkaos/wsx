# Web client chat

The chat panel of the hosted web client ([web-client.md](web-client.md)): a remote chat with one session's agent.

- Sending uses the exchange broker (`docs/agent-orchestration.md`): one exchange per pane, continued round by round. For an idle or done Claude the draft-stash variant is used, so the owner's unsent input is not merged into the message.
- The page shows the broker's evidence in plain words. `pty_delivery` is "typed into the agent's terminal; the agent has not confirmed it". Only `request_bound` is shown as confirmed.
- The transcript is the provider's own saved conversation (`wsx_core::integration::memory`). Terminal output is never read into chat. A sent message that is not in the saved conversation yet is shown as pending.
- A message wsxd could not deliver says so on the pending message, with wsxd's reason (the exchange's `failure`, for example `editor_stash_unconfirmed`), and **Retry** sends it again. A waiting message whose delivery fails stays in the queue, failed with that reason; it is never dropped.

# Timeline

`GET api/chat/<session>/timeline` answers `{session, status, truncated, model, items, from, exchange, queue, working, question, screen}`. `model` is the model named by the newest saved record that names one (Claude and Pi: each reply; Pi: a `model_change`; Codex: each `turn_context`), or `null`; the session's top row shows it after the state. A model switch shows once the provider saves it, for Claude with the next reply. With `?from=<item id>&at=<its at_unix_ms>` the items start at that item when it is still in the timeline with the same time, and `from` names it; otherwise `from` is `null` and `items` is the whole timeline. The page asks from its last user message: items before the start of that turn do not change. On a 200 KB conversation this cut each read from about 215 KB to 16 KB.

| Item field | Content |
|---|---|
| `id` | stable between reads: the record id, or the tool call id |
| `kind` | `user`, `assistant`, `tool`, `thinking`, `summary` |
| `at_unix_ms` | the record's own time, when it has one |
| `text`, `attachments` | for `user` and `assistant` items; `text` for a `summary` |
| `tool` | `{name, title, status}` for a `tool` item; `status` is `running`, `ok` or `error` |

- One parser, two projections: `Reader::read` (messages, used by `wsx agent context`) and `Reader::read_timeline` come from the same parsed records. Bounds: the last 1 MiB of the file, 4096 records, then the newest 400 items and 256 KiB. When the conversation goes on before that MiB and it holds no message the person wrote (a long turn of tool results), the read goes back 4 MiB, then 16 MiB. When the chain of the conversation goes on before that MiB, the read goes back 4 MiB once: the first turn after a Claude compaction (1 to 3 MiB in real transcripts, 2026-10) pushes the summary and the records it kept out of the newest MiB while the person's message is still in it, and the summary vanished from the chat. On 2026-10-26, 14 of 226 Claude and 6 of 1304 Codex transcripts on one machine needed it; 2 had the person's last message more than 16 MiB back.
- `title` is one line from the call's input: its `description`, else `command`, else `file_path` or `path`, else the tool name, at most 120 characters. The input itself, the tool result and the text of a thinking part are never sent. A `thinking` item says only that thinking happened.
- Records a provider writes in the person's name are left out: Claude `isMeta` records, its "[Request interrupted by user" notice, a command's output (`<local-command-stdout>`, `<local-command-stderr>`), and (Claude Code 2.1.300) records with `promptSource: "system"`, such as a `<task-notification>` when a background task ends. Claude's next answer says what the task did, so the page shows no line for it. The person's own prompts are `typed`, `suggestion_accepted`, `queued` or `sdk`; a record without `promptSource` (older Claude) is the person's unless one of the other rules applies. A slash command that Claude runs itself, such as `/compact`, is saved as `<command-name>`, `<command-message>` and `<command-args>` tags; the timeline shows it as typed (`/compact`, or `/name args`). A `!` shell line is saved as `<bash-input>` with the text after `!` (Claude Code 2.1.304); the timeline shows it as typed (`! git status`), and its output (`<bash-stdout>`, `<bash-stderr>`) is left out like a command's: Claude's next answer says what it printed. Also seen on 2026-10-15, unchanged: a message from another session is `system` and `isMeta`.
- A call with no result is `running` only in the last turn (after the newest message a person wrote). An older call without a result is `ok`.
- Records are untrusted: ids and names are clipped and control characters removed.
- The conversation is the chain of parents from the newest record. Claude Code 2.1.302 to 2.1.310 saved a `deferred_tools_record` attachment whose parent it never saved (3 of 226 transcripts on 2026-10-26; one showed nothing). Where an attachment's parent is missing, the chain goes on at the record saved before it; any other missing parent ends the chain.
- Claude 2.1.300 keeps the newest records through a compaction: its `compact_boundary` record names them in `compactMetadata.preservedSegment` (`headUuid` to `tailUuid`, after the summary `anchorUuid`). The timeline shows them right after the summary, as Claude's model sees them. On 2026-10-15 a `/compact` kept the last answer.
- Compaction: the newest summary is one `summary` item where the compaction happened (Pi keeps the earlier records in the same file; Claude starts a new chain, so its summary is first). A summary older than the kept items is the first item. It keeps up to half the byte budget. Claude's fixed words around it ("This session is being continued from a previous conversation … Summary:" and the closing "If you need specific details from before compaction …" instructions, which name a local transcript path) are removed. Pi's summary starts with its content; a Codex `compacted` record seen on 2026-10-15 had no text.
- The page shows a summary as "Summary of the earlier conversation" with a line at its start, whole.
- Formats read (checked against real sessions on 2026-10-12): Claude `tool_use`, `tool_result`, `thinking` parts; Pi and omp `toolCall`, `thinking` parts and `toolResult` messages; Codex `function_call`, `custom_tool_call`, their `_output` items and `reasoning`. A Codex result has no error flag, so a Codex call is never `error`.
- `working` is `null`, or `{since_unix_ms, activity}`. It is set only while wsxd reports the agent as working; the transcript never decides that. `activity` is "Compacting the conversation" while Claude compacts: a `/compact`, an automatic compaction inside a turn, or an idle one between turns ([agent-reporting.md](agent-reporting.md) "Claude compaction"), else the title of the running tool, else "Thinking", else "Working". `since_unix_ms` is when wsxd saw the state begin, or `null` with an older wsxd.
- The `history` event is the change signal. While an agent works and a page is open, the server compares transcript stamps about every 0.8 seconds, so a new tool line shows within about a second.
- The page shows a message it sent from the send's own answer, before it reads the chat again. A read that fails (the network, the device's request budget) is read again after 2 s: before, the chat kept its old state until another change came, which at the end of a turn may be never, so the answer showed only after a reload.
- A blocked agent shows a provider dialog. The chat refuses to send a message into it. With `chat_answer` the page shows the dialog and sends keys ("Answering"); without it the answer is given in the terminal panel or on the host.
- `screen` is `null`, or the last 8 rows of the terminal above Claude's editor box (its borders, the editor and the footer under it are left out; a screen without that box gives its last 8 rows) when something holds the chat that it cannot name: a blocked agent with no readable `question`, or a message that has waited in the queue for more than 10 s. Only a site with `terminal_view` gets it. The page shows "The terminal shows:" with the rows and **Open terminal** where the composer or the attention row was.

# Following the end

The session chat and the manager chat share one rule (`useFollowEnd` in `crates/wsx-web/web/lib.js`):

- A reader within 80 px of the end stays at the end. Only scrolling up leaves it: content that grows under a reader at the end is followed, also when it grows between the page's own scroll and its scroll event. A reader farther up is not moved; "Jump to latest" shows instead, or "↓ 3 new" while replies below it were not read. Only that button and the reader's own send go to the end.
- The log watches its own box and each of its rows. A row that grows after it shows (a diagram that draws, an image that loads, an entry animation), a row added or removed, and a box that moves or changes size (the "Since you left" line above it, the reservoir or the keyboard below it) settle the view before the browser paints: at the end it stays at the end; farther up, the first row that starts in view keeps its distance from the top of the screen.
- The row's position is its layout position (`offsetTop` in the positioned `.log`), so a transform in an entry animation does not count as a move.
- Chrome and Firefox also anchor the scroll with CSS (`overflow-anchor`); iOS Safari does not. The log's own anchor runs after the browser's and decides: where the browser already kept the row in place, it finds nothing to move. The anchor is not the row cut by the top edge: when that row grows inside, the part the reader sees is below the growth and moves with the next row.
- Checked in a real browser (`scripts/test-web-client.py --browser`): a session whose diagrams draw after it opens stays at its end at 320, 390 and 1280 px; in the manager chat at 390 and 1280 px a late diagram keeps the end, a reader scrolled up keeps the bubble in view within 2 px through a reply below, the "Since you left" line above and rows added and removed above, with CSS anchoring on and off; on a phone the composer with the keyboard up keeps the end.

# Opening a chat

Each device keeps, per chat (`wsx-read` in local storage, the newest 200 chats), the time of the newest reply that was on a visible screen and where the reader left the chat: the first named row in view and its distance from the top, or the end.

- With replies newer than that time, the chat opens with a "New" line over the first of them, the line at the top of the screen. Without, it opens where the reader left it, or at the end. A chat opened for the first time on a device opens at the end with nothing unread.
- A reply is read once its end was on screen while the page was visible, so a long reply opened under the line counts as new until the reader reaches its end. Replies are the agent's messages in a session, and the manager's, other managers' and workers' bubbles in the manager chat; the owner's own messages and status lines never count.
- The place is kept when the chat closes and when the page goes to the background, so a phone that drops the page keeps it too. Rows are the log's children: `data-key` names a row, `data-in` and `data-at` mark a reply and its time (`useFollowEnd` in `lib.js`).

# Replies

Both chats: a swipe right on a message (64 px, on a touch screen), or a long press (450 ms) or a right click and **Reply**, puts its first line (its own quote left out, at most 120 characters) over the composer with × to remove it. The menu also has **Copy**, since a long press on a message does not select its text on a touch screen. The sent message starts with `> <that line>` and an empty line. The page shows such a message's quote as one muted line; a tap on it scrolls to the newest message above it that starts with that line, or says that the message is no longer in the conversation shown. `#` and `@` stay in the manager chat only (`web/reply.js`).

# Markdown

An agent's message and the summary of an earlier conversation are rendered as CommonMark with GFM tables, strikethrough, task-list marks and autolinks. The person's own messages and waiting messages stay plain text.

- `web/markdown.js` asks markdown-it only for its token list (`html: false`) and builds the page's nodes from it. No HTML string made from a message reaches the DOM, so no sanitizer library is needed: raw HTML in a message is shown as text, and an attribute or a tag can only come from this file.
- A link is made only for `http`, `https` and `mailto`, and opens in a new tab with `rel="noopener noreferrer"`. Any other scheme and a relative address stay text. Text becomes a link by itself only when it has a scheme, so `main.rs` is not a link.
- A message cannot load a remote resource. An image is shown only when its file name is one of the files the server already granted for that message ([web-client.md](web-client.md) "Media"); any other image is its alt text. A tap on a shown image, or on an attached one, opens it in the image viewer with the message's other images ([web-client.md](web-client.md) "Image viewer").
- Prose keeps its reading width. A table, a code block and a diagram may be as wide as the conversation minus the gutter (16 px each side in the default theme), centered on the reading column; a narrower one keeps the column's width. The page reads the conversation's width as a container size (`container-type` on `.log-wrap`), so no script measures it. Content wider than that scrolls inside its own block: a code block sideways with a Copy action, a table sideways only, at its full height. Nothing widens the page.
- On a phone a table is as wide as its block and its cells wrap their words, so only a word that cannot wrap (a long path or code) scrolls it sideways. A table of more than three columns keeps the first two as columns; each further value is a line "Header: value" in the second cell, so nothing is left out. A wide screen is unchanged.
- Code is colored by highlight.js for rust, typescript, javascript, python, bash, json, toml, yaml, diff, html, css, sql and go. The page reads the highlighter's token tree and uses the theme's role colors (accent, attention, muted, danger), so no color is added to the theme contract. Blocks above 40,000 characters stay uncolored.
- A message is parsed once per text. A timeline refresh that brings the same text reuses the nodes. Measured in headless Chrome with the processor slowed four times: a 204 KB message with 145 code blocks takes about 0.2 seconds.
- Task text (the task sheet, the manager chat's bubbles and the project page) is read as prose: markdown-it's indented-code rule is off there, so a paragraph that a model indented by four spaces stays a paragraph. A fenced block (```) is still code. A session's chat keeps the rule.
- markdown-it 14.3.2 (125,451 bytes, 44,975 gzip, MIT) and highlight.js 11.11.1 with those 13 grammars (71,996 bytes, 22,705 gzip, BSD-3-Clause) are vendored by `scripts/vendor-markdown.sh` with pinned SHA-512 values. markdown-it is the published browser file, unchanged.

# Diagrams

A fenced block with the language `mermaid` is drawn as a diagram (`web/diagram.js`).

- Mermaid 11.17.2 is vendored by `scripts/vendor-mermaid.sh` (pinned SHA-512, MIT). It is 3,572,508 bytes, stored and served gzip-compressed as `assets/mermaid-11.17.2.js` (975,905 bytes, `Cache-Control: immutable`). A request that does not accept gzip answers 406.
- The page imports it when the first diagram appears. It is not in the service worker's shell list, so installing the page does not download it. The service worker keeps it after the first use, so a diagram also draws offline from then on.
- The CSP is unchanged. Mermaid must draw into the page to measure text, and it writes inline styles, which the CSP refuses. Three things replace that: the vendoring step moves the diagram's CSS from a `<style>` element to a constructed style sheet that the page adopts while drawing; while drawing, a `style` attribute that Mermaid sets goes through the CSSOM; and the vendoring step leaves out Mermaid's last DOMPurify pass over the finished SVG, because that pass parses every style attribute and the CSP reports each one.
- The finished SVG is never inserted as markup. It becomes an image from a `blob:` URL, which `img-src` already allows. An SVG image runs no script, follows no link and makes no request, which is what the left-out pass protected. Mermaid runs with `securityLevel: "strict"` and `htmlLabels: false`; labels are still sanitized by Mermaid.
- Colors and the font are the theme's tokens, read when the diagram is drawn. A diagram is drawn again when the device changes the scheme. Up to 40 drawn diagrams are kept by scheme and source, so a timeline refresh does not draw again.
- The whole diagram shows first: it is scaled down to the width of its box (the conversation minus the gutter) with its shape kept, centered, and never scaled up. When that would make its text smaller than 10 px, a flowchart drawn left to right (`flowchart LR` or `RL`, or `graph`) is drawn again top to bottom, as Pygmalion does in the terminal; when that one fits it shows with the line "Drawn top to bottom to fit this screen". Otherwise the diagram stays larger and scrolls sideways in its own block, with a fade on the side that holds more. A tap opens it in the image viewer ([web-client.md](web-client.md) "Image viewer").
- A block that does not parse, or a source above 20,000 characters, shows its source as a code block with the line "Diagram could not be drawn".

# Answering

wsxd knows that an agent is blocked, not what it asks. The question is the dialog the agent drew on its terminal. With `chat_answer`, the page shows that dialog and sends the keys the person chooses. No provider dialog is modelled: this works for any agent that wsxd reports as blocked.

- The timeline's `question` is `null` unless the agent is attached and blocked and the site has `chat_answer`. Else it is `{screen, stamp, options, request}`.
  - `screen`: the pane's screen up to its last written row, as plain text: at most 24 rows and 4 KiB, without control characters. It is read with the daemon's `view` request, like `wsx session peek`. `src/question.rs` is the only code of the web server that reads a screen.
  - `options`: `[{key, label}]`, one generic rule: a row that starts, after a box edge and an optional cursor mark, with `1.` to `9.` and a label. Only the last list that counts up from 1 is taken, so a numbered list in the agent's earlier text is not offered. Empty when no such list is on the screen.
  - `request`: `{name, title}` of the tool call that waits, when the saved conversation ends with one. The title is the same line as a step's. For a tool that asks a question (Claude's `AskUserQuestion`) it is the question text.
  - `stamp`: a hash of `screen`.
- `POST api/chat/<session>/answer` takes `{stamp, key}`. `key` is `1` to `9`, `enter`, `escape`, `up`, `down`, `tab`, or `text` with a `text` field of at most 2000 characters (typed, then Enter, without control characters).
- The server refuses unless the site has `chat_answer` (403), the agent is still blocked (409 `not_blocked`), and the screen read at that moment has the same stamp (409 `question_changed`; the page reads the question again). It takes the pane's terminal lease with a takeover for the one write, so a wsx window or a terminal panel that holds the pane loses it and says that control moved, like Stop. The lease is taken before the stamp is checked, so nobody types between the check and the write. Answers share the message rate limit.
- Named keys go through the daemon's key request, so they are encoded for the pane's keyboard mode. Text goes as one write.
- While a page is open, the server reads the stamp of each blocked session on every poll (about every 0.8 seconds) and raises `history` when it changes, so a dialog answered or moved elsewhere shows on the page.
- The page puts a question sheet where the composer was: the request title, the screen rows in the terminal font (the block scrolls; box drawing never wraps), one button per choice, then Enter, Esc, the arrows, "Type an answer" and "Open terminal". No choice is preselected or filled. After an answer the sheet says "Sent" and takes no further answer until the screen or the state changes.
- Limits: a choice is a key press in the agent's dialog, so it means what that dialog means at that moment; the stamp binds it to the screen that was read. wsxd reports "blocked" for Claude (permission dialogs and `AskUserQuestion`) and for agents whose integration reports it. Codex is not reported as blocked, so its dialogs do not reach the chat.

# Sessions without routine prompts

`agent_command` is the whole command line of a session started from the page; every argument is passed on. The intended shape for Claude is:

```toml
agent_command = ["claude", "--permission-mode", "auto"]
```

In auto mode a second model, the classifier, reviews Claude's actions instead of the person, so routine edits and commands run without a dialog. The prompts that remain, such as a question to the person or an action the classifier does not decide, arrive in the chat through "Answering". The flag and the mode name were checked against `claude --help` of Claude Code 2.1.296. Claude starts in manual mode instead when auto mode is not available to the account.

# Commands

Typing `/` at the start of the composer opens the agent's commands above the field. A note about the list (no match, only built-in commands, wsx too old to run a command) is one muted line at the end of the list's own box. On a phone each command is two lines, its name and source, then its description on one muted line; when less than 560 px is visible (the keyboard is up, or a short screen) the list keeps to 3.5 rows so part of the conversation stays in view. Typing filters it: names that start with the text first, then names that contain it. The arrows move, Tab or Enter picks (on a touch screen a tap), Escape closes it until the text changes. A pick fills the field with `/name ` and sends nothing. While the field starts with a listed `/name`, that name shows as one token in the accent color (an overlay behind the transparent field, so typing, IME, paste and the caret are the field's own). Backspace right after it removes the whole `/name`; the rest stays plain text. The text the agent gets is unchanged.

- `GET api/chat/<session>/commands` answers `{provider, listed, commands, truncated, skipped, runs}`; each command is `{name, description, source}` with `source` `builtin`, `project`, `user` or `plugin`. It needs `chat_send` (403 without it).
- Built-ins, from each provider's own documentation: Claude `compact`, `clear` (Claude Code commands reference; `/new` and `/reset` are aliases of `/clear`); Codex `compact`, `new` (Codex CLI slash commands); Pi `compact`, `new` (Pi 1.1.0 `docs/slash-commands.md`). Other providers have none listed.
- Claude (`listed: true`) adds skills (`skills/<name>/SKILL.md`) and commands (`commands/<name>.md`, one folder level as `folder:name`) from the session worktree's `.claude/`, from `$CLAUDE_CONFIG_DIR` or `~/.claude/`, and from each enabled plugin (`plugins/installed_plugins.json`, `enabledPlugins` in the settings) as `plugin:name`. The project's command wins over a user's of the same name. Other providers answer `listed: false`, and the list says that only built-ins are shown.
- Only the name and one line of description leave the server: frontmatter `name` and `description` (a folded block joined), else the first line of the text, folded to at most 160 characters. Bounds: 200 commands (`truncated`), 512 entries per folder, 64 plugins, the first 8 KiB of a file, 256 KiB of a settings file, names of at most 64 bytes of letters, digits, `-`, `_`, `.` and `:`. A file with unterminated frontmatter, invalid UTF-8 or an invalid name is counted in `skipped`.
- Shell lines: to a Claude session, a message without attachments that is one line of at most 256 bytes starting with `!` and a command (`! git status`) is sent with `command: true` too, so Claude enters its `!` shell mode. Checked on a live Claude Code 2.1.304 pane on 2026-10-21: the pasted line ran and Claude answered in a turn of its own, so the round ends like any other. Not for Pi, whose `!` and `!!` start no turn, so the round would wait until its deadline, nor Codex, whose documentation names no `!`. `!` alone or a line with a second line is a message. While the draft is such a line, the composer's border takes the attention colour and its button reads *Run* (accessible name "Run in the shell"). Against a daemon without `exchange_shell` the server answers 409 `daemon_upgrade_required`.
- Sending: a message without attachments whose one line starts with a listed `/name` is sent with `command: true`, so wsxd types it as written ([agent-orchestration.md](agent-orchestration.md) "Commands"). Any other text, such as `/usr/bin is the folder` or a command with a second line, keeps the exchange line. Against a daemon without `exchange_command` the server answers 409 `daemon_upgrade_required` (`runs: false`, and the list says so). A command sent while the agent works waits in the queue like any message.

# Conversations

The chat belongs to the session, not to one agent process.

- The server remembers the conversations each session's agent reported (`provider` and `session_ref`, the newest 10 per session, in `queue.json`). The session view's `conversation` says one is remembered; the page then keeps the Chat tab after the agent is gone, and the timeline reads the last remembered conversation when the pane has no agent.
- When the agent exits (it reports itself detached, or its pane loses it), the conversation gets the line "Claude exited.". The composer then reads "Message · resumes the conversation".
- A message to a session whose agent exited types the provider's resume command for the remembered conversation (`claude --resume <id>`, `wsx_core::integration::resume::plan`), after Ctrl+U, into the pane's shell, and waits in the queue until the agent reports; the line is "Resumed Claude in the same conversation.". It is refused when the pane's program ended, when the shell runs another program (`pane_activity`), and when the provider has no resume plan. An agent that does not report within 60 s fails the message with `resume_failed`. A send within that minute does not type it again.
- An agent that comes back to the same conversation by other hands (the person in the terminal) gets the line "Same conversation, continued"; another conversation in the pane gets "New conversation", and a full timeline begins with the last 60 items of the conversation before it, their ids prefixed `earlier-`, so it stays readable above the line.

# Queue and Stop

wsxd allows one active exchange per pane. Every message from the page goes through the web server's queue: the server delivers the oldest waiting one at once when the agent can take it, keeps it until the agent has it, and sends it again once when the agent did not take it ([agent-orchestration.md](agent-orchestration.md) "Taken, not typed").

- At most 5 messages wait per session. They are saved in `queue.json` in the site state directory (owner-only) and survive a restart of the server. A sixth message answers `queue_full`.
- A send, a Send again and the event observer deliver the oldest waiting message that did not fail, one delivery at a time, when the agent is attached and neither working nor blocked and wsxd accepts it. A message to a blocked agent is refused (`agent_blocked`): its question is answered first.
- "Not yet": `agent_busy`, `exchange_busy`, `editor_unavailable` (Claude draws its editor idle a moment after the turn ends), `daemon_unavailable`, `daemon_replacing` and `revision_conflict` (the exchange changed between the read and the delivery, as a receipt does). The message stays and is tried again at least every 800 ms. After 30 s of "not yet" it fails with that reason.
- Any other refusal, for example `write_claim_conflict` while another writer works in the worktree or an attachment that expired, and a delivery that fails (`delivery_failed`), mark the message failed with the reason. A failed message stays in its place with **Send again** (`POST api/chat/<session>/queue/<id>/retry`, delivered at once when the agent can take it) and **Remove** (`DELETE api/chat/<session>/queue/<id>`), but it does not hold back the messages after it, and a new message to an idle agent is sent at once. Order rule: waiting messages go oldest first, past any failed one; a retried message goes next in its old place.
- A delivered message stays in the queue, marked `delivered_unix_ms` with the exchange round that carried it, until the agent has it. An agent can drop a paste: on 2026-10-21 Claude lost a message typed into it the moment its turn ended. With an agent that reports prompt receipts (Claude), the server reads that round before every delivery: taken, the message stays until the conversation shows it, and leaves when the round is over also when its words never show (a compaction). Claude's prompt hook reports the turn before Claude saves the prompt, so a message that left at the receipt was missing from the chat until the prompt was saved; not taken (`not_taken`), it is sent again once, by itself, and the conversation gets the notice "Sent again: Claude did not take it the first time."; not taken a second time, it fails with "Claude did not take this message". Without receipts it leaves when the saved conversation shows its text, saved after the delivery (a person message with the same words from before does not count). A delivered message holds nothing back and does not count toward the 5; at most 3 are kept per session, oldest dropped first. The page shows it at the end of the conversation as a sent message, with **Copy** and **Send again**.
- Notices: what the server did by itself for a session's chat, such as a message sent again, is kept in `queue.json` (the newest 20 per session) and placed in the timeline as items of kind `notice` before the first item saved after them; the page shows each as a muted line.
- Every waiting message, and a sent message the conversation does not show yet, has **Copy** (the browser clipboard; "Copy failed" when the browser refuses). On a waiting message the actions are icons with their names as titles (Copy, Send again, Remove), so its words keep the row.
- **Send now** (`POST api/chat/<session>/queue/<id>/steer`): while Claude works, a waiting message can go into its turn. wsxd types it into Claude's input line ([agent-orchestration.md](agent-orchestration.md) "Steer"), and Claude takes it at its next step. The message is then delivered without a round and leaves the queue when the conversation shows it. A refusal (the input line has text, the turn ended) is a 409 with wsxd's reason, and the message keeps waiting.
- The page shows a failed message above the composer, its reason in words on a line of its own in the danger color.
- `POST api/chat/<session>/send` answers `{"queued": {...}, "exchange": {...} | null}`: the message's queue entry, and the exchange it went out in when it was delivered at once. The queue is the `queue` field of the timeline, and every change raises the `history` event.
- A queue belongs to one site. Another site's queue for the same session is not visible.
- Stop (`POST api/chat/<session>/cancel`) asks wsxd to interrupt the turn ([agent-orchestration.md](agent-orchestration.md) "Cancel"). Like a send, it takes the pane from a terminal that holds it ([agent-orchestration.md](agent-orchestration.md) "Terminal control"). After a stop, waiting messages are delivered as usual; a cancelled exchange is not continued, the next message starts a new one.
