# Web client tasks

The web side of manager mode ([tasks.md](tasks.md)). The server reads the task store and talks to the task hosts and the manager through `wsx_core::task` (`crates/wsx-web/src/tasks.rs`); the browser only names a project id, a task number and its text. Every route checks the chat panel, the capability and the grant; a project outside the grant, an unknown task and an unknown action answer 404.

| Route | Needs | Answer |
|---|---|---|
| `GET api/tasks` | `task_view` | the overview of every granted project |
| `GET api/tasks/<project>` | `task_view` | overview: `needs`, `working`, `to_check` (the count of open items), `tasks` (chips and the `#` picker with `stage`, at most 200), `decisions` (last 5), `resolutions`, `last_reply` (the manager's last reply, at most 120 characters, or `null`), `busy` (the manager's turn runs; the home row shows typing dots), `last_unix_ms` (the latest task change or manager entry, or `null`) |
| `GET api/tasks/<project>/t/<n>` | `task_view` | record, `stage`, `land_reason` (ready), `result`, `denials`, `asks`, `checks`, `report` (`report.md`), `waiting`, `conflict` (a turn resolves a landing conflict), `talk`, `timeline`, `overlaps` with paths, `to_check` (its items), `fixes` (the item it fixes), pending `approvals`, `actions`, `landed_commit`, `deploy` (`configured`, and whether the last deploy has the landed commit, `deployed`, and its `behind`), `hold`, `trial` (the project's trial when it is this task's, with `stage`) |
| `GET api/tasks/<project>/chat?after=<id>` | `task_view` | manager messages, replies, rotations and stops after `after` (at most 200), `running`, `busy`, `activity` |
| `GET api/tasks/<project>/brief` | `task_view` | the project's ledger ([tasks.md](tasks.md) "Ledger"), for the project brief |
| `GET api/tasks/<project>/since?after=<ms>` | `task_view` | task numbers that `started`, `landed`, `blocked`, `conflict` or were `revised` after that time, and the count of `replies` |
| `POST api/tasks/<project>/say` `{text}` | `task_act` | `{ok, id}`; starts the manager when it does not run |
| `POST api/tasks/<project>/t/<n>/<action>` | `task_act` | `add {text}`, `steer {text}`, `allow {host | path, project}` (one ask; `project` keeps it for every task; no tool rules from the web), `land {}`, `pass {}` (a land of a passed trial), `hold {text?}` (default reason "the owner holds it"), `unhold {}`; the host's `{ok, state, message}`. `hand {}`, `handback {}`, `trial {}` and `trial_end {}` run `wsx task hand|handback|trial [--end]` without `WSX_TASK_ACTOR` and answer its JSON (docs/tasks.md "By hand", "Hold and trial") |
| `GET api/tasks/<project>/checks` | `task_view` | `{open}`: the open To check items with their task's `title` and `did` (the worker's first sentence when it is not the title) |
| `GET api/tasks/<project>/checks/<id>/capture` | `task_view` | the item's kept capture as its image; 404 when it has none |
| `POST api/tasks/<project>/checks/<id>/pass`, `.../checks/all/pass`, `.../checks/<id>/fail` `{note}` | `task_act` | runs `wsx task check ...` without `WSX_TASK_ACTOR`; its JSON (`changed`, `open`, `message`); a refusal is a 409 |
| `POST api/tasks/<project>/approvals/<id>/approve` | `task_act` | 202 at once; the action runs as `wsx task ...` without `WSX_TASK_ACTOR`, and its outcome is the decision in the next overview |
| `POST api/tasks/<project>/approvals/<id>/deny` `{note}` | `task_act` | `{ok}` |

- Three states for the owner: `stage` is `working` (working, checking, or waiting on `hand`), `needs_you` (waiting on the owner, a permission or disk, failed, ready) or `done` (landed); the store's states stay in the record. A task is `ready` only when it did not land by itself: its landing stopped, it has no checks, or `tasks.land.auto` is false. A ready task the manager created waits for the manager's review, so its `stage` is `working` and it is not a need ("the manager reviews it"), unless it is held: a held task is the owner's need. The overview carries `try_live` (a deploy command that is not public) and `trial` (docs/tasks.md "Hold and trial"); a task row carries `hold`.
- `needs` is in this order: `waiting`, `failed`, `approval`, `land` (ready, with `reason`: "could not land: …", "try it first: <hold>", "no checks; land by hand" or "ready to land"; a task the manager reviews is not a need). Within a kind the oldest comes first. A working or done task is not a need. A waiting item has `waiting` (`{on, reason}`), the worker's `denials`, and its `asks` when it waits on `permission`; it reads "#4 needs to reach crates.io", "#4 waits for disk space" (it goes on by itself), "#4 stopped" or "#4 needs an answer". An approval item has `label`, the action it asks for in words (`Approve land #3`); the task's pending `approvals` have it too.
- `resolutions` is what was settled, newest first, at most 30, each `{unix_ms, task, text}`: from the logs of the 30 tasks changed most recently within 7 days ("#1 got an answer" for a message after a block, "#4 may reach crates.io (owner)", "#4 may write ~/.cargo, every task (manager)", "#5 was closed", "#5 was closed and discarded"), from the decisions in `approvals.jsonl` ("Approved land #3", "Denied discard #4") and from failed To check items ("#3 failed a check; #9 fixes it"). A landing is the worker's "done" bubble, not a line; old `verified` entries say nothing.
- `actions` lists the buttons a state has: working and checking `steer add`, waiting on a permission `add allow`, ready `land add trial`, failed and other waits `add`, waiting on `hand` only `handback`; an open task that is not checking or worked by hand also has `hand` (*Work by hand*, *Hand back* in the sheet; a task by hand is under *Running* as "by hand"); an open task has `hold` or `unhold`; none without `task_act`. The host still decides: its refusal is a 409 with `refused` and its reason, and a host that does not answer is a 409 `host_not_running`.
- Limits: a message or note is at most 64 KiB, a tool 256 bytes without control characters, a fail needs a note. Actions share the message rate limit. A landing waits for the host for at most 300 s. A second approve of a request whose action still runs is a 409.
- The timeline is the task log with each run of agent progress lines folded into one `steps` entry (count and last line); the last 300 entries.
- The manager's session is created with the server's own daemon client, which never starts wsxd.
- Events: the observer stats each granted project's `task.json`, `log.jsonl`, `result.json` and `report.md` files, `manager/log.jsonl` and `approvals.jsonl` on every poll. A change sends `tasks` (the project's overview, only when it changed), `task {project, task}` for each task whose files changed, and `manager {project}`.

# Home

`crates/wsx-web/web/home.js`, `#/` with `task_view`. One row per granted project: the name, a count of its needs, one status line, "N working" while tasks run, and the time since its last activity: the newer of `last_unix_ms` and the newest `state_since_unix_ms` of its listed agent sessions (task workers and the manager are not listed). The status line is the most urgent need in words ("#1 needs an answer", "Approve land #3", "#2 is ready to land"); else its agent sessions when one needs input, ended in an error, exited or works ("claude in main exited", "2 working"); else "5 to check" while To check items are open; else the manager's `last_reply`; else its other agent sessions ("claude in main done 5m ago", "2 idle"); else "Nothing needs you", or "No tasks yet" when the project has neither a task nor an agent session ("Loading…" until its tasks are read). One session is named by provider and branch, more are counted. Projects with needs come first, by their most urgent kind in the `needs` order and then by their oldest need of that kind; the rest follow by their last activity, newest first. A row opens the project screen. The Sessions tab beside Home opens `#/sessions`.

# Project screen

`crates/wsx-web/web/tasks.js` and `bubbles.js`. From the top: the top row (back, the project, the manager's state only when it matters: "typing" while its turn runs, "stopped" after it stopped; `⋯` with *Page*, *Sessions* (`#/p/<project>/sessions`) and *Files* where granted), the chat, the reservoir and the composer.

- Messages are bubbles: the owner's on the right, the manager's and the workers' on the left, each with its author (the manager's name, `manager.name` of the chat route: `tasks.manager.name`, else "Manager"; "#3 worker"; another project's manager by its name in `peers` ("Manager <project>" unless that project sets one), with "Reply" on its answer; the owner's has none; the manager's answer to a recap request is tagged "Recap", and the request itself is not shown, [tasks.md](tasks.md) "Recap") and its time. What this manager sent another one is its own bubble tagged "To Manager <project>" (or "To <name>") ([tasks.md](tasks.md) "Managers talk", "Config"). Consecutive bubbles of one author within 5 minutes group: the author once, the time on the last. A bubble shows whole ([web-client.md](web-client.md) "Screens"); a table, a code block or a diagram scrolls inside its bubble.
- An events message (written by wsx) becomes, for each line that carries a worker result (`landed`, `ready`, `failed`, `waiting`), a bubble by "#n worker" with the header `#n · <status>` (`done` for a landing, `ready`, `failed`, or the worker's own status of a wait, such as `blocked`) and the summary of the result logged before the message; the chat route adds these as `reports`. Every bubble shows the whole summary. Every other line is a muted status line in short form ("#4 waiting", "Approved land #3"), and so is each of `resolutions` and each owner grant to the manager ("Allowed by the owner: the manager writes <path> until <time>", [tasks.md](tasks.md) "Permissions"); a line for a task that has a bubble in the same message is not shown. A line that a resolution says too shows once; lines less than a minute apart join with " · " ("#2 ready · #4 ready").
- `#<n>` in any text is a short chip: the number on the baseline of the text around it and a state dot centered in it, its `stage` in its accessible name ("#3, needs you") and the title on hover (a task without `--title` is named by the first sentence of its latest worker summary, [tasks.md](tasks.md) "Store"); it opens the task sheet. The words "project page" in a reply link to the page. A working task has a pulsing dot (still under reduced motion).
- Each message is a bubble with its box, author and time. The owner's are on the right, up to 88% of the column. The manager's and the others' use the whole column, a small gap short of its right edge; code blocks, tables and diagrams stay inside the box.
- While the manager's turn runs (`busy`), a "<name> is typing" bubble ("Manager is typing" without a name) with three dots ends the chat; the dots pulse only without reduced motion. A sent message shows until the log has it.
- The reservoir, pinned over the composer, is the decision list: the one place for what waits for the owner, what runs and what is left to check. Closed it is one line: "2 need you", then the newest running task (the highest number) with its pulsing chip and its title cut with "…", then "+N more" for the other running tasks, then the open To check items ("2 need you · #6 Fix the login +1 more · 5 to check"). With nothing open, running or to check there is no reservoir: the chat goes down to the composer. Done tasks are not in it. A tap opens the list: each item that waits for the owner in the server's order, one row each with its chip, its title, what it waits for ("needs to reach crates.io", "no checks; land by hand") and its one action as an icon with its name as the title, so the title and what it waits for keep the row: *Allow* (one grant per ask; *Allow for project* is in the sheet), *Answer* (a field; an add) for a waiting or failed task, *Deny* and *Approve* for an approval (after Approve the row reads "Running…" until the decision settles it, and a second Approve, also from another device, answers what happened instead of an error), *Land* for a ready task. A held ready task has *Try live* before *Land* when the project has `try_live` and no trial runs; while its trial goes live the row reads "Going live…", and once live it reads "on the live site: try it" with *Fail: tell the worker* (a field; an add, which ends the trial) and *Pass and land*. After a success the overview is read again, the row leaves, and the focus moves to the next row's first action (to the closed line when none is left, to the composer when the reservoir goes), so the owner clears the list one row after another; a failure keeps the row, its draft and its error. Under the items, *Running*: one row per working task with its chip and title in the closed line's small size, the rows close together, "resolving a conflict" or "by hand" when it is one. Last, "5 to check", which opens the To check list. The list is at most 40% of the chat and scrolls inside itself; with the keyboard up it steps aside while the `#` or `/` list is open. Nothing moves the chat: it stays at the newest message unless the owner scrolled up.
- A chip or a row opens the task sheet over the chat. The chat does not scroll: there is no jump to where a task first came up.
- The composer has attach at the left, like a session's chat: the files upload at once, Send waits for them, and the message carries their paths under the attachment header. `#` at the start of a word in the composer opens the task picker in the box of the `/` list: the open tasks in attention order, then the rest, each with its number, title and state; digits or words filter it. Arrows, Tab or Enter (a tap on a touch screen) pick, Escape closes; a pick puts `#n ` in the field and sends nothing. Enter sends on a hardware keyboard; the draft is kept on the device per project.

# Project page

`#/p/<project>/page` opens `tasks/<project-id>/page.md` ([tasks.md](tasks.md) "Project page") in the sheet over the chat (`page.js`): markdown with mermaid diagrams, task chips, and "Updated <time> ago" in the top row. Above the markdown: the deploy and the release with their commit and how far behind, and the main checkout's branch and uncommitted files (`ProjectFacts` in `story.js`), read from the ledger when the page opens and at most every 2 s while the overview changes. `GET api/tasks/<project>/page` (`task_view`) answers `{text, unix_ms}` (`null`s before the manager first started); the observer stats the file and sends `page {project}` when it changes, and the open page reads it again.

# To check

`#/p/<project>/checks` opens the project's To check list ([tasks.md](tasks.md) "To check") in the sheet over the chat (`checks.js`): what only a person can check of the landed tasks, oldest first, each with its task chip, what the task did (its worker's first sentence, else its title), the check, "Passes if …", "Look at …" (a link when it is a URL or a page path), the kept capture (`GET api/tasks/<project>/checks/<id>/capture`, a link to the full image), and *Fail* and *Pass* as icon buttons at the row's top, with *Try* before them when the project has `tasks.preview` ([tasks.md](tasks.md) "Preview"): it starts the preview and becomes *Open*, a link to it. The sheet is as high as its rows, at most 85%, on the bottom of the visible screen. *Fail* opens a note field (required); the fail starts a task that fixes it, and the chat says "#3 failed a check; #9 fixes it". *All passed* passes every open item. The list reads again when the overview's `to_check` changes. Without `task_act` it shows the items only.

# Task sheet

`#/p/<project>/t/<task>` opens the task over the chat in a modal `<dialog>` (`Sheet` in `tasks.js`, which also holds the project page): 85% of the visible height from the bottom with a drag handle on a phone, a panel of twice the rail width at the right from 900 px. Back in its top row, the browser's Back, Escape, a tap on the backdrop and a swipe down of more than 80 px on the handle or the top row close it. The composer keeps its draft and gets the focus back. The sheet's content is `crates/wsx-web/web/task.js`. The top row has back ("Back to the chat"), `#n`, the title and the stage. It has no link to the worker's terminal: `wsx task show <n> --json` names the worker's log. Then, in one scroll container:

1. The top (`TaskStory` in `story.js`): the first sentence of the worker's summary (*More* shows the whole summary and a "Decided:" line), and one sentence of what the owner should know next when it matters, with the task's actions (2.) beside it as normal-size buttons that wrap under it on a narrow screen ("The worker waits for you to let it reach crates.io, or to answer.", "No checks prove it, so it waits for you. Land it to put it on main.", "On main; the last deploy does not have it yet"). A pending approval of the task comes first: "The manager asks: Approve land #3."
2. The one action the state allows, as buttons only and only with `task_act` (an approval's label shows when the task has more than one): a pending approval with *Deny* and *Approve*; *Allow* and *Allow for project* for a task waiting on a permission; *Land* for a ready task; *Try live* for a held ready task when the project has `try_live` and no trial runs; for its trial a status line ("Going live: …", "On the live site now: …"), *Pass and land* once live and *End trial*; *Work by hand* or *Hand back*; *Try* when the project has `tasks.preview`; *Hold for me* or *Release hold*. A held task shows "Held for you to try: <reason>" above the buttons.
3. The report (`report.md`), folded: Changes, Evidence ("· 4 checks passed"; open for each check and the worker's evidence), To check ("· 2 open": the task's items with *Pass* and *Fail* once it landed, the items it will add before), Left open. Its summary is the top; sections of older reports (Asked, Decisions, Human Verify) are not shown. No revision number shows, except on an item of an older revision than the task's.
4. The messages to the worker as bubbles: each add or steer after the prompt.
5. Shared files, only while a turn resolves a landing conflict: each other open task that changed a path this one changed, with up to 20 of the paths.
7. *History*, folded: one line per log entry with its time and what happened in words; agent progress is one line per run of steps.

Text on the sheet, in the chat bubbles and on the project page is markdown read as prose ([web-client-chat.md](web-client-chat.md) "Markdown"). *Session* opens the worker's terminal.

A message field stays at the bottom while the state takes one: *Send* is an add ("Answer the worker" when it waits on the owner), and while the worker runs *Steer now* sends into the turn and *Add* after it. The draft is kept on the device per task. An action's outcome is a notice; a failure is shown above the field and keeps the draft. The sheet reads again on a `task` event for it and when the project's approvals change.

# All sessions

With `task_view` the inbox is `#/sessions`, the Sessions tab, titled *Sessions*, and lists no task workers or manager. The Projects screen (no tab with `task_view`) lists every project; its list adds "N need you" after a project's session count, and a project opens its worktrees.

# Task notifications

A device that picks "A task needs me" in Settings (topic `tasks`, offered with `task_view`) gets two kinds of Web Push, decided by the event observer from the task records and `approvals.jsonl`:

| Change | When | Text |
|---|---|---|
| a task starts waiting (not on `hand`), a new approval request | once `merge_seconds` passed since the first of them; later ones in that window go in the same push | `#4 waiting · Approve land #5` |
| a task becomes `ready`, `failed` or `landed` | one digest once `digest_quiet_seconds` passed without another, at most `digest_max_seconds` after the first | `2 ready (#5, #6) · 1 landed (#3)` |

- Batches are per project; the title is `<site>: <project>`. A push about one task opens its task sheet, any other its project. A change is counted by its (state, revision); a project first seen after a server start notifies nothing, and working, checking and stopped never notify.
- No push goes to a device while one of its pages shows that project (any `#/p/<project>` route) and is visible. The page opens its event stream as `api/events?page=<id>` with an id it chose, and `POST api/presence {page, project}` tells the server the project it shows (`null` when hidden or elsewhere). The presence of a page ends with its last stream; a page id belongs to the device that opened it (404 for another device's or an unknown page).
- "Since you left": the device records when it left a project's screen (route change or hidden page). On opening it again, or coming back to it, more than a minute later, the screen asks `since` and shows one line, "Since you left: #2 #3 landed · #1 blocked · 2 replies", with *Dismiss* beside it on the same line (a long list is cut with an ellipsis). The line goes by itself once the newest reply that came while the device was away has been on screen, or when the owner sends a message. Nothing runs while the device is away; the line is computed from the logs.
- Limits: a batch waits while `wsxd` is unavailable, because the observer runs with the daemon's long-poll. Push text is written by wsx, never by the manager.
