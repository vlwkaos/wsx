# Web client tasks

The web side of manager mode ([tasks.md](tasks.md)). The server reads the task store and talks to the task hosts and the manager through `wsx_core::task` (`crates/wsx-web/src/tasks.rs`); the browser only names a project id, a task number and its text. Every route checks the chat panel, the capability and the grant; a project outside the grant, an unknown task and an unknown action answer 404.

| Route | Needs | Answer |
|---|---|---|
| `GET api/tasks` | `task_view` | the overview of every granted project |
| `GET api/tasks/<project>` | `task_view` | overview: `needs`, `working`, `to_check` (the count of open items), `check_items` (the open items, oldest first, each `{id, task, check, pass_if}`; the reservoir's To check rows), `tasks` (chips and the `#` picker with `stage` and `status`, docs/tasks.md "Status", at most 200), `decisions` (last 5), `resolutions`, `last_reply` (the manager's last reply, at most 120 characters, or `null`), `news` (`{unix_ms, text}` of the newest reply that is not quiet or To check item, or `null`), `asks` (the open questions, oldest first, each `{id, unix_ms, quote}`, [tasks.md](tasks.md) "Questions" under "Manager"), `busy` (the manager's turn runs; the home row shows typing dots), `manager` (its name, [tasks.md](tasks.md) "Config"), `last_unix_ms` (the newest owner-facing activity: `news`, an owner message, or a task entering its current state (`state_unix_ms` of its record); not a record save or a manager `agent`, event or quiet entry; or `null`) |
| `GET api/tasks/<project>/t/<n>` | `task_view` | record, `goal` (the prompt's opening paragraph), `progress` (an open task: `steps`, `step`, `stuck`, `last_unix_ms`, `now` `{line, said}`, `running`; `null` once finished), `stage`, `status` (docs/tasks.md "Status", with whether it is stuck and deployed), `land_blocked_by` (ready), `result`, `denials`, `checks`, `report` (`report.md`), `waiting`, `conflict` (a turn resolves a landing conflict), `talk`, `timeline`, `overlaps` with paths, `to_check` (its items, each with `capture_removed: true` once its capture is removed), `fixes` (the item it fixes), pending `approvals`, `actions`, `landed_commit`, `deploy` (`configured`, and whether the last deploy has the landed commit, `deployed`, and its `behind`), `hold`, `trial` (the project's trial when it is this task's, with `stage`) |
| `GET api/tasks/<project>/chat?after=<id>[&find=<words>][&around=<id>][&role=<name>]` | `task_view` | `rows`: the chat after message `after` (at most 200 log entries), or with `find` from the oldest entry that shows the words, or with `around` 200 entries from 40 before message `around`, over every rolled log file (`rows` hold it, or the newest part when the id is not in the log) ([tasks.md](tasks.md) "Log window"), as `wsx_core::task::chat::chat_rows` classifies it, the TUI's rows too: each `{kind: message\|line\|quiet\|note, key, id, unix_ms, author: owner\|manager\|peer:<project or role:name>, name, tag, quoted, quoted_id, text, quote, task, asks, post, level, approvals, provisional, danger}`, an owner message with its `attachments`; `asks`, the ids of the open questions (also of rows an earlier read brought); `running`, `busy`, `activity`; the manager's adds `roles`, the open roles as contacts `{name, brief, last_reply, last_unix_ms}`; with `role` the open role's chat (404 when it is not open) |
| `GET api/tasks/<project>/routines` | `task_view` | `{routines}` (at most 100), read from wsxd's scheduler as `wsx task routine list --json` does, without starting it: `name`, `enabled`, `trigger` (the cron, or `event:<kind>`), `command` (argv, at most 40 words of 200 characters), `running`, `last` (`{status, exit, unix_ms, finished_unix_ms, duration_ms, message}` or `null`; `message` is the id of the events message that told of the run's end, or `null`: the run printed nothing, so it made no message, or the log no longer holds it) and `next_run_unix_ms` (or `null`); `{routines: [], error}` when the scheduler does not answer |
| `POST api/tasks/<project>/routines/<name>/<run\|enable\|disable>` | `task_view`, `task_act` | starts the routine now, or turns it on or off (the scheduler's edit, as `wsx task routine enable\|disable`); answers the list as the `GET` does. 404 for a routine or project that is not there, 400 for another verb, 409 when the scheduler refuses (a routine that already runs); the message budget of the other task actions applies |
| `GET api/tasks/usage[?period&who&agent]` | `task_view` | the spend of every granted project, summed (`{today, week, days, total, agents, projects, limits}`; "All projects" below) |
| `GET api/tasks/<project>/usage[?period&who&agent]` | `task_view` | one project's spend for the usage sheet (the overview carries no usage) |
| `GET api/tasks/<project>/page` | `task_view` | `{text, unix_ms, cut}`: the project overview file, cut to 60 lines and 4,000 characters (`null`s before the manager first started) |
| `GET api/tasks/<project>/brief` | `task_view` | the project's ledger ([tasks.md](tasks.md) "Ledger"), for the project brief |
| `GET api/tasks/<project>/since?after=<ms>` | `task_view` | task numbers that `started`, `landed`, `blocked`, `conflict` or were `revised` after that time, and the count of `replies` |
| `GET api/tasks/<project>/mentions` | `task_act` | `{skills: [{name, description, source}], truncated, projects: [{id, name, manager}]}`: the owner's skills (same bounds as the session chat's commands) and the other granted projects, `manager` null when no name is set |
| `POST api/tasks/<project>/say` `{text, role?}` | `task_act` | `{ok, id}`; starts the manager, or the open role `role`, when it does not run |
| `POST api/tasks/<project>/t/<n>/<action>` | `task_act` | `land {}`, `pass {}` (a land of a passed trial), `hold {text?}` (default reason "the owner holds it"), `unhold {}`; the host's `{ok, state, message}`. The owner sends a worker nothing from here: `add` and `steer` are `wsx task` commands the manager runs, and these routes answer 404 for them. `hand {}`, `handback {}`, `trial {}` and `trial_end {}` run `wsx task hand|handback|trial [--end]` without `WSX_TASK_ACTOR` and answer its JSON (docs/tasks.md "By hand", "Hold and trial") |
| `GET api/tasks/<project>/checks` | `task_view` | `{open, items}`: `open` the open To check items, `items` every open item and the newest 100 in all, for the chat's bubbles; each with their task's `title` and `did` (the worker's first sentence when it is not the title), and `capture_size` (`[width, height]` of a PNG capture or poster, else `null`) |
| `GET api/tasks/<project>/checks/<id>/capture` | `task_view` | the item's kept capture, an image or `video/mp4`, with `Accept-Ranges: bytes`: one `Range` is answered 206 with `Content-Range` (iPhone Safari plays a video only so), a range past the end 416; 404 when it has none or it was removed; with `?download=1` it carries `Content-Disposition: attachment; filename="task-<n>-<id>.<ext>"` (the viewer's Download), else it stays inline |
| `GET api/tasks/<project>/checks/<id>/poster` | `task_view` | a video capture's poster image, the same way; 404 when it has none |
| `POST api/tasks/<project>/checks/<id>/pass`, `.../checks/all/pass`, `.../checks/<id>/skip`, `.../checks/all/skip`, `.../checks/<id>/fail` `{note?}` (the web's *Fail* sends none and only closes the item; a note also starts the fix task, as the CLI does) | `task_act` | runs `wsx task check ...` without `WSX_TASK_ACTOR`; its JSON (`changed`, `open`, `message`); a refusal is a 409 |
| `POST api/tasks/<project>/asks/<id>/dismiss` | `task_act` | runs `wsx task dismiss <id>` without `WSX_TASK_ACTOR`: the question asks no more; one that is not open is a 409 |
| `POST api/tasks/<project>/approvals/<id>/approve` | `task_act` | 202 at once; the action runs as `wsx task ...` without `WSX_TASK_ACTOR`, and its outcome is the decision in the next overview |
| `POST api/tasks/<project>/approvals/<id>/deny` `{note}` | `task_act` | `{ok}` |

- Three states for the owner: `stage` is `working` (working, checking, or waiting on `hand`), `needs_you` (waiting on the owner, disk or limit, failed, ready) or `done` (landed); the store's states stay in the record. A task is `ready` only when it did not land by itself: its landing stopped, it has no checks, or `tasks.land.auto` is false. A ready task the manager created waits for the manager's review, so its `stage` is `working` and it is not a need ("Ready, waiting for the manager's review"), unless it is held: a held task is the owner's need. The overview carries `try_live` (a deploy command that is not public) and `trial` (docs/tasks.md "Hold and trial"); a task row carries `hold`.
- `needs` is in this order: `waiting`, `failed`, `approval`, `land` (ready; a task the manager reviews is not a need). Within a kind the oldest comes first. A working or done task is not a need. Each task item has the task's `status`; a waiting item also has `waiting` (`{on, reason}`) and the worker's `denials`. An item reads `#<n> <status label>`: "#4 Waiting for your answer", "#4 Waiting for disk space", "#4 Stopped", "#3 Ready, waiting for you to land it". A task waiting on `limit` sends no notification. An approval item has `label`, the action it asks for in words (`Approve land #3`); the task's pending `approvals` have it too.
- `resolutions` is what was settled, newest first, at most 30, each `{unix_ms, task, text}`: from the logs of the 30 tasks changed most recently within 7 days ("#1 got an answer" for a message after a block, "#5 was closed", "#5 was closed and discarded"), from the decisions in `approvals.jsonl` ("Approved land #3", "Denied discard #4", "Dropped discard #4: #4 is closed") and from failed To check items ("#3 failed a check; #9 fixes it"). A landing is the events line "#3 done"; old `verified` entries say nothing.
- `actions` lists the buttons a state has: ready `land`, waiting on `hand` only `handback`; an open task that is not checking or worked by hand also has `hand` (*Take over*, *Hand back* in the sheet; a task by hand is under *Running* as "Waiting for you to hand it back") (hold and trial stay manager commands, with no buttons); none without `task_act`. The host still decides: its refusal is a 409 with `refused` and its reason, and a host that does not answer is a 409 `host_not_running`.
- Limits: a message to the manager is at most 60 KiB, a note 64 KiB, a tool 256 bytes without control characters, a fail needs a note. Actions share the message rate limit. A landing waits for the host for at most 300 s. A second approve of a request whose action still runs is a 409.
- The timeline is the task log with each run of agent progress lines folded into one `steps` entry (count and last line); the last 300 entries.
- The manager's session is created with the server's own daemon client, which never starts wsxd.
- Events: the observer stats each granted project's `task.json`, `log.jsonl`, `result.json` and `report.md` files, `manager/log.jsonl` and `approvals.jsonl` on every poll. A change sends `tasks` (the project's overview, only when it changed), `task {project, task}` for each task whose files changed, and `manager {project}`. Only a task's own `log.jsonl` (a worker's progress lines) is read without the overview; a change of the manager's log reads it, since a turn changes `busy` and `last_reply`. The server keeps each project's built overview while the stamp of those files and the settings it reads are unchanged (at most 60 s, for the words that count minutes), so `GET api/tasks[/<project>]` and the observer share one build; `busy` is read from the manager on every call. `resolutions` reads the last 256 KiB of each recent task's log. A chat call with `after` reads the last 256 KiB of the manager's log and the whole log only when that tail lacks the `after` entry. `WSX_TRACE_READ_LOG=1` prints one stderr line per whole-log read (the web scenario counts them).

# Home

`crates/wsx-web/web/home.js`, `#/` with `task_view`. One row per granted project: the name, a count of its needs, one status line, "N working" while tasks run, and the time since its last activity (renewed each second while a task or session works, else each minute): the newer of `last_unix_ms` and the newest `state_since_unix_ms` of its listed agent sessions (the order below uses the same time) (task workers and the manager are not listed). The status line is the most urgent need in words ("#1 Waiting for your answer", "Approve land #3", "#2 Ready, waiting for you to land it"); else its agent sessions when one needs input, ended in an error, exited or works ("claude in main exited", "2 working"); else "5 to check" while To check items are open; else the manager's `last_reply`; else its other agent sessions ("claude in main done 5m ago", "2 idle"); else "Nothing needs you", or "No tasks yet" when the project has neither a task nor an agent session ("Loading…" until its tasks are read). A project whose chat has a message this device has not read (a manager reply that is not quiet or a To check item, the overview's `news`, newer than what the chat marked read here, the same mark as the chat's "↓ N new") has an accent mark before its name and that message's first line under the status line; opening its chat and seeing the message clears it. A chat never opened on the device has nothing new. While the overview's `asks` holds, the project's name is in the accent (with "Asks you" for a screen reader), as the asking bubble's border is in the chat. One session is named by provider and branch, more are counted. Rows order as in a messenger: projects with needs come first, by their most urgent kind in the `needs` order and then by their oldest need of that kind; then projects with an unread message (the mark above), newest message first; the rest by their last activity, newest first, so a busy worker or manager that says nothing to the owner moves no row. The project whose chat this device shows (the rail beside it) counts as read at once: a message arriving there does not mark it. A row opens the project screen. The Sessions tab beside Home opens `#/sessions`. Where the site manages projects, Home's top row has a *+* that adds a project and each row slides left to remove it ([web-client.md](web-client.md) "Screens", *Projects*).

Each open role of a project is a row of its own under the project's row (`RoleRow` in `home.js`, `overview.roles`, the same contacts as the `⋯` menu: `name`, `last_reply`, `brief`, `news`), indented one step: a dot while the role's `news` is newer than this device read in that chat, the name, and under it the line of its last reply, else its brief. It opens `#/p/<project>/r/<role>`; on a wide screen the row of the open room is the current page and the project's is not. A role row has no Remove, no count and no time, and it follows its project in any order.

# Project screen

`crates/wsx-web/web/tasks.js`, `task-words.js` (stages, status words, chips) and `bubbles.js`. From the top: the top row (back, the project, the manager's state only when it matters: "typing" while its turn runs, "stopped" after it stopped; the shell icon where the site shows the terminal and grants `session_start` and `terminal_input`: it opens the project's shell in the terminal panel, the same session as the TUI's `S` ([tasks.md](tasks.md) "TUI"), through `POST api/projects/<project>/shell`, which answers `{session_id}` of the live shell or of a new one; `⋯` with *Sessions* (`#/p/<project>/sessions`), *Usage* (`#/p/<project>/usage`), *Files* where granted and the open roles), the chat, the reservoir and the composer. Between the manager's state and `⋯` sits an icon-only button, with an `aria-label` and a `title`: *Overview* (`#/p/<project>/page`). The project's routines are the fourth pill in the composer row, not a header button. The `⋯` menu does not list Overview again.

- Messages are bubbles: the owner's on the right, the manager's on the left, each with its author (the manager's name, `manager.name` of the chat route: `tasks.manager.name`, else the project's name; another project's manager by its set name, read only from granted projects (its project's name unless that project sets one), with "Reply" on its answer; the owner's has none; the manager's answer to a recap request is tagged "Recap", and the request itself is not shown, [tasks.md](tasks.md) "Recap") and its time. What this manager sent another one is its own bubble tagged "To <name>" ([tasks.md](tasks.md) "Managers talk", "Config"). Each speaker with a name has its own color on that name, never on its bubble: this manager, another project's manager (one color per project) and the muted wsx lines ([web-themes.md](web-themes.md) "Tokens"). Consecutive bubbles of one author within 5 minutes group: the author once, the time on the last. A bubble shows whole ([web-client.md](web-client.md) "Screens"); a table, a code block or a diagram scrolls inside its bubble.
- The chat is the owner and the manager talking. Each event of an events message (written by wsx) is its own muted, left-aligned status line in the short form its host wrote (`short`: "#4 waiting", "#3 done", "Approved land #3"), and so is each of `resolutions`; the page reads no event text; a worker's report is in the task sheet, not the chat. Only a line's leading task number is a chip; a task number later in a line is plain text. A manager reply marked `quiet` (its turn held only events, or only replies of other managers or roles, and it is one line of at most 200 characters, [tasks.md](tasks.md) "Manager"; a longer reply, with a table, a list or paragraphs, is a bubble) is a muted line of its own under the manager's name, which shows once for quiet replies in a row; it shows whole when it is one sentence or line, else its first sentence and *More*, which shows the rest. It is never cut inside a sentence, its task numbers are plain text, and it never joins an event line. When the agent's usage limit holds the manager's turn, wsx writes a `limit` entry: the chat shows it as a muted line like an event line, "<name> paused: usage limit, resumes at 07:45", and "<name> resumed" when the held turn continues; the typing bubble stays off while it is paused. Holds that repeat fold in `chat_rows`, so the page and the TUI agree: a run of stops of one reason with nothing shown between them is one note, "<name> stopped 3 times: <reason>; next try 10:11", with the newest time and the danger color, and a run of pauses alone is one line, "<name> paused 3 times: usage limit, resumes at 10:11" ([tasks.md](tasks.md) "Manager"). While the manager is held, an owner message it has not taken into a turn comes as a row with `queued` after the other rows (`waiting_ids`); the page leaves it out of the conversation and lists it in the same waiting queue as a session chat has (`ul.queue` of `li.queued`, its words cut to one line), above the composer, with no action; a turn that takes it makes it a bubble at its place, and a read after the last row brings it again until then. A reply of `-` or nothing reads as quiet ([tasks.md](tasks.md) "Manager") and shows nothing, and one that carries an approval request stays a bubble; a `sent` with no text shows nothing either. A reply that asks the owner (`asks`, never quiet) has a thin accent border on its box ("Asks you" in its aria-label) while it is an open question (the chat route's `asks`): an owner message that quotes it or, with no quote, the newest one before it answers it, and a dismiss closes it ([tasks.md](tasks.md) "Questions" under "Manager"). A reply that wsx posted, with no agent turn (`post`: what `wsx task digest`, `wsx task post` or the session news posts), has a thin border in `color-secondary` instead ("Routine" in its aria-label; "Asks you" wins when both hold). A post with a level (`wsx task post --level warn|bad`, [tasks.md](tasks.md) "Routines") has the row's `level` and shows the word as the box's tag, `Warn` or `Bad`, with its border and tag in `color-attention` or `color-danger` (the aria-label ends with the word; "Asks you" still wins the border); the TUI chat puts `warn` or `bad` after the time in the warning or error colour, with the bar in it. A line that a resolution says too shows once, as the events line: the same words ("Approved land #3"), or a close of the same task within ten minutes ("#5 closed" or "#5 done" keeps, "#5 was closed" goes). The same line again within a minute also shows once (`chat_rows`). A row's `quote` is the line a quote of it carries, cut once in wsx-core (`quote_of`, by characters), so the page's quote of a message and the manager's match. Quiet replies do not count as unread replies or as the home row's last reply. Three or more of these rows in a row (event lines and quiet replies, with no bubble or note between them) fold into one row: each task of the run once, with its newest words ("#89 done  #91 done  #88 done"), and "10 updates", the number of rows it hides. The run's last event line and the quiet replies after it stay below the fold, so the newest news reads without a tap; a run whose rows before that line are fewer than two does not fold. A tap on the row shows the rows under it ("Hide 10 updates"), another folds them. A run that grows keeps its one row and whether it is open (`Fold` in `bubbles.js`).
- `#<n>` in any text is a short chip: the number on the baseline of the text around it and a state dot centered in it, its `stage` in its accessible name ("#3, needs you") and the title on hover (a task without `--title` is named by the first sentence of its latest worker summary, [tasks.md](tasks.md) "Store"); it opens the task sheet. `<project> #<n>` in a text, with the name of a project the site grants (the `@` list), is that project's task: the chip reads "pizzahouse #34" with that project's title and state, and it moves to that project's chat (`#/p/<project>/t/<n>`) with the task sheet over it; Back returns. In a message of another project's manager (its source names the project, not a role), a bare `#<n>` is that project's task too, written the same way, and stays plain text when the site does not grant that project. A name the site does not grant is not known to the page, so `name #<n>` of it reads as a bare `#<n>` of this project. The words "project overview" in a reply link to it. A working task has a pulsing dot (still under reduced motion).
- Each message is a bubble with its box, author and time. The owner's are on the right, up to 88% of the column. The manager's and the others' use the whole column, a small gap short of its right edge; code blocks, tables and diagrams stay inside the box.
- A pending approval request also shows inside the manager reply that ended the turn which asked for it (the first reply at or after the request's time): one small tag under the reply's text, "Needs you: Approve discard #4" (the label, cut at the end), with no Approve or Deny: the Needs you list is the one place to approve. A tap on the tag opens that list (as a tap on its pill does) and scrolls to the approval's row, which shows the found tint for 2 s. The decision removes the tag and the row alike. A role's chat has no tags: it has no list. A dropped request reads as a status line with its reason ("Dropped discard #4: #4 is closed"), and so does its resolution.
- Each To check item ([tasks.md](tasks.md) "To check") is a bubble from the manager at the time it was added, tagged "To check": what the task did, the check, where to look, when it passes, its capture (a tap opens the image viewer) and *Try*, *Fail*, *Skip* and *Pass* as in the To check list; once decided it shows "Passed", "Skipped" or "Failed" (with the owner's note when there is one) in place: the bubble stays at the time the item was added (`added_unix_ms`), so a decision never moves it to the end or counts as new, and the buttons go. It counts as a new message. The reservoir's "N to check" and the To check list stay.
- While the manager's turn runs (`busy`), a "<name> is typing" bubble (the manager's name, [tasks.md](tasks.md) "Config") with three dots ends the chat; its box is as wide as the dots with even padding, not as wide as the name. The dots rise and brighten one after another only without reduced motion. A sent message shows until the log has it. Back from the background or the network, the chat reads again, so dots and a reply missed meanwhile are right at once ([web-client.md](web-client.md) "Event stream").
- Pills in the composer row, between the attach button and the Send button, count what the project holds: *Running* (the working tasks, a play icon), *Needs you* (every item that waits for the owner and every open question, a warning icon), *To check* (the open To check items, a check icon) and *Routines* (the project's routines, a clock icon; see "Routines"). Each pill is an icon and its count (a number that ticks when it changes); from 900 px wide (the wide layout) the label follows the count in a composer with three pills (and always in the bar of a device that cannot act); with four pills it is icon and count only, since the row, capped at 72ch, would leave the field under a quarter of it (170 of 680 px at 1280 px). The pill's `aria-label` always has its words ("2 running", "6 need you", "5 to check", "2 routines, 1 failed"). On a 320 px phone the four pills close their padding (`:has` the fourth pill: a media query would need a px literal, which the core CSS may not hold) to stay on the one row between attach and Send; the empty composer keeps its height. A pill is a small, fully rounded button (28 px high, a 16 px icon) with a raised fill and a hairline at rest, so it sits level with the field, and a gap of 12 px follows the last pill (on a phone the pills' row is 4 px or more under the field); pressed, its border is the accent. Its hit area stays 44 px (`::after`). A pill with a count of 0 is not shown (Routines shows while the project has any routine, also with 0 on), and with all of them at 0 there are no pills. A device without `task_act` has no composer, so its pills stand in a bar of their own where the composer would be, with the same lists and no row action. Done tasks are in none of them. A tap on a pill opens its list over the composer (the reservoir, `aria-pressed` on the pill), at most 40% of the chat, scrolling inside itself; one list is open at a time: a tap on another pill switches to its list, a tap on the open pill closes it, and a list whose count falls to 0 closes (Routines: when the last routine is gone). Each open list has a header of one line (the key height): its name (*Running*, *Needs you*, *To check*, *Routines*) at the left and one icon button at the right, *Close <name>*, that closes it as the pill does; the rows scroll under the header, which stays. Escape closes the list from inside it, from a pill or from the page. Closing never focuses a text field (on a phone that opens the keyboard): a focus inside the list moves to the pill that opened it, else nothing takes it. With the keyboard up the list steps aside while the `#` or `/` list is open. Nothing moves the chat: it stays at the newest message unless the owner scrolled up. Open, the list reads each item's task ahead, so a row's sheet shows its content at once. The four lists have one row type: the task's chip first (`#n` with its state dot, which pulses while the task works; never cut), then the label (cut at the end) with the context under it (small and muted), then the actions; a row without a chip (an open question; an approval, whose label names its task) starts with a tone dot. Every row uses the small size, and a tap on its text opens it. *Running*: one row per working task with its title as the label and, as the context, its status label, `status.wait` when the task waits for another ("then waits for #283: its checks fail on main until #283 lands") and the agent ("Resolving a conflict", "Waiting for you to hand it back", "Ready, waiting for the manager's review" or "Plan ready, waiting for the manager's review", both with a calm dot, "Waiting for the check slot", "Waiting for the scenario test slot", "Running checks", "Working on build (2 of 3)"). *Needs you*: each item in the server's order, one row each with its title, its status label ("Waiting for your answer", "Ready, waiting for you to land it") and its one action as an icon with its name as the title, so the title and what it waits for keep the row: *Answer* for a waiting or failed task (it puts `#<n> ` into the composer, see below), *Deny* and *Approve* for an approval (after Approve the row reads "Running…" until the decision settles it, and a second Approve, also from another device, answers what happened instead of an error), *Land* for a ready task, and after the tasks each open question (its first line, "Asks you") with *Reply*, which quotes it in the composer, and *Dismiss*. The question's label and "Asks you" are one button: a tap scrolls the chat to that reply, mid-log, and tints it in the accent for two seconds, fading out (the quote jump uses the same mark; there is no outline beside the bubble's own border, and under reduced motion the tint holds for the two seconds, then goes). A reply older than the rows loaded makes the chat read around it, as a quote jump does (`GET /api/tasks/<id>/chat?around=<message id>`, `Window::Around`, [tasks.md](tasks.md) "Log window"); one the log no longer holds says so in a toast. The list stays open. While a trial the manager started goes live the row reads "Going live…", and once live it reads "on the live site: try it" with *Fail: tell the manager* (the same mention; the manager's add ends the trial) and *Pass and land*. After a success the overview is read again, the row leaves, and the focus moves to the next row's first action (to the open pill when none is left; when the list closes no text field takes the focus), so the owner clears the list one row after another; a failure keeps the row and its error. *To check*: one row per open item (`check_items` of the overview: `id`, `task`, `check`, `pass_if`), in the sheet's order: its check as the label, "Passes if <what passes it>" as the context, and *Reply* first (it quotes the item in the composer, as the swipe or press-and-hold Reply on its chat bubble does; the sent text is `> check <id>`, and a reply of only `x` or `ㅌ` skips an open item with no manager turn, [tasks.md](tasks.md) "To check"), *Fail: close it, then tell the manager* and *Pass* as the sheet has them (Skip is in the sheet): each closes the item first, then quotes it in the composer as Reply does, for the owner's note.  A tap on the text opens the To check sheet scrolled to that item and marked (`#/p/<id>/checks/<item>`). After Pass the row leaves and the focus moves on, as in Needs you.
- A chip or a row opens the task sheet over the chat. The chat does not scroll: there is no jump to where a task first came up.
- The owner talks only to the manager, which relays to a worker with `wsx task add`; to work by hand the owner uses *Take over*. *Answer* and *Fail: tell the manager* focus the manager's composer with `#<n> ` after the draft and the caret after it. A draft stays; a draft that already names the task gets no second mention, and the caret goes after the one there. A role's chat is never the target. Sending is a normal message.
- The composer has attach at the left, like a session's chat: the files, or files pasted into the field, upload at once, Send waits for them, and the message carries their paths under the attachment header. A text paste of over 2,000 characters or 30 lines (and at most 1 MiB) is a file too (`pasteFiles` in `web/chat.js`, shared with the session chat): it uploads as `pasted-<time>.txt` (`text/plain`, UTF-8, the pasted bytes) through the same route and store, and the field gets no text. Its chip reads `Pasted text · <n> lines · <first line>` (the line cut at 80 characters, then by the width) and has *Paste as text*, which reads the stored file, inserts it at the caret and drops the attachment, for a paste the owner wants to edit. A shorter paste stays a native text paste, as does every paste on a site without `media_upload`. The TUI manager chat has no counterpart for the file: its one-line field takes a bracketed paste as typed text (`Action::Paste`, `ui/text_form.rs` `one_line`: line breaks become spaces), and the media store belongs to the web site's server (`<state>/web/<site>/media`, its index in that process's memory; `Media::open` removes files it has no row for), so a second process writing there would race it. `#` at the start of a word in the composer opens the task picker in the box of the `/` list: the open tasks in attention order, then the rest, each with its title, its number (small, muted, never cut) and its state; digits or words filter it. A task done or closed more than a day ago is left out until the text after `#` names it, and a note says how many are left out. `@` at the start of a word lists the other registered projects (the name, and the manager's name when one is set) and a pick puts `@<project> `: the manager consults that project's manager. `/` at the start of a word lists the owner's skills, the ones the manager has as `owner:<name>` (name and one line, `GET api/tasks/<project>/mentions`); a pick puts `Use owner:<name>: ` at the start of the text, `owner:<name> ` after other words, and the owner types the rest, since the manager is headless and takes no slash command. When the read of these lists fails, the list shows the error and Retry, which reads it again. Arrows, Tab or Enter (a tap on a touch screen) pick, Escape closes; a pick sends nothing. Enter sends on a hardware keyboard; the draft is kept on the device per project.

# Task sheet

`#/p/<project>/t/<task>` opens the task over the chat in a modal `<dialog>` (`Sheet` in `tasks.js`, which draws each sheet from its `SHEETS` table by the route's `sheet`: task, overview, checks, usage, panels; the other four pages share `SheetPage` and `useSheetRead` in `ui.js`): 85% of the visible height from the bottom with a drag handle on a phone, a panel of twice the rail width at the right from 900 px. Back in its top row, the browser's Back, Escape, a tap on the backdrop and a swipe down of more than 80 px on the handle or the top row close it. The composer keeps its draft and gets the focus back. The sheet's content is `crates/wsx-web/web/task.js`. The top row has back ("Back to the chat"), the title, `#n` after it (small, muted) and the stage. On a phone a sheet button that has an icon (Deny, Approve, Answer, Allow, Land, Pass and land, Try) shows the icon alone, with its words as its name, so the sentence beside the buttons keeps the row. It has no link to the worker's terminal: `wsx task show <n> --json` names the worker's log. Then, in one scroll container:

1. The top (`TaskStory` in `story.js`) answers what the task is about, where it stands and what it does now. While a task is open it starts with the progress view: the status label (docs/tasks.md "Status") in its tone (attention for an approval or an answer, danger when failed or stuck, else the stage's), how long ago the worker last wrote (the newest write to `log.jsonl` or a `check-*.log`), the goal, the workflow steps with the current one marked (`aria-current`) and those before it ticked, and the now line. A task without workflow steps has no step row. A finished task (`landed`, `closed`) has no progress view: no steps, no now line, no age.

   - *Goal*: the first sentence of the prompt's opening paragraph (`goal` of `GET api/tasks/<project>/t/<n>`, at most 400 characters of it; a "Goal:" lead is cut). It is left out when the title, which is made from the prompt's first line unless the task has a `--title`, already says it. The latest summary is below it, and it names the task when there is no `--title`.
   - *Now* (`progress.now`, `progress.running`; nothing is added for the worker or the manager to write, the line is read from what is logged):

   | State | Shows | From |
   |---|---|---|
   | `working`, or stuck | the newest tool as words: "editing task.js", "reading y.rs", "running cargo nextest" (a leading `cd <dir> &&` cut, 48 characters), "searching code", "listing files", "fetching example.com", "using Foo" for a tool of neither list; the worker's last sentence when its own words are the newest line | the last entry of `log.jsonl` when it is an `agent` line (`progress.now = {line, said}`); the tools of both adapters (claude: `Read`, `Edit`, `Write`, `Bash`, `Grep`…; pi: `read`, `bash`, `edit`, `write`, `grep`, `find`, `ls`) are worded by `doing` in `story.js`, never a path or a full command; a line wsx wrote shows as it is, cut to 60 characters |
   | `checking` | "running <commands>" (60 characters) | `progress.running`, the record's checks |
   | any wait (`waiting` set), `ready` | no line | the status sentence (2.) says what it waits for |

   The now line follows the log: every write to the task's folder raises a `task` event (`watch` in `src/tasks.rs`), which reads the sheet again, so it is as fresh as the observer's step. A stall raises no `task` event, so the sheet also reads again on a `manager` event; with no manager running, a sheet left open shows stuck at its next read. Past the log's 8 MiB, progress lines are dropped, so the age and the line stop there. The age is said again every 30 s without a read.

   Then the worker's whole summary and a "Decided:" line, when no newer work runs after it (while a task works, an older revision's summary is not shown; History has its Result line), and the status sentence (docs/tasks.md "Status"), with the task's actions (2.) beside it as normal-size buttons that wrap under it on a narrow screen ("Waiting for your answer for 3 min: Which port? Answer the manager; the worker goes on then.", "Ready, waiting for you to land it for 5 min: no checks prove it. Land it to put it on main."). While the status has `since_unix_ms` the sheet reads the task again each minute, so the time stays true.
2. The one action the state allows, as buttons only and only with `task_act` (an approval's label shows when the task has more than one): a pending approval with *Deny* and *Approve*; *Answer* for a task that waits on the owner or failed: the sheet closes in the tap and the manager's composer gets the mention ("Project screen"), also when the sheet was opened from elsewhere, which goes to the project's chat; *Land* for a ready task, with "Land stops: main has uncommitted changes in <files>…" under the buttons when its land would overwrite changed files of the main checkout; for a trial the manager started a status line ("Going live: …", "On the live site now: …"), *Pass and land* once live and *End trial*; *Take over* or *Hand back*; *Take over* has a line under the buttons ("Stops the worker. You continue in its session."), and the story line tells a task on `hand` to commit and hand it back; *Try* when the project has `tasks.preview`. A held task shows "Held: <reason>" above the buttons.
3. Open sections, never folded: *To check* (open items of a landed task, with their buttons), *Waited for by* (only while an open task waits for this one (`wsx task after`): each such task as a `#n` chip from `status.waited_by`; the story's sentence says it too, "Waited for by #279, #282.", and, for the task that waits, why: "Its checks fail on main until #283 lands.") and *Shared files* (only while a turn resolves a landing conflict: each other open task that changed a path this one changed, with up to 20 of the paths).
4. Folds, one level, all closed at first, as siblings of one list: a fold never holds a fold.
   - *Report · 4 checks passed · 2 left open*: `report.md` as headings in one fold: Changes, Evidence (open for each check and the worker's evidence), To check (the items it will add before it lands; "all checked" after) and Left open. Its summary is the top; sections of older reports (Asked, Decisions, Human Verify) are not shown. No revision number shows, except on an item of an older revision than the task's. No fold without a report.
   - *Messages · 2*, only when there are any: the messages to the worker as bubbles, read only: each add or steer after the prompt.
   - *History*: the task's usage as one muted line at its top, "Usage: $3.42 · in 12k · cache 1.2M read / 80k write · out 9k · 14 turns", once it had a turn, then one line per log entry with its time and what happened in words; agent progress is one line per run of steps.

   One column at every width: the top, the open sections, then the fold heads, so on a phone the three heads fit the first screen of a working task and a panel at 900 px and up holds the same column.

An action's outcome is a notice; a failure is shown at the bottom of the sheet. The sheet reads again on a `task` event for it and when the project's approvals change.

# Task notifications

The event observer decides from the task records, `approvals.jsonl` and the open To check items ([web-client.md](web-client.md) "Notifications" has the switches, the text and the timing):

| Change | Goes to |
|---|---|
| a task starts waiting (not on `hand`), a new approval request, new To check items, a reply the manager or a role starts on its own after events or a recap (`manager/log.jsonl`, `roles/<name>/log.jsonl`) | "Manager needs me": one push that names every open item of these kinds and the new reply, replacing the earlier one |
| a post with a level (`wsx task post --level warn\|bad`) in `manager/log.jsonl` | "Manager needs me": one push of its own for the post, `<project>: <title>` over its first line; not an item of the push above ([web-client.md](web-client.md) "Notifications") |
| a task becomes `ready`, `failed` or `landed`, a deploy or a release | no push; a project's digest routine reports them ([tasks.md](tasks.md) "Routines") |

- A change is counted by its (state, revision); a project first seen after a server start notifies nothing, and working, checking and stopped never notify.
- No "Manager needs me" push goes to a device while one of its pages shows the project of every new item (any `#/p/<project>` route) and is visible. The page opens its event stream as `api/events?page=<id>` with an id it chose, and `POST api/presence {page, project}` tells the server the project it shows (`null` when hidden or elsewhere). The presence of a page ends with its last stream; a page id belongs to the device that opened it (404 for another device's or an unknown page).
- "Since you left": the device records when it left a project's screen (route change or hidden page). On opening it again, or coming back to it, more than a minute later, the screen asks `since` and shows one status line, "Landed #2 #3 · Ready #4 · Blocked #1 · 2 replies", with *Dismiss* beside it. Each group starts with its word (Landed, Ready, Failed, Blocked, Conflicted, Revised, Started), so the meaning shows before any ids; the "Since you left" prefix is not shown, because on a phone (390 px) it costs ids and the words carry the meaning. The text wraps and is never cut: it takes at most two lines, and when a group's ids would need more it shows the first ids and "+N more" (the task list has the rest); with many groups it shows only each group's count ("Landed 2 · Started 8"). The tasks that landed, became ready or failed are the routine digest's states (`REPORTED_STATES` in `wsx-core` `task/view.rs`, which the manager's event list also builds on). Nothing runs while the device is away; the line is computed from the logs.
- Limits: a push waits while `wsxd` is unavailable, because the observer runs with the daemon's long-poll. Push text is written by wsx, never by the manager.

## Motion

Under `prefers-reduced-motion: no-preference` only (the block in `app.css`; reduced motion is static): the typing dots in the header (crossfading to "stopped") and in the typing bubble loop; a list opens by height, its rows fade in and out, the pills' counts tick when they change; new bubbles and status lines slide in after the first read (not the message this device sent); the typing bubble goes at once when the reply comes, so the reply keeps its place (docs/web-client-chat.md "Following the end"); a task chip's dot changes color softly and settles once when it stops running; the since line expands in; the task sheet slides up from the bottom (in from the right on a wide screen) over a fading backdrop.
