# Web client tasks

The web side of manager mode ([tasks.md](tasks.md)). The server reads the task store and talks to the task hosts and the manager through `wsx_core::task` (`crates/wsx-web/src/tasks.rs`); the browser only names a project id, a task number and its text. Every route checks the chat panel, the capability and the grant; a project outside the grant, an unknown task and an unknown action answer 404.

| Route | Needs | Answer |
|---|---|---|
| `GET api/tasks` | `task_view` | the overview of every granted project |
| `GET api/tasks/<project>` | `task_view` | overview: `needs`, `working`, `to_check` (the count of open items), `tasks` (chips and the `#` picker with `stage`, at most 200), `decisions` (last 5), `resolutions`, `last_reply` (the manager's last reply, at most 120 characters, or `null`), `news` (`{unix_ms, text}` of the newest reply that is not quiet or To check item, or `null`), `busy` (the manager's turn runs; the home row shows typing dots), `manager` (its name, [tasks.md](tasks.md) "Config"), `last_unix_ms` (the latest task change or manager entry, or `null`) |
| `GET api/tasks/<project>/t/<n>` | `task_view` | record, `stage`, `land_reason` and `land_blocked_by` (ready), `result`, `denials`, `checks`, `report` (`report.md`), `waiting`, `conflict` (a turn resolves a landing conflict), `talk`, `timeline`, `overlaps` with paths, `to_check` (its items, each with `capture_removed: true` once its capture is removed), `fixes` (the item it fixes), pending `approvals`, `actions`, `landed_commit`, `deploy` (`configured`, and whether the last deploy has the landed commit, `deployed`, and its `behind`), `hold`, `trial` (the project's trial when it is this task's, with `stage`) |
| `GET api/tasks/<project>/chat?after=<id>` | `task_view` | manager messages, replies, rotations and stops after `after` (at most 200), `running`, `busy`, `activity` |
| `GET api/tasks/<project>/brief` | `task_view` | the project's ledger ([tasks.md](tasks.md) "Ledger"), for the project brief |
| `GET api/tasks/<project>/since?after=<ms>` | `task_view` | task numbers that `started`, `landed`, `blocked`, `conflict` or were `revised` after that time, and the count of `replies` |
| `GET api/tasks/<project>/mentions` | `task_act` | `{skills: [{name, description, source}], truncated, projects: [{id, name, manager}]}`: the owner's skills (same bounds as the session chat's commands) and the other granted projects, `manager` null when no name is set |
| `POST api/tasks/<project>/say` `{text}` | `task_act` | `{ok, id}`; starts the manager when it does not run |
| `POST api/tasks/<project>/t/<n>/<action>` | `task_act` | `add {text}`, `steer {text}`, `land {}`, `pass {}` (a land of a passed trial), `hold {text?}` (default reason "the owner holds it"), `unhold {}`; the host's `{ok, state, message}`. `hand {}`, `handback {}`, `trial {}` and `trial_end {}` run `wsx task hand|handback|trial [--end]` without `WSX_TASK_ACTOR` and answer its JSON (docs/tasks.md "By hand", "Hold and trial") |
| `GET api/tasks/<project>/checks` | `task_view` | `{open, items}`: `open` the open To check items, `items` every open item and the newest 100 in all, for the chat's bubbles; each with their task's `title` and `did` (the worker's first sentence when it is not the title), and `capture_size` (`[width, height]` of a PNG capture or poster, else `null`) |
| `GET api/tasks/<project>/checks/<id>/capture` | `task_view` | the item's kept capture, an image or `video/mp4`, with `Accept-Ranges: bytes`: one `Range` is answered 206 with `Content-Range` (iPhone Safari plays a video only so), a range past the end 416; 404 when it has none or it was removed |
| `GET api/tasks/<project>/checks/<id>/poster` | `task_view` | a video capture's poster image, the same way; 404 when it has none |
| `POST api/tasks/<project>/checks/<id>/pass`, `.../checks/all/pass`, `.../checks/<id>/skip`, `.../checks/all/skip`, `.../checks/<id>/fail` `{note}` | `task_act` | runs `wsx task check ...` without `WSX_TASK_ACTOR`; its JSON (`changed`, `open`, `message`); a refusal is a 409 |
| `POST api/tasks/<project>/approvals/<id>/approve` | `task_act` | 202 at once; the action runs as `wsx task ...` without `WSX_TASK_ACTOR`, and its outcome is the decision in the next overview |
| `POST api/tasks/<project>/approvals/<id>/deny` `{note}` | `task_act` | `{ok}` |

- Three states for the owner: `stage` is `working` (working, checking, or waiting on `hand`), `needs_you` (waiting on the owner, disk or limit, failed, ready) or `done` (landed); the store's states stay in the record. A task is `ready` only when it did not land by itself: its landing stopped, it has no checks, or `tasks.land.auto` is false. A ready task the manager created waits for the manager's review, so its `stage` is `working` and it is not a need ("the manager reviews it"), unless it is held: a held task is the owner's need. The overview carries `try_live` (a deploy command that is not public) and `trial` (docs/tasks.md "Hold and trial"); a task row carries `hold`.
- `needs` is in this order: `waiting`, `failed`, `approval`, `land` (ready, with `reason`: "could not land: …", "try it first: <hold>", "no checks; land by hand" or "ready to land"; a task the manager reviews is not a need). Within a kind the oldest comes first. A working or done task is not a need. A waiting item has `waiting` (`{on, reason}`), the worker's `denials`; it reads "#4 needs an answer", "#4 waits for disk space", "#4 waits for the session limit" (both go on by themselves) or "#4 stopped". A task waiting on `limit` sends no notification. An approval item has `label`, the action it asks for in words (`Approve land #3`); the task's pending `approvals` have it too.
- `resolutions` is what was settled, newest first, at most 30, each `{unix_ms, task, text}`: from the logs of the 30 tasks changed most recently within 7 days ("#1 got an answer" for a message after a block, "#5 was closed", "#5 was closed and discarded"), from the decisions in `approvals.jsonl` ("Approved land #3", "Denied discard #4", "Dropped discard #4: #4 is closed") and from failed To check items ("#3 failed a check; #9 fixes it"). A landing is the events line "#3 done"; old `verified` entries say nothing.
- `actions` lists the buttons a state has: working and checking `steer add`, ready `land add`, failed and other waits `add`, waiting on `hand` only `handback`; an open task that is not checking or worked by hand also has `hand` (*Take over*, *Hand back* in the sheet; a task by hand is under *Running* as "by hand") (hold and trial stay manager commands, with no buttons); none without `task_act`. The host still decides: its refusal is a 409 with `refused` and its reason, and a host that does not answer is a 409 `host_not_running`.
- Limits: a message or note is at most 64 KiB, a tool 256 bytes without control characters, a fail needs a note. Actions share the message rate limit. A landing waits for the host for at most 300 s. A second approve of a request whose action still runs is a 409.
- The timeline is the task log with each run of agent progress lines folded into one `steps` entry (count and last line); the last 300 entries.
- The manager's session is created with the server's own daemon client, which never starts wsxd.
- Events: the observer stats each granted project's `task.json`, `log.jsonl`, `result.json` and `report.md` files, `manager/log.jsonl` and `approvals.jsonl` on every poll. A change sends `tasks` (the project's overview, only when it changed), `task {project, task}` for each task whose files changed, and `manager {project}`. Only a task's own `log.jsonl` (a worker's progress lines) is read without the overview; a change of the manager's log reads it, since a turn changes `busy` and `last_reply`.

# Home

`crates/wsx-web/web/home.js`, `#/` with `task_view`. One row per granted project: the name, a count of its needs, one status line, "N working" while tasks run, and the time since its last activity: the newer of `last_unix_ms` and the newest `state_since_unix_ms` of its listed agent sessions (task workers and the manager are not listed). The status line is the most urgent need in words ("#1 needs an answer", "Approve land #3", "#2 is ready to land"); else its agent sessions when one needs input, ended in an error, exited or works ("claude in main exited", "2 working"); else "5 to check" while To check items are open; else the manager's `last_reply`; else its other agent sessions ("claude in main done 5m ago", "2 idle"); else "Nothing needs you", or "No tasks yet" when the project has neither a task nor an agent session ("Loading…" until its tasks are read). A project whose chat has a message this device has not read (a manager reply that is not quiet or a To check item, the overview's `news`, newer than what the chat marked read here, the same mark as the chat's "↓ N new") has an accent mark before its name and that message's first line under the status line; opening its chat and seeing the message clears it. A chat never opened on the device has nothing new. One session is named by provider and branch, more are counted. Projects with needs come first, by their most urgent kind in the `needs` order and then by their oldest need of that kind; the rest follow by their last activity, newest first. A row opens the project screen. The Sessions tab beside Home opens `#/sessions`.

# Project screen

`crates/wsx-web/web/tasks.js` and `bubbles.js`. From the top: the top row (back, the project, the manager's state only when it matters: "typing" while its turn runs, "stopped" after it stopped; `⋯` with *Page*, *Sessions* (`#/p/<project>/sessions`) and *Files* where granted), the chat, the reservoir and the composer.

- Messages are bubbles: the owner's on the right, the manager's on the left, each with its author (the manager's name, `manager.name` of the chat route: `tasks.manager.name`, else the project's name; another project's manager by its name in `peers` (its project's name unless that project sets one), with "Reply" on its answer; the owner's has none; the manager's answer to a recap request is tagged "Recap", and the request itself is not shown, [tasks.md](tasks.md) "Recap") and its time. What this manager sent another one is its own bubble tagged "To <name>" ([tasks.md](tasks.md) "Managers talk", "Config"). Each speaker with a name has its own color on that name, never on its bubble: this manager, another project's manager (one color per project) and the muted wsx lines ([web-themes.md](web-themes.md) "Tokens"). Consecutive bubbles of one author within 5 minutes group: the author once, the time on the last. A bubble shows whole ([web-client.md](web-client.md) "Screens"); a table, a code block or a diagram scrolls inside its bubble.
- The chat is the owner and the manager talking. Each line of an events message (written by wsx) is its own muted, left-aligned status line in short form ("#4 waiting", "#3 done", "Approved land #3"), and so is each of `resolutions`; a worker's report is in the task sheet, not the chat. Only a line's leading task number is a chip; a task number later in a line is plain text. A manager reply marked `quiet` (its turn held only events and it is one line of at most 200 characters, [tasks.md](tasks.md) "Manager"; a longer reply, with a table, a list or paragraphs, is a bubble) is a muted line of its own under the manager's name, which shows once for quiet replies in a row; it shows whole when it is one sentence or line, else its first sentence and *More*, which shows the rest. It is never cut inside a sentence, its task numbers are plain text, and it never joins an event line. A quiet reply of `-` shows nothing, and one that carries an approval request stays a bubble. A line that a resolution says too shows once, as the events line: the same words ("Approved land #3"), or a close of the same task within ten minutes ("#5 closed" or "#5 done" keeps, "#5 was closed" goes). The same line again within a minute also shows once. Quiet replies do not count as unread replies or as the home row's last reply. Three or more of these rows in a row (event lines and quiet replies, with no bubble or note between them) fold into one row: each task of the run once, with its newest words ("#89 done  #91 done  #88 done"), and "10 updates", the number of rows it hides. The run's last event line and the quiet replies after it stay below the fold, so the newest news reads without a tap; a run whose rows before that line are fewer than two does not fold. A tap on the row shows the rows under it ("Hide 10 updates"), another folds them. A run that grows keeps its one row and whether it is open (`Fold` in `bubbles.js`).
- `#<n>` in any text is a short chip: the number on the baseline of the text around it and a state dot centered in it, its `stage` in its accessible name ("#3, needs you") and the title on hover (a task without `--title` is named by the first sentence of its latest worker summary, [tasks.md](tasks.md) "Store"); it opens the task sheet. The words "project page" in a reply link to the page. A working task has a pulsing dot (still under reduced motion).
- Each message is a bubble with its box, author and time. The owner's are on the right, up to 88% of the column. The manager's and the others' use the whole column, a small gap short of its right edge; code blocks, tables and diagrams stay inside the box.
- A pending approval request also shows inside the manager reply that ended the turn which asked for it (the first reply at or after the request's time): a row under the reply's text with its label ("Approve discard #4"), *Deny* and *Approve*, one tap each, only with `task_act`. The decision settles it in the bubble and the reservoir alike. A dropped request reads as a status line with its reason ("Dropped discard #4: #4 is closed"), and so does its resolution.
- Each To check item ([tasks.md](tasks.md) "To check") is a bubble from the manager at the time it was added, tagged "To check": what the task did, the check, where to look, when it passes, its capture (a tap opens the image viewer) and *Try*, *Fail* and *Pass* as in the To check list; once decided it shows "Passed" or the failure and the task that fixes it instead of the buttons. It counts as a new message. The reservoir's "N to check" and the To check list stay.
- While the manager's turn runs (`busy`), a "<name> is typing" bubble (the manager's name, [tasks.md](tasks.md) "Config") with three dots ends the chat; its box is as wide as the dots with even padding, not as wide as the name. The dots rise and brighten one after another only without reduced motion. A sent message shows until the log has it. Back from the background or the network, the chat reads again, so dots and a reply missed meanwhile are right at once ([web-client.md](web-client.md) "Event stream").
- The reservoir, pinned over the composer, is the decision list: the one place for what waits for the owner, what runs and what is left to check. Closed it is one line: "2 need you", then the newest running task (the highest number) with its pulsing chip and its title cut with "…", then the open To check items ("2 need you · #6 Fix the login · 5 to check"). With several tasks running, the running slot turns through them every few seconds (chip and title, a short slide and fade) with its place ("1/3") after it; it waits while the pointer or the focus is on the line and while the page is hidden. Under reduced motion the slot keeps the newest task and the line says "+N more". In the open list a task's row has its state dot, its title and then its number, small and muted; the number is never cut, the title is. Open, the closed line is gone: only the chevron stays, with no row of its own, at the right end of the list's first row (the first label, or the first item row). With nothing open, running or to check there is no reservoir: the chat goes down to the composer. Done tasks are not in it. A tap opens the list: each item that waits for the owner in the server's order, one row each with its title, what it waits for ("needs an answer", "no checks; land by hand") and its one action as an icon with its name as the title, so the title and what it waits for keep the row: *Answer* (a field; an add) for a waiting or failed task, *Deny* and *Approve* for an approval (after Approve the row reads "Running…" until the decision settles it, and a second Approve, also from another device, answers what happened instead of an error), *Land* for a ready task. While a trial the manager started goes live the row reads "Going live…", and once live it reads "on the live site: try it" with *Fail: tell the worker* (a field; an add, which ends the trial) and *Pass and land*. After a success the overview is read again, the row leaves, and the focus moves to the next row's first action (to the closed line when none is left, to the composer when the reservoir goes), so the owner clears the list one row after another; a failure keeps the row, its draft and its error. *Running* comes first and stays at the top of the open list while the rest scrolls under it: one row per working task with its pulsing dot, title and number, the rows close together, "resolving a conflict", "by hand", "waiting to run checks", "running checks" or the workflow step (`plan (2/3)`). Last, "5 to check", which opens the To check list. Every row of the open list, its labels and its answer field use the closed line's small size, and so does the To check list. Open, the list reads each item's task ahead, so a row's sheet shows its content at once. The list is at most 40% of the chat and scrolls inside itself under *Running*; with the keyboard up it steps aside while the `#` or `/` list is open. Nothing moves the chat: it stays at the newest message unless the owner scrolled up.
- A chip or a row opens the task sheet over the chat. The chat does not scroll: there is no jump to where a task first came up.
- The composer has attach at the left, like a session's chat: the files, or files pasted into the field, upload at once, Send waits for them, and the message carries their paths under the attachment header. `#` at the start of a word in the composer opens the task picker in the box of the `/` list: the open tasks in attention order, then the rest, each with its title, its number (small, muted, never cut) and its state; digits or words filter it. A task done or closed more than a day ago is left out until the text after `#` names it, and a note says how many are left out. `@` at the start of a word lists the other registered projects (the name, and the manager's name when one is set) and a pick puts `@<project> `: the manager consults that project's manager. `/` at the start of a word lists the owner's skills, the ones the manager has as `owner:<name>` (name and one line, `GET api/tasks/<project>/mentions`); a pick puts `Use owner:<name>: ` at the start of the text, `owner:<name> ` after other words, and the owner types the rest, since the manager is headless and takes no slash command. When the read of these lists fails, the list shows the error and Retry, which reads it again. Arrows, Tab or Enter (a tap on a touch screen) pick, Escape closes; a pick sends nothing. Enter sends on a hardware keyboard; the draft is kept on the device per project.

# Project page

`#/p/<project>/page` opens `tasks/<project-id>/page.md` ([tasks.md](tasks.md) "Project page") in the sheet over the chat (`page.js`): markdown with mermaid diagrams, task chips, and "Updated <time> ago" in the top row. Above the markdown: the deploy and the release with their commit and how far behind, and the main checkout's branch and uncommitted files (`ProjectFacts` in `story.js`), read from the ledger when the page opens and at most every 2 s while the overview changes. `GET api/tasks/<project>/page` (`task_view`) answers `{text, unix_ms}` (`null`s before the manager first started); the observer stats the file and sends `page {project}` when it changes, and the open page reads it again.

# To check

`#/p/<project>/checks` opens the project's To check list ([tasks.md](tasks.md) "To check") in the sheet over the chat (`checks.js`): what only a person can check of the landed tasks, oldest first. Each item's title line is its task chip and what the task did (its worker's first sentence, else its title). Labeled lines follow, with muted labels: *Check*, *Look at* (a link when it is a URL or a page path) and *Passes if*, then the item's kept capture (`GET api/tasks/<project>/checks/<id>/capture`), its link as wide as the image; a tap opens it in the image viewer with that item's captures only ([web-client.md](web-client.md) "Image viewer"). A video capture shows its poster (`.../poster`, or a blank 16:9 frame without one) under a play mark; the viewer plays it in a `<video controls playsinline preload="metadata">` with the poster, never by itself. A decided item whose capture was removed says "Capture removed" in the task sheet. *Fail* (×), *Skip* (»: closed without a verdict and no task, shown "Skipped" in the task sheet) and *Pass* (✓) are icon buttons in one place on every item: on a phone a row under the words at its right edge, so the words keep the full width; on a wide screen a column right of the words, level with the title line. *Try* comes before them when the project has `tasks.preview` ([tasks.md](tasks.md) "Preview"): it starts the preview and becomes *Open*, a link to it. The sheet is as high as its rows, at most 85%, on the bottom of the visible screen. It opens once the list is read, and each capture's box has its size by then (`capture_size` of the list, read from the header of a PNG capture or a video's PNG poster), so it rises in one motion and its top stays where it lands, also when the captures come late. *Fail* opens a note field (required) with *Send*; × again or Escape closes it and leaves the sheet open. The fail starts a task that fixes it, and the chat says "#3 failed a check; #9 fixes it". *All passed*, in the top bar while items are open, passes every open item. The list reads again when the overview's `to_check` changes. Without `task_act` it shows the items only.

# Task sheet

`#/p/<project>/t/<task>` opens the task over the chat in a modal `<dialog>` (`Sheet` in `tasks.js`, which also holds the project page): 85% of the visible height from the bottom with a drag handle on a phone, a panel of twice the rail width at the right from 900 px. Back in its top row, the browser's Back, Escape, a tap on the backdrop and a swipe down of more than 80 px on the handle or the top row close it. The composer keeps its draft and gets the focus back. The sheet's content is `crates/wsx-web/web/task.js`. The top row has back ("Back to the chat"), the title, `#n` after it (small, muted) and the stage. On a phone a sheet button that has an icon (Deny, Approve, Allow, Land, Pass and land, Try) shows the icon alone, with its words as its name, so the sentence beside the buttons keeps the row. It has no link to the worker's terminal: `wsx task show <n> --json` names the worker's log. Then, in one scroll container:

1. The top (`TaskStory` in `story.js`): the first sentence of the worker's summary (*More* shows the whole summary and a "Decided:" line), and one sentence of what the owner should know next when it matters, with the task's actions (2.) beside it as normal-size buttons that wrap under it on a narrow screen ("The worker waits for your answer.", "No checks prove it, so it waits for you. Land it to put it on main.", "On main; the last deploy does not have it yet"). A pending approval of the task comes first: "The manager asks: Approve land #3."
2. The one action the state allows, as buttons only and only with `task_act` (an approval's label shows when the task has more than one): a pending approval with *Deny* and *Approve*; *Land* for a ready task, with "Land stops: main has uncommitted changes in <files>…" under the buttons when its land would overwrite changed files of the main checkout; for a trial the manager started a status line ("Going live: …", "On the live site now: …"), *Pass and land* once live and *End trial*; *Take over* or *Hand back*, with a line under the buttons that says what it does ("Take over: the worker stops, and you continue in its working copy with its conversation in your own terminal. Hand back gives the task back to the worker, which checks your work."); *Try* when the project has `tasks.preview`. A held task shows "Held for you to try: <reason>" above the buttons.
3. The report (`report.md`), folded: Changes, Evidence ("· 4 checks passed"; open for each check and the worker's evidence), To check ("· 2 open": the task's items with *Fail*, *Skip* and *Pass* once it landed, the items it will add before), Left open. Its summary is the top; sections of older reports (Asked, Decisions, Human Verify) are not shown. No revision number shows, except on an item of an older revision than the task's.
4. The messages to the worker as bubbles: each add or steer after the prompt.
5. Shared files, only while a turn resolves a landing conflict: each other open task that changed a path this one changed, with up to 20 of the paths.
7. *History*, folded: one line per log entry with its time and what happened in words; agent progress is one line per run of steps.

Text on the sheet, in the chat bubbles and on the project page is markdown read as prose ([web-client-chat.md](web-client-chat.md) "Markdown"). *Session* opens the worker's terminal.

A message field stays at the bottom while the state takes one: *Send* is an add ("Answer the worker" when it waits on the owner), and while the worker runs *Steer now* sends into the turn and *Add* after it. The draft is kept on the device per task. An action's outcome is a notice; a failure is shown above the field and keeps the draft. The sheet reads again on a `task` event for it and when the project's approvals change.

# All sessions

With `task_view` the inbox is `#/sessions`, the Sessions tab, titled *Sessions*, and lists no task workers or manager. The Projects screen (no tab with `task_view`) lists every project; its list adds "N need you" after a project's session count, and a project opens its worktrees.

# Task notifications

The event observer decides from the task records, `approvals.jsonl` and the open To check items ([web-client.md](web-client.md) "Notifications" has the switches, the text and the timing):

| Change | Goes to |
|---|---|
| a task starts waiting (not on `hand`), a new approval request, new To check items | "Manager needs me": one push that names every open item of these kinds, replacing the earlier one |
| a task becomes `ready`, `failed` or `landed`, a deploy or a release | the daily digest, read from the store at its time |

- A change is counted by its (state, revision); a project first seen after a server start notifies nothing, and working, checking and stopped never notify.
- No "Manager needs me" push goes to a device while one of its pages shows the project of every new item (any `#/p/<project>` route) and is visible. The page opens its event stream as `api/events?page=<id>` with an id it chose, and `POST api/presence {page, project}` tells the server the project it shows (`null` when hidden or elsewhere). The presence of a page ends with its last stream; a page id belongs to the device that opened it (404 for another device's or an unknown page).
- "Since you left": the device records when it left a project's screen (route change or hidden page). On opening it again, or coming back to it, more than a minute later, the screen asks `since` and shows one line, "Since you left: #2 #3 landed · #1 blocked · 2 replies", with *Dismiss*. Nothing runs while the device is away; the line is computed from the logs.
- Limits: a push or a digest waits while `wsxd` is unavailable, because the observer runs with the daemon's long-poll. Push text is written by wsx, never by the manager.

## Motion

Under `prefers-reduced-motion: no-preference` only (the block in `app.css`; reduced motion is static): the typing dots in the header (crossfading to "stopped") and in the typing bubble loop; the closed reservoir's running slot turns on a timer; the reservoir opens and closes by height, its rows fade in and out, its counts tick when they change; new bubbles and status lines slide in after the first read (not the message this device sent), and the typing bubble fades out when the reply comes; a task chip's dot changes color softly and settles once when it stops running; the since line expands in; the task sheet slides up from the bottom (in from the right on a wide screen) over a fading backdrop.
